**The template-block question is answered, not fixed.** On the mock an unfiltered Advanced Query lists the Meeting Notes Template's blocks first. Traced on the real backend: `compile_query_ctx` (`agaric-store/src/query/engine.rs`) filters on `space_id`, `deleted_at IS NULL` and the compiled tree only, with no `NOT EXISTS (… tp.key = 'template')` clause like the agenda queries carry. So the real backend returns template blocks too; it is not a mock artefact. The fix is a Rust change to that predicate, plus the mock, a conformance fixture regenerated by cargo and an `e2e-tauri/` spec. This was a frontend-only session with no cargo, so none of that was built. Not run on the real backend either.

**i18n.** *System* still follows the device language: a first version made `resolveLocale('system')` return `en`, and the maintainer rejected that on the PR's day ("system should read the language from the system"), so `locales.ts`, its test, the help text and `preferences.ts` are back to `main`. The default stays `en`, which is what keeps a Spanish device off the partial catalog unless the user picks System or Español. The Page column header in `QueryResultTable` and the tag colour swatch names in `TagList` go through the catalog. `DonePanel` and `TagFilterPanel` use `count` with `_one` / `_other`; their `PRE_EXISTING_COUNT_EXEMPT` entries are deleted, and the tag-count suffix names the mode with its toggle label. `PdfViewerDialog`'s `GenericL10n('en-US')` stays as it is, with a comment: with no pdf.js locale files vendored, `GenericL10n` only ever yields its built-in en-US bundle (`#generateBundles` / `#getPaths` in `pdf_viewer.mjs`), so passing the app language changes nothing on screen.
