## Session 2752 — Per-peer sync progress in the device row

Issue #5842: show a peer's running session in its device row in Settings › Sync & devices, ops first, then the attachment exchange with bytes.

**Premise check.** The store held one global copy of the file progress (`filePhase`, `filesDone`, `bytesDone`, …) that nothing read, and `DeviceManagement`'s *Sync now* and *Sync all* passed no progress callback. That missing callback did more than leave the row blank. `start_sync` only wakes the daemon and returns. The progress reaches the frontend over the channel `SyncScheduler::register_channel` keeps for that peer, and a later registration replaces an earlier one. So a press with no callback also silenced the channel `useSyncTrigger` had registered. The channel stays registered after the command resolves, so the row clears on the stream's terminal updates (op `complete` / `error`, files `complete`), not when `startSync` resolves.

**What shipped.** `useSyncStore.peerProgress` is keyed by peer id, written by `recordPeerProgress(peerId, update)`. It replaces the global file fields, which had no reader. `useSyncTrigger` and both `DeviceManagement` sync paths feed it. `PeerSyncProgress` renders in `PeerListItem`: the visible text, a native `<progress>` labelled per device when bytes are known (the `ImportSection` precedent, since there is no Progress primitive), and an always-mounted `<output>` live region that changes at most every 3 s.

**Background-sync decision.** No `sync:progress` listener. `TauriEventSink` drops `FileProgress`, so a listener would show a daemon session's op counts and never its attachment bytes, which is the part the issue is about. Showing them needs Rust changes. The progress shows for sessions this device starts (*Sync now*, *Sync all*, the periodic `useSyncTrigger` run), not for a session the other device dialled in. `docs/features/sync.md` and `docs/architecture/data-and-events.md` now say so. The latter's claim that per-invoke channels live only as long as one `invoke()` was wrong for `start_sync` and is corrected.

**Tests.** Vitest covers the store keying and terminal clearing, the row (op phase, file phase with progressbar values, clearing, the throttled live region, axe), and *Sync now* routing channel updates into the store. Each was shown red by a mutation. The mock-lane spec `e2e/sync-peer-progress.spec.ts` keeps the channel the app hands `start_sync` and plays the backend's stream. It went red with the *Sync now* callback removed. No `e2e-tauri` spec: a two-device sync finishes in a few ticks, and asserting on its transient progress would only test timing.

## Session 2716 — Accepted-equivalent mutants move out of the issue bodies (#5986)

The weekly mutation lanes kept the mutants triage proved unkillable in a
hand-pasted block in the body of #4690 and #4691, keyed by
`(file, line, column, mutator)`. Any PR that moved a line expired entries, the
filer dropped them ("re-anchoring"), the children reopened, and the maintainer
re-pasted ids. The block and its history were about half of #4691's body.

**What replaced it.** `mutation-accepted.tsv` at the repo root, one file with a
lane column (the filer reads one path; the two lanes' keys differ in shape, so
each line starts with its lane). The key is line-independent:

- frontend: file, mutator, trimmed text of the mutated line, column relative to
  that text, nth occurrence of that text in the file (from the Stryker report's
  own `source`);
- rust: file, cargo-mutants description (function included), trimmed line, read
  from the `src-tauri` checkout.

The text is part of the key, so an entry whose line was edited is inert and can
never suppress another mutant. The filer logs how many entries matched nothing;
it writes no accepted state and no history into any body. A line that does not
parse throws, so the lane goes red through the existing scheduled-failures
reporter: no new hook or job. `--accept` (stdin) turns survivor-block ids into
file lines for the PR that proves an equivalence.

**Deleted:** `renderAcceptedBlock`, `parseAcceptedSurvivors`/`parseAcceptedOn`,
`appendReanchorNote`, `parseReanchorNotes`, `noteSafeId`, `announceReanchoring`
and their three self-tests (about 700 lines).

**Kept on purpose.** The rust key has no column: two mutants with one
description on one line (`!=` twice in `attachment_ops.rs`) share an entry, which
accepts both, as the ids did. The child close note still names the accepted ids.

**Migration.** 286 frontend + 13 rust ids converted by `--accept`. One frontend
id (`vault-import.ts:65:10`) pointed at a blank line at `origin/main`, so it was

## Session 2710 — Markdown reveal beside page, tag and block-ref chips

#5974, option A (maintainer's pick). The maintainer's "link markers do not
show" report was `[[Page]]` chips, which #5689 kept as chips (ids protected by
#5686) and session 2420 recorded as "Chips stay chips"; the earlier block-mode
and page-mode checks only exercised external links.

**What shipped.** With *Show Markdown syntax around the cursor* on, a page link
draws `[[` and `]]`, a tag `#` and a block ref `((` and `))` as widget
decorations beside the chip, in block mode and page mode (one plugin). No new
setting, op, store or migration.

**The rule: "next to a chip".** An empty selection touching a chip
(`$from.nodeBefore` / `nodeAfter`), or a NodeSelection on one. Both sides of
the touched chip are drawn whichever side the caret is on, as for a mark's two
delimiters; the caret stays outside the syntax (opening widget `side` 100,
closing -200, so a mark's delimiters sit outside them, as the serializer
writes). A range selection shows none: it is the narrowest rule that shows the
syntax where the user is at the chip, and it needs no walk (`nodeBefore` and
`nodeAfter` are O(1)). Page mode's cross-block guard (`spansPageBlocks`) is
reused.

**Why separate from `revealedMarkers`.** Those markers are one unit with
Backspace, Delete, arrows and click stops (`markerBesideCaret`,
`stopForClick` counts `.md-reveal-marker`). Chips are not text, so
`revealedChipMarkers` (still in `revealed-markers.ts`, no TipTap import, the
cold-start boundary holds) feeds only decorations, with class and test id
`md-reveal-chip-marker`: every key keeps behaving as with the setting off, and
a test compares the outcome with it on and off for each key and position.
An alias label or a broken link needs nothing: the chip's label or title is
whatever is drawn, and the syntax is the same.

**Layout.** Same muted token and `aria-hidden` / `data-find-skip` as the other
markers. The text after a revealed page link shifts by the two widgets' width
(about 24 px at the default size, as the existing markers do); read from the
screenshots at 1280x800 and 360x780.

**Tests.** `markdown-reveal.test.ts` and `page-mode-reveal.test.ts` (positions,
selected chip, setting off, range, cross-block, 60-block page, key parity, order
against bold's delimiters), `e2e/chip-reveal.spec.ts` (block mode, phone, page
mode; Backspace and persistence) and a case in
`e2e-tauri/markdown-reveal-persist.e2e.ts` (WebKitGTK caret and typing beside
the widget). Each was shown red by breaking the code it covers.

## Session 2706 — The Markdown reveal in page mode, and why no link marker showed

#5974 (sub-issue of #5691): with *Show Markdown syntax around the cursor* on,
page mode drew nothing, because `MarkdownReveal` was registered only in the
roving editor. Page mode now registers it too, and the reveal's own code did
not change.

**The link finding (block mode).** Nothing was broken at `50a2ac908`. With the
setting on, a markdown link with a label shows `[` and `](url)` while the caret
is in or touches the label: the unit tests (`markdown-reveal.test.ts`, the
links describe, built from `parse()`d Markdown), seven Playwright cases
(`e2e/markdown-reveal.spec.ts`, links and bare URL) and the real-backend
`markdown-reveal-persist.e2e.ts` (WebKitGTK) all passed. What shows nothing is
by design: a bare or autolinked URL (`writesBareUrl`: it is stored as it
reads), and a `[[page]]`, tag or block-ref chip. The likeliest reading of "no
link markers" is page mode, or a pasted URL. No block-mode fix was needed.

**Wiring is the ordering.** Among equal priorities TipTap runs the extension
registered last first, and `MarkdownReveal` (1001) must act before
`pageListKeys` (1001, Backspace takes the list style off) and `PageKeys` (1000,
the join). It is registered right after `pageListKeys`; a test goes red when it
is registered before. Page mode draws a list marker in the block's node view,
outside the text, so the widget `side` ordering of block mode does not apply
(`## 1. Title` cannot become `1. ## Title`); a test pins the DOM order.

**One new rule.** A selection that reaches into several `pageBlock`s reveals
nothing (`spansPageBlocks` in `revealed-markers.ts`): Ctrl+A would otherwise
walk the whole page for headings and runs. Its node name moved to
`page-mode/page-block-name.ts`, which `revealed-markers.ts` can import without
loading TipTap (`use-block-keyboard.ts` is on the cold-start path).

**Defined and tested, not built.** ArrowRight at a block's end steps out of the
mark (stored marks), the next ArrowRight is the editor's and leaves the block,

test.

## Session 2705 — page mode's block menu (#5972)

Right-click on a block in page mode used to open the webview's menu. `PageBlockMenu.tsx` now listens for `contextmenu` (and the menu key / Shift+F10) on the document, resolves the block under the pointer from `data-page-block-id` (or `posAtCoords` in the margins), and opens the existing `BlockContextMenu` on it, with `selectedBlockIds` taken from the text selection when it spans blocks and holds that block.

Decisions:
- The structural rows (indent, dedent, move up/down, duplicate, merge, delete) are document commands by id (`page-block-actions.ts`; `indentIds`/`outdentIds` are `page-keys.ts`' Tab commands with the blocks named instead of read from the selection). Task, priority, properties and history reuse the session's `afterSave` actions, so a save in flight lands first.
- Over a multi-block selection the menu loops its action over every selected id; each structural row therefore runs once on the selection's roots (`once`), because per-id indent/dedent/move would double-apply or reorder.
- Native menu stays only for a right click on text selected inside one block. A selection across blocks gets the bulk menu (its Copy selection is the copy path).
- Left out: Turn into (no document edit for it yet, #5743), Collapse, Zoom in, drag moves. Duplicate copies text, not task state or properties (same as copy-paste in page mode).
- Trap: the React Compiler memoised `pageStore.getState().blocksById.get(id)` read during render, so a second menu on the same block showed the old task state. The row is read in the event handler and kept in the open-menu state.
- A menu row's action returning a promise keeps the menu open until it settles (`handleAction` awaits), so specs wait for the menu to close before the next right click.

Suites: vitest `src/editor/page-mode`, Playwright `e2e/page-mode-block-menu.spec.ts`, `e2e-tauri/page-mode-block-menu.e2e.ts` (see the PR for whether it ran).
