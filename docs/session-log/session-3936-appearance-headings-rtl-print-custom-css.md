# Session 3936 — Appearance: headings follow the text size, right-to-left text, print stylesheet, custom CSS

Issue #6558, all four checkboxes.

**Headings.** Headings were fixed rem with a phone step-down (Tailwind `text-xl sm:text-2xl` …), mirrored in `.ProseMirror hN`, `HEADING_CLASSES` and the `--block-first-line` rules. They now read `--heading-N-size` (a multiple of `--agaric-font-size`) and `--heading-N-leading` through `text-heading-N` utilities in `src/index.css`; all three places use them. Desktop Medium is unchanged (24 / 20 / 18 / 16 / 14 / 12). The phone step-down stays (the issue puts dropping it out of scope): below `sm` the factors are 1.25 / 1.125 / 1.0625 / 0.875 / 0.875 / 0.75, which keeps today's phone sizes at Medium except h3, 16 → 17 px, the one change the acceptance (h3 > body at 390 px, Large) needs. The tokens are absolute (`calc(var(--agaric-font-size) * f)`, not `em`), so a heading rendered outside block text (a search row, a preview) does not shrink with its container.

**Right-to-left.** Experiment run in Playwright (Arabic, mixed, list item, table cell; static, editor, page mode): before, everything sat left. `unicode-bidi: plaintext` on block text and its `p, h1–h6, li, th, td` fixes it; `StaticBlock` also carried a leftover `text-left` that pinned the static render, now removed so the initial `text-align: start` follows the paragraph. Caret placement by click works at both ends of an Arabic line. A block-mode list bullet moves right with its text (correct for RTL); page mode's list marker is a separate element and stays left.

**Print.** The webview check (does `window.print()` open a dialog with PDF on WebKitGTK, WKWebView, WebView2) needs the three desktops and was not run, so there is no *Print…* item. The stylesheet alone is harmless where printing is unsupported, so it ships: chrome hidden, the shell's fixed-height scroll boxes unclipped, transitions off. Dark themes print light via `beforeprint` / `afterprint` in `useTheme`, because a CSS-only route needs either the light palette duplicated or the theme blocks wrapped in a media query (a whole-block reindent). `content-visibility` is not used anywhere (the issue's claim is stale); block mode's off-screen rows are `useViewportObserver` placeholders, which CSS cannot fill, so only page mode prints a long page whole.

**Custom CSS.** Two device preferences (`agaric-custom-css`, `agaric-custom-css-enabled`), applied by `useCustomCss` into one `<style>` at the end of `<head>`; no new IPC, store or table. The safe start is the existing `deeplink:open-settings` route with the tab `safe-mode`, handled in `handleOpenSettingsPayload` (no Rust change: the router passes tab names through). `--font-sans` / `--font-mono` moved from `@theme inline` to a plain `@theme` block, since inlined values never see a user override. The versioned token list lives in `docs/features/appearance.md` between markers; `custom-css-tokens.test.ts` checks every listed token is declared for each of the six themes and none only in `@theme inline`. The reading width (`--container-reading`) is inlined and not on the list.

**Checks run.** New specs `heading-font-size`, `rtl-text`, `print-page`, `custom-css`, each shown red before the fix or by a mutation, plus `gutter-alignment` and `page-mode-gutter`; targeted vitest for the touched hooks, Appearance tab, deep-link router, KeyboardShortcuts (its route list gained `safe-mode`), RichContentRenderer, StaticBlock, i18n; `npm run typecheck`; `prek run --all-files` and the manual stage; bundle budget.

**Review.** The phone step-down was restored with h3 at 1.0625× (shown red at 1×); `rtl-text` now also clicks the static Arabic render at both ends and checks the caret lands there (red with `textPointAtClick` disabled); the custom CSS docs name the Android link and say the CSP blocks a remote `@import` or web font.
