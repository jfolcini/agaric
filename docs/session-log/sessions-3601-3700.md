## Session 3700 — the Markdown generators stop spelling foreign math (#6277)

The round-trip proptests in `markdown_source_tests.rs` and `markdown_document_tests.rs` could generate stored text holding `\(` or `\[` with its closer later on the line, e.g. `SCHEDULED: <2026-10-01> \(a \)`. A foreign read takes that as math (`normalize_foreign_inline`, #6033 S4) and reads `$a$`, so the round trip failed at random on unrelated PRs: Dependabot #6467's `cargo-tests (1)`, at `an_export_with_every_block_anchored_imports_as_its_tree`.

No writer stores that text. The editor writes `\(` only before `((ULID))` and never writes `\)`, and paste, import and the MCP append and update paths normalize the form. So the generators were wrong, not the app.

- **Existing-test edits (approved by the maintainer):**
  - `arb_line` (in `markdown_source_tests.rs`) and `arb_own_block_line` (in `markdown_document_tests.rs`) reject a line where `holds_foreign_math` finds the pair.
  - The filter sits on the line, not on `arb_word`, because the pair can span two words or a line prefix (`\`, `\[ ] `) and a word, and the math reader works per line. A lone escape is still generated.
- **New test:** `a_stored_latex_inline_span_reads_back_as_math` pins the intended foreign reading: stored `\(a\)` and `x \(a\)` export and read back as `$a$` and `x $a$`.
  - Red when the `\(` reader in `import.rs` is broken: it received `\(a\)`.
  - Not pinned: `a:: \(a\)`. Through parse and normalize it reads `\a:: $a$`, a reading this PR leaves open.
- **Reproduced:** with CI's seed added to the regression file and the filters off, the test fails exactly as on #6467 (`$a$` against `\(a \)`). With the filters on, it passes. The seed is not committed.
- **Ran:**

## Session 3693 — #6277 H2: the mirror reads edited files back

#5363 slice 2. A page's file edited outside Agaric is read back into the page, and the file keeps its own bytes.

- **Premise check.** The plan said to save with `apply_page_source_inner(merge: true)` against the closest shadow. A shadow, though, is a file text: since A3 it anchors only addressed blocks. The save's `base_source` must be a buffer with every block anchored, because `read_base` compares it with `render_page_document` and `merge_outlines` pairs by id.
  - Maintainer's answer: rebuild a fully anchored base, apply unchanged.
  - The base is stored, not rebuilt. Each `Shadow` keeps the page's buffer from the read its text was written from (`PageFile.buffer`). Re-deriving the anchors would copy the writer's anchor rules: a code line's anchor on its own line, escapes around the marker.
  - A shadow written by slice 1 has no buffer. It serves, against the page's current buffer, only while the page still renders as that text; otherwise the file stays diverged.
- **The ingest** (`mirror/ingest.rs`):
  - A file is read once two ticks read the same bytes.
  - It must be UTF-8; a BOM is dropped and line ends become LF; an empty file is refused.
  - Each line takes its anchor's id, or `pair_unanchored_lines` gives it one, pairing against the shadow closest to the file in lines. An editor that kept an older text open then doesn't undo Agaric's newer edit.
  - The save goes through `apply_page_source_inner` with `merge`, against that shadow's buffer. Its op refs go out in a `mirror:ingested` event, which `useMirrorIngestEvents` puts on the page's undo stack.
  - A refused file isn't retried until its bytes change.
  - A file moved by a rename while edited outside is read in at its old path first, then moved.
- **The writer keeps bytes** (`mirror/splice.rs`). Every write splices the render over the newest shadow: only blocks that read differently take the render's lines. "Reads differently" covers content, properties, depth, `is_code`, anchor and list number. A splice that doesn't read back as the render, block for block, is replaced by the render.
- **Detection.** Every tick stats each page's file, so an edit to a page nothing else marks dirty is still read.
- **Existing-test edits, approved by the maintainer:**
  - `buffer: None,` in the `Shadow` literal of `a_state_keeps_the_last_three_texts_written_once_each`;
  - step 3 of `e2e-tauri/mirror-outbound.e2e.ts`, which now expects the file read in and the app's edit kept.
- **Ran:**
  - `cargo nextest run -p agaric --lib -E 'test(/mirror::/)'`: 61 passed.
  - 14 breaks of the new code, one at a time: 13 turn a test red, once two tests were added (a save landing during an ingest, and a new line keeping its own bytes).
  - One break stays green: skipping the memo of a refused file's bytes. It only saves a rolled-back retry each tick, and `read_edit`'s doc says so.
  - The `useMirrorIngestEvents` vitest, red against two breaks.
  - `npm run typecheck`.

## Session 3672 — the pairing window redials a peer that was not listening yet

#6451: on a first pair, the desktop (host) found the phone over mDNS and dialled it right away. The dial ran out its 10 s `CONNECT_TIMEOUT` while the phone's user was still typing the passphrase, and nothing dialled again inside the 5-minute window.

### The trace

- In a pairing window, an unpaired peer is dialled from two places only: Branch A, on an mDNS resolve (`process_discovery_event`), and Branch B, on a local change wake (`peers_for_change_round`). Branch C, the 30 s resync tick, enumerated paired peers only (`peers_due_for_resync(&refs)`).
- So once the first dial timed out, the peer was redialled only if it re-announced or this device made a local change. The phone confirming wakes only the phone's own daemon, and that daemon can dial the desktop only if it found the desktop itself.
- The stale `sync.pending_pairing` marker: `start_if_peers_exist_with_lifecycle` already clears it at startup, and 0.23.0 ships that. A daemon going active seconds after boot is the host's own `start_pairing` arming the marker. No change.

### The change

`run_resync_round` (Branch C) redials the window's unpaired candidates (discovered peers and the scanned host) after the paired round while `is_pending_pairing` holds. A cancel in the paired round skips the tail. The scheduler's per-peer backoff paces the retries, and ordinary sync keeps its 10 s budget. The reporter's workaround, raising the timeouts to 120 s, was rejected: a dead address would then cost 120 s per round.

The cost: a peer that comes up after a failed dial waits for the next tick, up to 30 s plus backoff.

### Tests

- **`the_resync_round_redials_a_pairing_peer_that_was_not_listening_yet_6451`** (`sync_daemon/tests.rs`): the host's round dials a discovered unpaired peer at an address nothing holds yet, and the dial times out. Then a responder comes up at that address and key, and the next round pairs the two: the host's `peer_refs` row is pinned to the joiner's key. Red on main at the first assertion, because the round never dials an unpaired peer.
- `ServiceHarness::at` (test support) binds the service at a chosen address and key.
- No e2e-tauri spec: that lane pairs through the QR, with the peer dialling the app, because a CI runner cannot rely on mDNS. The failure needs the app to find the joiner over mDNS and dial it.

#### Existing-test edits (approved by the maintainer)

Branch C's first tick runs as soon as the daemon starts. So `daemon_branch_b_dials_discovered_unpaired_peer_while_pairing_pending_3533` and `daemon_branch_b_dials_the_scanned_host_with_an_empty_discovered_map_4037` passed with Branch B's pairing round removed. Both now start their daemon backgrounded, as their negative sibling does, so only Branch B can dial. The #3533 test's "Branch C cannot be the thing that dials here" comment now says why. Both pass as edited and go red with Branch B reverted, at their `wait_for` on the connecting event.

## Session 3601 — a pairing that both devices dial at once no longer stalls

Run 42078795569 (attempt 2), job 127429912180: `sync-two-device.e2e.ts` failed in "pairs with a second device", where the headless peer waited 60s and its row for the app was still `None`. The uploaded app and peer logs show glare. Within twenty milliseconds the peer dialled the app twice (the QR candidate raced against mDNS, #4037) and the app dialled the peer once. Each responder found the per-peer lock held by its own outbound session and refused with `Busy`, so every session ended refused.

- This is not #6353's path. #6355 and #6374 cached the address so that a later dial could find the peer. Here no later dial happens at all. Inside a pairing window a refusal books no backoff (#3505), so nothing re-arms on a timer, and the resync round reaches only paired peers (`peers_due_for_resync(&refs)`), which neither device was yet. The pairing stays stuck until something else wakes a round. Two real devices can hit this too.
- Fix: on a `Busy` refusal in the pairing window, the device whose endpoint key sorts lower calls `notify_change()`, which runs one more change round (`redials_after_glare` in `session_supervisor.rs`). Only one side does, so the retry cannot collide again; by then the other side's outbound session has ended and its responder takes the dial. No timeout, retry loop, op, table or message was added.
- Red: `after_a_busy_in_the_pairing_window_only_the_lower_key_dials_again` (`sync_daemon/tests.rs`) failed before the fix with `left: 0, right: 1` on the lower-key arm, its no-backoff precondition holding. Flipping the comparison reds the same arm, and "always re-dial" reds the higher-key arm (`left: 1, right: 0`).
- Not reproduced in the real-backend lane. The race showed once in the last 100 e2e-tauri runs, so the deterministic test pins it, and the PR's own e2e-tauri run covers the spec.
