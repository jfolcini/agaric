# Session 3930 — Enter and merge under latency: the mock knob, and no lost keys

Issue #6559, checkboxes 1 and 3. Checkboxes 2 (measure the real wait, desktop and phone) and 4 (page mode's per-block IPC) need the real backend, a phone or Rust, and were not built.

**The knob.** `setMockLatency(ms)` in `src/lib/tauri-mock/injection.ts`, exposed as `window.__setMockLatency`, makes the mock answer every command `ms` later; 0, the default, keeps the synchronous answer every existing test relies on, and `resetMock()` clears it. Pinned in `src/lib/__tests__/tauri-mock.test.ts`.

**The bug, verified before the fix.** With 50 ms of latency, block mode's Enter unmounted the editor, awaited `create_block` (and, mid-line, `edit_block`), and only then focused the new block: keys typed meanwhile went into the emptied editor and were dropped by the next mount, and a second Enter was dropped on purpose. A Backspace merge did the same around its edit and remove. `e2e/enter-merge-latency.spec.ts` (journal day and page editor, Enter at the end, Enter mid-line, Backspace merge) was red on main with exactly that: typing `a`, Enter, `b`, Enter, Enter, `c` left the rows `a` and an empty one; `xyz` typed after a merge vanished.

**The fix.** `handleEnterSave` mints the new block's id (`createBelow` takes it as an optional third argument), calls `createBelow` without awaiting it, and focuses the row it inserted at once; a refused create puts the user back in the source block with its full text, unless they already moved on. A second Enter is no longer dropped; only the #2914 multi-paragraph flush still drops one, because it focuses only after its creates land. `handleMergeWithPrev` mounts the merged text on the target with the caret at the join before awaiting; the post-merge `setTimeout` and its cleanup went. Both then focus the editor at once: the commit that moves it into its new row drops its focus until `mount()`'s next-frame refocus, and a repeated run of the spec lost a key to that gap once in 24, latency or not. Because IPC calls are not answered in order on the real backend, the page store now keeps `createsInFlight` (per store, in `page-blocks.ts`): `edit`, `createBelow` below such a block and `remove` (before its splice, or the create's own reconcile reloads the page) wait for the create, and `load()` waits for all of them, or its snapshot would drop the focused new block and clear the focus.

**Traps.** The issue's design said "queue the second Enter"; a queued Enter lets the keys typed after it land in the previous block, so the second Enter must run its synchronous part at once. The issue's expected `a`, `b`, empty, `c` is wrong: with no latency the focus-leave cleanup drops the blank block, so the page holds `a`, `b`, `c`. A programmatic mount puts the caret at the end of the block, so after a mid-line Enter typed keys land at the end of the split-off text with or without latency; the spec accepts either position and that caret is not changed here. A page-mode paste spec under latency was tried and dropped: un-chaining page mode's save queue did not turn it red.
