## Session 2499 — Edit as Markdown keeps a draft, and Reload saves nothing

Mock-lane specs for #5733 items 7 and 8, in `e2e/page-source-edit.spec.ts`.
#5685 has merged, so the hold on them is released.

**How the product behaves** (`PageSourceEditor.tsx`):
- **The draft:** unsaved buffer text is stored as a draft, keyed by the page,
  when typing pauses and when the editor unmounts. Going to another page
  unmounts it.
- **Reopening** restores the draft silently, with the note "Restored your
  unsaved edits."
- **Clearing:** Save, Cancel → Discard and Reload each clear the draft.
- **Reload** is a choice in the conflict dialog that Save opens when the
  page changed elsewhere. It swaps the buffer for the page as it is now.

**Specs:**
- **A draft:**
  - Typed text left by going to another page is not saved, and reopening
    Edit as Markdown restores it with the note, still on its block's line.
  - Discard clears it: the next reopen shows the page as saved.
- **Reload:**
  - After another device edits the page, Save → Reload shows the other edit
    and the original line, and Save is disabled.
  - Leaving the page then shows nothing was saved, and reopening Edit as
    Markdown finds no draft.

**Corrections to the issue:**
- **Item 7:** the draft is stored on going to another page; there is no
  separate "close" action.
- **Item 8:** Reload is a choice in the conflict dialog, not a control on
  the buffer.

**Review:**
- **A precondition:** the draft test now waits for the saved block before
  asserting it lacks the typed text.
- **Reload's draft clearing:** leaving the page with the buffer open, not
  Cancel, now checks it. Cancel clears the draft itself, so it would have
  hidden a Reload that left one.

**Shown red:**
- **The draft:** never stored, and not cleared by Discard.
- **Reload:** swapping in the opened base instead of the current page, and
  leaving its draft behind.

## Session 2490 — Page mode shows and sets tasks

Slice 2 of #5743, after slice 1's typed tags (#5777). A page whose blocks hold a
task state now opens in page mode.

**Design.**
- `pageBlock` has a plain DOM node view when page mode is given a task source
  (`src/editor/page-mode/page-tasks.ts`). It wraps the block's content in
  `.page-block-content`. A non-editable `.page-block-controls` holds block
  mode's own `BlockInlineControls`, mounted through TipTap's `ReactRenderer`
  only while the block has a state. The controls sit in the left slot page mode
  already kept for them, at the same pixel as block mode's checkbox.
- The state is not a node attribute. It is read by id from the page store
  (`blocksById`), which each node view subscribes to. An attribute would follow
  the node and not the id: Enter at a task's start would leave the checkbox on
  the new empty block. Only a store change redraws a checkbox, so typing never
  does. A peer's change arrives with the store's reload, outside the document
  and its undo history.
- The click and `cycleTaskState` (Ctrl+Enter, a plugin at priority 1000, ahead
  of the hard break's Mod-Enter) go through `handleToggleTodo`
  (`useBlockProperties`), queued on page mode's save chain after a save. A new
  empty block is created for it first (`PageSaveState.keep`).
- A marker left as text is folded where slice 1 commits tags: in the blocks the
  caret changed and left, now every block a transaction changed
  (`changedBlocks`), so a multi-line paste counts too. `commitPageTask` reads
  the marker from the saved node: `processCheckboxSyntax`, or the bare `[ ] `
  block mode's input rule also takes. It then commits through
  `commitCheckboxState`. The tag commit runs after it, on the text it wrote.
- Only a marker the edit typed is folded, as block mode's `classifyUnmountFlush`
  requires: each changed block is recorded as it was before its first change
  (`transaction.before`), and a block that already started with a marker, such
  as `[x] means unknown`, keeps it as text (review of #5805).
- `TODO` stays a word, as the editor docs say block mode keeps it. The brief
  asked for the keyword, but block mode does not convert it, so neither does
  page mode.
- `TaskPaste` is not added. In page mode it would hide the marker, with nothing
  drawn until the caret leaves. Pasted lines reach the same fold as typed ones.
- The `tasks` blocker and `pageMode.blocked.tasks` are gone. The properties
  blocker ignores `SYSTEM_MANAGED_PROPERTY_KEYS`. The todo-state command writes
  `created_at` on every task and `completed_at` on DONE, so without this every
  real task page stayed blocked under the properties kind.
- Closed tasks are struck through and use `text-muted-foreground`. Block mode
  uses `opacity-50`, which measures 3.4:1. axe flags that in page mode and
  reports block mode's copy as incomplete.

**Tests, each red first at the predicted assertion:**
- vitest `PageModeEditor.test.tsx`: checkbox and axe, click through the command
  and its refusal, Ctrl+Enter on a block and on a new empty one, a typed `[ ] `
  converting only on leave, `- [x] ` giving DONE with `TODO` left as text,
  pasted lines, a refused marker staying text, a peer's change, and no redraw on
  typing.
- `page-mode-fit.test.ts`: a page of tasks in, a task with a priority or a date
  out, and the stamps ignored.
- The fast-check property gained marker-then-leave and cycle steps. The backend
  holds each block's last given state and no other. The marker leaves the text.
- Playwright `page-mode.spec.ts`: click, Ctrl+Enter and a typed marker, then
  away and back, then axe. It passed 30 of 30 at 8 workers. ArrowDown pressed in
  the frame the last key was drawn was lost natively, without the checkbox too
  (2 of 8). The spec now waits a frame, as the typed-tag spec does.
  `page-mode-setting.spec.ts` now blocks on a priority.
- e2e-tauri `page-mode-tasks.e2e.ts`: a typed marker, a click, a round trip and
  the Agenda list, which reads `blocks.todo_state`. Undated tasks never reach
  `agenda_cache`. This spec is type-checked only; it runs in CI. Its first CI run
  failed at the round trip: the page reopened in blocks, because the switch
  changes the page on screen only and the setting was Blocks, with Page still
  offered. The spec now chooses Page again after reopening.

**Measurement.** `AGARIC_PERF=1 e2e/perf.spec.ts -g 'page mode'` now seeds every
block as a task, TODO and DONE in turn. With the run's sizes held to 500 and 5
repeats, unthrottled, median and band:

| Measure | Block mode | Page mode, tasks | Page mode, no tasks |
| --- | --- | --- | --- |
| Open | 48 [45–70] ms | 367 [349–383] ms | 359 [343–362] ms |
| Worst frame while opening | 68 [53–127] ms | 193 [176–217] ms | 55 [0–70] ms |
| Key to paint, p50 | 2.8 [2.8–3.1] ms | 5.6 [5.5–5.9] ms | 4.4 [4.3–4.6] ms |
| Key to paint, p95 | 4.5 [3.2–12] ms | 7.3 [6.5–8.7] ms | 5.7 [5.4–6.7] ms |

Typing in page mode with tasks makes 2–3 React commits per 30 keys, the same as
without tasks, and has no long frames. The 500 checkboxes mounting at once cost
the open's long frame. Mounting them per viewport is the lever, if the cap is
raised.

**Gates:** vitest over `src/editor src/stores src/components/pages`,
`npm run typecheck`, `npm run typecheck:e2e-tauri`, `npm run lint`, and the
page-mode, page-mode-setting and perf Playwright specs.

## Session 2488 — "N ago" labels count up

The #5739 sweep found that the sidebar Sync tooltip read "Last synced just
now" until the next successful sync, however long ago the last one was.
- **The cause:** `formatRelativeTime` read `Date.now()` inside the call, and
  the React Compiler caches each label on its inputs, the timestamp and
  `t`. So a re-render never recomputed it. The builder compiled the files
  with the repo's compiler plugin and read the built bundle to confirm.
- **Who it hurt:** a user whose device had stopped syncing, which is
  exactly when that line matters.

**Changed:**
- **`useMinuteClock()`** returns a `now` that it re-reads each minute, and
  clears its timer on unmount. `formatRelativeTime` takes `now` as an
  argument, defaulting to `Date.now()` for other callers. The compiled
  labels now re-run as time passes.
- **Fixed with it:**
  - the sidebar tooltip and the Settings sync card;
  - the Agent access activity feed. Its 60-second tick re-rendered the tab,
    but the compiled tab reused the cached feed, so a row read "just now"
    until the next agent call.
  - the per-device "Last: …" lines in Settings and in the pairing dialog.
    They refreshed only by accident, through an uncompiled parent's tick
    and a fresh inline prop.
- **Deleted:** the two tick counters, in `useMcpActivityFeed` and
  `DeviceManagement`.
- **`docs/features/sync.md`:** the sync dot colours now match the tokens,
  idle green and syncing amber.

**Specs:**
- **`e2e/sync-last-synced.spec.ts`:** the sidebar tooltip and the Settings
  card move from "just now" to "5m ago" after five minutes on a paused
  clock.
- **`e2e/mcp-activity-events.spec.ts`:** a new test ages an activity row the
  same way.

Fake-clock vitests cover the hook, the formatter and each label. The mock
writes no per-peer sync time, so the peer rows rely on their vitests.

**Shown red:**
- **The e2e specs:** against the unfixed sidebar, card and feed. The case
  that keeps the tick but drops its value stays green in vitest, where the
  compiler is off, and fails in the compiled e2e bundle.
- **Each label's vitest:** with the minute clock not driving a re-render.
- **The hook test:** with its timer cleanup removed.

**Ran:**
- the new specs with `--repeat-each=3`;
- the sync, agent-access and MCP specs;
- vitest over every touched file, the Settings and App tests and the
  pairing dialog;

## Session 2480 — Page mode commits a typed #name as a tag

#5743 slice 1. In page mode a `#name` typed as text stayed text, so the block never got the tag; block mode commits it on blur (`commitTypedTags`). The maintainer chose #5743 as the next feature work, in slices.

**When.** The tag is committed when the caret leaves the block it was typed in (arrows, a click, Enter, a join), and when the user leaves page mode or the page. Never on the idle save, an editor blur or an export flush while the caret is still in that block, so a half-typed `#proj` stays text. This is block mode's blur moment.

**How.** Leaving saves that block at once, then `commitPageTags` (`src/editor/page-mode/page-tags.ts`) feeds its last-saved text to block mode's own `commitTypedTags`. That reuses `tagIds`: an existing tag is matched case-insensitively, a new one is created, and `requireActiveScope` applies. A failure logs and leaves the text, as in block mode. The new `#[ULID]` text comes back the way a remote change does: the page is re-read and the block is patched outside undo history. The block keeps its id. Ctrl+Z removes the typing with the chip when the typing was one undo group; with a pause between groups the patch has replaced the earlier group's text, so those presses do nothing visible and the chip stays until it is deleted. Only blocks the caret changed are converted. Per transaction the cost is one caret-block lookup and a set insert, with no document scan.

`key:: value` lines and task markers still stay text: they need #5743's Properties and Tasks blockers first.

**Tests**, each shown red:
- **vitest:**
  - typed and left, including undo;
  - a caret still after the name;
  - an existing tag reused;
  - leaving page mode, and leaving the page;
  - a rejected tag creation;
  - a block typed in again and left while its tag is being made (the commit loop walks a copy of the set).
- **fast-check:** a type-`#name`-then-move step, 2,000 runs × 3.
- **Playwright:** the chip appears, survives navigating away and back, and axe passes. Stable at 88/88 repeats.

## Session 2454 — A tap on the block or chip below the edited one lands

#5723 reported two misses on touch, under Playwright's Pixel 7 emulation.
Both were reproduced against the mock before any change.

**Mechanism.** On a coarse pointer the static block has a 2.75rem minimum
height for its tap target, but the editor's `.ProseMirror` had only the
desktop 1.75rem. A one-line block measured 44 px static and 32 px while
edited. A press that blurred the editor grew the block back, and the rows
below moved down under the finger. Chromium sends a tap's compat
`mousedown`, `mouseup` and `click` in separate tasks, hit-testing each, so
the release landed on another element.

- **A text tap on another block.** #5722's `keepEditorUntilClick` already

## Session 2452 — The block index from SQL: no TreeIDs to build it from

#5707 step 2: try building each engine's `block_id → TreeID` index from SQL
instead of walking the Loro tree, the part session 2424 found dominant at boot.
Nothing in the engine changed. The two rehydrate halves became `pub` for a new
Criterion group.

**Premise: SQL holds no TreeID.** No migration declares one, and no code
outside `agaric-engine/src/loro/engine/` names the type. A `TreeID` is the
Loro id of the node's create op. The block id it maps from lives only in the
node's meta map (`FIELD_BLOCK_ID`), so the index cannot exist without reading
every node's meta from Loro, and the option as stated cannot be built.

**Where the walk's time goes.** A release probe against loro 1.13.6 (no LTO)
on the synthetic vault's 30 MB snapshot (105,052 live nodes), median of 7:

- `doc.import`: 40 ms.
- The first `get_nodes(false)`: 206 ms. Almost all of it is the lazy decode
  of the tree container: `nodes()` costs the same, and a later `get_nodes`
  costs about 14 ms.
- `get_meta` for every node: 22 ms. Reading `block_id` and inserting it into
  the map: 177 ms. A second walk of the same doc costs 64 ms.
- The first read of one block on a fresh doc: 214 ms. That is the tree
  decode again, which any engine read pays.

**Q2: the boot reads the engine right after the rehydrate.**
`snapshot_watermark` (`agaric-engine/src/loro/snapshot.rs`) stamps one below
the head, so every healthy boot re-applies that one op. The path runs through
`replay_unmaterialized_ops`, then `apply_*_via_loro`, then `read_block`, then
`node_for`, and so needs the index and the tree.

**Deferral, measured.** This was a throwaway build: the index sat in a lazy
cell built on first use and logged its split. It ran with the session-2424
harness and isolation: 14 interleaved boots per binary, rewind 0, against
session 2424's `agaric-split` as the control, on copies of the same synthetic
and real-vault baselines. Medians in ms, [min–max]:

| Part | Synthetic control | Synthetic deferred | Real-vault control | Real-vault deferred |
|---|---|---|---|---|
| snapshot import | 156 [145–176] | 158 [153–173] | 9 [8–21] | 9 [7–10] |
| index rebuild | 459.5 [437–613] | 0 [0–1] | 4 [4–14] | 0 [0–0] |
| replay | 6 [5–7] | 504 [492–688] | 2 [1–4] | 7 [6–8] |
| log start → sync started | 777.5 [725–1,085] | 849.5 [777–1,156] | 120 [53–258] | 101.5 [41–201] |
| log start → `boot resolved` | 1,096.5 [1,010–1,522] | 1,137 [1,063–1,890] | 447 [361–1,075] | 413.5 [364–638] |

Every deferred 100K build fired inside the replay, so `boot resolved` does not
move. On the real vault the gap is noise: `logInit->poolsOpen`, which the
change does not touch, differs by 16 ms. In the app the build split into the
tree decode (`get_nodes`) at 265.5 ms [250–312] and the meta reads at
235.5 ms [220–382].

**What could still pay.** Only the meta half is specific to the index; the
replayed op pays the tree decode anyway. Persisting the index beside each
snapshot in `loro_doc_state` would replace the meta half with a 4 MB read
that decodes in about 13 ms. The ceiling is about 220 ms at 100K, roughly a
fifth of `boot resolved`. It needs a new column, which is a migration.
`save_all_engines` exports from a doc handle outside the engine lock, so the
stored index would also have to carry the frontiers it matches, with a walk as
the fallback. Not built: that is the maintainer's call.

**Bench.** `rehydrate` in `engine_bench` (`benches/groups/rehydrate_bench.rs`)
times `snapshot_import` and `index_rebuild` on a fresh engine per sample, at
10K and 100K blocks (a page per 100). The rebuild sample ends with one block
read, so deferring the walk cannot read as a win. Its shape probe asserts
that the rebuilt index resolves every seeded block. Under `release-test`, at
load 5–6: `snapshot_import` 2.2 ms and 25.0 ms, `index_rebuild` 40.5 ms and
500.9 ms. The group is registered right after `engine_checkpoint`.
`sync_import_bench`'s outer body asserts that it ran at least one iteration,
so any name-filtered run of `engine_bench` panics there, after the groups
before it have reported.

**Isolation.** Both baselines were copied, and their fingerprints and
`notes.db` md5s did not change. Every boot ran on a fresh copy under
`TMPDIR` in the scratch dir, through the harness's own
`unshare`/`xvfb-run`/`dbus-run-session` isolation. The lazy-index experiment
was restored from backups after its build.

**Gates.**
- The shape probe went red (`left: 0, right: 10000`) with
  `rebuild_index_after_import` skipping `rebuild_index`.
- The full `engine_bench --test` passed under `release-test`: 75 successes.
- `cargo nextest run --workspace -E 'test(/rehydrat|import|snapshot|reload_registry/)'`:
  501 passed. `-E 'package(agaric-engine)'`: 1,191 passed.

## Session 2424 — The boot rehydrate split: the index rebuild dominates at 100K blocks

#5707 step 1: split the boot-time Loro rehydrate into its two parts, give each
its own `scripts/measure-boot.mjs` milestone, and measure which part dominates.
No optimisation in this step.

**The seam.** `LoroEngine::import` (`agaric-engine/src/loro/engine/snapshot.rs`)
ran the doc import and its format gates, then `rebuild_index` and the one-time
sibling-order migration. It is now `import_deferring_index` followed by
`rebuild_index_after_import`, and `import` calls both, so every other caller is
unchanged. `rehydrate_registry` (`agaric-engine/src/loro/snapshot.rs`) imports
every space first and logs `loro: imported per-space LoroDoc snapshots …` once,
then rebuilds every index. The existing `loro: rehydrated per-space …` line in
`lib.rs` stays as the end of the whole rehydrate. The harness reads the new
line as `snapshotsImported`, so its steps show
`identityLoaded->snapshotsImported` (the SQL read of the snapshots plus the doc
import) and `snapshotsImported->rehydrated` (the index rebuild).

**Trap.** Loro 1.13 decodes imported container state lazily
(`loro-internal`'s `ContainerWrapper`), so the import step is cheap and the
index walk pays the decode of the tree and of every live node's meta map. The
split times the code seam, not "parse" against "walk".

**Method.** The same harness and isolation as session 2324, with this branch's
release build (`npm run tauri -- build --no-bundle`), 14 boots per scenario,
rewind 0. The baselines are copies: the warmed synthetic vault from session
2324 (99,992 blocks, 140,305 ops, a 30 MB snapshot in one space) and a copy of
`vault-baseline` (1,586 live blocks). Each copy got one warm-up boot with a
clean close, which applied the pending migrations (through 0126) and re-saved the snapshots.
Load average was 4.7–7.7, lower than in session 2324, so these totals are not
comparable with that session's.

Medians in ms, [min–max]. Share is the part's median over the median of log
start → sync started (backend) and log start → `boot resolved` (boot).

| Part | Synthetic 100K | Share backend / boot | Real-vault copy | Share backend / boot |
|---|---|---|---|---|
| snapshot import | 167.5 [151–345] | 17% / 12% | 8 [7–12] | 11% / 2% |
| index rebuild | **588** [499–1,050] | **59%** / 43% | 5 [4–5] | 7% / 1% |
| log start → sync started | 996.5 [843–1,672] | | 71 [41–182] | |
| log start → `boot resolved` | 1,376 [1,144–2,930] | | 350.5 [305–498] | |

**Reading.** At 100K blocks the index rebuild is about 3.5 times the import.
Read on its own from a copy of the database, the 30 MB snapshot `SELECT` took
12–66 ms, so `doc.import` is roughly 100–150 ms of the import step. On the real
vault both parts are noise next to the webview.

## Session 2422 — MCP agents connect with a token, one socket, mode and spaces at dispatch

Step 4 of #5667, the breaking cut, built as a draft PR held for the
maintainer's review. Steps 1–3 (#5687, #5706, #5710) were the base.

**One socket, a token, a refusal.**
- The read-only and read-write sockets, their markers, `McpRwLifecycle`,
  `McpRwToggleGate`, `McpSurface` and the three `mcp_rw_*` commands are gone.
  There is one socket (`mcp.sock`; Windows `\\.\pipe\agaric-mcp`) and one
  marker (`mcp-enabled`). At boot either old marker becomes it.
- `agaric-mcp` requires `--token`; without one it exits 2 naming Settings →
  Agent access. It writes `AGARIC-TOKEN <token>` before any MCP byte.
- `handle_connection` reads that line through a `BufReader` it then hands to
  rmcp, so bytes past the line still reach it. A missing, unknown, revoked or
  malformed token gets one JSON-RPC `-32001` naming Settings, in reply to the
  client's first request, and the connection closes.
- The agent's mode picks the registry: `ReadOnlyTools` or `ReadWriteTools`.

so a revoke refuses the next call. It refuses a `space_id` or
`target_space_id` outside the agent's spaces, and stamps `last_used_ms` at
most once a minute. `list_spaces` keeps only the agent's spaces. Writes carry
`agent:<agent name>`; `clientInfo`, `sanitize_agent_name` and
`durable_agent_name` are gone. Refusals reach the activity feed.

- A `[[ULID]]` written across spaces is refused by the existing cross-space
  ref guard. Gaps 1 and 3 (a title in rendered Markdown, a backlink target

  not "kept in scope".
- All five gaps are pinned by `agents/tests.rs`'s `gap_*` tests, and the docs
  say so.

all. The per-socket copy buttons went; each agent's row has its own config.

the conformance waivers and the Playwright specs follow.

## Session 2403 — Deleting or moving a page closes it in every tab

Writing #5737's real-lane spec for the kebab's Delete page found this bug.
A page open in two tabs stayed open in the second one after a delete.

**The bug.**
- `PageHeader`'s delete called `onBack` → `goBack`. That closed the active
  tab and switched to the other one, which held the same page id.
- `PageEditor` got identical props, so nothing reloaded and the
  `not_found` heal in `page-blocks.ts` never ran.
- The deleted page stayed on screen, and its id stayed in `agaric:tabs`.
- The Pages-list row delete and batch Trash left background tabs on the
  deleted page. Those healed on click, with a "page is in the trash" toast.
- The review reproduced the same bug for Move to space, through the same
  `onBack` call.

**The fix.**
- A new tab-store action, `removePages`, drops the pages from every tab of
  the active space. It closes the tabs that empty, and keeps the active
  tab or activates the next one.
- When no page is left, it lands where `goBack`'s last-tab branch lands:
  `exitViewForTab`, the view the page was opened from (#4287).
- These call it: `usePageDeleteAction` (the kebab, the Pages row and the
  journal day), `PageBrowserBatchToolbar`'s Trash, and Move to space.
- The `onBack` prop chain through `ViewDispatcher` and `PageEditor` is then
  unused and goes.

**Not wired, by design.** In these paths the background tab heals with a
notice when clicked, and the active editor is never stale:
- the batch Move to space;
- block-tree deletes that cascade nested pages.

**Ran:**
- vitest on the stores, the page components and `usePageDeleteAction`:
  77 files, 2018 tests;
- `npm run typecheck`;
- Playwright: `delete-page-tabs`, `trashed-page-recents`,
  `spaces-management`, `background-tabs`, `keyboard-tabs-drawers` and
  `page-kebab`.

Each new test was shown red with `removePages` as a no-op, and the two-tab
unit test also with `onBack` restored.

## Session 2402 — Keyboard and Load more in the virtualised History and Trash lists

Writing #5737's "Vim keys in the History list" spec found that the keys
did not work past the first screen.

**The keys.** History's scroll effect in `useHistoryKeyboardNav` looked up
the focused row among the mounted rows, so End or PageDown past the
virtualised window found nothing. The row was never mounted and no cursor
showed.
- `HistoryListView` now calls `virtualizer.scrollToIndex`, as
  `TrashListView` already did.
- Once the row mounts, it also `scrollIntoView`s it, as
  `VirtualizedResultListbox` does. The list's bottom can sit below the page
  fold under the compaction card, so scrolling only the list left the row
  off screen. A spec shows red without each half.

**The review found a regression the first fix introduced.**
- The new effect also ran on every `entries.length` change. Without a
  `resetKey`, `useListKeyboardNavigation` resets the cursor to 0 when the
  count changes. So Load more threw the list back to the top.
- The list now scrolls only when the cursor moves, and History passes
  `resetKey: queryKey`, as DonePanel and DuePanel do.

**The Trash list had the same Load more jump on main.** It was reproduced
by `e2e/trash-load-more.spec.ts` (scrollTop 3840 → 0) and fixed the same
way. Its `resetKey` is the space plus the client-side filter.

**Behaviour change.** After a restore or purge shrinks Trash, the cursor
keeps its index, clamped to the end, instead of jumping to row 0.

**Left out.** Opening History doesn't focus the list. App's one-frame focus
runs before the grid renders, so focus lands on `#main-content`. The keys
still work, because the listener is on the document, and the first key
focuses the grid. Fixing it needs a deferred-focus mode that nothing in the
app has yet.
