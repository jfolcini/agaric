# Session 1234 — Fuzz lane compile regression (#2897 fallout)

**Issue:** none filed — regression found directly on `main`.

## What

The weekly `scheduled-deep-checks` `fuzz` job has not fuzzed anything since
2026-07-24: the fuzz crate fails to COMPILE, so `cargo fuzz run` never starts.

Cause: `2a021d0f2` ("refactor(app): remove 60 of 66 post-#2621 re-export
shims", #2897) removed the app-side re-export shims that two fuzz targets
imported through. `src-tauri/src/snapshot/mod.rs` is now a `#[cfg(test)]`-only
test host, and `src-tauri/src/import.rs` kept only the Tauri-integration
`ImportProgressSink` seam — so in a non-test build both modules are empty of
the fuzzed symbols:

```
error[E0432]: unresolved import `agaric_lib::snapshot::decode_snapshot`
error[E0432]: unresolved import `agaric_lib::import::parse_logseq_markdown`
```

`import_parse` was broken by the same commit and is fixed here too.

Fix: point the targets at the crates that actually own the production code —
`agaric_sync::snapshot::decode_snapshot` (#2621 Sync-D) and
`agaric_engine::import::parse_logseq_markdown` (#2621 wave E4-import) — and add
matching `agaric-sync` / `agaric-engine` path deps to `src-tauri/fuzz/Cargo.toml`
(plus their `cargo-machete` ignore entries, which the crate already needs for
`agaric` / `agaric-store` because machete does not trace `fuzz_targets/*.rs`).

## Second finding: two targets were built but never fuzzed

`#2945` added the `fts_strip` and `html_parse` `[[bin]]` targets but never
touched `.github/workflows/scheduled-deep-checks.yml`, whose loop hardcodes
`snapshot_decode deeplink_parse import_parse`. That session's log assumed "the
CI deep-check fuzz lane runs the corpus" — it does not; the list is explicit.
No comment or commit anywhere records an intentional exclusion, so this was an
oversight, not a budget decision. Both targets are added to the loop and the
loop now carries a keep-in-sync comment.

Budget: 5 targets x 120s default = 600s of fuzzing (was 360s) inside a
60-minute job whose cost is dominated by the cold crate build, which is shared
across all five bins. Comfortable headroom.

## Verification (honest status)

Run locally in the worktree on `nightly-1.99.0` with `cargo-fuzz 0.13.2`:

- BEFORE the fix, `cargo +nightly check --all-targets` in `src-tauri/fuzz`
  reproduced both E0432 errors — the regression is real, not theoretical.
- AFTER the fix, the same command is clean.
- All FIVE targets smoke-run crash-free under the real libFuzzer
  instrumentation, mirroring the CI invocation
  (`RUSTFLAGS=-C target-feature=-crt-static`,
  `--target x86_64-unknown-linux-gnu`, `-rss_limit_mb=4096`), 20s each:
  `snapshot_decode` 200,894 runs; `import_parse` 745,379; `deeplink_parse`
  1,214,662; `fts_strip` 470,517; `html_parse` 843,849. No crashes, no OOM,
  no hangs.
- Corpus entries generated by those runs were `git clean`ed so the diff carries
  no incidental corpus churn.
- `cargo fmt --check` and `taplo fmt --check` clean on the changed files.
- NOT run: the workflow itself (scheduled/dispatch only) and the full CI-length
  120s-per-target budget. The 20s smoke runs are the local arbiter.
