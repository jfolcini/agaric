# Session 1544 — The tag view is read-only

Fourth PR of the batch run alongside a second agent in another container (1541 to 1543 carry the others). It closes #4725 with the maintainer's decision: a tag never holds children of its own, so the tag page is read-only.

The tag page was the plain page editor with the tag's id on the page stack, and the editor's first-block auto-create seeded an empty content block under every tag anyone opened; that is where the ten empty offenders came from. The backend now refuses a tag parent on both write paths: `create_block_in_tx` reads the parent's `block_type` from the SELECT it already ran and rejects a tag with a bare validation error, and `validate_move_in_tx` does the same for a new parent, which also covers the batch move. The page editor reads the page block's type once on mount, withholds auto-creation until the answer arrives, renders no editor and no add-block button for a tag, and shows any legacy children read-only through the embedded tree rather than hiding them. The mock mirrors both rejections with the backend's wording. The existing empty-block sweep already reclaims a tag's stray blanks: its hold-back guard is page-only, so no repair routine was added.

Review found the move validator one line over the seventy-line ceiling, which clippy would have turned into a red PR; the parent check moved into its own function. A doc bullet claiming the tag page lists the tag's references was wrong (that list lives in the Tags view) and was trimmed to the true half, a call-shape assertion the strict-IPC teardown already enforced was deleted, and four narrating comments were cut. The move guard is unreachable from any surface today (in-page moves never target a tag and MCP has no move tool) and stays because it rides on the same SELECT and makes the invariant whole. Nothing already on the mount held the page's type, so the one extra primary-key read stays; the tabs store was not widened.
