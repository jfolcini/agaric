# Session 1489 — One oversized draft no longer strands every other flush

`flush_all_drafts_inner` ran every draft in the vault through one `BEGIN IMMEDIATE` transaction and treated an over-`MAX_CONTENT_LENGTH` row as a batch-level failure: `return Err(Validation)`, tx dropped, nothing flushed. A single block holding a ~300 KiB paste — reachable, because `save_draft` applies no cap and the debounced `edit_block` commit that would have rejected it leaves the draft row behind — therefore voided the flush on every `visibilitychange`, before every update, and at every boot, for every other block, for as long as that row existed. The unsaved text of blocks the user was actively typing in stayed unflushed because of one block they were not.

The H-12b branch now warns and continues, the shape its H-12a orphan sibling already had. The difference is what happens to the row: H-12a *deletes* the draft, because its target block is gone and there is nothing to flush into. An oversized draft's row is left in place instead. The first justification written for that was wrong: it argued the row is the only stored copy of the text and deleting it is unrecoverable — but nothing reads a draft row back, so the text is not recoverable either way and unrecoverability is moot. What retention actually buys is the #2540 contract: a row boot failed to process is never silently discarded. Same decision, real reason. It does not count toward `flushed`, which now reports rows consumed rather than rows seen. The doc block lost its all-or-nothing contract; what survives is the narrower truth that an error the loop does not anticipate still rolls the batch back.

`recover_single_draft` had the mirror-image hole: no length check at all, so boot recovery appended the over-cap `edit_block` op that `edit_block_inner` and both flush paths reject, and replicated it to peers. It now refuses, and refuses with `Err` rather than `Ok(false)` — `recover_at_boot` deletes the `block_drafts` row on either `Ok` arm, so `Ok(false)` would have destroyed exactly the text the keep-the-row choice above exists to protect. Boot logs the failure, keeps the row, and carries on with the other drafts.

Three tests. `flush_all_drafts_atomic_rollback_on_inner_failure` asserted the contract that just became false, so it was rewritten rather than supplemented: two valid drafts flush and lose their rows, the oversized one gains no op and keeps its content verbatim. The narrower rollback claim it used to pin now has its own test, with a `BEFORE INSERT ON op_log` `RAISE(ABORT)` standing in for the error the loop does not anticipate. The recovery test pins `Err(Validation)`, zero op_log rows and an untouched `blocks.content`; it does not assert that the draft row survives, because `recover_single_draft` holds no `DELETE` and no production change could redden that. All were shown red against a reverted copy of the source before being called done.
