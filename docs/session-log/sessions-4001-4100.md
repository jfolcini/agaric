## Session 4100 — the real-backend helpers move the caret through the editor, not with End

`block-structure-roundtrip.e2e.ts` › "one Ctrl+Z takes back a split, and one a merge with the child it moved" failed once on #6713, a packaging-only PR: `enterBlankSibling` found the new block holding the tail of the text, `ght-<run id>`. The question was whether Enter splits at a stale offset (a product bug) or the helper sent its keys too soon.

### What it was

The test. Enter split where the caret was; the caret was not at the end because the helper's End had been undone.

- The spec opens the block with `row.click()`, the row's centre, and the caret goes where the click lands (#6562): 40 characters into the 56 here, which is the split point of the failure.
- The mount focuses the editor a frame later. On focus ProseMirror arms a 20 ms timer (`handlers.focus` in `prosemirror-view`) that writes its selection back to the DOM when the DOM selection is not the one it last observed.
- The helper pressed End about 20 ms after the focus. WebKit moved the caret at once and queued `selectionchange`; the timer ran first, took the moved caret for one the browser had made on focus, and put it back at the click point. Enter then split there, with the DOM and the editor agreeing on that caret.

Shown in the real app with a probe that logged every `Selection` write with its stack: in the mis-split round the write that put the caret back came from that timer, 4 ms after End's keydown and before its `selectionchange`. A second probe moved the caret 19 ms after focus, either as End does (`Selection.modify`, DOM only) or through the editor (`setTextSelection`): the DOM move was put back in 7 of 10 rounds, the editor's in none of 10.

A person would have to press End in the last few milliseconds of those 20, 50 to 130 ms after their click, and would then see the caret where they clicked, not a wrong split.

### What changed

`caretToEnd` in `e2e-tauri/helpers.ts` sets the selection through the editor, as `placeCaret` and other specs already do for other positions, and checks it in the same call. `enterBlankSibling` and `editAtEnd` use it in place of End. The twins, a click that opens a block followed by End or Ctrl+End: `due-date-agenda` (now `editAtEnd`, the same four lines), `block-edit-persist`, `block-line-break-persist`, and two places in `sync-two-device`. `e2e-tauri/AGENTS.md` has the rule. No product code changed.

### Found on the way, not changed

In Chromium on the mock, End then Enter with nothing between them mis-split 12 of 20 times with no latency at all, by another route: Enter is handled before `selectionchange` reaches ProseMirror, so `useBlockKeyboard` reads the editor's older selection while the DOM caret is at the end. Idle, `selectionchange` arrived 10 to 25 ms after End's keydown and a 50 ms gap passed 10 of 10. With the two keys 60 to 80 ms apart inside a 150 to 300 ms main-thread stall it mis-split 10 of 10: input is handled ahead of the queued event. So a person reaches it only when the page is stalled across both key presses. The rules in `useBlockKeyboard` read `editor.state.selection` the same way. A fix would read the DOM selection at keydown (ProseMirror's `domObserver.flush()`, an internal); nobody has reported it, so it is left alone and written down here.

### Traps

- **A local repeat count says little about this failure.** The window is the last few milliseconds of the 20 after focus, so it depends on how long the driver's calls take. A loop with the helper's own calls between the focus and End went 0 of 120 here, the first probe, with one call fewer, went 2 of 36, and CI hit it once in six runs. The probe that moves the caret inside the window is the evidence; the 15 green repeats are not.
- **The Tauri build embeds `dist/`, and so does Playwright's web server.** A mock-lane bundle built while the real-backend binary compiles goes to its own `--outDir`, served with `vite preview --outDir`, or the app embeds the mock.
- **The lane runs in a cloud container**: `apt-get install webkit2gtk-driver openbox xdotool`, `cargo install tauri-driver --locked`, then `scripts/e2e-tauri-local.sh <spec>`, which is what `just e2e-real` runs; one spec is about half a minute once built.

### What ran

Real-backend lane, locally, on the fix: `block-structure-roundtrip.e2e.ts` 15 times, 15 green. The 34 spec files that call `enterBlankSibling`, `editAtEnd` or `caretToEnd`, once: 33 green. `sync-two-device` failed one test, "Settings shows this device's sync address", which does not touch the caret: the container's only interface is `192.0.2.2`, which the app passes over as not a host address (its log says so), so there is no address to show. Its two tests that use `caretToEnd` passed. `npm run typecheck`, `npm run lint`, `npx vitest run e2e-tauri`, `node --test scripts/e2e-related.test.mjs`, `prek run --hook-stage manual --all-files`. No `src/` or `src-tauri/` change, so no full vitest and no Rust gates.

## Session 4099 — the agenda counts follow a date write; the release vault holds an attachment, a compaction and a peer; release.sh writes it

Finishes #6567: the stale-views box, the upgrade-path box and the release step, as the maintainer decided them on 2026-11-13.

### Stale views after a local write

Session 4071 measured the windows at the command layer. This one looked at the running app.

- **The agenda counts go stale on screen.** The week view's per-day due count (`useBatchCounts`, `count_agenda_batch_by_source`) is the reader that is mounted beside an editor that can set a date. In the app the whole-cache rebuild takes about 35 ms per thousand dated blocks (29 to 36 ms at 1K, 94 and 109 ms at 3K, debug build), so it passes the 150 ms debounce near 4,500. The Due panel reads the same cache but lists other pages' blocks only and is mounted in the daily view alone, so no local write changes it while it is on screen.
- **The fix is the event the views already hear, sent twice.** A property command's wrapper emits `block:properties-changed` at once, and again after `flush_background`, as the post-sync sink waits before its `blocks:changed`. `useBatchCounts` now reads the property counter as well as the graph one. No new event, store or queue.
- **Not covered:** writes that emit no property event and move the agenda (undo and redo, delete and restore, an import) still re-read once, a debounce after the write. That is the change-feed plan's.
- **Search does not go stale on screen.** The one view that writes while its results are listed is the replace run; with the index held back a second the replaced rows still left the list unasked. A spec written for it passed on the unfixed tree and was not kept: nothing showed it red.
- **The Tags view does not either.** It appends its own create without reading back, and nothing mounted with it adds a tag to a block.

### The seam

Seeding thousands of dated blocks through commands is not something a spec can do. After one batch of a thousand creates and a batch date write, the settled oracle reported 472 blocks missing from `fts_blocks` and every `agenda_cache` row; 200-block batches that set the date in the create ended in `database is locked`; a Markdown import of 1,000 dated tasks logged `background queue full, dropping task` and showed no result in a minute. At a rate the app kept up with, 9,000 blocks would take about ten minutes. No vault of that size was watched going stale: the sizes come from timing the rebuild.

So `run_background` has a debug-only delay (`AGARIC_E2E_BACKGROUND_DELAY_MS`), and `wdio.conf.ts` sets it for the specs in `SPECS_WITH_A_SLOW_MATERIALIZER`. `agenda-count-after-write.e2e.ts` was red on the unfixed tree, green with the fix, and red again with the second event sent without the wait.

### The release vault

- The generator now ages its ops a year and runs the release's own compaction (the daily job's command), then writes an edit, an attachment and the Work page after it. The age is the one thing no command writes; the README says so.
- The peer row is written by `peer_refs::bind_endpoint_id`, the function the pairing handshake pins with, and the device list's two commands. Pairing itself needs a second device on the wire.
- `counts.txt` holds the release's own block and op counts and its compaction frontier, so a release whose commands write a different number of ops does not fail the test on `main`.
- Reds, each by a throwaway migration or mutation at head: the watermark deleted; the peer's key nulled; the attachment read from another directory. A stored path rewritten by a migration is caught by the oracle (`attachment_blobs.on_disk_path`) before the byte read.
- Two assertions were written and deleted. A rewound apply cursor did not red "boot rewound nothing": head's boot heals it. `MIN(seq)` above the frontier cannot fail unless the op count already has.

### release.sh

The script writes the vault from `HEAD` before the bump, runs the upgrade test over it, stages it, and `bump-version.sh` accepts a staged vault as the one exception to its clean-tree rule. The test opens the one vault there is; `gen-release-vault.sh` replaces the old one.

- `docs/BUILD.md` and the issue spoke of the script's self-test. There is none: `bump-version.sh --self-test` was removed some time ago. `src/__tests__/release-vault-step.test.ts` runs the real `release.sh` in a scratch repository with the long steps stubbed, and the real `bump-version.sh` as far as its identity gate.
- The staging line in `release.sh` is covered by that test; that `git commit` then takes the index is git's.

- Two heavy jobs at once (`npm ci` beside a `cargo check`) got the cloud container killed and restarted. Commits and the scratchpad survived; the running gates did not.
- `git merge origin/main` under a running gate chain: killing the cargo of one step let the chain go on to the next step on the merged tree. Stop the shell that runs the chain, not the cargo.

## Session 4098 — an image pasted as HTML is gated like a typed one

Found while writing page mode's paste specs for #6714 (session 4095). Page mode keeps ProseMirror's own HTML paste, which reads `<img>` through the image node's parse rule. That rule took any `src`, so `<img src="javascript:alert(1)">` pasted from a web page was stored as `![evil](javascript:alert(1))` and drawn as an image whose load the browser refuses. Block mode converts pasted HTML before it reaches the schema and drops such an image there (`html-paste-1439.spec.ts`), so only page mode showed it.

### Shipped

- `src/editor/extensions/image.ts`: the `img[src]` parse rule refuses a `src` that `isValidImageSrc` refuses, the predicate the typed `![alt](src)` rule already uses. The text around the image still lands.
- `src/editor/__tests__/image-input-rule.test.ts`: both arms through a real editor (an unsafe `src` makes no node, an `https` one keeps its node and alt).
- `e2e/page-mode-paste-image-src.spec.ts`: the same two arms in page mode, read back from the backend.

### Decisions

- The gate is on the node's parse rule, not in page mode's paste: every HTML the schema reads goes through it (a paste, a drop, `setContent` with HTML), and block mode's own conversion stays as it is.
- An image already stored with a refused scheme (an import could hold one) is not touched: Markdown is parsed to JSON, not through this rule.

### What ran

- Red first: the e2e spec and the unit test failed on the unsafe arm before the fix. After it, each arm was shown red again by one mutation (the gate accepting every `src`; the gate refusing every `src`).
- The full vitest suite, `npm run typecheck`, `npm run lint`, `node --test scripts/e2e-related.test.mjs`, `prek run --hook-stage manual --all-files`.
- Playwright: the new spec and the image and HTML-paste specs (`html-paste-1439`, `image-node`, `inline-image-1434`, `linked-image-6342`, `image-resize`, `external-image-policy`, `inline-image-fold`, `page-mode-bubbles`).

## Session 4097 — macOS file saves go through the backend; *Print…* in the page menu

Two items built without the hardware that can confirm them, on the maintainer's decision of 2026-11-13: code that needs a Mac or a Windows PC to verify merges now, and the hardware checks move to #6514 and #6515 as checklist lines. One PR, #6652 and the last box of #6558.

### File saves on macOS (#6652)

The premise was read again in wry 0.57.0 before building: `wkwebview/navigation.rs::navigation_policy` answers `Cancel` to a download navigation when `has_download_handler` is false, and nothing in `src-tauri` registers one. So on macOS every `<a download>` click saved nothing while the toast said saved.

Two fixes were possible. Registering `on_download` is small in Rust, but the main window comes from `tauri.conf.json`, which has no hook for it, so the window would have to be built in code on every platform, and whether WKDownload then saves a `blob:` URL is exactly what cannot be run here. The other is a command that writes the bytes, which is plain file I/O and tests on Linux. That one shipped: `save_to_downloads` (`src-tauri/src/commands/downloads.rs`) writes into the Downloads folder under a new name, numbering a taken one (`notes (1).md`) and never overwriting.

The frontend had two anchor-download helpers, `downloadBlob` in `export-graph.ts` and `triggerDownload` in `attachment-utils.ts`. They are now one: `saveBlob` in `attachment-utils.ts`, which `triggerDownload` wraps for raw bytes; `downloadBlob` is gone. It is async and rejects on failure, and every caller awaits it before its success toast. That is the place the Android save path (#6546) belongs too: its branch replaces the "saving is unavailable" notice at the top of `saveBlob`. No such branch existed on the remote when this was built.

Linux and Windows keep the anchor download. The only change there: the export, bug-report and Markdown-file saves now revoke the object URL a tick later, as attachment saves already did (#2275).

Traps:

- `isMac()` is true in a Mac browser running the mock, where `save_to_downloads` is a no-op. Nobody develops this app on a Mac today; if that changes, the mock handler is where a browser download goes.
- The bytes cross IPC as base64 (`Base64Bytes`, the upload shape), so a large export is held about twice in memory on macOS.
- A test that spies `navigator.platform` must restore the spy and reset the platform cache, or the next test in the file takes the macOS branch.

### Print (#6558)

The print stylesheet was already on `main` (#6621). This added what the box still lacked:

- *Print…* in the page kebab, absent on Android. It calls `window.print()`. On macOS Tauri replaces `window.print` with a call to its own `plugin:webview|print` command, which needs `core:webview:allow-print`; that permission is not in `core:webview:default`, so it was added to the desktop capability. Without it the item would do nothing on a Mac.
- Block mode prints a long page whole: `useViewportObserver` treats no row as off screen between `beforeprint` and `afterprint`, and flushes that synchronously, because a print lays the page out as `beforeprint` returns.
- A heading stays with what follows it, and an external link prints its address after its text. A bare URL therefore prints twice; CSS cannot tell a label from its address.

Trap: under Playwright's print emulation the scroll boxes lose their fixed height, every row intersects, and the observer fills the rows in by itself over a few frames. A spec that waits for the rows passes with the `beforeprint` code removed. The spec reads the placeholder count in the same task that dispatches `beforeprint`.

## Session 4096 — engine durability spike: a restart no longer undoes a peer's later write

`Refs #6521`. The spike the issue asks for first. Its findings are a comment on the issue; this log holds the measurements, the recommendation, and the one fix that shipped.

### The loss found, and the fix

A snapshot pass stamped each `loro_doc_state` row one below the op-log head it read, and then moved the apply cursor to that head. Every boot therefore rewound the cursor by one and replayed this device's newest op. A replayed op is not a no-op for the engine: `apply_edit_via_diff_splice` diffs the op's whole `to_text` against the engine's current text, and a property write lands as a newer last-writer-wins value. So if a peer changed the same block after that op, and a sync session saved the peer's change, the next restart wrote the old state back, and the next sync sent that to the peer. The peer's text or value was gone on both devices. No crash is needed: a clean exit and start does it.

Two tests in `spaces/session_save_tests.rs` show it, red on `3b717b1`: B's last op edits X to `abcB`, A extends it, B's session saves that, B restarts, and both devices end at `abcB`. The same with a select property (`1h` against A's later `2h`).

The fix: a pass stamps the head it read. A healthy boot then finds nothing to rewind and replays nothing. The `debug`-level branch that hid the routine one-op rewind (#4018) is deleted with the rule it served.

What the fix trades, for the maintainer:

- The replayed newest op used to mask one window for that op only: a pass that reads the head between a delete, restore or purge commit and its post-commit engine fan-out. `op_log_head`'s doc already accepts that window for every older op. It now covers the newest op too.
- Rows written by an older build are stamped one below their cursor, so the first boot after the update replays the newest op once more, and logs the stale-snapshot `warn` once.

### Windows, and what the tests showed

Run here, not committed, because each pins a loss that is still open (the test code is in the issue comment):

- **Rows written, cursor not moved.** A pass writes its rows, then drains the background queue, then moves the cursor. A kill in between (or a pass where one space failed to save, or the two callers of `save_all_engines` that never move the cursor) leaves the cursor behind the rows. Boot replays every local op since the old cursor onto engines that hold them. Result: the same loss as above, for every block those ops touched: `abcB, and A went on` became `abcB` on both devices.
- **Kill between an import's commit and the session-end save**, with a local edit on top. Boot replays the local edit onto an engine without the peer's edit, and the peer's text is in the block twice on both devices: `abcXZX`.
- **A pass exports a write whose transaction rolls back.** `DetachedRevert::revert` does not mark the space dirty again, so the pass clears the flag: the saved row held the rolled-back block, the live engine did not, and the space read clean.

Traced in code, not run: the post-commit fan-out window above, and two passes interleaving because `mirror_sql_tombstones_onto_engine` calls `save_all_engines` outside the one-pass lock.

### Measurements

Harness: `agaric-engine/src/loro/durability_cost_tests.rs`, an ignored test, command in its module doc. One space of `n` blocks, each edited `m` times. Release build without LTO, a 4-core cloud container, two runs. Each cell is the two runs' medians, then the lowest and highest sample of either run.

| | 10K blocks × 10 edits | 100K blocks × 10 edits |
|---|---|---|
| Snapshot export (what one pass costs per dirty space) | 54–61 ms [51–223], 1.4 MB | 791–807 ms [716–2688], 14.2 MB |
| Snapshot row write | 2.5–3.0 ms [2.2–50] | 46–62 ms [21–147] |
| Delta of one edit: export | 0.010–0.013 ms [0.009–0.22], 91 bytes | 0.013–0.028 ms [0.013–0.31], 93 bytes |
| Delta of one create | 0.021–0.032 ms [0.019–0.079], 223 bytes | 0.024–0.046 ms [0.021–0.19], 228 bytes |
| Delta of one property write (one run) | 0.014 ms [0.012–0.046], 95 bytes | 0.030 ms [0.016–0.062], 98 bytes |
| Delta row insert in an open transaction | 0.034–0.036 ms [0.033–0.31] | 0.033–0.046 ms [0.031–0.25] |

| Boot: snapshot + 1000 deltas | 93–96 ms [90–122] | 895–1010 ms [815–1025] |

| One sync update of 1000 edits: size, and import at boot | 13 KB, 27 ms [26–41] | 13 KB, 201–212 ms [194–234] |

Read as direction, not as deltas:

- A snapshot pass grows with the space. A delta does not: 10K and 100K overlap.
- A delta is three to five orders of magnitude smaller than the snapshot it would replace, in bytes and in time.
- At boot, importing 1000 deltas and replaying 1000 edits are inside each other's noise.
- The 1000-edit import includes the index rebuild `LoroEngine::import` runs over every live block.

Per importing session on a 100K-block space, the issue's three numbers:

- **Today, with the session-end save:** one snapshot pass for the space, about 0.5 to 0.8 s of export and 9 to 14 MB written, whatever the size of the import.
- **(1) Keep the inbox blob:** no write beyond the inbox row a session already writes (13 KB for 1000 edits). Boot imports it in about 0.2 s.
- **(2) Delta in the transaction:** the same 13 KB, stored with the projection. A local write adds about 100 to 230 bytes and under 0.1 ms.

Not measured: the SQL half of boot replay, the whole-tree projection a replayed inbox slot runs today (`loro_snapshot_bench`'s `cold_first_sync`, which has no 100K number yet), memory, Android.

### Recommendation

Option (2), built in stages, after the small fixes that need no schema. It needs one new table, which is the maintainer's to approve. The reasoning and the open questions are in the issue comment. Option (1) is not recommended: it also needs a migration, closes one window, and brings back an ordering problem between kept blobs and replayed local ops.

- `effort` is a built-in select; a free-text value is refused.
- A test-only module with runtime `sqlx::query` must be named `*_tests.rs`, or the dynamic-SQL guard counts it as production code.
- `git mv -k` on an untracked file does nothing and exits 0.
- The debug build, a release build of one crate and clippy filled the container's disk; `target/debug/incremental` was 9 GB.

### Tests changed, and why

Each pinned the old stamp or the routine replay:

- `snapshot.rs`: four tests expected `head - 1` (499, 6); they expect the head (500, 7).
- `replay.rs`: `routine_one_op_rewind_does_not_warn_4018`, `a_stale_snapshot_still_warns_4018` and `a_missing_snapshot_warns_even_at_a_gap_of_one_4018` pinned the deleted log-level split. One test replaces them: a snapshot one op behind is rewound and announced. `heal_rewind_target_is_not_pinned_by_a_quiescent_space_3309` expected a rewind to 19; nothing rewinds now, and the cursor stays at 20.

- `session_save_tests.rs`: the hydration test no longer needs a filler edit to keep the child's ops from being the replayed one.

### Ran

## Session 4087 — a PDF comment's keys typed while pdf.js had taken its box out of the page

`main`'s Playwright shard 2 failed once (run 43499854333, commit 2f1c268) in `e2e/pdf-highlight-blocks-6629.spec.ts`, "page mode: Save adds the block, and its chip reopens the reader there": after the second Save the comment "Note" had no block.

### Cause

The spec typed before pdf.js had finished placing the comment box. Not a product defect: a person cannot type inside the window.

On a page that already holds an annotation (here the highlight the first Save wrote), pdf.js sorts a new editor among the others: one zero-delay timer after making the box it removes the box from the document and inserts it again (`AnnotationEditorLayer.moveEditorInDOM`), which drops the focus, and one more timer later it gives the focus back. In between, the dialog's focus trap holds the focus. The spec waited for the box to be focused, which is already true before the move, and typed. Four keys that arrive in the gap go to the dialog. The box is still empty when the Comment tool is switched off, so pdf.js removes it; removing it reports the editing state, which says "not empty" because of the highlight, so Save turns on. Save then writes a copy with no new annotation, and the only block is the highlight's.

Read in `node_modules/pdfjs-dist/build/pdf.mjs` and `web/pdf_viewer.mjs`, then shown: with a temporary in-page event log, and with pdf.js's zero-delay timers stretched from the test, typing while the focus was on the dialog and switching the tool off after it returned gives CI's failure exactly (`['Page two']`, no `'Note'`). It did not occur naturally in 140 local runs of the old spec, CPU throttled and loaded.

A first comment on a page with no other annotation is not moved, so only the tests that reopen an annotated copy were exposed, block mode and page mode alike. Page mode had nothing to do with it.

### Shipped

`pinPdfComment` in `e2e/helpers.ts`, used by this spec and by `e2e/pdf-annotation-1452.spec.ts`, which had the same steps. It waits for two things before typing: the text layer naming the box in `aria-owns`, which pdf.js sets as it places the box, and then the focus. After typing it checks the box holds the words, so a lost key fails there and not three steps later. It also clicks the editor layer once it is in comment mode, not the page: the Comment button shows pressed before pdf.js has finished switching (it first reads the file's annotations back into editors), and with the timers stretched the click landed on the text layer and made no box.

## Session 4068 — Enter and merge as one backend command each (`split_block`, `merge_blocks`)

#6531, after the maintainer's go-ahead of 2026-11-13: a design note on the issue first, then the build it left with no open decision.

### What shipped

- **`split_block` and `merge_blocks`** (`src-tauri/src/commands/blocks/split_merge.rs`). Each opens one `CommandTx`, arms the engine rollback and runs the helpers the single commands run: a split is `create_block_in_tx` then `edit_block_in_tx`; a merge is `edit_block_in_tx`, `move_blocks_batch_in_tx` over the merged-away block's live children, then `delete_block_in_tx`, with `dispatch_deletes` after the commit. No new op type, table, store, queue or sync message.
- **The backend decides placement.** A split reads the block's parent and slot in the transaction; a merge picks the children and appends them to the target. The caller's snapshot of the tree no longer decides either, so a child the store has not loaded is moved, not cascaded into the trash.
- **Both pass `base_text` to `edit_block_in_tx`**, so a split or a merge from an editor that has not seen a peer's edit is rebased as `edit_block` is. A split used to send none.
- **Store actions `splitOff` and `mergeInto`**, optimistic and rolled back by reference. The map of blocks whose create is in flight became `heldBlocks`: a split holds its two blocks and a merge its target, so a later edit of them, and a `load()`, wait for the command. That closes the reorder #6559's status comment left open (text typed at the join and saved before the merge answered).
- **`handleEnterSave`'s caret split and both merge handlers** call them. Deleted: `mergeBlocksAndHandle` with its `revertEdit`, the split's delete-the-sibling rollback, and the hook's `edit` parameter.
- Mock handlers in `src/lib/tauri-mock/handlers/split-merge.ts`, wrapped in `allOrNothing`, pinned by backend-authored `split_block.json` and `merge_blocks.json`.

### Decisions

- **Request structs, not positional arguments.** The design note listed positional arguments; `split_block_inner` would have had eight, one over clippy's limit, and `src-tauri/src/commands/AGENTS.md` says to collapse into a request struct. Both commands take one, for symmetry and because two adjacent block ids in `merge_blocks` are easy to transpose.
- **Not migrated:** Enter at the end of a block (its flush and its create are independent), the several-paragraph split at blur (`splitBlock`, N creates and an edit), Backspace on an empty block with children (a move, then a delete), the `listStyle` write after Enter in a list, and page mode, whose save is a diff of the document and has no split or merge to send.
- **Sync convergence is unchanged.** Two devices splitting or merging the same block still duplicate the moved text; doing better needs an op the engine understands as one operation.

### Traps

- **A ULID is Crockford base32.** `01SPLITNEW…` reads like an id and is refused (`I`, `L`), by `create_block_in_tx` and not by `BlockId::from`.
- **`CONFORMANCE_UPDATE=1` rewrites every fixture.** After `oxfmt` four unrelated fixtures still differed, by key order only; they were restored from `HEAD`.
- **A mutation that makes the mock loop hangs its test and keeps the mutation on disk**, because the restoring `trap` runs only when the command exits. Removing the mock's "target is the block's own child" refusal moved a block under itself; the run was killed by hand and the file checked. Falsification runs now go under `timeout`.
- **A span field needs the PII allowlist.** `#[instrument(fields(into_id = …))]` passed clippy and failed `span_fields_stay_on_the_pii_allowlist` in the second nextest half. `block_id` is on the list and is the only field kept.
- **The pre-commit `tsc` hook checks the staged tree plus every untracked file**, and prek stashes unstaged changes while it runs. A commit of one slice fails on an untracked test of the next (it was moved aside for that commit), and a commit made while a subagent or a build works in the tree hands them a tree that changes under them. The backend and the mock are one commit for the first reason: the bindings alone fail `satisfies TypedHandlers`.
- **The mock-parity guard read a handler module only when `satisfies Pick<` was followed by a line break**, which oxfmt writes only when the key list does not fit one line. Its regex now accepts both.
- **Moving `edit`'s list-style clear into a helper changed what its `try` covered.** `contentShowsListMarker` had been inside it, and a test that mocks the Markdown parser relied on that: outside, the predicate threw and rolled the edit back. One existing test caught it; the predicate is inside the `try` again.
- **Undoing a split restores the text the block last stored.** Text typed and split before the idle commit was never stored whole, so one Ctrl+Z takes the typing with the split, as it did with two commands. The real-backend spec re-opens the page before splitting for that reason.

### Review

An independent read of the transaction and op sequence found no atomicity or ordering defect: both commands arm the rollback before the first engine write, `i64::MAX` as the batch move's slot is clamped to an append before any op carries it, and the split's `index + 1` counts live siblings as the create does. Taken from it: the fixture `split_merge_keep_moved_link.json`, which pins the op order #5272 needs by behaviour (only the op-type list did), four Rust tests that repeated fixture steps were deleted, and assertions that restated their setup were removed. Left: the mock's batch move refuses neither a move past the depth cap nor a target deeper inside the moved block, as before this change; a merge can reach both only near depth 20.

## Session 4066 — the sync endpoint follows the network and keeps its port (#6526)

The issue said the endpoint binds once and a laptop that changes network keeps a socket on the old subnet. It had not been run. Running it changed the design.

### What a lost address does to an iroh endpoint

A throwaway test bound an endpoint on an address alias (`10.77.1.2/24` on `eth0`, added and removed by `ioctl` from a root shell), then took the alias away. With iroh 1.4.1, within three seconds and with no traffic:

- `accept` returns `None`, so the daemon's accept loop ends;
- every dial fails at once with "endpoint stopping", inbound dials time out, and a connection that was open is lost with `INTERNAL_ERROR`;
- `is_closed()` stays `false` and `addr()` still names the old address;
- the same address coming back revives nothing.

So an interface that drops and comes back on one network kills sync until restart, which is wider than the issue's case, and comparing addresses on the resync tick, the issue's whole design, misses it: the address is the same. `close()` on such an endpoint returns in under a millisecond, the old socket is free afterwards, and a new endpoint with the same key and port binds and syncs.

### What shipped (PR for #6526, items 1 and 2)

`daemon_loop` is an outer loop around `run_daemon`, one bound endpoint. It binds again when the accept loop ends (Branch F, at once, after a one-second pause that also keeps endpoints that stop as they are bound from spinning the loop), when the resync tick finds the bind policy picking another LAN address and no session active, and when a bring-up failed (doubling from `MIN_BACKOFF` to `MAX_BACKOFF`). A rebind clears every peer's backoff. `select_bind_target` no longer logs, since the tick calls it; `BindDecision::log` logs the decision that gets bound.

The bound port is stored under `sync.endpoint_port` in `app_settings` and asked for at each bind, with a fallback to an OS port that is then stored. `get_local_sync_address` reads the bound socket for a row in Settings › Sync & devices, which says "no local network" on the loopback fallback.

Decisions that differ from the issue:

- **No new `SyncEvent` for the loopback bind.** The address row carries the fact, and #6687 and #6688 were both rewriting the event enum, the sink and `useSyncEvents`.
- **A decision with no LAN moves nothing.** An interface that reads as down for a moment would otherwise take a working endpoint to loopback; an endpoint whose address is really gone stops by itself. From the review.
- **The tick's check runs while backgrounded.** A minimized desktop app has to follow the network too. From the review.
- **Item 3 (release the Android multicast lock while suspended) is not built.** The daemon learns of backgrounding only by polling on its tick, and Android freezes a suspended process before a 30 s tick fires, so the release has to live in the app's `WindowEvent::Suspended` handler with the lock in state shared with the daemon. None of that JNI path compiles on the host, and a missed re-acquire costs the phone its discovery until restart. Only the false sentence in `docs/features/sync.md` was corrected.

### Tests, and what they cannot show

`sync_daemon/tests/endpoint_follows_network.rs`, Linux only: each `/24` of the loopback `/8` is one network. `BindPolicy` is the seam; its test-only `bound` hook hands the test each endpoint, and closing one ends the accept loop as a lost address does. Every production branch was mutated and seen red on its own assertion. A lost address itself cannot be staged without `CAP_NET_ADMIN`, so that trigger rests on the hand run above.

Left open, said on the issue: the `InternetFacingBind` banner and the `MdnsDisabled` status only ever latch, so after a rebind they can describe the previous endpoint; and nothing was tried on two real devices.

### Traps

- **`E0275` at `tokio::spawn(daemon_loop(..))`.** The `Send` proof of the daemon future runs through Loro's types and is sensitive to the future's shape: removing `service.close().await`, or replacing one `select!` with `break`, failed to compile with "overflow evaluating the requirement", though the shipped code compiles with a recursion limit near 100. A mutation that does not compile is not a kill; pick another, or raise `recursion_limit` for the run.
- **A resync interval under `RESYNC_TICK` trips `peer_pulled_from_us_recently`'s `debug_assert`** in a worker thread, and the test then times out somewhere else. Make a peer due by nulling `peer_refs.synced_at` instead.
- **A falsification script that `cd`s must hold its backup by absolute path.** One restore failed on a relative path and left two mutations in an untracked file; it was restored by hand and re-run.
- **Deleting an address with `SIOCSIFFLAGS` deletes the subnet's secondaries with it.** Add the address that must survive first.

### What ran

## Session 4050 — Page-heavy vaults: a bench fixture, a tail-only rank reprojection, one page list for the pickers

`Refs #6527`: what was left after #6673. One PR, a commit per item.

### What shipped

- **Bench fixture.** `interactive_slo`'s `page_heavy` module seeds `PAGES` root pages of `BLOCKS_PER_PAGE` blocks in one engine-backed space and reports five probes on it, measurement only. `docs/architecture/operations.md` names both vault shapes.

A tail write onto that gap puts two siblings on one rank. So the tail is written only when the sibling right before the slot sits at its rank, else the whole group is. That one read does not prove the prefix dense: undoing a move ranks live siblings only (`history::reproject_live_sibling_group`), so a trashed block can keep a stale rank that cancels a gap. The first version of the fixture put it last, and a create then renumbered it with every page behind it. The command-level count test caught it; `assert_shape` in the bench compares the two root orders.
- **Seeding the engine through its own create is quadratic**, since that create reads every sibling to find its slot. `LoroEngine::seed_block_at_slot` is a `test-util` seam that takes the slot.
- **The engine's sibling scans still cost as much as the SQL half did.** Timed alone in an optimized build (`release-test` profile) at 33,000 root siblings: `apply_create_block` 55 ms, `children_ordered_block_ids` 45 ms; at 20,000: 30 ms and 24 ms. ## Session 4049 — page mode's save of a block sends the base text

## Session 4044 — The mirror's change scan compares with a stat taken before the read

Continues `claude/mirror-read-back-race` from the overnight handover (#6667), for the flakes in `e2e-tauri/mirror-inbound.e2e.ts` and `mirror-read-back.e2e.ts` (#5363).

### The race

`Mirror::write_page` kept the page file's stat for `changed_files` by calling `file_stat` after `try_write_page` returned: after the file was read, and on a write after the rename and the state file's save. A save from another editor landing between that read or rename and that stat had its own stat kept as the one seen. The scan then found the file unchanged, the page was neither diverged nor failed, and nothing read the save until something else made the page dirty: an edit of it in Agaric, a sync naming it, a restart or the hourly pass. Both specs save the file as soon as it holds the text they typed, which is at the rename.

`get_mirror_status`'s `pending` list reads the files themselves, not the scan's stats. That is why the read-back spec saw the file listed and still timed out on "never read in".

### The fix

- `write_page` takes the stat before the file is read.
- A write keeps the stat of what it wrote: `store::write_atomic` returns the temporary file's metadata, read by path before the rename, and `Mirror::write_file` keeps it.

Taking the stat before the read in every case was the smaller change. It was not taken because each write would then make the page dirty for one more pass, and a page whose render did not splice to itself would be written every tick.

### What shipped

  `on_local_commit` hook; `lib.rs` points it at `SyncScheduler::notify_local_edit`),

### Why two devices cannot ping-pong

A served session asks for a round only when the device that dialled is ahead.

nothing new and the exchange ends after two sessions. The cases where a pull
does not close the gap (a refused export, an update parked on a missing
dependency) are bounded by `peer_refs.loro_vv_bytes`: the responder pulls back
only for a space whose advertisement has moved since that peer's last completed
session. The placement and repairs that follow an inbound session run inside
`db::following_a_sync`, so their commits ask for no round.

  example. An edit the block already holds is written once: the idle commit and the blur that
  re-sends its text, landing in the other order, would otherwise write the text twice.
- Splices count code points, so two edits of one grapheme (a letter and its combining mark, an
  emoji and its skin-tone modifier) are apart and both kept, giving a cluster neither side typed.
- The editor's baseline moves only when a commit answers, so a blur overtaking an idle commit
  would rebase from a stale base and write that commit's text twice. The page store sends no base
  while another edit of the block is unanswered.
- After a rebased commit the store adopts the merged text and the editor keeps its own until the
  block is left (a reload re-feeds it only with text the store does not hold yet); each later
  commit rebases again from the editor's text.
- The current text is the SQL row read in the transaction. `import_and_project` imports into the
  engine before it takes the writer lock, so a commit that wins the lock in that gap is not
  rebased and behaves as before this change. Closing it means reading the engine's text instead;
  raised with the maintainer.
- Not covered: page mode, *Edit as Markdown*, a draft flushed at blur or recovered at boot, an
  Enter that splits the block mid-text, a slash command or *Turn into* that rewrites it, and the
  blur branches that split or fold a task marker, property line or tag. They send no base, so
  they still write the editor's text over a peer's edit.
- The positional `baseText` in the generated binding changed every `edit_block` payload. A
  hundred call-shape assertions in existing tests were updated to the new shape, editor commits
  asserting their real base; none was removed or weakened.
- The real-backend case has to land a pull under a dirty editor: it types faster than the commit
  debounce and clicks Sync from script, because a pointer press blurs and saves first.
- `CONFORMANCE_UPDATE=1` dirties four fixtures committed in non-canonical form (key order,
  compacted arrays). They hold no drift; restore them.
- The mock counts code points and the backend cuts bytes on char boundaries. A property test
  holds `rebase_edit` to a `char`-counted twin of the mock's algorithm, and the fixture gained the
  case where UTF-16 units would decide otherwise: `😀😁`, the peer deletes the first, the editor
  types between them. Counted in units the deletion reaches past the insertion and nothing is
  merged; the mock written with `split('')` goes red on it (`😀x😁` for `x😁`).
- `main` gained a caller while the branch waited (`renameSavedView`); it sends no base.

`Refs #6525` (box 3, step 4, as the maintainer decided on 2026-11-12; steps 1 to 3, with the

- `hydrate_page_subtree_into_engine` seeds a whole page group, so the restriction is a filter on

- A local block whose parent the engine lacks is skipped: `resolve_parent` would put it at the doc

- A local child under a peer's page the engine still lacks at the upgrade boot stays SQL-only for
