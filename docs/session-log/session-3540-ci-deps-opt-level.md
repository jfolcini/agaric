# Session 3540 — cargo-tests optimizes dependencies, in CI only

Part of the slow-tests sweep. #6369 tried `opt-level = 2` for every dependency in the dev profile. Its CI run 41984685737 cut the cargo-tests shards' llvm-cov test step from 397.2 s / 418.6 s (main run 41980707506) to 98.9 s / 81.2 s. But the change more than doubled a cold dependency build everywhere: locally 474 s → 1047 s, and in CI the build step went 272 s / 276 s → 843 s / 963 s and clippy 162 s → 662 s. #6369 merged with SQLite alone at opt-level 3. From 22 h of CI logs, the coordinator found the Rust cache fully hits on 93% of cargo-tests runs, against a break-even miss rate of about 35%. The maintainer chose to apply the all-dependencies setting in that one job.

The cargo-tests nextest command now passes `--config 'profile.dev.package."*".opt-level=2'`. `cargo llvm-cov nextest` forwards it to the inner `cargo nextest run` (seen in its `-v` output), and the `cargo llvm-cov report` that follows only merges profiles and exports lcov, so it rebuilds nothing. Only cargo-tests uses the `rust-cov` cache, and `cargo-coverage` only merges the shards' lcov artifacts, so nothing else builds twice. Lint, mcp-tests and local builds keep the dev profile. A flag, unlike a `CARGO_*` variable, is not part of rust-cache's key, so the first main run after merge rebuilds the dependencies cold, and later runs are warm again. The equivalent `CARGO_PROFILE_DEV_PACKAGE_<PKG>_OPT_LEVEL` variable is not honoured by Cargo: with it set, `libsqlite3-sys` stayed Fresh.

Corrections to session 3530 (#6369), whose log merged with them. Its agaric-store figures (75–80 s → 56 s for SQLite alone, −28%) were measured on 33d16ce, a base without #6363, so they mostly measured SQLite running migrations. On 8c8d3ba (with #6363), plain `cargo nextest run -p agaric-store` takes 25.4 / 25.3 / 25.7 s on main, 22.5 / 22.0 s with SQLite at opt-level 3 (−12%), and 12.9 / 13.9 s with every dependency at opt-level 2 (−47%). Under `cargo llvm-cov nextest -p agaric-store` the same three take 25.8 / 25.4 s, 23.1 / 23.0 s (−10%) and 14.4 / 14.8 s (−43%). Session 3530's full-workspace figures were on 8c8d3ba and stand. The hypothesis raised along the way, that a per-process cost of writing coverage counters was CI's floor, is refuted: locally coverage adds almost nothing per test (25.4 s plain vs 25.6 s covered), so CI's gain comes from optimizing the dependencies.

The effect is shown on this PR's own CI run (in the PR body). `prek run --files .github/workflows/_validate.yml` passed (actionlint, zizmor).
