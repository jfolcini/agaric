## Session 2400 — A deleted page's tree in Trash, on the real backend

- **The editor kebab's "Delete page".** The issue called it "Send to Trash".

## Session 2392 — Attachment hashes on peers, the integrity arm and the version message (#5728)

Review of #5728, the last three steps of #5608's design (6 to 8) and one
kernel change, checked against what the builder claimed.

**What it ships.**
- `AddAttachmentPayload.content_hash`, omitted when `None`. The engine entry
  and the SQL row store it and the command's follow-up `UPDATE` is gone, so a
  peer's row carries the hash the attachment was added with.
- `receive_offered_file` refuses an offer whose hash differs from the row's
  (`file_offer.hash_mismatch`, no ACK), before the blob link.
- `reconcile_engine` compares `attachments` rows with the engine's entries
  both ways (`engine.attachments.*`).
- `SyncEvent::Error` gains an optional `code`. `engine_format_mismatch` makes
  the frontend say to update both devices, naming the peer ("the other device"
  when it has no name).
- `apply_attachment_op` names `RenameAttachment` and refuses any other op type.

**Where the plan was wrong.**
- Design § 5 said both devices show the format error. Only the responder does:
  `on_head_exchange` fails the session before it replies, so the dialling
  device sees the stream end and a generic `Sync failed`. Each device shows
  the message when the other one dials it. A daemon test pins that the dialler
  gets no frame; `sync-protocol-spec.md` says so.
- #5728 asked to measure "the extra hash" on the receive path. There is none:
  the writer already hashes as it streams and the new check compares two
  strings. The builder's 50 MB timing test measured the old writer, so it is
  deleted. A peer row with a hash also takes `resolve_offer_hash`'s stored-hash
  path when it relays, where a missing hash rehashed the file until the next
  boot backfill.

**The refusal cannot fire on data a user can legitimately hold.** A hash comes
from `persist_attachment` (the blake3 of the bytes in memory) or, for a row
that predates it, the boot backfill (the blake3 of the file). Hydration copies
the row's hash, the projection copies the entry's, and the sender offers its
row's hash or a fresh hash of its bytes. So an offer differs from the row only
when the sender's bytes are not the ones added. A dedup repoint and an undo's
re-add keep the hash, and a row with no hash (an add before #5728) accepts any
offer. After a refusal the file phase's `Err` is non-fatal on both sides: the
session completes, no backoff, no event, no toast, one `error!` naming both
hashes and one `warn!`. The next sync asks again and meets the same offer, which
ends the rest of that session's file phase (on the initiator, that includes
serving the peer's request), as the size check does. Left alone.

**Found and fixed.**
- `docs/architecture/data-and-events.md` still gave `SyncEvent::Error` without
  `code`. FEATURE-MAP did not say which device shows the message; it says the
  dialled one now. Three comments still said a remote add carries no hash.
- `offer_file_5608` waited 500 ms for the ACK. A receiver 700 ms slow made
  `an_offer_of_the_added_bytes_is_accepted_5608` hang to the nextest
  timeout, because the sender never sent `FileTransferComplete`. The wait now
  ends when the receiver does, so no clock decides it.
- A peer's row with a hash and no bytes yet reports `attachment_blobs.refcount`
  in the integrity check: its blob entry is written when the file phase lands
  the bytes. The oracle header now lists it beside the other deferred passes.
  A fix needs the filesystem in the oracle, so it is documented, not changed.

**Tests and their reds** (each file restored by a trap and compared).
- Legacy op round trip: removing `skip_serializing_if` from `content_hash`
  reddens one of the 1476 `agaric-store` tests,
  `add_attachment_payload_legacy_json_decodes_and_reserializes_unchanged`.
- Refusal before the link: moving the check after the link reddens
  `an_offer_of_other_bytes_is_not_linked_to_a_blob_held_under_its_hash_5608`
  alone. Always refusing reddens the acceptance test; never refusing, an
  inverted comparison and a removed body redden the refusal tests.
- Oracle: disabling the extra-row direction drops `SQL_ONLY` from
  `engine.attachments.row` in `attachment_rows_behind_the_engine_are_reported_5608`.
- Kernel: restoring the wildcard arm makes the refused op return `Ok(())`.
- Format code: emitting `None` reddens the orchestrator and daemon tests;
  making the frontend ignore the code reddens the two `useSyncEvents` cases
  and the Playwright spec.
- The rewritten helper: with the 700 ms receiver the old one timed out at 60 s,
  the new one passes in 1 s and the refusal reds above still hold.
- Probed, not committed: the engine arm is quiet after add, rename, delete,
  undo of a delete, undo and redo of an add, a dedup add, a hostile peer entry
  projected by the production code, and a cross-space move and back.

**Not done.** The issue's real-lane bullets: `sync-two-device.e2e.ts` does not
assert the peer row's hash or that a second identical image is linked; the
loopback test `a_peer_row_carries_the_hash_and_held_bytes_are_not_requested_again_5608`
does, over real QUIC. Two identical images that are both missing in one session
are both requested (2 files, checked); both rows end on one file.

Gates, on the branch as reviewed: `cargo clippy --workspace --all-targets -- -D
warnings`; `SQLX_OFFLINE=true cargo check --workspace --all-targets`; nextest
7047 of 7047 in two partitions, no FLAKY; doc-tests 10 passed, 5 ignored;
`cargo doc` with the doc-link lints; the four `sqlx prepare --check` lanes;

## Session 2390 — Page mode: one WYSIWYG document per page, saved per block

#5691, built to the design the maintainer approved on 2026-10-17. Page mode is a per-device setting (Settings › Editor › *Edit pages as*, default Blocks). The page header has a Blocks | Page switch and `Ctrl+Shift+M`. It is hidden on touch.

**Model.** The page is one flat document of `pageBlock(blockId, depth)` nodes over block mode's own extensions (`contentExtensions`, factored out of `use-roving-editor.ts`). The id rules are the source buffer's, moved to `src/editor/token-ids.ts` and shared by both:
- the id stays with the text where its block starts;
- a paste brings new ids, unless it is a cut and paste within the page, which is a move;
- duplicates are dropped.

**Save.** It runs on idle (700 ms), on blur, on a mode switch, on leaving the page, when the app is hidden and before export. Only the blocks that changed since their last save are written, through the existing commands, in the order creates, moves, edits, deletes. A block's saved state advances only when its write succeeds. A refused write re-reads the page and saves once more. Three premises of the design were wrong:
- `create_blocks_batch` takes no client ids;
- `move_blocks_batch` moves one contiguous run;
- `restore_block` also restores deleted ancestors, so the save re-reads the tree.

**Remote changes** are patched in by id, outside undo: text, creates, moves and deletes. A block with unsaved local text keeps it, and one deleted elsewhere while edited here keeps its text as a new block, with a notice.

**What keeps a page in block mode** (`page-mode-fit.ts`): tasks, priorities, dates, properties, attachments, queries, embeds, or more than 500 blocks. The switch says why, and #5743 tracks lifting each one. #5743 also holds block mode's blur conversions that page mode lacks: a typed `#name`, `key:: value` line or `TODO` marker.

**Review** found and fixed six defects, each pinned by a test shown red:
- a peer moving a child out of a block it deleted was read as a local move and reverted by the next save;
- several colliding ids were repaired one per save;
- a blocker once found kept the switch disabled after it was gone;
- page mode ignored the "Tab indents blocks" opt-out;
- the switch's selected item was never highlighted;
- the rebase had moved `MarkdownReveal` in block mode's extension order.

The review also deleted a custom incremental code highlighter. It was built for a 1,000-block cap that was measured only on Chromium, and the cap is back at 500 until #5743 measures WebKitGTK.

**Measured** with `AGARIC_PERF=1 npx playwright test e2e/perf.spec.ts -g 'page mode'`: Chromium against the mock, medians of 3 with their bands. At 500 blocks, typing INP and long frames sit inside block mode's noise on the same page, unthrottled and at `AGARIC_PERF_CPU=4`.

**Mutation testing** (`node scripts/run-mutation.mjs`): `page-save` 84.5%, `page-block-ids` 76.5%, `token-ids` 89.7%, with the survivors triaged.

Gates:
- vitest over the whole tree: 21,730 passed;
- typecheck, lint, knip, the bundle budget and `typecheck:e2e-tauri`;
- Playwright with the setting on Blocks and on Page.

The four `e2e-tauri` page-mode specs (restart, sync peer, `((ref))`, deleted elsewhere) run in CI only.

## Session 2368 — A sync session holds its deletions until every space has landed

#5712's remaining loss, after #5720: when a pull imported the old space's
doc before the new one, Pass D deleted the moved blocks' rows. The new doc's
import recreated the blocks, but rows no Loro doc carries were gone:
- the peer's drafts and "last opened" entries;
- backlinks, reference-type property values, tags, inherited tags, tag refs
  and page-link cache rows on other blocks pointing at the moved ones.

The maintainer chose the session-end sweep over a move-out marker. It needs
no engine format change, and it approved the one new device-local table.

**Change.**
- Migration 0126 adds `sync_deferred_purges` (STRICT,
  `ON DELETE CASCADE` to `blocks`).
- Pass D records the ids no engine holds, in its own transaction, and
  deletes nothing.
- `sweep_deferred_purges_if_last` runs where a pull completes
  (`complete_pull_session`) and after a snapshot catch-up. It purges the ids
  no engine holds by then, clears the table and fans the purged ids out. It
  reads the table before taking the write lock, so most pulls never take it.
- The import no longer returns a purged list, since it never purges now.

**Where the design was incomplete.**
- **The #5670 boot repair can meet a deferred row.** Boot replays the sync
  inbox before the repair, and a failed repair runs again next boot. It now
  skips deferred ids, so a moved or purged block isn't hydrated back into
  its old space.
- **The snapshot catch-up** imports every space too, so it sweeps at its end.
- **Concurrent pulls** from different peers share the table, so one
  session's end could sweep ids another session deferred before its new doc
  landed. Review closed it. A session that imports takes a claim on the
  engine registry's in-flight inbound syncs before its first import (a
  catch-up inherits the claim of the session that fell back to it), and
  leaves in the sweep, holding the write lock, which a deferral needs. Only
  the last session to leave sweeps, the ids of earlier and failed sessions
  included. Boot replay records deferrals before the daemon starts and never
  sweeps.
- **The e2e spec.** A ref-only property has no inline chip, and backlinks
  show only within one space. So the spec reads the ref in the property
  drawer, and each page ends in its referrer's space.

**Tests,** each shown red under one of eleven mutations:
- unit tests for Pass D, the sweep, an empty sweep, the cascade, the
  crashed-slot tombstone, the pull hook and the catch-up;
- the repair skip and the migration;
- the integration test across all eleven tables in both orders: there and
  back, an interrupted session, move then purge, a real purge, and a session
  without the new doc (which pins the gap);
- a 64-case proptest over shuffled, cut and crashed delivery rounds, with a
  mid-run invariant and final equality with A (about 21 s, in the
  slow-test override);
- `crossing_moves_reach_the_peer_whole_over_quic_5712`, red in 4 of 4 runs
  across both HashMap orders;
- `e2e-tauri/sync-cross-space-move.e2e.ts`, run on the real lane and red at
  the predicted point;
- overlapping sessions, each red without its part of the claim: a pull that
  ends while another still imports (`a_pull_ending_while_another_still_imports…`),
  the same for a catch-up, the catch-up taking over the claim of the session
  that fell back to it (the daemon's `run_snapshot_catchup` hands it over),
  the last session sweeping the earlier ones' ids, and a session that starts
  while the sweep waits for the write lock.

**Bench.** `sync_import_bench` covers the design's four cases at 100K blocks
over 3 spaces. It passes in criterion's test mode. Its numbers come from a
release run, which the scheduled lanes do not give it. `interactive_slo`
carries two measurement-only probes, `sweep_deferred_purges` with nothing
deferred and with 10K unheld ids at 100K blocks, which the weekly `bench-slo`
lane measures.

Gates:
- `cargo check` and clippy;
- targeted nextest;
- the full workspace, in two partitions;
- fmt;
- e2e-tauri typecheck and vitest (46);
- `just gen-sqlx`.

## Session 2362 — The AppImage carries its GStreamer plugins, so it finds the camera

#5718: the AppImage's QR scanner found no camera. The AppImage shipped the
GStreamer core without plugins, and its `AppRun` pointed GStreamer at the
empty bundled plugin directory, so WebKitGTK saw zero capture devices. The
maintainer approved bundling once session 2354 confirmed the cause.

**Change.**
- `bundle.linux.appimage.bundleMediaFramework: true`. tauri-bundler then runs
  linuxdeploy's gstreamer plugin, which copies the build machine's whole
  plugin directory and the scanner helpers. `libpipewire` stays on the
  host, by linuxdeploy's excludelist.
- The machines that build the AppImage install `gstreamer1.0-plugins-base`,
  `-plugins-good`, `-pipewire` and `-gl` (WebKit draws video through
  `glupload`).
- `scripts/check-appimage-media-plugins.sh` fails closed, in `ci.yml` and
  `release.yml`, when the AppDir lacks the plugin directory or `pipewire`,
  `app`, `video4linux2` or `pulseaudio`. It failed on the old AppDir, and on
  a build with the flag off.
- `BUILD.md`: the AppImage carries its plugins, and the `.deb` needs the
  host's `gstreamer1.0-pipewire`, which it doesn't declare.

**Measured on a local release build:**
- Size: +11.4 MB (+10.9%) against the same binary with the flag off.
- Boot: unchanged within noise (22 interleaved boots each). GStreamer starts
  only on first media use, when rebuilding its registry from cold costs
  about 0.5 s.
- In an isolated session with the host's PipeWire socket, the scanner played
  a live preview from the built-in camera. The old AppImage reproduced the
  maintainer's error.

**Not fixed here: voice notes still cannot record on Linux.** WebKitGTK
2.52's `MediaRecorder` needs `uritranscodebin` from plugins-bad. On
GStreamer older than 1.24.9 (Ubuntu 24.04 has 1.24.2) it refuses webm and
ogg, which leaves MP4 with a high-ranked AAC encoder. A test with those
added still produced an empty recording. Tracked in #5730.

## Session 2354 — The webview grants the microphone; the AppImage camera's cause found

**The microphone (#5717).** On Linux, `allow_camera_permission` answered
WebKitGTK's `permission-request` only for the camera. A voice note's
microphone request got `Default`, which WebKitGTK treats as a denial. A
WebKitGTK 2.52.6 probe outside WebDriver showed `NotAllowedError` for both
audio and video when the request is unanswered or answered `Default`, and a
live track when it is allowed. The handler is now `allow_capture_permission`,
granting the camera and the microphone and leaving every other request to
WebKitGTK's default.

**What the e2e lane can and can't test.** Under WebDriver, WebKit grants
`getUserMedia` itself and never emits `permission-request`. A build whose
handler denied the camera still passed `camera-permission.e2e.ts`, whose
header claimed it pinned the handler. A Rust unit test is therefore the only
check of the grant. The headers now say what the specs check: that the real
webview delivers a live track from the mock capture devices.

New specs:
- `qr-scanner-camera.e2e.ts` drives the real scanner through html5-qrcode's
  own calls and expects a playing preview and no error;
- `microphone-permission.e2e.ts` is the camera spec's twin.

All three went red with the mock devices off and no reachable device.

**The AppImage camera (#5718).** The maintainer saw the scanner's
"permission" text. The cause is that the AppImage ships the GStreamer core
but no plugins, and its `AppRun` points GStreamer at the empty bundled plugin
directory. WebKitGTK then finds no camera ("no device was found amongst 0
devices" in the journal at 01:48:20), and `getUserMedia` rejects with
`OverconstrainedError: Invalid constraint`.
- The 01:45 build predates #5673. Its error mapping missed html5-qrcode's
  string error and showed the generic text.
- Main maps the same failure to "No camera was found".
- #5673's `aspectRatio` is not involved: html5-qrcode applies it to the track
  after `getUserMedia`, and every constraint combination resolves under the
  mock devices.

Bundling the plugins, which the maintainer approved once the cause was
confirmed, follows in its own PR.

Gates:
- e2e-tauri: the camera, microphone and scanner specs, 3 of 3;
- the handler's unit test;
- vitest `src/components/peers` (219);
- typecheck, including e2e-tauri;
- lint, clippy and fmt;

## Session 2330 — A peer keeps a page moved to another space, whatever order the docs arrive

#5712: a peer could lose the blocks of a page that another device had moved
to a different space, depending on which space's doc it imported first. The new space's engine still held the
page, but the SQL rows were gone.

**Cause.** A cross-space move prunes the subtree from the old space's doc
(#2907). On the peer, the import derives its purged set as "held before minus
held after", so the prune reads as a purge, and Pass D deleted those rows from
every table. When the new space's doc had already been imported, nothing
recreated them. The responder sends spaces in `registry.space_ids()` order,
which is HashMap order, so either order happens.

**Fix.** Pass D (`project_pass_d`) now sweeps only the ids that no engine
holds, using `LoroEngineRegistry::spaces_containing` from #5711. The same
filter covers the crash-recovery path's saved tombstone, so
`narrow_tombstone_to_sweep` (#2292's narrower filter for that list alone) is
gone.

**Tests.** `move_page_across_spaces_then_import` in `src/spaces/tests.rs`
drives the real commands and forces each import order through
`apply_remote`. New-space-first went red without the filter; old-space-first
was already green. `replay_keeps_rows_another_space_holds_despite_the_tombstone_5712`
pins the recovery path, and it alone went red when the filter covered only
the engine's purged set.

**Still open; the maintainer approved closing it.** When the old doc
arrives first, Pass D still deletes the rows and the new doc's import
recreates them from the engine. Whatever the docs don't carry is lost in that
order:
- the peer's own device-local rows on the moved blocks: `block_drafts` and
  `page_opens` (through the `blocks` cascade). Attachment rows come back
  with the new doc now that #5608 keeps them in the engine;
- rows on untouched blocks that point at the moved ones: `block_links`
  backlinks and `block_properties.value_ref`, probed in review. `block_tags`
  likely goes the same way, but it was not probed.

The new-space-first order keeps all of them. A move-out marker in the old doc
(a follow-up under #5712, designed separately) is to let the peer tell a
prune from a purge and keep those rows.

The review also probed moving a page there and back, with and without an
intermediate sync and in both import orders: all four end with the blocks
live in the old space.

Gates: targeted nextest (sync, spaces, projection, registry, loro_sync),
1,581 passed; full workspace nextest, 3,504 + 3,496 passed; clippy, fmt and
`SQLX_OFFLINE=true cargo check --workspace --all-targets`, all clean.

## Session 2328 — Attachment metadata lives in the Loro engine and reaches peers

#5608 (severity high): attachments never reached the other device, with no
row and no bytes. The maintainer chose option (b), attachment metadata in
Loro with an engine format bump. They approved the design's points:
- the `block_attachments` root, nested per block;
- `ENGINE_FORMAT_VERSION` 3 → 4;
- `content_hash` on the add payload, the only part of #4955 taken; iroh-blobs
  is deferred;
- undo of a delete reading an add op of either provenance;
- `fs_path` naming the stored path after dedup.

This covers design steps 1–5, built on #5647's branch for its shared registry
probe. The PR is held for the maintainer's review.

1. **Engine model** (`loro/engine/attachments.rs`). Block → attachment id →
   fields, both levels mergeable maps. A delete is a `deleted_at` tombstone,
   because removing a key would let a later `ensure` resurrect a mergeable
   child. Purge drops the block's map. There are 13 unit tests and a
   three-peer convergence proptest (also run at 20,000 cases).
2. **Writes, undo and replay** go through `apply_*_attachment_via_loro` in the
   kernel, `merge::dispatch_engine_op`, the three commands and the undo
   arms. `find_attachment_block` shares #5647's `spaces_containing`. Undo
   read only local add ops (`is_replicated = 0`); that filter is dropped in
   the delete reverse and, as found here, in history's three positional-undo
   queries and the batch reverse. With it, Ctrl+Z skipped a peer
   attachment's delete and undid an earlier op instead. Until step 6, the
   row's `content_hash` is written by one `UPDATE` after projecting.
3. **Peers.** The import projection writes attachment rows from the engine.
   The new root is classified per block, and the format version is now 4.
   The #5608 loopback test (real QUIC) covers add with B's bytes equal to
   A's, rename, delete, and delete against a concurrent rename. Without the
   projection, B ends with no rows: the issue's own symptom.
4. **Existing vaults.** `hydrate_attachments_into_engine`, the sixth boot
   repair, writes no ops. It runs after #5670's one-shot engine hydration,
   which would otherwise seed whole a space whose engine the backfill
   created. Seeding a page into a space carries its attachments and
   tombstones any old entry that has no row.
5. **Disaster recovery** restores attachment rows from the engine.
   `recover_attachments_from_op_log` replays only ids no engine holds.

single-device one stays. Also known: a page that returns to a space with no
attachments brings its old deleted entries back live on a later add. Page

**Remaining:**
- step 6: `content_hash` on the op and the receiver's check;
- step 7: an attachments arm in the reconciliation oracle;
- step 8: e2e peer commands and spec (#5365's image-bytes scenario), the

## Session 2326 — Crash replay reaches the engine for restore, purge, space move and retries

#5647 listed four ways a crash-recovery replay still missed the Loro engine
after #5630. A read-only plan pass confirmed all four on main. It corrected
the issue's steps for the purge case and widened the space-move case. The
maintainer approved the one persisted-format change in case 4.

1. **Restore.** SQL already holds the restore, so the cohort query comes back
   empty. On replay with an empty cohort, the descendants (matching
   `deleted_at`) and the ancestors are now read from the engine.
   `ApplyEffects::restore_space_id` keeps the fan-out on the right engine
   when a later op in the tail re-deleted the seed.
2. **Purge.** SQL no longer has the row, so its space did not resolve. On
   replay the block is purged from every engine that holds it, found by the
   new `LoroEngineRegistry::spaces_containing`.
3. **Space move.** SQL already shows the new space. Replay takes the new space
   from `resolve_op_space` and the old doc from the registry. Hydration also
   admits rows deleted at or after the move. Without this, the old doc kept
   the subtree even when nothing deleted the page later.
4. **A retried replay op** ran as an ordinary op and lost replay routing. Its
   retry row is now `ReplayApplyOp:<seq>:<device>`, a new persisted
   spelling; the old `ApplyOp:` spelling is still read. It runs as
   `ApplyMode::ReplayRouted`. Recording a failure or a success retires the
   other spelling for the same op.

went red first, including both variants of restore and of space move.
Comments that said replay rebuilds the engine from scratch, or that the
purge fallback is unreachable, are corrected.

spelling before inserting its own, as two statements. The retry row is the

## Session 2314 — Reduced motion stops transitions; wide math scrolls while editing

Two rendering bugs found during #5678's investigation, plus a graph flake
with the same root cause.

**#5692.** Under reduced motion (the OS setting or Animations "Off"), Mermaid
flowcharts rendered several times too large; one grew from 378×1322 to
2094×4325.

- **Cause.** Both reduced-motion resets in `src/index.css` (the OS media
  query and `[data-motion='off']`) set `transition-duration: 0.01ms` on `*`
  and left `transition-property` at its default `all`. Every element without
  its own transition gained one on every property, for one frame. Mermaid
  measured its nodes mid-transition.
- **Same cause, graph.** graph-view's zoom tests caught the canvas and its
  labels drawn at the old zoom for a frame after each step. They flaked 7 in
  60 runs and reddened main once. Reduced-motion users saw that frame too.
  #5703 had fixed it with a graph-only rule; this global fix makes that rule
  redundant, so #5703 is closed and its regression test moves here.
- **Fix.** Both blocks set `transition: none`. At zero specificity, any
  transition a class declares still wins, and the token durations those use
  are already 0 under reduced motion.
- **Audit.** No code in `src/` listens for `transitionend`. Radix presence
  watches `animationend`, and sonner and cmdk use neither. The only listener
  is cytoscape's cache invalidation inside Mermaid's bundle, which is
  harmless.
- **Tests.** `e2e/diagram-reduced-motion.spec.ts` compares a flowchart's size
  with reduced motion on and off, for both triggers. It was off by 2,943 px
  before the fix, and reverting either CSS block reds only that block's
  test. The graph test, "under reduced motion a zoom step draws the canvas
  and its labels at the new zoom at once", passes with the global fix alone
  and reds without it (0.769 against 1).

**#5693.** In the editor at phone width, wide display math was clipped. The
math node view's `<button>` grew to fit the equation, so `KatexMath`'s
scroller (already `SCROLL_ONLY_WHEN_WIDER`) never overflowed, and the column
clipped it. Display math now makes the button `block w-full`, so the scroller
overflows when the equation is wider and shows no bar when it fits. A test at
390 px checks that the scroller overflows, ends on screen, moves on wheel, and
that a click still opens the source; without the fix it fails on "the
equation overflows its own scroller".

## Session 2312 — The zip advisories leave by dropping a feature we never used

Every PR touching Rust started failing `cargo deny`. It reported three new
RustSec advisories against `zip` 4.6.1:
- RUSTSEC-2026-0367: SUID and SGID bits preserved on extraction;
- RUSTSEC-2026-0368: `extract` creating symlinks outside the destination;
- a third: permissions applied through symlinks.

All three are fixed in `zip` 9. The crate arrives only through
`tauri-plugin-updater` 2.13.1.

**No upgrade path.** Every released updater (2.13.2, 2.13.3, 2.14.0,
3.0.0-alpha.3) still requires `zip = "^4"`.

**What the feature does** (`tauri-plugin-updater-2.13.1/src/updater.rs`).
`zip` is used only on Windows, in `extract_zip`, behind the default `zip`
feature, which also enables `tar` and `flate2` for Linux's
`.AppImage.tar.gz` branch. macOS declares its own `tar` and `flate2`, not
behind the feature. `download()` checks the minisign signature before
`install()` sees any bytes. Agaric's release ships raw bundles (`-setup.exe`,
`.msi`, `.AppImage`, `.app.tar.gz`; `createUpdaterArtifacts` stays off), so
the zipped formats and their unpacking were dead code for us.

**Fix.** `tauri-plugin-updater` takes `default-features = false` with
`rustls-tls` and `system-proxy`, the rest of the default set. `zip` leaves
both lockfiles, and `cargo deny` reports `advisories ok`. Putting the old
manifest and lock back reds it on all three advisories. The version floor
moves to 2.11.0, where `system-proxy` first appears; the lock stays on
2.13.1.

**Not compiled for Windows.** PR CI never builds Windows, and a cross
`cargo check` stops at `ring`'s and `aws-lc-sys`'s C builds. Reading the
source shows every Windows use of `zip` (`extract`, `extract_zip`, the
`Extract` error variant) behind `cfg(feature = "zip")`, so the
featureless build is a configuration upstream supports. The first Windows
compile will be the release build.

Gates: `cargo deny check`; `cargo tree -i zip --target all` (none);
`SQLX_OFFLINE=true cargo check --workspace --all-targets`; clippy;
`cargo metadata --locked` for the main and fuzz locks; prek on the changed
files.

## Session 2308 — Live blocks an engine lost come back; the replay that lost one is pinned

#5670: #5628's integrity check, run on a copy of the maintainer's vault,
found one live block in Work that Work's Loro engine did not hold.

**Diagnosis** (posted on #5670). Every op was local. On 0.13.0 the local path
did not advance the apply cursor, so each boot replayed the previous session
onto an engine that already held it. A boot on 2026-09-16 replayed an indent,
which moved the block under C90, already deleted in the engine. Replay's
sweep then tombstoned it. Its outdent, replayed next, found no space and took
the SQL-only fallback, which un-swept SQL but never moved the engine node.
Purging C90 on 10-08 removed the block from the engine with it. #5630 (replay
routing and no sweep during replay) and #5418 (the snapshot pass advances the
cursor) fixed the cause.

**Regression test.**
`replay_over_an_engine_ahead_of_the_cursor_keeps_an_outdented_block_through_the_purge_5670`
replays the vault's sequence onto an engine ahead of the cursor, purges the
old parent, and checks that the block is live under its SQL parent and that
the engine and SQL trees match. It goes red only with both halves of #5630
reverted; routing alone stays green, because the sweep is what tombstoned the
block.

**Repair.** `repair.engine_missing_live_blocks.v1` runs once at boot. It finds
live blocks their space's engine lacks and re-seeds their page groups with
the existing hydration walker. It writes no ops, because the op log already
holds them, the same as #4775's hydration; `commands/AGENTS.md` now says so in
one sentence. The marker is written only after the engines are saved, since
nothing would replay a lost repair. On the vault copy it hydrated the one
block in about 126 ms, left zero divergences, and a second run took 0.3 ms.

**Review found one defect.** Siblings seeded at space assignment ranked by a
legacy position stamp that later moves never refresh. So a restored block
could land between siblings in a stale order, and the follow-up position
pass would write that order to SQL. The repair's seed now ranks by SQL first
and uses the stamp only for siblings SQL does not hold. A test reorders
siblings before the loss and reds with the old precedence. Review also pinned
the marker-after-save order with a test that reds when the marker is written
first.

**A second review found that fix too wide.** It ranked every hydration by
SQL, and the seed at space assignment cannot rank that way: a page's seed
renumbers its group without the nested pages it stops at, so a nested page
seeded later tied the sibling renumbered into its rank and landed after it.
The #5239 fixture had been edited to hide that. The fixture is back, and only
the repair ranks by SQL (`SeedRank`); every other hydration seeds as on main.
The restored test reds when the space-assignment seed ranks by SQL.

**Accepted risk.** A peer that moved the purged node before merging the
purge could revive a second live node. The maintainer's only peer last
synced before this block existed.

Gates after the second review: the targeted nextest (385), clippy,
`SQLX_OFFLINE=true cargo check`, fmt, and the full workspace suite
(partitions 3,499 and 3,491, all passed).

**Diagnosis** (posted on #5686).

- **Edit as Markdown** writes `[[Title]]` and `#name` wherever the importer

  - duplicate titles, cross-space and deleted targets.

The maintainer pointed out that cross-space links and duplicate page titles
are refused today, so those cases can only come from older data or offline
sync. They asked to keep the ULIDs, to show a faint title on hover or at the

- It is generated content, so it is never in the text or the clipboard.

- A hidden live region announces "Points to …".

- The fade uses `--duration-fast`, which reduced motion already zeroes.

It covers the start of the next line while it shows.

## Session 2302 — Edit as Markdown gets Edit / Preview / Changes

#5685: Edit as Markdown saved with no way to see the rendered result or what
changed. The maintainer chose a three-way switch, a word-highlighted line
diff, and a Save that counts the changes and is disabled when nothing
changed.

**Diff.** jsdiff (`diff@^8.0.4`) was already in the lockfile as a dev-only
transitive dependency. Making it direct changes two lines and fetches
nothing. It caps the work on big rewrites (past 2,000 changed lines, a page
becomes one hunk; past 200 changed words, a line is marked whole), ships its
own types and splits words Unicode-aware. A hand-written LCS would have
needed its own handling of CRLF, long pages and word boundaries.

**UI.**
- **The switch** is the existing `ToggleGroup`. Going back to Edit returns
  the caret to the editor, which stays mounted.
- **Changes** (`line-diff.ts`, `PageSourceChanges.tsx`) shows removed then
  added lines. `−`/`+` gutters and hidden "Removed:"/"Added:" labels mean
  colour is never the only cue. Changed words are struck through or
  underlined, with three lines of context and longer runs folded. Word diffs
  run only while Changes is open.
- **Save** reads "Save (N changes)", N being the change runs, and is disabled
  at zero. The count needs the line diff on every edit, so that diff is
  memoised and deferred rather than lazy.
- **On phones,** Save and Cancel move under the view in Preview and Changes.

**Preview gap.** Preview (loaded on demand) reuses `renderRichContent`,
`PropertyChip`, `TaskCheckbox` and `ListMarker` through the frontend's block
reader, so `[[Name]]` and `#tag` render as chips, including names the save
would create. It is not the backend's save parser: a heading typed without a
bullet does not nest what follows it, and aliases and refused property values
are not checked. Exact parity needs a backend dry run of the save, which
stays open on #5685.

**Tests.** Seventeen mutations, each killed by the predicted assertion. Two
that first survived (the edit cap, and Save disabled on the phone toolbar)
got stronger tests. Tests and helpers that matched Save by exact name,
including the real-backend `pageSourceButton` helper, now match by pattern.

Gates: vitest (32 files, 1,092), `npm run typecheck`, oxlint, oxfmt,
`npm run build` with the bundle budget (jsdiff adds about 2.5 KB gzip to the
lazy page-editor chunk; Preview is its own 1.9 KB chunk), and the
page-source-edit and checkbox-typing Playwright specs (69/69,
`--repeat-each=3 --retries=0`).
