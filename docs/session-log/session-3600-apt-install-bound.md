# Session 3600 — bound and retry the apt install in apt-install

Run 42078795569's "Real-backend specs (1)" sat in `Install runtime dependencies` with no output until it was cancelled, while its sibling shards passed the same step in seconds. The action bounded `apt-get update` twice but ran `apt-get install` with no bound, and its stdout goes to a log printed only on failure, so a slow install is silent.

- The update was not the stall: it prints a `::warning::` on every timed-out attempt and none appeared. The same silent, long install recurs in the e2e-tauri history and finishes successfully, its only output being needrestart's closing lines: jobs 127320928631 (run 42048022669), 127281611611 (run 42037023371), 127007410934, 126936159680, 126936159619 and 126949717796 among them. The build job's `Install system dependencies`, which restores the .debs from `actions/cache`, was never slow in the same window; the runtime install, which downloads them, was. So it is a mirror trickling .debs to one runner, which `Acquire::http::Timeout` does not catch: that fires on a silent connection, not a slow one.
- Fix: `apt-get install` runs under `timeout -k 30` with a new `install-timeout` input (default the update's bound) and gets one retry after the same kill, lock wait and `dpkg --configure -a` the update path used, now shared as `reap_apt` and `wait_for_apt_locks`. The retry opens new connections and keeps every .deb the first attempt finished. A timeout prints the apt log, whose `Get:` lines name the slow mirror. Two timeouts exit 75 with `AGARIC_APT_INFRA`; any other install failure still exits with apt's status, unretried.
- Ran the action's script with shimmed `sudo` and `apt-get`: an install that never returns hung the old script until an outer timeout and made the new one exit 75 after two bounded attempts; slow-then-fast exits 0; `E: Unable to locate package` exits 100. `prek run --all-files` and `prek run --hook-stage manual --all-files`.
