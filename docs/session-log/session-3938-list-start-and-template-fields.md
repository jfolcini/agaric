# Session 3938 — An ordered list keeps its start, `/template` keeps task state and properties (#6530)

The two checkboxes of #6530 that #6590 left open.

**Ordered-list start numbers.** The issue's Change and Done-when ask for it ("keep an ordered list's start number"; "an ordered list starting at 5 round-trips unchanged"), so it is built, against #6590's note that it needed a decision. The note's reason, that numbers are computed and never stored, is the block model's: a block with `listStyle: ordered` is still numbered by position (`list-ordinals.ts`, the Rust export's `compute_list_ordinals`), and that is unchanged. What changed is an ordered list inside one block's text: `parseOrderedList` puts the first item's number on the node as `attrs.start` (left off for 1, so a parsed list still equals one built without attrs), `serializeOrderedList` counts on from it (`5.` / `9.` is written `5.` / `6.`), and the static renderer writes `<ol start>`; TipTap's `OrderedList` already carries `start`. Two adjacent lists still merge, the second taking the first's count. Rust needs nothing: it stores block text as written and has no twin of the in-block list serializer.

The shared vectors: the corpus row `agaric-export block 8` (`2. Pay deposit`) carried a reviewer-written `editorCanonical: "1. Pay deposit"`; it is dropped, so the row now pins the start through `block-content-conformance.test.ts`. No `blocks` rows were added for link and image titles: Rust authors their `rustReads` and `fts`, and `derivations.rs`'s golden hashes every vector text, so they need the Rust lane (`CONFORMANCE_UPDATE=1` and the golden).

Six existing tests pin the old renumbering and are left red: `#4071` and `#4076.2` in `markdown-roundtrip-fidelity.test.ts`, the two list tests in `compute-content-delta-canonicalization.test.ts`, and the two `3. buy milk` tests in `use-roving-editor.test.ts`.

**`/template`.** The premise holds: `insertTemplateBlocks` sent `blockType: 'content'`, `properties: {}` and one `create_blocks_batch` per depth level. No existing command copies a tree in one transaction: a batch can only name parents that already exist, since batch ids are minted on the server, and `paste_blocks` would mean writing the template out as Document text on the frontend. The copy still runs one batch per level, now with each block's `todo_state`, `priority`, `due_date`, `scheduled_date` and its text properties in the spec's map. A property held as a number, date, ref or boolean goes through `set_property` afterwards, because the batch types every value as text. The keys `INLINE_PROPERTY_RESERVED_KEYS` names (the app's stamps, `template`) are not copied, as the Rust copy does not copy them. `onOpRefs` hands every ref to `useTemplateSelection`, which records them as one undo step (`merge: false`). The doc comment no longer claims a rollback. One transaction needs the command the issue describes: copy a template page under a block through `copy_page_blocks_in_tx` with `expand_template_variables`, returning the `{{cursor}}` block.

The custom properties are read with one `get_batch_properties` before anything is written. Sixteen existing `insertTemplateBlocks` tests stub IPCs strictly and do not list that command, so they are red. Their assertions are unchanged; adding `get_batch_properties: () => ({})` to `stubTemplates` makes them pass.

Checks run: the new vitest cases and `e2e/ordered-list-start-edit-6530.spec.ts` and `e2e/template-keeps-fields-6530.spec.ts`, each shown red by a mutation of the code it covers; targeted vitest over the serializer, parser, property, conformance, renderer, template and slash-command suites; `npm run typecheck`.
