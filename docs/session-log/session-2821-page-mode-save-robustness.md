# Session 2821 — one refused block no longer holds back the page's other writes, and a reread never patches in rows its load did not apply

Three findings of the #5691 review of 2026-10-21, verified by a second pass, in page mode's save.

- **A refused create held back everything.** When the backend refused a new block (content linking a page in another space, or a block over 256 KiB), the save returned at the failed create, and a gate then held back every delete. No other edit or delete on the page was written while that block held that content, and leaving dropped them. Now a failed create or restore only holds what depends on it. Its children's creates and restores wait, and the creates are replanned so a block placed after it takes its slot from the tree as it really is. `planMoves` neither moves a block the backend does not hold nor anything under one. An edit waits only if it removes text from the block just before a block still to be created, the block that may have been split from (#5272), at whatever depth the new half now is. A delete waits only while a block under it (itself included) is one the document shows, or has its text in a block the backend does not hold as shown, for the delete takes the blocks under it along. A paste in the middle of a block hands its tail to the last block pasted, so if that one is refused after the blocks pasted before it were created, the tail is held by nothing and is lost if the page is left. The order (creates, moves, edits, deletes) and the rule that a block's saved state advances only on success are unchanged.
- **A reread could patch in stale rows.** `read()` returned the store's rows even when its own load was overtaken by a newer one or failed. `read()` now returns the store's rows only if they are a new array after its load, which only a load that landed sets (a failed one, or one a newer load overtook and that is still going, leaves them), and throws otherwise. It reads the store, not a subscription, because the save made as the page closes reads after the subscription is gone. A failed read patches nothing in.
- **A failed reread skipped the toast.** When a refused write's reread failed, `runSave` threw past both the save-failed toast and the undo entry for the ops that did land; a `finally` now records both.

The mock still overwrites a colliding create id the backend refuses, so the mock lane cannot show a colliding-id hold. The cross-space refusal can only be shown on the real backend.

Suites run: `npx vitest run src/editor/page-mode src/stores/__tests__/page-blocks`, the page-mode property test alone, typecheck, lint, and `e2e/page-mode.spec.ts`. Every new test was shown red by breaking the code it covers, and the review's repro tests passed on the unfixed tree and fail at their defect assertion now.
