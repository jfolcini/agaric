# Session 3927 — A click into a block puts the caret where it landed (#6562, second checkbox)

**Goal.** A click or tap on a static block mounted the roving editor with the caret at the end, wherever the click was. #6599 stopped focusing a block from moving text, which this fix relies on: the click is read from the static render before the mount.

**What changed.**
- `src/editor/click-caret.ts` (new, TipTap-free at runtime): `textPointAtClick` reads the DOM point under the click (`caretPositionFromPoint`, or WebKit's `caretRangeFromPoint`) and `textPointAt` turns it into a `TextPoint`, a count of the document's own text characters plus a `bias`. A DOM text node counts when it continues the text runs of `parse(content)` (a highlighted code block splits one run over several nodes) or is a whole later run (a diagram's source is never drawn); chip labels, the list marker and the space the renderer puts between paragraphs count nothing. Chips and block boundaries carry no characters, so `bias` picks the side: `'after'` at a run's start, `'before'` elsewhere, and for a point in uncounted text, after it unless the point is at its start. `posAtTextPoint` maps the point into the ProseMirror doc after the replace, clamping past the end to the end of the last textblock (after a trailing chip).
- `StaticBlock.handleOuterClick` passes the point to `onFocus`; `EditableBlock.handleFocus` hands it to `mount` as `cursorPlacement`; `mount` focuses at `posAtTextPoint`. `MountOptions.cursorPlacement` is now `'start' | 'end' | TextPoint`.
- A double-click needed nothing: its second press lands on the mounted editor, which selects the word natively (`sticky-toolbar.spec.ts` already pinned it).
- Page mode needed nothing: its one editor is always mounted, so a click places the caret natively (checked with a throwaway spec before focus, not kept).

**Decisions and traps.** The issue suggested counting a chip as one position; matching the document's text runs instead needs no knowledge of how each chip renders, and the bias settles the one ambiguity counting would have solved. `posAtCoords` after the mount was rejected by the issue: the static render and the editor draw chips and markers differently. Known limit, in the module doc: a chip label that begins the next text run is taken for that run. `|` as the spec's typed marker is escaped at a line start (table syntax), so the spec types `Q`. `sticky-toolbar.spec.ts` clicked a row's first word and pressed End before ArrowDown or typing, relying on the caret already being at the end; End is read too late (the documented `selectionchange` trap), so it went red at "stays mounted while the focus moves". Its four `End` presses are now `caretAtEnd` (`selectEditorRange` to the text's end); the assertions are unchanged.
