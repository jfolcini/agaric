## Session 2682 — the weekly frontend mutation lane runs as four groups, so it fits its timeout again

#5915. With all 36 modules enrolled, the one `mutants-frontend` job of dispatch
run 39183149461 started at 01:03 and was cancelled by its 60-minute timeout at
02:03, partway through `page-rendered`; every report was lost with it.

- **Groups:** `node scripts/run-mutation.mjs --group k/n` runs the modules
  whose index in `MODULE_NAMES` is k-1 modulo n. Each matrix leg passes
  `${{ matrix.group }}/${{ strategy.job-total }}`, so every module lands in
  exactly one group and a new module joins one without a matrix edit. Four
  groups: from the cancelled run's per-module times, scaled to the slow
  34-minute runner of 2026-10-12, three would put one group near 39 minutes.
- **Merge:** `mutants-frontend-merge` downloads every group's
  `mutation-frontend-report-<group>-of-<legs>` artifact, reads the expected
  count from the `-of-<legs>` suffix, names any missing group and fails, runs
  `check-mutation-reports.mjs` and the summary over the union, and uploads
  the merged `mutation-frontend-report` under its old name.
- **Short merge:** like the Rust lane, the merge reports how many groups it
  merged, and the survivor filer runs with `--dry-run` when one is missing,
  so a dead group's survivors are not marked resolved and refiled next week.
- The timeout is unchanged.

Shown red: a module dropped from the partition (the union test and the merge
guard both name it), a group that never uploads (the merge fails naming it),
and the merge's missing-group check disabled (the merge passed; restored, it

## Session 2673 — the first Cmd+K, Ctrl+F and search-sheet open render at once instead of 300 ms later

Found while speeding up `App.test.tsx` (#5908): the first open of each search
overlay waited behind React's Suspense reveal throttle although `App.tsx`
preloads their chunks.

- **Mechanism (React 19.3.0):** `lazyInitializer` calls the factory, attaches
  `then(cb)` and, in the same call, checks whether `cb` already set the payload
  resolved; the old factory, `loadX().then(m => ({ default }))`, returned a new
  Promise each time, whose `cb` runs a microtask late. So the first render
  always suspended, committed the null fallback, and the retry waited out
  `FALLBACK_THROTTLE_MS` (300 ms) after it.
- **Fix:** `lazyView`, written for the views in #5444 for exactly this, moves
  to `src/lib/lazy-with-preload.ts` as `lazyWithPreload`: its factory hands
  `lazy` a thenable whose `then` calls back at once once preloaded, so nothing
  suspends. `CommandPalette`, `InPageFind` and `SearchSheet` use it and
  `preloadSearchOverlays` calls each `.preload()`; the search sheet's own lazy
  `InPageFind` and `PaletteBody` had the same problem and preload with its
  module. What is lazy and when chunks download are unchanged.

Measured in Playwright, 10 fresh loads each, Cmd+K to the palette input in the
DOM: median 400 ms (max 528) before, 22 ms (max 65) after, at load 35–40.

Tests: `App.test.tsx`'s overlay test expects each overlay right after its
opening `act` once the idle preload has run, and
`SearchSheet.preload.test.tsx` does the same for the sheet's segments; both
fail on main's code at the predicted lookup.

Ran: vitest over `App.test.tsx`, `src/components/mobile/__tests__/` and the
ViewDispatcher tests (208), `npm run typecheck`, `oxlint src`, the 14 palette,
find and search Playwright specs (76).

## Session 2667 — the real-backend reminder spec runs at any hour, in one scheduler minute

`e2e-tauri/reminder-due-task.e2e.ts` (#5908) refused to run within 15 minutes
of local midnight, which failed PR #5919's real-backend shard at about
23:50 UTC, and took 2–3 minutes.

- **Midnight:** the reminder job counts a task as due today by the local date
  at the moment it runs, once a minute. The spec set the reminder for the next
  minute but always made the task due today, so near midnight the run that
  fired could already be on the new date and skip the task; the guard hid
  that. The guard is gone: the reminder is the current minute and the task is
  due on that minute's date, typed as `YYYY-MM-DD`; with under two minutes to
  midnight the spec sets the reminder for midnight and the task due tomorrow.
  Using the run's own local date is right for the product; no bug there.
- **Slow:** the time was waiting for scheduler runs, the first 60 s after
  launch. A reminder set for the current minute fires on that first run, and
  the third test's second wait is gone: "a later run doesn't notify the first
  task again" is the Rust test `fires_exactly_once_across_two_ticks` in
  `reminders.rs`, which the header now names. The spec takes about 1:26, the
  one real scheduler minute it exists to prove.

Shown red under `libfaketime` at 23:59:15: the old spec refused to run, the old
spec without its guard timed out with no notification (the hidden bug), and
the new spec with its midnight margin set to 0 timed out the same way; the new

## Session 2658 — an undo in page mode gives each text back the id it had, even after a peer rewrote the joined block

The #5908 row for `page-mode.property.test.ts`: a counterexample, and the test
hitting its 20 s timeout under load.

- **The counterexample** (CI run 39056549471, seed 966892422): two "alpha"
  blocks; cut the second's text and paste it at the start of the first; a peer
  rewrites the joined block; undo twice. The second undo brought "alpha" back
  under a new id, which breaks any `((ref))` to it. #5911 fixed the variant
  where the peer creates a block, not this one.
- **Cause:** after an undo, `page-block-ids.ts` reassigned every id by which
  character starts each block. The peer's rewrite had replaced the joined
  block's text, so its new first character carried the second block's id,
  overriding the id the undo had put back; the next undo then found that id
  taken and made a new one.
- **Fix:** `restoredIds`: after an undo or redo, each block keeps the id the
  undo put back unless another block holds it too; every other block goes by
  the character rule, unless its id was already kept. The peer's text then
  sits under the first block's id and the next save gives the second block
  its cut text back, page mode's existing local-change-wins rule.
- **Pinned** as the fifth entry of the test's `EXAMPLES`; red without
  `restoredIds` at the CI's assertion.
- **Runtime:** almost all the cost is driving TipTap (typing, clipboard,
  paste rules, a new editor per run), not the mock. Runs drop from 150 to
  `EXAMPLES.length + 50`, so every pinned example always runs: median 6.9 s

## Session 2655 — a tooltip never sits over its trigger's open Select or menu

Two #5908 flakes, `pages-view.spec.ts` sort ("the listbox stays open after
Escape") and `spaces-management.spec.ts:118` (the switcher's "Ctrl+1–9"
tooltip intercepting the click on an option), had one cause, and the second
was failing most PR runs of its shard.

- **Mechanism (Radix source):** the Select trigger calls `preventDefault()` on a
  mouse pointerdown, and Radix skips the tooltip trigger's own close once the
  event is prevented. The tooltip's pointerdown-outside dismissal is attached
  in a `setTimeout(0)` after it mounts. So a tooltip that opens in the same
  moment as the press (focus returning to the trigger, or a hover) stays open
  over the listbox as the topmost layer, with inline `pointer-events: auto`:
  it takes the Escape meant for the listbox and the clicks on its options. A
  person could hit it too.
- **Fix, in `ui/tooltip.tsx` only:** a tooltip refuses to open while its
  trigger (or something inside it) has `aria-expanded="true"`, and while open
  a `MutationObserver` on the trigger closes it when the menu opens, checking
  once on start because the menu can open before the effect runs. It covers
  the Pages sort, the space switcher, the page header kebab and every icon
  button that opens a menu, with no call-site change.
- **Workarounds removed:** `switchToSpace`'s `page.mouse.move(0, 0)` and the
  spaces spec's "first Escape only closes the tooltip" skip; the spec's open,
  check, Escape step from before #5515 is back.

Shown red naturally: with that step restored, the old code failed 5 of 10
runs at two workers; the fix passed the sort and switcher tests 40 of 40.
The vitest race case fails without the observer, the open-gate cases fail
without the gate, and the old code fails all three.

## Session 2623 — deleting a property the block doesn't hold appends no op, so the page's undo keeps working

## Session 2603 — main prunes superseded Rust caches, and the fuzz corpus is an artifact

Steps 1 and 2 of #5853's cache map.

- **`cache-prune`** (`ci.yml`, after `validate`, `build` and
  `android-build`, `main` only, `actions: write` on that job alone): for
  every `v0-rust-` family it keeps the newest `refs/heads/main` entry and
  deletes the rest, PR copies included. No family list to maintain: every
  Rust `save-if` is main-only. Two prunes can run at once (one concurrency
  group per commit on `main`); each deletes only entries older than one it
  listed itself, so neither can delete a family's newest entry. A key that
  does not parse as `<family>-Linux-x64-<env>-<lock>` stops the job before
  any delete, because a misread family could merge two families. A failed
  list or delete is a warning; an entry already gone is fine.
  `mutants-merge` deletes `rust-mutants` when the shards finish: next week's
  run never reads it.
- **Fuzz corpus:** the cache keep-alive was losing it anyway (nothing found
  on 10-08 or 10-15), so it is a `fuzz-corpus` artifact kept 90 days. The
  fuzz job restores the newest unexpired one from a `main` run, found by
  artifact name rather than by a successful run, because a run with a
  crashing target still saves its corpus. A failed lookup fails the restore,
  so the run uploads nothing instead of overwriting the lineage with seeds.
