## Session 3194 — Link targets resolve in chunks the backend accepts

Found while reviewing #6214's page-mode probes. `fetchAndCacheLinks` sent every uncached link target of a page to `batch_resolve` in one call, and the backend refuses more than `MAX_BATCH_BLOCK_IDS` (1000) ids (`ensure_batch_within_cap`). A page linking more than 1000 distinct targets, in page mode (`resolveLinks`) or block mode (`useBlockLinkResolve`), got a `Validation` refusal, logged a warning and resolved none of its chips.

**What changed**
- `fetchAndCacheLinks` sends the ids in chunks of at most 1000, one after another, each with its own `try`/`catch`, and writes each chunk's answers back as it lands. A refused chunk no longer drops the others' answers. One chunk behaves as before. Sequential, so a large page does not take every reader connection at once.
- `MAX_TRASH_BATCH_IDS` in `src/lib/ipc-helpers.ts` is renamed `MAX_BATCH_BLOCK_IDS`, the Rust constant it mirrors, and its doc points at `ensure_batch_within_cap`.
- `docs/architecture/queries.md` notes the per-call cap.

**Left alone, checked**
- **`resolveTitles`** (`UnfinishedTasks`, `DonePanel`, `AgendaView` and others) sends its misses in one call too, and `UnfinishedTasks` can load up to 5000 tasks. But its ids are parent pages, and the resolve store preloads every page title in the space (`listAllPagesInSpace`), so they are cache hits; more than 1000 misses would need more than 1000 non-page parents. Not reachable in normal use.
- **The mock** enforces the cap on no batch handler, the trash ones included, so no mock-lane spec can show the refusal; the vitest stand-in refuses past 1000 the way the backend does.

**Red first:** with the chunk size set to every id, "resolves every target into the cache" (1001 targets) and "keeps the other chunk's answers when one chunk is refused" both fail; with the `catch` returning early, the second fails on the last id; without the `logger.warn`, it fails on the warn count.

**Suites:** vitest over `src/components/block-tree`, `src/editor/page-mode`, `src/stores`, `src/lib`, `src/hooks`, `src/components/pages`, `src/components/properties` and `TrashView`; typecheck; lint; the manual-stage hooks; Playwright `page-mode`, `link-chip-lifecycle`, `link-labels`, `inner-links`, `trash-bulk`, `trash-load-more` and `block-linked-references` (86 passed).

## Session 3192 — Page mode's batch reads probed at its cap

#5691's backend box, as the maintainer readjusted it: probe the batch reads page mode leans on at the size of the largest page it opens, `PAGE_MODE_BLOCK_CAP` (1000), and at twice that, since the cap may rise as far as measurements allow.

**What page mode reads.** On open and again after every save (`bringIn`), page mode calls four batch reads: `load_page_subtree` (the store's `load`), `get_batch_properties` and `list_attachments_batch` (`readPageFit`), and `batch_resolve` (`resolveLinks`). The save's writes are per-block commands with their own probes. Before this change these reads were probed only at a journal day's size (inside `journal week open`), `load_page_subtree` at 500 blocks and `batch_resolve` at 50 ids.

**What changed.** `interactive_slo.rs` seeds a page of 1000 and one of 2000 blocks in the 100K vault, each block linking a background block, with a property on every 5th, a task on every 10th and an attachment on every 20th. Each read is timed per size and reported through `report_measurement_only` until `bench-slo` has measured it; an untimed shape probe asserts the exact count each read answers for.

**Trap for raising the cap.** Every batch read rejects more than `MAX_BATCH_BLOCK_IDS` (1000) ids, and `readPageFit` and `fetchAndCacheLinks` send a page's ids in one call. So page mode cannot open a page past 1000 blocks until those callers chunk; the 2000-block probes time the reads as two calls of 1000, as a chunking caller would. `load_page_subtree` has its own cap of 10,000.

**Bug found under today's cap.** `fetchAndCacheLinks` sends every uncached link target on the page at once, so a page whose blocks link more than 1000 distinct targets gets a `Validation` refusal from `batch_resolve`, logs a warning and resolves none of those chips. Block mode shares the call. Fixed in a separate PR.

**Suites:** clippy `--all-targets -D warnings` and fmt locally. The seeders and timings run only in CI's `bench-smoke` and `bench-slo` lanes, dispatched on this branch; this PR merges on their result.

## Session 3177 — Rename a select option; one row per option (#5841 S4)

Slice S4 of #5841, the last one, built on S1 (#6187), S2 (#6196) and S3 (#6204). The maintainer decided its open questions in issue comment 6517465507.

**Shipped:**
- **The op.** `rename_property_option { space_id, key, old_option, new_option }` renames in place: the definition's options keep their order, and every value of the space's blocks equal to the old name gets the new one, the Trash included. It writes the existing roots, so there is no format bump.
  - The release hold since S1 covers the one thing that needed it: an S3 build cannot parse this op.
- **Refusals.** Built-ins (`priority`, `todo_state`) and the app's own keys; a blank name; renaming onto itself; an undeclared key or a non-select; an old name that is not an option. Renaming onto an existing option, or onto a name some block still holds, is refused, so the undo's swap is exact.
- **Undo.**
  - It renames back whatever holds the new name now, so a later edit on a renamed block survives.
  - It follows a later rename of the key. The undo op records the key it renamed under, so replay, sync and redo agree.
  - It is refused with the reason when the definition was deleted or merged away, or the old name is an option or a held value again.
  - Undoing an earlier set of the old name lands on the new name. The mapping is one way: a value equal to the new name from before the rename is a different value.
- **UI.**
  - Settings › Properties loses its raw-JSON options editor. It reuses the page property table's editor, with one row per option: add, remove, reorder, Save.
  - Both editors get an inline Rename per saved option, with an Undo toast. After a rename from the page table, the open page reloads its values.
- **History** labels the op "Property option renamed", with the summary `key: old → new`.
- **Mock.** It mirrors the above and is pinned by three fixtures: `property_option_rename`, `property_option_rename_undo_maps_value` and `property_option_rename_undo_follows_key`.

**Accepted, not fixed:**
- **Two devices, last writer wins.** A peer's concurrent options edit can leave the new name outside the options, and two different renames can leave both names on blocks. Both stay visible, and the devices agree.
- **A replay at boot renames a peer value imported between the op and a crash.** That value then syncs as a normal write, so the devices still converge.

**Review.** An independent review found nothing blocking.
- **Fixed here:** the inline rename now trims the new name before checking whether it is taken and before sending it, as Add already did. A padded copy of an existing option used to get through.
- **Left for the follow-up PR:** a rename from the page table reloads every open page through the sync path, which also re-anchors each page's undo, so a pending redo is lost. The op is space-keyed and shifts no page's undo positions.

**Release hold:** it ends when this PR merges.

## Session 3175 — Tauri events pinned in the conformance fixtures

Section C of #6054: the mock emits the events the backend emits for the commands the frontend calls, and the fixtures pin them.

**Audit.** Of the frontend-invocable commands, only the eight property commands emit (`block:properties-changed`, from their `#[tauri::command]` wrappers). `start_sync` and `cancel_sync` emit nothing themselves; the sync daemon's sinks emit `sync:*` and `blocks:changed`, and the mock has no sync transport. `sync:progress` is live (daemon sessions without a channel) but has no frontend listener. `mcp:activity`, `recovery:degraded`, `deeplink:*` and the remaining `sync:*` events have no command behind them.

**Design.**
- `property_changed_events` in `commands/properties.rs` builds every wrapper's payload, and the Rust harness calls it, so each `via: "command"` record carries an `events` list (omitted when empty, so fixtures without emitting ops did not churn). The wrapper itself does not run in the harness: each arm restates the ids and keys it passes, which the review accepted because no smaller shape removes that.
- The mock publishes through `src/lib/tauri-mock/events.ts`; `setupMock` routes it to the real `emit()`, the replay records it per op. The mock's `apply_page_source` reuses property handlers internally, so those calls run under `withoutEvents`, as the backend's internal calls emit nothing.

**Divergences found and fixed.**
- `delete_property` emits even when it removed nothing (`[]`), and deleting `repeat` names the bounds it removed.
- The mock's `set_todo_state`, `set_priority`, `set_due_date` and `set_scheduled_date` accepted an unknown state, a bad date and a trashed block; the backend refuses all of them (pinned in `property_change_events.json`).

**Dropped:** an AppHandle-based ratchet over the command list. AppHandle is the wrong proxy for "can emit" (most such commands only reach the OS or the app-data dir), and the fixtures already pin the real emitters.

**Tests.** `e2e/property-change-refresh.spec.ts` draws a list marker with no reopen, which only the event refresh makes pass (red with the event sink unwired). Four existing specs had comments saying the mock emits no event; the comments are corrected.

## Session 3150 — Change a property's type, with a preview (#5841 S3)

Slice S3 of #5841, built on S1 (#6187) and S2 (#6196). The maintainer decided its twelve open questions in issue comment 6507641357, each as recommended.

**Shipped:**
- **No new op.** The type change is `rewrite_properties` with `reason: change_type`: one definition write, and one value write for each value whose form changes. There is no format bump.
- **`coerce(value, to)`** (`agaric-engine/src/loro/coerce.rs`) is pure. Its conversion rules:
  - **number:** trimmed text in Rust's f64 grammar, finite only;
  - **boolean:** exactly `true` or `false`;
  - **date:** strict `YYYY-MM-DD`;
  - **ref:** a ULID shape, stored uppercase;
  - booleans and numbers never convert into each other;
  - select option membership is the change's own check, never the projection's or undo's.
- **Commands:**
  - `preview_property_type_change` and the cursor-paged `list_property_type_change_values` read the space's SQL rows, Trash included. A value only the doc holds is not counted.
  - `change_property_type` takes the acknowledged counts and refuses a stale acknowledgement with `UnacknowledgedPropertyLoss`.
  - The list reads rows as a stream and stops at `limit + 1`.
- **Projection.** A `Str` is projected through `coerce` against its declared type. A stray string under boolean or date, or a non-finite number, now reads as absent instead of `value_bool 0` or unchecked text in `value_date`. Numbers and booleans keep their native column whatever the type (decision 6).
  - The review checked every writer: no value the app writes becomes hidden.
  - A stray string under boolean that used to show as false disappears the next time its block is re-projected. There is no repair (decision 11).
- **Apply.** It also re-projects a retyped key's holders whose stored form doesn't change, for example text → date for a valid date.
- **Undo:**
  - S1's restore guard now runs only for a merge's undo. A type change's undo writes back the values it converted itself, so the guard would have refused almost every undo.
  - Undoing an older set into a retyped key converts the value, or refuses with "change its type back first" (`fit_reverse_to_declared_type`). It checks the slot only, never select options, and finds Trash blocks and the space block itself.
  - The plan put this fix in `find_prior_property`. As in S2, the real funnel is `with_recorded_prior_in_tx`.
- **Settings › Properties** gets *Change type…*. The dialog shows the counts with a Trash note, and Removed and Converted tabs with Load more, ref titles, a stale-acknowledgement re-preview and an Undo toast. History labels `rewrite_properties` "Properties rewritten", with a summary for each reason.
- **Mock.** It mirrors `coerce` exactly, including Rust's trim and its f64 display (`-0`, no exponent). `isIsoDate` had read years 0–99 as 1900–1999 through `Date.UTC`; it now sets the full year, which also fixes the search date filter.

## Session 3113 — selectEditorRange sets ProseMirror's selection

**The flake.** `e2e/kind-change-undo.spec.ts`'s "block mode: Ctrl+Z in the editor after a typed `# ` brings the bullet back" failed on CI (on #6197, which does not touch it).
- The test focuses the block, places the caret at offset 0 with `selectEditorRange`, then types `# `.
- The text came out as `alpha#`, with the bullet kept: the keys landed at the end of the block.

**Cause.** `selectEditorRange` set the DOM selection and dispatched `selectionchange`, but ProseMirror never adopted it. There are two ways it refuses:
- Offset 0 landed inside the list marker, a widget span. The helper's text walk meets the marker's text node first, and ProseMirror ignores a caret in a widget.
- Just after a focus, ProseMirror takes a caret at the document's start for Chrome's focus reset, and puts its own selection back.

Either way its selection stayed at the end, where the click had put it, and its next transaction drew that back over the DOM. A real user does not hit this: a click inside the editor or a keypress ends the focus-reset window, and a click on the marker glyph is ignored without moving the caret.

**Fix.** The helper maps its DOM points with `view.posAtDOM(node, offset, 1)`, the bias ProseMirror uses to read a selection, and sets the selection through the editor's `setTextSelection`. This changes the test helper only; every spec that calls it gets the fix.

**Red first.**
- **Forced:** the first bullet-marker push after a mount was made to land late, between the helper and the typing. The old helper failed 5 of 5 on the `alpha#` assertion, and the fixed one passed 10 of 10. The reviewer re-ran it: 3 of 3 each way.
- **Under load:** 3 CPU burners. The old helper failed 14 of 40 at that assertion; the fixed one failed 0 of 40.

**Suites:** every spec that calls `selectEditorRange` (14 files, Playwright), plus typecheck and lint.

## Session 3112 — Rename a property key and merge one into another (#5841 S2)

Slice S2 of #5841, built on S1 (#6187). The maintainer decided its four open questions in issue comment 6504560322:
- undo follows renames and merges made on other devices;
- merge's *from* must be a declared key;
- merge counts include the Trash;
- internal keys are refused on both sides.

Merging keys of different types is refused (earlier answer Q3).

**Shipped:**
- **Two ops,** both keyed to the space (`op_log.block_id` is the space id), with no format bump:
  - **`rename_property_key { space_id, old_key, new_key }`** moves every value and the definition in the space doc and in SQL. It moves a value only where the new key is absent, so a boot replay leaves a later write under the old key alone.
  - **`rewrite_properties { space_id, reason: merge, defs, values }`** holds absolute writes, so undo is a swap. S3 adds `change_type` to the reason.
- **Commands:** `rename_property_key`, `preview_property_merge` and `merge_property_key` (in `commands/property_keys.rs`). A stale merge acknowledgement is refused with `UnacknowledgedPropertyLoss`, and merge reads holders from SQL, as its preview does.
  - Rename refuses a target that is built in, internal, declared, or used on any block of the space (Trash included).
  - A block holding both keys keeps *into*, and undo restores its *from* value.
  - A select's options are the union of both keys' options.
- **Undo follows the key.** The design put this bug in `find_prior_property`. That premise was wrong: every live writer records its `prior`, so the lookup only serves older ops. The real bug was the reverse op's key.
  - **The fix:** `with_recorded_prior_in_tx`, which every undo, revert, page-undo, redo and restore path goes through, forwards a set's or delete's key through the space's later renames and merges (`forward_property_key`).
  - **How it walks:**
    - A rename swaps its two names. A rename's target is always unused, so a key equal to the target names a value that is gone.
    - A merge's per-block writes are read as a move in or a move out. A move out is followed unless a move in came first.
  - **The plan's rule was wrong twice:**
    - **"Removed value equals written value"** lost data when a delete and a merge into the same key were undone together. The builder's proptest found it.
    - **"Rename only follows `old_key`"** overwrote a live value once a rename reused a name an earlier op had used. The review found it with a wider fuzz. The builder's proptest had missed it because its oracle copied the production rule. The proptest now reuses names, writes undeclared keys, and checks against an independent cell model.
- **Settings › Properties** gets Rename and *Merge into…*, each with an Undo toast. The merge dialog shows the counts, notes the Trash, and previews again on a stale acknowledgement. History labels both ops.
- **Rename pre-flight.** `renameMayDeclareKey` now probes `queryByProperty` in the space instead of the vault-wide key list (a carry-over from session 2855).
- **`INTERNAL_PROPERTY_KEYS`** has a Rust mirror in `op.rs`, pinned by a parity test.
- **Mock.** The mock mirrors all of this and is pinned by five new fixtures.

**Accepted:**
- **A merge payload is large.** It holds two absolute writes per moved value, about 2.6 MB at 10K values. Each undone set or delete parses every later merge payload of its space. The review measured about 76 ms for a 100K-value merge, which matters only for a large batch undo after a large merge.
- **A merge leaves a hidden value hidden.** A value under *from* that SQL hides, such as a ref to a purged page, moves and stays hidden.
- **The two-device outcome of a concurrent rename depends on merge order.** A value written under the old key at the same time as the rename may stay under that key or be lost to the rename.
