## Session 4497 — the find bar no longer loses the block tree mid-commit

A regression from #7117, found by the `in-page-replace` bridge spec failing on every PR's merge run.

**What broke**

- On a desktop with the find bar open, a long page's Replace all walked the page to its bottom, and a re-render could send the bar back to match 1.
- `useBlockTreeEventListeners` re-registers its tree with the block command bus whenever its handlers change, which is nearly every render. React runs every passive cleanup in a commit before any passive create, in tree order. Since #7117 the desktop find bar sits in the App header, ahead of the content, so its matcher effect could run in that gap.
- There `treeStoresIn` came back empty, the bar walked the DOM instead, and the next block run counted as a fresh search: match 0, scrolled into view. Replace all saves block by block, so each save could jump the page further down, and scroll restore kept the bottom on the next visit.

**What shipped**

- The registration is a layout effect. Its cleanup and re-registration both finish before any passive effect in the commit, so a passive reader of the bus (find's matcher, `countUnreplaceable`) never sees the tree missing.

**Tests**

- vitest: `use-block-tree-event-listeners`, a passive reader placed ahead of the tree sees it registered at mount and across a re-render.
- e2e (bridge): the existing `in-page-replace` "replaces one and all … one Ctrl+Z undoes a replace all" is the regression spec, unchanged.
- Shown red on `main`: the bridge spec at its reopened-page check, and the new vitest. The registration back to a passive effect turns both red again.

## Session 4491 — the four import edge cases #7075 left open

Session 4439 (#7075) left four import edge cases open. One was a real bug and is fixed. The other three cannot be reached; two now say why in a comment, and one was dropped because its premise was false.

**Fixed: a retry swept nothing a failed batch purged.**
- The sequence:
  1. A boot-replay batch imports a peer's purge and stamps the purged ids on its slots.
  2. Its projection fails, and the per-slot retry runs in the same boot.
  3. The retry passed the tombstones the walk had read before the stamp, which were empty.
  4. Its re-import resolves no purge, because the engine already holds it, so the retry's purge pass had nothing to sweep.
  5. The retry committed and deleted the slot along with its tombstone.
- Result: the purged page and its block kept live SQL rows for good.
- Fix: `replay_accepted_slots_individually` now reads each slot's tombstone from its row before the retry (`stamped_tombstone`).
- `decode_purged_tombstone` moved unchanged into `loro_sync.rs`, so that the boot walk and the retry share it.

**Unreachable, with a comment saying why.**
- **The format gates after a landed import** (`reject_legacy_v1_snapshot`, `reject_unknown_format_version`):
  - Only sync deliveries and their inbox replay import through the shared body.
  - The handshake (`on_head_exchange`) turns away a peer on another engine format before anything is imported.
  - Disaster recovery and boot rehydrate use plain `import` into engines they throw away on error.
- **The trusted no-op exit with a failed import** (`import_and_project_saving`): only a live delivery is trusted, and a live delivery is one blob. Only a replay batch fails with part landed, and a replay is never trusted. No input reaches the exit, so no test can.

**Dropped: `LocalTextKept` on a failed live import.** A live import is one blob, and loro 1.19 imports one blob whole or not at all. Checksum, decode and missing-op failures are caught before anything applies, and a failed state apply is rolled back. So a failed live import lands nothing, keeps no block and has no notice to send. This rests on reading loro's source and its `import_atomicity` tests, not on a test of ours. A loro bump that changes single-blob atomicity reopens this case and the no-op exit above.

**Left alone.**
- A live import that succeeds with a kept block, and whose projection then fails, sends no `LocalTextKept` notice. The Trash page still appears at the next boot replay. That needs a projection failure at the same time as a purge rescue, which is none of the four.
- The `engine_format_version == 0` branch in `on_head_exchange` is dead, but removing it is out of scope.

**Ran.**
- `retry_after_a_failed_projection_sweeps_what_the_batch_purged`:
  - Red before the fix, on "what the peer purged has no row", with the page and the block still listed.
  - Green after.
  - Red again on the same assertion with the retry reading the walk's stale tombstone.
- Its trigger fails only the batch's projection. It keys on the `loro_doc_delta` count, which grows by one when the failed import saves its delta on its own (#6521). The test asserts that growth as a precondition.

## Session 4479 — a device makes its commits durable before it serves them to a peer

#6524: the pools run `PRAGMA synchronous = NORMAL`, so a committed transaction can sit in the WAL unsynced. If a device serves a peer ops from such a commit and then loses power, it comes back without them. It then re-issues their counters and forks its own lineage on that peer. The maintainer chose durable-before-send.

**The barrier.** `agaric_store::db::make_commits_durable` takes a write turn and commits one page-changing write, a counter in `app_settings` (`sync.durable_barriers`). It does this on a connection of its own with `synchronous = FULL` and `fullfsync = ON`.
- From the bundled SQLite, a FULL commit syncs the whole WAL file. That covers every earlier commit still in it.
- Commits already checkpointed were synced by the checkpoint: the WAL is rewritten only after a full backfill, and the database file is synced before it.
- A commit that changes no page writes no frame and syncs nothing, so the counter is what makes the barrier work.
- The write turn also waits out a transaction that wrote the engine before the export read it.

**Where it runs.** Once per served stream, before anything is queued or sent:
- the responder's main stream (`head_exchange_outgoing_loro`);
- the snapshot catch-up (`try_offer_loro_snapshot_catchup`).

These are the only paths that send this device's ops. The dialler's change round sends heads and `SyncComplete`, attachments send file bytes, and MCP and the mirror send nothing to peers. A failed barrier fails the stream before its first byte.

**Docs.** data-and-events, sync-and-network, sync-protocol-spec and crdt-and-recovery describe the barrier.
- editor-and-content's "power failure loses at most the typing since the last debounce" was wrong under `NORMAL` and is corrected.
- docs/features/sync.md and the FEATURE-MAP Sync row say a power cut loses at most edits no other device had received.
- On the rebase over #7091, both PRs' fixes to the same sentence about undetected own-lineage forks took #7091's wording.

**Review.** An independent review checked the durability argument against SQLite 3.54.1's `walFrames`, `walCheckpoint` and `walRestartLog`. It also re-ran the four call-site reds, and made three changes:
- It deleted an `#[ignore]`d cost harness whose output nothing read.

## Session 4470 — a bridge worker re-seeds its template when the date changes

#7091's bridge shard went red at three tests that count pages. Each found one page more than it expected: `pages-view` › "default journal chip" (7 pages, not 6), `pages-view` › "Orphan narrows" (5 matching, not 4), and `pages-browser-happy-paths` › "a saved view…" (7 titles, not 6). Its tests ran between 00:01 and 00:03 UTC.

**Cause.** A Playwright worker seeds its bridge's template vault once (`e2e/bridge.ts`), and every test gets a copy. The seed writes today's journal page and dates counted from today, using the date it runs on. This worker seeded before midnight. After midnight, the app and the specs (`localDateStr(new Date())`) read the new day, so the seeded journal page became an ordinary past page beside today's.

**Fix.** `Bridge.reset()` replaces `request('reset')`. When the local date differs from the day the template was seeded, it stops that bridge and starts a fresh, re-seeded one first. Only `e2e/helpers.ts`'s `realBackend` fixture resets.

**Ran.**
- A seed run under a clock shifted one day back makes the date check restart the bridge, and the journal-chip and Orphan tests pass. With the check removed, the same run fails both tests with CI's counts (7 vs 6, 5 vs 4).

## Session 4463 — the healthy side of a forked pair is told, keeps no refused snapshots, and stops redialling

#7065 step 1, plus two things the build found on the same path. Since Loro 1.16.4, an import that reuses op ids is refused with `LoroError::UsedOpID`. The rewound device already reported `own_history_fork`, but its peer only showed "Sync failed: …".

- **The report.**
  - `snapshot.rs` maps `UsedOpID` to a constant prefix that `is_used_op_id` reads back. Detection is typed, not text matching.
  - Only the catch-up (`merge_one_snapshot`) turns that refusal into `SyncErrorCode::PeerHistoryFork` / `peer_history_fork`. Its sentence names the other device and the recovery: export, set up fresh, pair, import. It is translated in all five locales and mapped in `codedSyncErrorKeys`.
  - The constant log text also makes the repeat-report suppression hold across retries.
- **No refused snapshot is kept.** `apply_remote` writes the blob to `loro_sync_inbox` before importing. A `UsedOpID` refusal now deletes that slot, because the refusal is deterministic, so no replay can import it, and the peer sends it again anyway. Without this, every retry left another full snapshot, and boot replay then moved it to quarantine with its bytes. Other import failures keep their slot for boot replay.
- **The hold.** After a failure coded `own_history_fork` or `peer_history_fork`, the scheduler's backoff no longer lets that peer be dialled automatically: not by mDNS events, change rounds, the resync tick or the frontend's scheduled sync. Before, a forked pair re-ran the whole session, snapshot included, about every minute while both were online.
  - The hold lifts on a press on Sync, a pairing, or a restart.
  - A network rebind no longer clears it (`clear_backoff_for_new_network`).
  - Inbound sessions from a held peer are still answered.

**Not built: detecting the shape that corrupts silently.** A rewound device that has written past its peer's counter for it is not detected. The pull completes, and the healthy device's copy of a lost block is overwritten.
- No message today separates it from a healthy in-app restore: both show differing op-log hashes at the same seq.
- A shorter rewrite fails as an uncoded Loro decode error instead.

The options (a `HeadExchange` field after a spike, or a partial check on the rewound side) went to the maintainer. The docs now say this shape also overwrites the other device's copy, not only that the lost edits never come back.

## Session 4448 — a page undo or redo pressed while another runs is queued

#7023: Ctrl+Z pressed several times quickly on a page dropped every press that came in before the previous undo's answer. Undo and redo now share one queue per page in `src/stores/undo.ts`, so N presses take N steps in press order. This replaces `undoInProgress`, `redoInProgress` and their skip branches.

**The three decisions the issue asked for:**
- **Interleaved undo and redo run in press order.** Each run reads the stacks the previous one left.
- **A press still queued when its page is cleared (left) is dropped.** The cleared page has no stacks, so the press would fall to the positional undo at depth 0. That targets the op the previous press may just have reverted, because the backend's group walk skips undo ops, not forward ops already reverted. Dropping the press loses no edit; running it could misapply one. `reanchorAfterRemoteOps` does not drop queued presses, because the in-flight result still applies there. A press made after coming back still runs.
- **A press that finds nothing, or that the backend refuses, settles like any other.** The runs catch their IPC errors, and the chain continues on both arms, so even a run that throws lets the next press run.

**Kept:** `undoInProgressEntry` and `topIsInFlightUndo`. `onNewAction` (a blur commit, say) does not go through the queue, so it can still land mid-undo. Forcing the check to `false` turns the mid-undo coalesce test red. The map moved to module scope so `latestUndoEntry` can read it.

**Review fixes:**
- **Toast Undo during a Ctrl+Z.** With the queue, the four toasts' "still the latest entry" check (broken-link removal, paste take-back, page-source save, board move) passed while a Ctrl+Z was reverting that same entry. Their Undo then queued behind it and took the step below. `latestUndoEntry` now returns `undefined` for an entry an undo is reverting, so those toasts see it as stale, as the old drop effectively did.
  - board-move's stale path calls `undo_ops` on refs the Ctrl+Z is reverting. `verify_undo_targets_in_tx` refuses an already-reversed target (#2468), so nothing is reverted twice.
- **Tests added:**
  - The rewritten concurrent-redo test now fails on the old code.
  - A run that throws, pinning the chain's rejection arm.
  - A press made after leaving and coming back.

**Edited assertions (the old ones pinned the drop):**
- "rejects concurrent undo…" became "runs a concurrent undo on the same page after the first, at the depth it left".
- "rejects concurrent redo…" became "a concurrent redo runs after the first and replays the next group".
- "clears the re-entrancy guard…" became "a second undo after the first settles works".
- Two e2e comments that described the drop are deleted.

**Not changed:** presses inside a focused block whose editor history is used up are still dropped while `runBlockPageHistory` runs (flush, page undo, reload). That drop is pinned on purpose by `e2e/block-undo-chains-page-undo.spec.ts` (#6556), so changing it is a maintainer decision.

## Session 4439 — Review notes from #7064 and #7072: a failed import keeps its purges

## Session 4428 — each npm audit retry asks the registry again

**Ask.** Fix every flake. `validate / lint` failed `npm audit signatures` twice:
- #7050's first run, on `playwright@1.65.1`;
- this PR's first push, on `@tiptap/extension-code-block-lowlight@3.34.0`.

Both times the registry's attestations endpoint answered `OK` where JSON belongs. Then fold in the sweep's non-blocking review notes.

**Cause.** The retries never asked the registry again.
- npm stores what the registry answered in its cache, and the attestations endpoint sends `cache-control: max-age=31557600` (one year).
- So the first attempt's bad body was stored, and every retry got it back from the cache. Run twice in one cache, `npm audit signatures --loglevel http` logs the second fetch of an attestation as `(cache hit)`.
- That is why all five attempts failed on one URL across four minutes in this PR's first run, while other lint jobs restoring the same CI cache key passed. The fault was one bad answer, replayed.
- `--prefer-online` is not enough: the GET carries `last-modified`, so a revalidation can return 304 and keep the cached body.

**Fix.** `scripts/npm-audit-retry.sh` runs each attempt with its own empty npm cache (`npm_config_cache` under one `mktemp -d`, removed on exit).
- This PR's first push widened the backoff to about four minutes, on the belief that the fault lasted minutes. That belief came from the replay, so the backoff goes back to 5 s then 15 s.
- New test: "every attempt runs with its own empty npm cache". It fails on main's wrapper, where all three attempts share one cache.

## Session 4421 — the sync peer holds its session lock while it writes

**Ask.** Fix every flake. `e2e-tauri/sync-two-device.e2e.ts` failed "lists the peer's property definition, and reads the value the app held as a date (#5841)" on PR #7038, whose diff could not reach it: the peer refused `create_property_def` because it already held the app's value as text.

**The race.** The app's `set_property` asks for a round after the 2 s `LOCAL_EDIT_DEBOUNCE`. That round is the app dialling the peer; the peer serves it, sees the app ahead, and dials back to pull the value. When the pull-back landed before the test's `createPropertyDef`, the peer refused `date` over the stored text, as it should. "converges concurrent edits to one block on both devices" has the same shape: the peer must write before it pulls the app's edit. Its comment said the peer dials unprompted only on an mDNS sighting, which has been false since #6551.

**The fix.** The test peer gains `hold_sync` / `release_sync`: it takes the daemon's own per-peer session lock for the app (`try_lock_peer(peer_lock_key_from_stored(..))`, the key both roles lock on) and keeps it until released. While held, the app's dial is refused as busy (the app books a backoff and reports nothing) and the peer skips its own dial; `hold_sync` answers only once a running session has ended. Both tests hold the peer before the app writes, after waiting for the sidebar's Sync to be idle (a pressed sync refused as busy would toast), and release it in a `finally` before pressing Sync. No app code and no assertion changed.

**Red, then green.** With a 10 s pause before the peer's write in both tests, main's ordering failed both, the #5841 one with CI's error verbatim; the held ordering passed both under the same pause. The whole file passed three runs in a row on binaries built from the final sources.

## Session 4417 — a content slash command's text reaches the editor before its write

**Ask.** Root-cause `page-mode-slash.spec.ts` "/callout-warning", which once stored block mode's block as `buy milk ` with no callout, in a loaded bridge run.

The weekly `stale-pins` lane (run 44478509486) reported three pins behind upstream past the 7-day cooldown. This PR moves all three and fixes what Rust 1.100.0 broke.

### What shipped

- **cargo-binstall 1.20.1 → 1.27.0, nvm 0.39.7 → 0.41.0** through `scripts/pins.mjs bump`. A second download of each binstall archive gave the same sha256s, and each holds one `cargo-binstall` binary; the new `nvm.sh` hash matches the file in a `v0.41.0` checkout. Nothing else in `pins.txt` moved.
- **Rust 1.99.1 → 1.100.0** in `rust-toolchain.toml`, every `toolchain:` input in `.github/actions/toolchain` and the workflows, and `rust-version` in every crate manifest.
- **Clippy 1.100**: `map_unwrap_or` now covers `.map(f).unwrap_or_default()`; those chains are `.map_or_default(f)` (mechanical, applied by `cargo clippy --fix`). `needless_bool` caught the `if … { return true } false` tail of `is_blocked_ip`'s Teredo check.
- **Cargo 1.100's build-dir layout**: intermediate artifacts moved from `target/<profile>/deps/` to `target/<profile>/build/<crate>/<hash>/out/`. Two things read the old path:
  - the bench smoke step in `scheduled-deep-checks.yml` globbed `target/release/deps/<name>-*`, and would have found no binary. The compile step now maps bench names to executables from `cargo bench --no-run --message-format=json-render-diagnostics`;
  - `docs/BUILD.md`'s debug-info sweep. It now matches `*.rcgu.o` / `*.rcgu.dwo` only, because the same `out/` directories hold build scripts' C objects (sqlite, blake3).

### Decisions and traps

- **`pins.mjs stale` cannot run in a cloud session.** api.github.com answers 401 with the session's `GITHUB_TOKEN` and 403 without it, so every `github:` upstream shows as an error. The run's own table was the source; it was a few hours old.
- **The `panic` setting ignored for the `bench` profile** warning predates 1.100 (1.99.1 prints it too), so it stays out of this PR.
- **The fuzz crate needs `SQLX_OFFLINE=true`** to `cargo check` from `src-tauri/fuzz`; without it, sqlx tries `dev.db` relative to that directory.
- **Release notes** also list never-type fallback to `!` on every edition and `Infallible` as an alias of `!`, the rustdoc `invalid_markdown_table` lint, Cargo's `[lints.cargo]` table, and Unicode 18 in `escape_debug`. None of these surfaced in clippy, rustdoc or the tests.

### What ran

- `cargo clippy --workspace --all-targets -- -D warnings` and `cargo fmt --all -- --check` on 1.100.0.
- `cargo nextest run --workspace` in two partitions. Partition 1 ran before rebasing onto #7009 and failed only `conformance_fuzz::mock_matches_backend_on_fixed_seed_op_chains_6567`, main's known red; after the rebase that test passes. Partition 2 passed in full.
- `cargo test --workspace --doc`; the `cargo-doc-links` rustdoc command; `SQLX_OFFLINE=true cargo check` in `src-tauri/fuzz` (lockfile unchanged).
- The new bench mapping, run locally on `core_bench`.
