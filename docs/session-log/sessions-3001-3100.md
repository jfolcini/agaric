## Session 3098 — Enter in Edit as Markdown keeps the block's level

**The decision.** After G3 (#6192), Enter in an indented plain paragraph of the Document buffer started a top-level block, because the moved text lost its leading blanks. The maintainer decided Enter makes a sibling at the same level, as page mode's Enter does (comment 6506141629 on #5691).

**Changed:**
- **`siblingHead`** (`source-buffer-blocks.ts`) gives the head the writer would write a sibling of the block at the cursor with. It builds that from the writer's own pieces, so there is no second placement rule.
  - The head is the block's indentation, plus `+ ` when its parent is a list block.
  - It also carries the block's own list marker, numbered on. Page mode's Enter carries the list style too (`PageListKeys`, `setStyle(made, shownStyleOf(id))`), and a task's sibling is plain in both modes.

- **Enter with the caret before an indented line's text** keeps the text's indentation, where it used to move the block to depth 0. The reviewer found this in the same defect class.

**Left as is:**
- `* a`'s further line gives a `- ` sibling, because the writer writes bullets as `-`. Its first line still continues `* `.
- Enter at column 0 of an indented line leaves the caret before the indent.
- Enter in the middle of a heading gives a plain paragraph for the moved text, while page mode makes two headings. This predates the change.

## Session 3094 — App.test loads the lazy views up front

App.test's "switches to Pages view" failed once on a heavily loaded machine: `expected null not to be null` at its `.page-browser-header` `waitFor`, after the 8 s `asyncUtilTimeout`.

**Cause.** `ViewDispatcher` preloads every lazy view chunk at idle after the first App mount. The Pages test is the first to open a lazy view, and under load its `waitFor` was spent waiting for the PageBrowser chunk to load behind the others. A slow chunk then leaves only React's Suspense throttle and a render. The Tags, Trash, Settings, Search and page-editor tests are each the first into their own chunk too.

**Fix.** The test file imports the lazy view modules for their side effect, so they load in the file's import phase, which has no timeout. App's own `import()` calls then hit the module cache. No assertion or timeout changed, and no production code changed. In production a slow chunk shows the `ViewFallback` skeleton, the click is kept, and a failed preload is logged and retried by the render, so there is nothing to fix there.

**Red first.** Natural failures did not recur in about 130 loaded runs, so the failure was forced. A 9 s top-level await appended to `PageBrowser.tsx`, applied and restored in one command, fails the test on the same assertion without the imports and passes with them. The builder and the reviewer each ran it.

**Suites:** vitest over `App.test.tsx`, `src/components/mobile` and `src/components/common` (553 tests), typecheck, lint.

## Session 3085 — Property definitions sync as ops; engine format 6 (#5841 S1)

Slice S1 of #5841, built to the revised design (comment 6254978621) and the maintainer's answers after it. Definitions used to be a local table no op wrote, so a key declared `date` on one device projected as `text` on the other. Now each definition write appends one `set_property_def` op, and each space's Loro doc carries the definitions.

**Shipped:**
- **The op.** `SetPropertyDef { space_id, key, def, prior }`, where `def`/`prior` are `{value_type, options}` or null. `op_log.block_id` is the space id. The reverse swaps `def` and `prior`. No migration: `op_log.op_type` has no CHECK.
- **The engine.** A `property_definitions` root in every space doc holds one plain map per key, with no nested container. `ENGINE_FORMAT_VERSION` goes from 5 to 6. SQL `property_definitions` is now a projection of that root.
- **The commands.** Create, options edit and delete go through one writer, `write_property_def_in_tx`, in a `CommandTx` with engine rollback armed. They return `WithOps`, and delete returns the deleted definition.
  - A write that changes nothing appends no op.
  - The writer refuses built-ins and a type change. No production caller can reach the type-change refusal yet; S3's type change is its own op.
- **New spaces.** `create_space` and the fresh-vault bootstrap emit one op per default. A received space's doc therefore carries its definitions, so the receiver doesn't seed anything itself.
- **Import.** A definitions-only update is no longer swallowed by the no-op fast path, and the healing fallback includes the root's keys. A new definitions pass runs before Pass A in the same transaction. Only keys whose storage column changed have their values re-projected, and those blocks feed the agenda rebuild.
- **Recovery.** It projects the doc's definitions (upsert only) before it types the values.
- **Boot backfill.** `repair_property_definitions` appends one housekeeping op for each SQL row the doc lacks, trashed spaces included. It runs after the #5670 hydration, not in `Repair::OPS`: run earlier, it gave spaces that never had an engine one, and the hydration then seeded them whole (`boot_hydrates_legacy_attachment_rows_into_the_engine_5608` caught it).
- **Undo refuses a re-typing that would hide values.** Undoing a delete, or redoing a create, refuses with the forward create's validation when the key's held values don't fit the restored type. An options-only undo is never refused.
- **History.** The space filter also lists that space's `set_property_def` ops, which it used to drop because a space block has no `space_id`.
- **Settings.** Every definition write, and *Copy to space…*, gets an Undo toast. History labels the op.
- **Mock.** It mirrors all of the above and is pinned by the new `property_def_undo.json` and a same-options step in `property_def_writes.json`.
- **Docs.** AGENTS.md invariant 2 is amended, with the maintainer's approval in the issue. `crdt-and-recovery.md`, `data-and-events.md`, `editor-and-content.md`, `features/properties.md` and FEATURE-MAP are updated.

**Fixtures.** Every `create_space` adds five ops to a fixture's digest. Two fixtures name ops by position: `space_move_onto_a_taken_name` (the move is now O32) and `undo_revives_no_taken_name` (O16, O18, O19). Both are relabelled, comments included. The regeneration re-serialised every fixture. Each one whose parsed JSON was unchanged was restored byte for byte, and the changed ones keep the original key order.

**Accepted, not fixed:**
- **Definition ops touch the space page.** They bump the space page's `last_edited_ms`, and positional page undo on the space's own page can reach them.
- **Definitions that diverged before S1 resolve last-writer-wins.** A fresh device can bring back a default deleted before S1. Only the definition comes back, not its values.
- **A rare crash can resurrect a deleted definition.** Sequence: a peer's delete arrives, and this device crashes between the engine save and the SQL commit. The healing import cannot delete the stale row, and the backfill then re-emits it.
- **Every boot marks spaces with definitions dirty once.** The backfill reads through `for_space`. Cost only.
- **No `reconcile_engine` oracle compares definitions with the doc.** Aliases have none either.

**For S3.** `reproject_property_row_from_engine` routes any `Str` to `value_date` under `date` without checking it. A synced definition can now put a peer's non-date text there. S3's `coerce` is the fix.

**Release hold:** no release between S1 and S4.

- Full vitest: 23,781 passed.
- The whole Playwright lane: 1,567 passed. The only failures are the two `diagram-legibility` cases, which fail the same way on `main` with this container's headless shell.

## Session 3077 — Ctrl+Z inside the editor brings back the list style a kind change took off

This is #6156 part 2. Part 1 (#6176) made a kind change, and the list style it took off, one page-level undo step. The maintainer wants one step in both modes. So this part makes the in-editor Ctrl+Z (ProseMirror history) put the style back too, and a redo takes it off again.

**Why the editor decides:** the planned store-side fix could not work, for two reasons.
- `FlatBlock` carries no list style, and `delete_property` returns no prior value, so the store never knows which style it cleared.
- The store's `edit` cannot tell an undo from an explicit Turn into → paragraph or a Backspace on the `#`, because they reach it with the same content.

Only the editor sees history transactions and the marker it shows, so it decides in both modes.

**Changed:**
- **Page mode** (`page-lists.ts`):
  - When a block leaves its list, `PageLists` remembers `{style, depth}` for it, unless the change is itself an undo.
  - On an undo, a block whose depth is the current depth + 1, and which went from no marker to a marker, gets its style back through `setStyle`, so the write lands in the page-level undo.
- **Block mode:** a new `listStyleUndo` extension holds one slot. The undo of exactly that change sends `RESTORE_LIST_STYLE`.
  - The tree's handler flushes the draft, writes the style and records the undo, so the restore joins the saved text's entry.
  - It writes nothing if the stored content still shows a marker, meaning the change was never saved.
- **Undo recording:** `PageModeEditor` and `useListStyleSyntax` record through `notifyUndoNewAction`, which acts on #6176's review note.

**Red first:**
- **Page mode:** removing the restore loop reddens `page-lists` (`['none','none']` against `['none','ordered']`) and the page-mode e2e (`listStyle: null`).
- **Block mode:** removing the depth check makes a Backspace or a later change's undo ask for a restore.
- **The handler:**
  - removing the marker gate gives an extra write;
  - removing the flush splits the undo entry.
- **Each review fix,** removed alone, reddens its own test.

## Session 3041 — In the Document dialect, a heading, fence or break typed under text starts its own block (#5691 G2a)

G1 (#6162) left one question open: is a heading, code fence or `---` typed directly under a paragraph part of that paragraph? **Reader (Document only):**
- A heading is one line that owns nothing.
- A fence opener or a thematic break typed under text starts a block.
- `para`, `---`, `after` is three blocks, never a setext heading.
- At a bullet's content column, a fence or break starts a child block, as CommonMark reads a fence inside a list item. Source still continues the bullet there.

**Writer:**
- Such a line inside a block's text is escaped with a `\`, the escape Source already uses.
- One predicate, `needs_document_line_escape`, is shared by the writer and the reader's unescape, so the escape is injective.
- A heading with a hard break (`## Heading\` + newline, as the editor stores it) is written escaped and reads back as one block.
- Breaks are tested by their opening run, so `--- x` is escaped too. That over-escape keeps the anchored and anchor-free forms in agreement.

**Open for the maintainer, before G3:** text typed directly under a closing fence, with no blank line, stays in the code block (2 blocks, where CommonMark, Import and Source read 3).
- This follows D1's letter, and it carries the fence-plus-text blocks a Logseq import makes.
- Its cost: a `[[link]]` or `#tag` typed there is not created until a blank line separates it.

## Session 3039 — A key pressed just after focus is not undone by ProseMirror's focus heuristic

`bubble-keyboard.spec.ts`'s page-mode test failed in CI on an unrelated PR. After the selection bubble's Bold, the test's second keyboard selection (`Ctrl+Home`, then five `Shift+→`) came back empty.

**The cause is in prosemirror-view, and it is real for users.** `DOMObserver.flush` restores the editor's own selection when all of these hold:
- the DOM caret moves to the document's start with no mutation;
- it happens within 200 ms of a focus event (the private `view.input.lastFocus`);
- there was no click or touch first.

- The check runs in every browser, and prosemirror-view 1.42.8, the latest, still has it.
- No public API controls it.

## Session 3016 — A Document dialect for Edit as Markdown's grammar, beside Source (#5691 G1)

Set out to build G1 of the line-split Markdown format: the Rust writer and reader for a `Document` dialect, following the maintainer's D1–D4. It is additive. Every Tauri command still passes `Source`, so the UI, the bindings and the mock are unchanged; G2 exposes the dialect.

**Shipped:**
- **`ParseMode::Document` on the shared `Scan`** in `agaric-engine/src/import.rs`, with `parse_document_outline` and `parse_document_text`. Every new branch sits behind a mode check, so Import, Source and paste read exactly as before.
- **`Dialect { Source, Document }`** in `commands/pages/markdown.rs`, with `anchor_free_as`, `get_page_buffer_as` and `apply_page_source_as`. The commands call these with `Source`.
- **The Document format:**
  - a blank line between blocks;
  - `- x` / `* x` read as a bullet and `1. x` / `1) x` as numbered;
  - a task is `- [ ] x`, a third list kind;
  - `+ x` is a plain child of a list block;
  - a `\` line is an empty block.
- **Both-kinds blocks.** A block with a task state and a list style is written as a task. Its hidden list style goes only when that block, or one of its property lines, is edited. Save with no edit appends no ops.
- **`conformance/document-lines.vectors.json`** is authored by a Rust test, for G2's TypeScript reader.

**Deviations from the design, accepted in review:**
- There is no `dialect` field on `SourceSaveFlags`. Struct literals of it sit in existing tests, so the dialect is a parameter instead.
- A first block starting `---` is written `+ ---`, so it cannot read as front matter. The `+` escape needs no reader change.
- A paragraph runs to the next blank line, so a heading, fence or `---` line under a paragraph continues it. This follows D1's letter, "no blank line stays one block", and the writer depends on it, because a fence is written verbatim. D1's rationale ("how import and paste already read Markdown") disagrees: Import and Source make each of those lines its own block. The question goes to the maintainer before G2 and G3 put it in front of users.
- An empty `1.` inside a list item starts a child, because its anchor-free line has no text.
- A task state with no checkbox marker is written as a plain line plus `todo_state::`, the only spelling that cannot read back as a bullet.

**Proofs:**
- Three proptests mirror the Source ones: render then read, the same with ids, and a byte fixpoint. A table test covers each row of the format.
- An apply test shows the page's own buffer saves as zero ops, including a both-kinds block.
- Review added a run of ten numbered items (the content column of `10. `) and a test pinning the property-line terms of the edit check. Each was shown red.
- Every escape and rule was shown red alone, eleven mutations in all.
- A differential against the base commit's reader and writer was byte-identical for Source, Import, paste, Clipboard, Agent, Export and subtree output, over 4,000 generated pages and 16,000 typed buffers.

- the markdown, import, page-source and document filter (545);

## Session 3011 — A list marker shows only on a list block (#5691)

Set out to apply the maintainer's rule: "Bullets are only for unordered list blocks, not for any other block, either in Block or page mode" (and numbers only for numbered ones).

**Shipped.** One predicate decides whether a block shows its marker, in every mode: `showsListMarker` / `contentShowsListMarker` in `list-style.ts`. A block whose text opens with anything but a plain paragraph (heading, code, quote, callout, table, divider, query, embed) shows no marker, whatever `listStyle` it stores. It drives:
- the static block;
- the roving editor's marker decoration and list keys;
- page mode's node view;
- the Edit as Markdown preview.

Typed input rules, dividers, tables, queries, embeds and paste had all leaked a bullet onto such blocks.

**Leaving the list:** a list block whose text this device stops opening with a paragraph has its style cleared.
- **Block mode** clears it in the page store's `edit`, after `edit_block` succeeds, in its own `try`. A refused edit keeps the style, and a failed clear is logged but does not roll back the saved text. A `load()` (sync, undo, restore) clears nothing.
- **Page mode** clears it from `page-lists`' `onTransaction` and skips `REMOTE_PATCH` transactions, so a receiving device writes no op.

**Decisions and traps:**
- **The first write side was too broad.** It was an `EditableBlock` effect on any content change, so refused-edit rollbacks lost the style and receiving devices wrote ops. Review moved it into the store and onto local transactions.
- **A stored style is kept on a heading,** and only its marker is hidden. Edit as Markdown can still carry `listStyle` on any block. The style is dropped only when this device edits a list block out of being a paragraph.
- **Existing tests changed by the rule:** `page-mode.spec.ts`, `ListMarker.test.tsx`, `markdown-reveal.test.ts` and `page-mode-reveal-lists.test.tsx` had asserted a marker on a heading. They now assert none, or use a link's brackets where the heading stood in for "markup before the marker".
- **One stub:** `page-blocks.split-indent.test.ts` gained a `delete_property` stub. The split's first half turns a paragraph into a heading, so the store now makes that call. Deleting an absent key appends no op (`delete_property_absent_key.json`).
- **Left as it was:** the Preview's own ordinals loop. Replacing it with `computeListOrdinals` grouped differently when an indent level is skipped, so the refactor was reverted and the Preview's use of the rule got its own test.

## Session 3009 — Returning from Edit as Markdown shows the saved page (#5691)

Set out to fix a lost edit found by the three-modes code review (#5691, PR-0).

**The bug, on main:**
1. Type in page mode.
2. Open Edit as Markdown from the kebab.
3. Cancel, or Save with nothing changed.
4. Page mode reopens on the page store as it was before the switch, so the next keystroke writes that stale text back over the edit from step 1.

**Shipped.** One file, `use-page-mode.ts`, so the rule "save, reload, swap" lives in one place.
- `afterFlush` now runs in `changeMode('blocks')`'s order: save, reload the store, retake the cursor, then swap. It still swaps nothing if the save failed.

**Decisions:**
- **F2 is narrowed.** From the kebab, the document has already lost the focus before Markdown opens, so no caret is restored. After Cancel the focus stays on the kebab, as block mode's `handleCloseSource` leaves it, and the scroll position is kept.

Under the red-first rule, the reviewer decided it is setup only: every assertion passed unchanged, and the test-setup afterEach that rejects unstubbed commands was the only failure.
- **Left alone:** a reload that fails after a successful save still swaps, so page mode would reopen on the old store. It is rare and visible through a retry toast.
