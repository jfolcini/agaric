## Session 3797 — Versioned derivations, and the integrity report in plain words

The maintainer wanted the class of #6488 eliminated: a change to a rule a cache stores the output of left every row written before it stale, and the integrity check reported each one. Session 3786 (#6492) re-stripped `fts_blocks` once; this replaces that one-off marker with a mechanism, and rewrites the report for a reader who is not us.

### What shipped

- `agaric-store/src/derivations.rs`: a `Derivation` per rule (FTS strip, link tokens, tag-ref tokens, agenda, title sort key, page-link roll-up), each with a version and an `app_settings` key. Each vault-wide rebuild records its version once it has written everything; boot's `rebuild_stale_derivations` rebuilds every cache whose recorded version is not the code's. The block links and the title keys have no materializer task, so `rederive_block_links` and `rekey_title_sort_keys` run there in one transaction each.
- The tie: `a_rule_whose_output_changed_has_a_new_version` hashes each rule's output over the four `conformance/*.vectors.json` files (SQL rules hash their statement) and fails, naming both new values, when the output moves without the version.
- The report: the screen groups divergences into out-of-date caches (rebuildable), disagreements with the sync engine, and blocks with a non-standard id. Each group says what it is and what to do, and each table gets its plain name and problem above the internal artefact name, three of its keys and one truncated expected-versus-found pair. The pair is on screen only; Copy and the bug report carry group labels, names, counts and every key, never note text (#609, #4854). Only the box, its border and its heading are tinted, so the text keeps the normal tokens' contrast.
- `rebuild_derived_state`: rebuilds every cache, then returns the settled report. Never the engine rows, which no rebuild repairs.
- The membership check skips blocks in `sync_deferred_purges` (a flag on the oracle's block dump, read without a join), and `blocks.id_form` reports blocks whose `id`, `parent_id` or `page_id` is not uppercase.

### Decisions and traps

- The existing `repair.block_links_backfill.v2` and `repair.agenda_cache_rewrite.v1` markers stay: they already ran, and retiring them meant deleting their tests for no gain. New rules use the registry.
- `ArtefactDivergences` is unchanged and the samples ride an optional report field, because Rust and TS tests build both shapes literally.
- The pages-cache rebuild only keys rows whose title changed, so a title-key rule change needs its own pass; the rebuild alone would never reach existing rows.
- The PR moved to `claude/6488-integrity-report` off fresh `main` once #6492 merged; the earlier branch was based on #6492's and would have needed a force-push.
- The cloud container's disk filled three times; `CARGO_INCREMENTAL=0` keeps the target directory from regrowing.

### Tests

Each new test was shown red first: the golden test against placeholder goldens and again against a mutated `TAG_REF_RE`, which it named. Two existing tests changed under the maintainer's standing rule because they pinned wording the maintainer asked to replace; the PR body lists them.

## Session 3786 — Re-strip stale FTS rows once, and let the integrity check settle

The maintainer's integrity check reported 27 `fts_blocks.stripped` divergences after the 0.23.0 upgrade (#6488). The strip changed in #6330, #6348 and #6421, the oracle folds with the new strip, and boot rebuilt the index only when it was empty, so every row indexed before the upgrade kept the old text.

### What shipped

- A completed full FTS rebuild (`rebuild_fts_index`, `rebuild_fts_index_split`) writes `FTS_STRIP_MARKER` (`repair.fts_strip.v1`) to `app_settings` after its last chunk commits. Boot's `schedule_fts_rebuild_if_due` enqueues `RebuildFtsIndex` while the marker is absent, as well as on the old empty-index condition. The rebuild runs through the serial background queue, so it cannot interleave with an `UpdateFtsBlock`.
- `settled_reconciliation_report` flushes the foreground queue and fires the pending inbound-sync rebuild, then drains the background queue before the oracle reads, so work in flight is not reported as a divergence.

### Decisions and traps

- The marker is written by the rebuild, not by the boot code that enqueues it: `RebuildFtsIndex` is not persisted to `materializer_retry_queue` on failure, so a marker written at enqueue time would retire a rebuild that never ran.
- The bug-bundle log allowlist (`STABLE_MESSAGES`) carries the boot line, so its wording moved with it.

### Tests

## Session 3784 — Trash bulk actions that match nothing stay silent

The maintainer reported that on the 0.23.0 desktop app, Trash's "Empty trash" and "Restore all" left the list unchanged. Their follow-up made it precise: the confirm dialog closed, no toast of any kind followed, and the items were still in the trash after a view change. Nothing had happened, and nothing said so.

A real-backend spec of the plain flow passed: 2 pages, 60 pages across list pages with and without Load more, trashed pages with children, content blocks. So did every shape tried, until the ids changed. `list_trash` returns each id as stored. `purge_blocks_by_ids` / `restore_blocks_by_ids` take `Vec<BlockId>`, whose deserializer uppercases, and match by `json_each` byte comparison. A trashed row stored under a non-canonical (lowercase) id is therefore listed but never matched. The call resolves `{ affected_count: 0 }`, and `TrashView` toasted only on a positive count. Seeding two trashed pages with `lower(id)` in `notes.db` reproduces the symptom exactly.

Shipped: a confirmed Empty trash / Restore all / batch purge / batch restore that affects 0 while rows are listed now logs a warning (which reaches the Rust log) and shows the action's existing failure toast and announcement. `e2e-tauri/trash-bulk-noncanonical-ids.e2e.ts` seeds the shape and was shown red, then green, with `scripts/e2e-tauri-local.sh`. `src/components/__tests__/TrashView.nothing-changed.test.tsx` covers the four handlers, each falsified separately. Single-row restore/purge were already loud: the canonicalised id finds no row and the IPC errors. The Trash count badge (`useTrashCount`) only polls every 30 s and on focus; it wasn't the reported defect and was left alone.

The non-canonical-id shape is a reproduction, not an established cause. A bounded pass over the writers argues against it. Every soft-delete entry point (`delete_block`, `delete_blocks_by_ids`, the empty-block sweep) seeds its `UPDATE` with an id that went through `BlockId` or `from_trusted`, so it is uppercase and cannot match a lowercase row. Such a row could only be trashed by a cascade from a canonical parent, which gives it the parent's `deleted_at`, and `list_trash` then hides it as a non-root. The Loro projection constructs ids through `from_trusted` too. Issue #107 only propagated the newtype through `FromRow` structs. This clone's history starts in November 2026, so whether pre-canonicalisation data was ever normalised could not be checked here. The maintainer's actual cause is still unknown. With this change their next attempt logs `TrashView: empty trash changed nothing` with the listed count; `SELECT id FROM blocks WHERE deleted_at IS NOT NULL AND id <> upper(id)` rules the id shape in or out.

Suites run: the new spec on the real backend, vitest on both TrashView files, `npm run typecheck`, `npm run lint`.

## Session 3751 — Attachments made in one millisecond list in the order they were made

`conformance_fixtures_match_backend` went red on #6484 at random, in fixture `meeting_add`, query `the_recording_blocks_files`: the meeting's audio and transcript came back transcript first.

- **Cause.** `list_attachments` already orders by `created_at, id`, so the brief's "no tiebreaker" premise was wrong. - **User-visible.** A block's attachments render in the order `list_attachments` returns, so a meeting's files no longer swap places between loads. The `meeting_add` fixture pins that order on both stacks.

## Session 3737 — Read aloud on Android (#5745 S7)

Built the last code slice of #5745: *Read aloud* on Android, through the OS `TextToSpeech`.

- **Shape.** `SpeechPlugin.kt` is a Tauri mobile plugin in the app module (`status`, `speak`, `stop`), loaded by `commands::speech::plugin()` with `register_android_plugin`. Rust puts the engine behind a `SpeechEngine` trait; `get_speech_status` stays a `cfg` constant (`Native` on Android), and the new `get_speech_engine_available`, `speak_text` and `stop_speaking` drive the engine. `read-aloud.ts` picks the webview or the backend route from the status.
- **Safe without a device.** The maintainer decided no manual device checks will run, so a plugin that fails to load, a `TextToSpeech` that fails `onInit` or has no installed voice, and one that never answers within `AVAILABILITY_TIMEOUT` all leave *Read aloud* hidden. The plugin's constructor does no work, the engine starts on the first availability check (the first time a menu offers *Read aloud*), and every Kotlin command catches and rejects instead of throwing. R8 keeps `@TauriPlugin` classes, their `@Command` methods and the runtime annotations; the manifest gains the `TTS_SERVICE` `<queries>` entry API 30+ needs to see an engine.
- **Traps.** Tauri runs plugin commands on a Rust thread while `onInit` lands on the main thread, so the plugin posts everything to the main looper and never blocks.
