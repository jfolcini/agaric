## Session 2192 — A committed boot-timing harness

#5418's replay numbers (chunked replay against a copy of the real vault) came
from a harness that lived only in a session scratchpad, and AGENTS.md says a
performance claim needs a committed one that reproduces it.
`scripts/measure-boot.mjs` is that harness ported to Node. It boots each
release binary on a fresh copy of a vault backup with the apply cursor
rewound, A/B interleaved. It reads replay and sync-start milestones from the
JSON log and prints per-binary medians. `src-tauri/benches/AGENTS.md` points
to it, since boot time is not a bench.

What it needs to be safe is in its header: a `.backup` copy rather than the
live vault, `AGARIC_E2E_SANDBOX` so a missing data dir fails the boot, no
network so the copied identity cannot sync, and a private D-Bus so the
single-instance plugin cannot hand off to a running Agaric. The frontend's
"boot resolved" moment is not timed: `main` logs no milestone for it, and
#5418's claim rests on the backend ones.

Validated with two rounds of two scratch builds against a vault copy with
789 ops rewound. Every milestone was found, the copies were removed, and no
process was left behind. The first round ran cold for both binaries, hence
the header's five-round advice. Those numbers came from a loaded box and are
not a measurement.

## Session 2172 — Boot replays only the ops after the last snapshot

#5418 step 2. Measured on a copy of the maintainer's vault with a 789-op
backlog (the issue's number): after #5482's chunking, replay still took
428 ms median and about 40% of log start → frontend `boot resolved`. The
issue's condition for step 2 ("if replay is still visible") held.

The issue said `save_all_engines` "already stamps `applied_through_seq`".
It did, but as `cursor − 1`, and the apply cursor does not move during a
session: only boot replay, draft recovery and the retry sweeper advance it
(`advance_apply_cursor`, MAX semantics); local commands pass `false`. So
every boot re-applied the whole previous session.

Now the snapshot watermark is the op-log head (local ops, `is_replicated =
0`) read before any engine is collected, minus one. `save_all_engines`
returns that as `persisted_through`. `save_engines_and_advance_cursor` runs
one pass and, only when every dirty space was written, drains the
background queue and advances the cursor to the head. The drain matters:
replay re-sends each op's FTS/link/tag fan-out, which lives only in memory
until the background queue runs it. Passes are serialized by a mutex, so a
stale row is never marked clean behind a higher watermark; there is no test
for that race, and the doc comment says so. The periodic task, the
background job and the exit handler all call it. The `− 1` stays, so a
clean boot still replays one op and #4018's routine one-op rewind holds.

Crash safety: rows are written first and the cursor last, so a crash at
any point leaves the old cursor and means more replay, never less. The heal
still rewinds to the lowest watermark when a row lags. Trade-offs: quitting
waits for the background queue to drain, and an engine change lost
mid-session is repaired at boot only if no pass ran after it.

Tests, each red against a mutated copy: the pass advances the cursor to the
head; a failed write leaves it; an undrained queue leaves it; and a crash
test on #5482's oracle workload (live ops, a pass, more ops, a crash with no
exit save, a real rehydrate and boot) ends with engine and SQL equal to the
pre-crash session and replay covering the tail plus one op.

Found, not fixed here (pre-existing, same with the old cursor): a delete
in the post-snapshot tail never reaches the engine on replay, because the
space lookup skips deleted blocks and sends the op down the SQL-only path.
The crash test leaves out its workload's final delete for that reason; it
is #5630.

## Session 2167 — a property op refreshes only its own block's projected agenda (#5423 item 5)

In #5592's after-run, `set_property (todo_state, 2K-block page) @ 100K` took 2.33 ms for the command and 76.50 ms settled. The probe's vault has 200 repeating tasks, and every todo, date or repeat write enqueued `RebuildProjectedAgendaCache`. That rebuild deletes every row of `projected_agenda_cache` and re-projects every repeating block under one write lock. `agenda_cache` is already diff-based and is not enqueued for `todo_state`, so this rebuild accounted for the whole gap.

**The task.** `MaterializeTask::UpdateProjectedAgendaBlock { block_id }` runs on the background queue and is deduplicated per block. Its retry mirror (`RetryKind::UpdateProjectedAgendaBlock`) keeps the block id.

**Dispatch.** `push_property_op_invalidations` now pushes the per-block task for a projected-relevant key. Two cases still push the full rebuild:
- `template`, which changes every block on its page;
- an unparseable payload.

No other op's invalidations change.

**`update_projected_agenda_block`.** In one `BEGIN IMMEDIATE` it:
- reads the horizon's `rebuild_today`;
- deletes the block's rows;
- selects the block with the full rebuild's own predicate plus `b.id = ?1`;
- projects it at that anchor;
- inserts through the existing flush helper.

It never rewrites the horizon row. If there is no horizon row, or `rebuild_today` is not today, it rolls back and runs the full rebuild. So the first projected write of a day still re-anchors the horizon, as every such write used to.

**`dedup_tasks`.** Adding the task's key pushed it past clippy's 70-line limit. Its seven per-id sets are now one set keyed on (kind, id), with the same behaviour.

**Tests.**
- **Oracle:** `property_op_refreshes_one_block_equal_to_a_full_rebuild_5423` covers 13 shapes, each driven through `dispatch_op` and a flush:
  - daily and weekly repeat;
  - due only, scheduled only, both;
  - repeat-until, repeat-count;
  - DONE then TODO;
  - repeat removed, dates removed;
  - soft-deleted;
  - on a template page;
  - a block gaining `repeat`.

  After each one the whole cache equals a fresh full rebuild, and two other repeating blocks keep exactly their rows. The handler reads the wall clock, so a run that straddles local midnight fails this test; the module doc says so.
- **Store**, pinned to a date:
  - `per_block_refresh_projects_from_rebuild_today_5423`, which also checks that the horizon row is left alone;
  - `per_block_refresh_re_anchors_a_stale_or_missing_horizon_5423`.
- **Dispatch:** the property-op label tests now expect the per-block task. New tests cover `delete_property repeat` and `template`, set and deleted.
- **Retry and dedup:** both round-trip the new kind.

**Review** (a different model) found no correctness defect. It found two gaps in the oracle, both closed here:
- **Nothing pinned the narrowing itself.** Its "other blocks keep their rows" check also held under a whole-vault rebuild, so wiring the handler back to the full rebuild kept every test green. Before each op, the oracle now plants a cache row no rebuild writes, and requires the op to leave it.
- **No shape set `repeat-seq`**, so the per-block query's join to it was unpinned. A "repeat-seq set against a repeat-count" shape now covers it.

The review also diffed the old and new `dedup_tasks` over 30,000 random batches and found them identical.

## Session 2159 — Claude Code's TypeScript LSP is the repo's own tsc

The official `typescript-lsp` plugin starts `typescript-language-server`,
which needs the JavaScript `tsserver`. TypeScript 7, which this repo uses, is
the native compiler and ships no `tsserver`, so that plugin could not start
here. Making it start would have meant a second, older compiler whose errors
disagree with `npm run typecheck`.

TypeScript 7 has its own language server, `tsc --lsp --stdio`. A one-plugin
marketplace in `.claude/marketplace/` runs it from
`${CLAUDE_PROJECT_DIR}/node_modules/.bin/tsc`, and `.claude/settings.json`
declares that marketplace, enables the plugin, and turns the official
`typescript-lsp` off for this project only. Because the settings are
committed, every checkout and worktree gets the same server. Language
servers do not run in cloud sessions.

Checked: `claude plugin validate` passes for the marketplace and the plugin.
With the user-level marketplace registry entry removed, a fresh session
registered the marketplace from the relative path in project settings.
A headless session's LSP `findReferences` on `SectionGroupHeader` returned
the same five files as a hand-driven `tsc --lsp` probe.

## Session 2156 — an unchanged block is not flushed on a no-blur unmount (#5423 item 6)

## Session 2154 — the dialing side of a first pair closes its pairing window

The real-backend lane found this on #5609's first run.

**Symptom.** Unpairing a device within five minutes of pairing it did not stick.
- The app re-dialed the unpaired device on its next mDNS announcement.
- That session re-created the device's row, and its syncs were admitted again.
- The device list still showed no peers.

**Cause.** Opening the pairing dialog arms a pending-pairing marker, with a 5-minute TTL. While the marker is armed:
- `should_attempt_sync_with_discovered_peer` dials every discovered device;

- The joiner's marker clears the same way when it dials first. Once its bind is done, it needs no window. The host's later dials are admitted by key, and leaving the marker armed would give the joiner the same five minutes of dialing and admitting strangers.

## Session 2153 — an open tag search re-resolves after a sync

The real-backend lane found this on its first run of `sync-refresh.e2e.ts` (#5609). An open search for `tag:#name` stayed at "No results" after a pull brought that tag in. The tag and the tagged block were both in the backend.

**Cause.** `invalidateNameCaches()` fires twice per pull: on `sync:complete`, which arrives before the cache rebuild, and on `blocks:changed`, after it.
- `useTagResolution` reacted only by dropping names it had cached as "not found".
- The first invalidation started a lookup that read `tags_cache` before the rebuild committed.
- The second invalidation arrived while that lookup was still in flight. With nothing yet cached to drop, it changed nothing.
- The stale lookup then cached "not found", and no later invalidation retried it, so the search was stuck.

**Fix.** Every name change now bumps a `reloadKey` that the lookup effect depends on. A lookup in flight is cancelled and re-issued. Resolved ids stay as they are, so a sync does not put the search back on hold. This is the `reloadKey` pattern that `useBlockTags` and `usePageAliases` already use.

**Test.** Two orders, in `useTagResolution.test.ts`:
- **Race order:** the name change lands while the re-lookup is in flight. It fails without the fix, with the stuck `{ tagIds: [], hasUnresolved: true }` state.
- **Control order:** the change lands after the re-lookup settled. It passes either way, so the test isolates the race.

Removing the `cancelled` guard in `settle` also fails the race order: the stale answer overwrites the fresh one.

Checked the other subscribers to the same signal (`useBlockTags`, `TagList`, `use-block-resolve`, `TagFilterPanel`). Each re-issues or sequences its requests already. `usePageAliases` re-issues, but has no `cancelled` guard on its fetch, so a late older answer could overwrite a newer one. That is a different shape and was left alone.

## Session 2147 — two-device sync: concurrent edits and unpair

**Concurrent edits converge.**
- `edit_block_inner` reaches Loro as a character splice between the common prefix and suffix (`LoroEngine::apply_edit_via_diff_splice`). So the peer prepends and the app appends to the same block, and the edits cannot overlap.
- The order is what makes the edits concurrent.

- Each side then pulls, and both read exactly `PEER_HEAD PEER_EDIT APP_TAIL`.

- `delete_peer_ref_inner` deletes the local row and tells the other device nothing.

## Session 2138 — "Sync now" fires while a peer is announcing

"Sync now" did nothing while another device was on the LAN. Found by the
two-device spec in #5589: in its failing CI run the click came at
19:49:38.5, and the app never dialled the peer in the 50 s after it.

The cause has two halves:

- `start_sync` only calls `notify_change()`, which Branch B of the
  daemon's `select!` debounces over 3 s.
  `SyncScheduler::wait_for_debounced_change` started a fresh 3 s `sleep`
  each time it was called, and the loop re-creates that future on every
  pass.
- `iroh-mdns-address-lookup` 0.6.0 reports every republish of a known
  peer as a new `Discovered` event. Its known-peer check compares a `Peer`
  that includes `last_seen`, so the check never matches. In CI these
  arrived about every 0.8 s, so Branch A won each pass, Branch B's window
  restarted each time and never closed.

The fix stamps the time of the last `notify_change()` on the scheduler,
and the debounce sleeps until that stamp plus the window. A re-created
future now finishes on time, and a change inside the window still extends
it. `wait_for_change_after` and `debounced_through` are unchanged.

Two paused-time tests in `sync_scheduler.rs`:

- `debounce_window_survives_a_sibling_arm_that_keeps_winning` runs the
  daemon's shape, a `select!` against an 800 ms sibling, and asserts the
  round fires at exactly 3 s. Restoring the old `sleep(window)` turns it
  red with `left: None, right: Some(3s)`.
- `a_change_inside_the_debounce_window_extends_it` asserts a second change
  at 1 s moves the round to exactly 4 s. Reading the deadline once before
  the loop turns it red with `left: 3s, right: 4s`; no existing test
  caught that.

Not fixed here: the upstream lookup still emits an event per republish.
With the window now surviving cancellation, the extra wakes no longer
starve a round. Outside a pairing window each costs Branch A two small
reads; inside one, each republish re-dials the peer, bounded by the
per-peer lock and backoff as before.

## Session 2120 — Pages sorts read from an index

#5371 follow-up, the maintainer's "make them work". The sorts #5371 shipped
drove from `blocks` through `idx_blocks_space_type`: the list filters by
space, which `pages_cache` did not carry. So every first page sorted the
whole space with a temp B-tree before the `LIMIT`.

Main's weekly perf gate went red after #5371. In CI run 38748918610, on
main's code, Last opened at 20k pages took a median 615 ms against the
250 ms gate. Created and Alphabetical took 39 and 96 ms. That gate runs only
in the `bench-slo` lane, so PR CI did not catch it.

What changed:
- **Migration 0124.** `pages_cache.space_id` is backfilled from the page
  block. There is one `(space_id, key, page_id)` index per sort, in the
  sort's own direction, plus `idx_page_opens_opened`.
- **Query.** It drives from `pages_cache` and cross-joins the live page
  block, so SQLite cannot reorder away from the index.
- **Keysets.** Each keyset reads bare columns, and a cursor page seeks into
  the index at the cursor's key.
- **Last opened.** It reads two arms: opened pages from `page_opens` in open
  order, then the space's never-opened pages in id order. A cursor in the
  tail reads the tail arm alone.
- **Keeping `space_id` right.** A page's `space` op moves it in the same
  transaction (`cache::sync_pages_cache_space_ids`, also used by the boot
  placement). The page-create INSERT copies it, and the page-row rebuild
  repairs any other path.
- **Restores.** The rebuild drops a trashed page's row. With an inner join,
  a restored page would vanish until the next rebuild, so every restore path
  re-inserts the missing row in its own transaction
  (`cache::insert_missing_pages_cache_rows`). The paths are the projection,
  the three restore commands, and undo.
- **Boot check.** Boot schedules the rebuild when a live page has no row or
  a row in another space. That covers an engine reproject in recovery,
  which writes `blocks.space_id` without the cache. The reconciliation
  oracle reports a row in the wrong space.

The review also found the #469 comment on `recompute_all_pages_cache_counts`
false. It claimed the CTE runs each count once per row, but SQLite 3.46
flattens the CTE: the counts run in the change-guard `WHERE` for every row
and again in the `SET` for a row that changes. The comment is deleted.

Trades, measured and accepted:
- The `COUNT` behind `total_count` runs the same predicate from the new
  driver and costs about 1.6x what it did.
