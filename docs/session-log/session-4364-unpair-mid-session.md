# Session 4364 — an unpaired device that a running sync brings back

The real-backend lane went red on #6956 (`sync-two-device.e2e.ts`, "unpairing refuses the peer's next sync"): the device list was empty right after the unpair and showed the peer again after a round trip through the Journal.

**Cause, from the run's app log:** after the spec's restart, the app's own syncs with the peer completed at 18:26:11.98 and 18:26:12.92, and the unpair landed between them. At 18:27:12.93 the periodic resync, which dials only peers that have a `peer_refs` row, dialed the peer again, so the row was back. A session running when the user unpaired put it back when it ended: `record_pull_in_tx`, `record_stream_in_tx` and `persist_peer_loro_vvs` each ran `upsert_peer_ref_in_tx` (`INSERT OR IGNORE`) before their `UPDATE`, and the responder's `bind_peer_to_key` ran `bind_endpoint_id` (an upsert, key included) after every completed session. The bug predates #6956; none of the last 40 completed e2e-tauri runs failed this test before #6956's.

The snapshot catch-up's `record_catchup_pull` is a fourth such insert (named in #6965), and a catch-up also runs on a pairing session, after a reinstall. So it takes the same flag, carried on `EngineReloadCtx::paired_peer`.

**Fix:** the daemon marks a session with an already paired peer (`SyncOrchestrator::with_paired_peer`): the initiator when the peer was in the round's `peer_refs`, the responder on its bound-row branch. Such a session only updates the row, and an `UPDATE` that finds none drops the transaction. Only a pairing session, which starts with no row, creates one. The responder binds only inside a pairing; outside one the row already carries the key.

**Test:** `unpairing_during_a_session_keeps_the_peer_unpaired` runs a real loopback session in which each side's event sink deletes its row on the first event. The responder needs something to stream: with an empty vault it short-circuits and records before its first event, and the test passed with the responder's half reverted. Shown red three ways: the initiator's `with_paired_peer` removed, the responder's removed, and the responder binding outside a pairing. `a_catchup_for_an_unpaired_peer_leaves_it_unpaired` runs an empty catch-up for a paired peer with no row, and goes red with the catch-up's insert restored. The supervisor line that sets `paired_peer` from the orchestrator has no test that reddens without it.
