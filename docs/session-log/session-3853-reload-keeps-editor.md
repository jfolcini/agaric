# Session 3853 — A reload keeps the open page's block tree mounted (#6533, first item)

#6533's first checkbox: a sync, an MCP write (`blocks:changed`) or a page undo reloads the open page's store through `load()`, which sets `loading: true` on every call, and `BlockTree` rendered only its skeleton while `loading` was true. Every reload unmounted every row and the focused editor: focus fell to `<body>` and later keys were lost, the scroll collapsed on a slow reload, and the unmount flushed a dirty editor's draft (`save_draft` + `flush_draft`) with no input.

**Change.** `BlockTree` shows the skeleton only while `loading && blocks.length === 0`, the store's first load; the store's `loading` still toggles on every load. `BlockListRenderer` gets the same first-load value, not the raw flag: it was only ever rendered with `loading` false, and now that it stays mounted through a reload the raw flag would drop the mount-limit "Show more" row and the drop sentinel for the reload's duration. A page switch makes a new store in `PageBlockStoreProvider`, so it still shows the skeleton. An empty page still flashes the skeleton on a reload; it has no row or editor to lose, so no `hasLoaded` flag was added. A failed reload keeps the rows and still raises the retry toast (store unchanged).

**What the remount was hiding.** The rows' property chips, list markers and image sizes come from `BatchPropertiesProvider`, which `BlockTree` re-reads only on a per-block `block:properties-changed` event. A page undo or redo, a sync and an MCP write change `block_properties` with no such event, so the remount was what re-read them: with the tree kept mounted, Ctrl+Z left the chip or the bullet it had taken back on the row until the page was reopened. `invalidateDerivedCaches()`, the one reset sync, MCP, import, undo and redo share, now also dispatches a payload-less property change (`dispatchBlanketPropertyChange`), which the scoped hook already treated as a blanket change, so every open tree re-reads its batch once. Attachments, query blocks, link chips and embeds already refresh through their own signal or store.

**A focused editor through a reload.** Clean, on a block the peer changed: on `main` the editor died and the keys typed were dropped, the peer's text staying stored; a click on the row brought back an editor fed with the store's old text, and its first keystroke committed that over the peer's edit. Now the editor stays live with the old text and that keystroke does the same one click sooner; leaving the block untouched still shows the peer's text (#5278). Dirty: on `main` the unmount flushed the editor's text as a draft and an op at the reload; now it commits on the usual debounce and later keys land. The same text wins in both, so the overwrite stays with #6533's second and third items.

**Page mode and Edit as Markdown** take their own paths and are unchanged: `PageModeEditor` subscribes to the page store directly, skips while `loading` and brings the fresh blocks in by itself; `PageSourceEditor` reads the page once when opened and never watches reloads. The one stale comment there (`use-page-mode.ts`, "a skeleton showing meanwhile" on the switch back to blocks) now says the tree reads the page again; the store is already loaded by then, so no skeleton shows.

**Tests.** `e2e/reload-keeps-editor.spec.ts`: on a 150-row page scrolled to its bottom, for `blocks:changed`, `sync:complete` naming the page and `sync:complete` naming none, keys typed during a delayed reload and after it land, the editor stays focused, the text commits (re-queried), the scroller never moves and a MutationObserver sees no skeleton, row or editor node removed; a page undo at the bottom with `load_page_subtree` delayed never moves the scroller or attaches the skeleton; a reload keeps a selection and ProseMirror's own undo history; a reload under a dirty editor issues no `save_draft` / `flush_draft` (the autosave's later `save_draft` is the positive control). Two more take a property chip and a list marker off a row and back with a page undo and redo, no reopen and no row removed. All eight red on `main` at the predicted assertion; the last two are also red on the tree that only stopped remounting, at the chip left on the row. `BlockTree.reload.test.tsx`: two trees side by side (one reloading, one on its first load), the mount-limit boundary through a reload, a failed reload, and a page switch. `derived-caches.test.ts` lists the trees' property batches among the caches it drops, and `useBlockPropertyEvents.test.ts` pins the scoped hook's bump for a change no event names.

**Traps.** On the long page, rows that leave the viewport turn into placeholders a few frames after a scroll; the spec waits for the hydrated rows to hold still before it starts counting removals, or it counts that churn. The undo test's final `scrollTop` matched on `main`: the collapse to 0 is visible only in the positions the scroller passes through, so the spec records every scroll event. The mock's undo, like the backend's, emits no `block:properties-changed`, while a `set_property` through `ipc` does: only the undo shows the stale chip. The machine's Playwright browsers were one revision behind the installed `@playwright/test`; runs used a scratch `PLAYWRIGHT_BROWSERS_PATH` symlinking the old revision under the new name.
