## Session 2990 — The ref peek stops blinking out when its content lands

Set out to fix a red CI run on #6134. `BlockRefPeek.test.tsx` "Preview of Design Notes" found the peek with an empty accessible name. It looked like a flake, but it was a real defect.

**Cause.** `BlockRefPeek`'s placement effect re-runs when the payload lands, so that `flip()` sees the full box. Each run began with `setPosition(null)`, so a peek already showing went `visibility: hidden` until `computePosition` resolved again. It blinked out each time its content arrived, and for that moment it left the accessibility tree. The test caught the moment.

**Fix.** A placement now carries the anchor rect it was computed for (`Placement`, `placementFor`). A placement for another anchor counts as none:
- moving to another chip still hides the peek until it is placed;
- a re-place for the same anchor keeps the peek visible.

The anchor only changes through `open()`, which always takes a fresh `getBoundingClientRect()`. So the check by reference errs towards hiding, never towards showing a stale box.

**Tests:**
- **vitest:** a shown peek stays visible, with its accessible name, while its blocks land. Red against the old code: `toBeVisible` saw `visibility: hidden`.
- **Playwright (`e2e/page-link-preview.spec.ts`):** a MutationObserver records the peek's `style.visibility` at every DOM change, which is before any paint, so the mock lane can see a one-frame blink. Red against the old code: `["", "hidden", ""]`. Green with `--repeat-each=15`.
- The backend plays no part, so there is no `e2e-tauri` spec.

**Suites:**
- vitest on the peek component, hook and `block-ref` (67 tests);
- typecheck and lint;
- Playwright over the page-link preview, block-ref peek keyboard and related specs (8 passed).

## Session 2965 — the last page-gutter mutant: a lane press is no click

#6108 had one mutant left after #6127 (session 2917): the capture flag on the gutter lane's mousedown listener (`page-gutter.ts`, `addEventListener('mousedown', this.pressLane, true)`). It is not equivalent, and a test now kills it.

**Why the flag matters:**
- ProseMirror registers its own mousedown on `view.dom` in the bubble phase. It skips a press whose `defaultPrevented` is set (`eventBelongsToView`). Otherwise it records the press, and the release then reaches every plugin's `handleClick` (`handleSingleClick`).
- With the lane listener in the capture phase, the lane prevents the press first, so a press in the gutter lane is no click for the editor.
- In the bubble phase, ProseMirror runs first and a lane press counts as a click in the text.

**The test** registers a plugin with a `handleClick` spy and stubs `document.caretPositionFromPoint` / `elementFromPoint`, which jsdom lacks, so ProseMirror can place a press:
- a press in the lane must not call the spy;
- a press in the block must call it once. That half makes the first non-vacuous.

The stubs are removed in `finally`.

**Red:** flipping only the `addEventListener` line's `true` to `false` fails the spy assertion ("expected not to be called, called 1 times").

**Counts** (split Stryker run at the blank line before `move`):
- before: 231 killed and 14 survived;
- after: 231 killed, 1 timeout and 13 survived.

The 13 survivors are exactly the page-gutter lines already in `mutation-accepted.tsv`. The timeout is the `lucide-…` class string, killed in the before run and timed out on the loaded box; Stryker counts a timeout as detected. A filer dry run reports 13 suppressed and 0 reportable.

**Suites:**
- `src/editor/page-mode` vitest: 757 passed;
- the gutter file under `--sequence.shuffle` with two seeds;
- typecheck, oxlint and oxfmt.

The reviewer checked the ProseMirror lines in the installed `prosemirror-view` 1.42.6.

## Session 2950 — a new page's first block closed the menu opened over it

`e2e/history-revert.spec.ts`, "reverting a delete onto a taken title says so and restores nothing", failed on #6136, a PR that changed only page-tasks tests. The click on the Page actions menu's "Delete page" item timed out: the item was detached from the DOM partway through the click. The failure's snapshot shows the new page's block editor focused, `New page created` announced, and no menu open. The maintainer asked for every flake to be fixed rather than re-run.

**Cause:** creating a page seeds a first block and focuses it for typing. That focus goes through the roving editor (`src/editor/use-roving-editor.ts`), which lands a frame or more after the seed `create_block` answers. On the mock, the title showed first, and the editor took focus 70–106 ms later. `createPageFromPagesView` returned as soon as the title showed, so the spec could open Page actions before the focus landed. On desktop, Page actions is a non-modal Radix `Popover`, and focus moving outside it dismisses it.

**Fix:** `createPageFromPagesView` returns only once the first block is focused. The late focus is what the app means to do, and no user beats a 0.1 s window between creating a page and opening its menu, so the helper waits instead of the product changing. Every one of the helper's eleven calling specs creates a page that seeds that block, so the wait holds for all of them. On a phone the seed block takes focus the same way: an iPhone 13 probe confirmed it.

**Shown red:** a throwaway probe held the seed `create_block` until the Page actions menu opened. With the old helper the late focus closed the menu, and the click on "Delete page" timed out, matching CI's snapshot. With the fixed helper the same probe passed. Run unchanged, the spec passed thirty times in thirty locally both before and after the fix, so only the held reply shows the race.

**Suites:**
- the eleven specs that call `createPageFromPagesView` (96 of 96);
- `history-revert.spec.ts` with `--repeat-each=30`;
- `npm run typecheck` and `npm run lint`.

## Session 2949 — the Edit as Markdown frame rings toolbar and text

The maintainer reported that the focus ring of *Edit as Markdown* did not wrap its toolbar and was not uniform on all sides.

**Cause:** the border, the shadow and the 3 px `focus-visible` ring were on the ProseMirror element alone (`BUFFER_CLASS`), and the formatting toolbar sat above that box, outside it. The toolbar is `sticky top-0 z-10 bg-background`, so its opaque background painted over the top edge of the ring, which left the top thinner than the sides.

**Convention followed:** block mode's `.block-editor` is one rounded box holding both the toolbar and the text, and `ToolbarFrame` is already drawn as that box's header (`rounded-t-md border-b`). GitHub's and GitLab's comment editors work the same way: one bordered frame around the header and the text area, a hairline between them, and focus anywhere inside rings the whole frame. In this app a composite control rings on `focus-within` with the same opaque 3 px token (`PropertyChip`).

**Change:** `PageSourceEditor` wraps the lazy buffer in a frame (`BUFFER_FRAME_CLASS`) that carries the border, the shadow and a `focus-within` ring. The text keeps only its padding, font and height. The classes stay in `PageSourceEditor`, where the existing comment keeps them so the lazy buffer's chunk imports no design-system module. The frame sits inside the `Suspense`, so the loading fallback is not framed.

**Checked by eye:** Playwright Chromium screenshots at 1024×768, light and dark, with the text focused and with a toolbar button focused. The ring is the same width on every side and encloses the toolbar.

**Suites:**
- a new `page-source-edit.spec.ts` test: the element painting the 3 px ring holds the whole toolbar, both with the text focused and with a toolbar button focused. It was shown red with the ring moved back onto the text;
- the PageSourceEditor, PageSourceToolbar and PageEditor tests (168 of 168);
- `page-source-edit` and `page-source-ulid-tokens` in Playwright (26 of 26);
- typecheck and oxlint.

## Session 2948 — a leaving toast took the source editor's Save click

`e2e-tauri/agenda-projected-repeat.e2e.ts` failed on #6133, a PR that changed only jex-import tests: "/repeat .+ counts from today…" died in `seedTasks` with `element click intercepted` on `clickPageSourceButton('Save')`. - `dag::ingest_remote_record` raised the page through `record.block_id`. That is a sidecar `From<OpTransfer>` always leaves `None`, so no synced op raised any page.
- The dag unit test passed only because its fixture filled the sidecar.
- The raise now takes the block from the payload with `extract_indexed_ids_from_payload`, as `op_log.block_id` does. That matches the local raise op for op.

**`page_id` lagged the raise.**
- The engine projection inserts a synced non-page block with `page_id` NULL, and a moved block keeps its stale one. `RebuildPageIds` fixes both, but behind the inbound debounce, and `flush()` never fired that debounce.
- `complete_pull_session` now calls `fire_pending_inbound_rebuild()` (on `ApplyHost`) before the flush that precedes the audit ingest. The flush's barrier waits for the whole fan-out it enqueued.
- That covers three cases:
  - a new block;
  - a cross-page move, which now raises the new page and not the old one, as a local move does;
  - a new page whose cache row came before its children's page ids.
- **Cost:** the fan-out now runs inside the session, before `SyncComplete`, and only when the session carries audit records. On a pessimistic debug build at 100K blocks it took about 6 s. The bound is 120 s.
- **Residual:** a full background queue can shed the fan-out, and that session's raise then misses. That is no worse than before.

**Not here:** the fix is forward-only. Pages that already diverged stay reported by App health until something edits them again.

**Shown red:**
- With the raise keyed on the sidecar again, the dag test and three real-QUIC tests fail. The QUIC tests assert that `reconcile_all` reports no divergence and that B's times equal A's.
- With the early fire deleted, or moved after the flush, the three QUIC tests fail.
- `e2e-tauri/sync-refresh.e2e.ts` checks that a block the peer adds lifts its page above a newer one in "Last edited". It passed five runs out of five on the real backend, and failed with its own message with the dag fix reverted.

**Suites:**
- the whole workspace under nextest;
- clippy, fmt and `SQLX_OFFLINE` check;
- `typecheck:e2e-tauri`, the e2e-tauri helper tests, and lint;
- the real-backend sync-refresh spec.

## Session 2902 — MCP create_tag tells open views, once the tag list holds the tag

#6049, the Rust half. A tag an MCP agent creates stayed missing from an open journal's `#` picker until the next sync event. Typing it offered only "Create". The backend then reuses the existing tag of that name (#5236), so nothing is lost; the picker was just out of date. The frontend half (#6068) gave every out-of-band write path one `invalidateDerivedCaches()`. This half makes `create_tag` send the event that runs it.

**The event.**
- `handle_create_tag` emitted nothing. It had nothing to send: a tag sits on no page, and an empty `changed_page_ids` means "reload every mounted page store".
- It now sends the tag's own id. The frontend's targeted path finds no store that holds the id, so it reloads none, and it still runs `invalidateDerivedCaches()`. That empties the picker's tag list.
- No new payload field: an id no store holds already meant exactly this, and the empty set keeps its meaning for every other emitter.

**The order.** The picker refills from `tags_cache`. The background queue rebuilds it after the commit, with no debounce for a create but behind whatever is already queued. A `#` typed between the event and the rebuild would refill the list without the tag and keep it, because a non-empty list is never fetched again. `create_tag` now awaits `flush_background()` before it emits. `SpacePlacementSink` and the recovery cache refresh do the same for the same reason. The reply waits for the background queue, which matters only under a backlog.

**Shown red:**
- With the emit removed, `create_tag_creates_in_space_and_reuses_the_name` sees no event.
- With the flush removed, `create_tag_signals_once_the_tag_list_holds_the_tag_6049` reads the tag list at the emit and finds it without the tag, six runs out of six.
- On the frontend, two `useSyncEvents` changes each redden "reloads no page store for an id none holds, and still drops the picker name caches": a set that names no page reloading every store, and the targeted path skipping the cache reset.
- `e2e-tauri/mcp-create-tag-picker.e2e.ts` creates a tag through MCP while the journal is open and its picker list is already filled, then types it. It is CI's real-backend lane that runs it. The MCP agent setup moved into `e2e-tauri/helpers.ts`.

**Not here:**
- Deleting or restoring a tag through MCP rebuilds `tags_cache` on the 300 ms inbound debounce. A `#` typed in that window can keep a deleted tag in the picker.
- MCP `create_page` and the Pages list, which reads `pages_cache`, have the same shape.
- The `[[` picker reads `blocks` and has no race.

**Suites:**
- nextest over `create_tag`, MCP, `blocks_changed`, sync events, `resolve_changed_page_ids` and `tags_cache`;
- clippy, fmt and `SQLX_OFFLINE` check;
- vitest over `src/hooks`, `src/lib`, `src/stores` and `src/components/block-tree`, and the e2e-tauri helper tests;
- typecheck, including `typecheck:e2e-tauri`, and lint.

## Session 2901 — undici, happy-dom, fast-uri and serialize-javascript advisories

New npm advisories turned the `npm-audit` hook red on every PR (first seen on #6100):
- undici before 7.30.1 and 8.12.2: denial of service and a Subresource Integrity bypass (two high);
- happy-dom up to 21.0.3 (high);
- fast-uri up to 3.1.8: URI scheme spoofing, host confusion and two lows;
- serialize-javascript before 7.1.3 (low).

All four are dev-only, and none is in `npm ls --omit=dev`:
- happy-dom is vitest's DOM.
- undici comes through webdriverio (cheerio and webdriver) and jsdom.
- fast-uri comes through Stryker's `ajv`.
- serialize-javascript is an existing override.

`npm update fast-uri undici happy-dom serialize-javascript` moves only those packages in the lockfile: undici 7.30.1 and 8.12.3, happy-dom 21.0.4, fast-uri 3.1.9, serialize-javascript 7.1.3. Every declared range already allowed them, so `package.json` does not change.

Three fixes are younger than `.npmrc`'s seven-day `min-release-age`. `.npmrc` names `--min-release-age` as the way to take a fix early. It ran at one day rather than zero, which takes serialize-javascript 7.1.3 rather than the half-day-old 7.1.4.

`scripts/npm-audit-retry.sh` passes. vitest over `src/lib`, `src/hooks`, `src/stores` and `src/components` passes on the new happy-dom.
