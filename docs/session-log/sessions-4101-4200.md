## Session 4200 — Drag a board card to another column, by pointer and by touch

Built slices 3 and 4 of #6542 (pointer drag, then touch drag) on the Advanced Query board that #6700 and #6711 shipped.

**One move path.** The menu's pick and a drop both end in one `move(from, block, target)` in `QueryBoard`, which does what the menu did before: focus the column the card left (or the target when the last card leaves *Other values*), then `moveCard` from `board-move.ts`. So a drop makes the same single write (`set_todo_state`, `set_property`, `delete_property` for *No value*), the same *Moved to …* toast with Undo, and joins the page's undo stack the same way. A drop on the card's own column, on *Other values* (a disabled droppable) or outside any column writes nothing.

**Reused, not added.** dnd-kit was already installed and drives bookmarks and tabs through `layout/reorder-dnd.ts`. Its pointer half is now `usePointerDragSensor` (8 px of travel on a fine pointer, the 400 ms long-press hold on touch, keyed on `useIsTouch()`), and `reorderAccessibility`'s `titleOf` also gets the item's data, so the board's announcements name the card and the column rather than ids. The board takes no keyboard sensor and does not spread dnd-kit's `attributes` on the card: Space must still open the card, the roving tab index must stay, and keyboard and screen-reader users keep the menu. Columns are found with `pointerWithin`. The ghost is a `DragOverlay` with no drop animation (the card lands in another column after the refetch, so a settle onto its old place would be wrong), and edge auto-scroll is off under reduced motion, as in the block tree. A card's id is its column's id and its block's, since a refetch can briefly list a moved card in two columns.

**Traps.** dnd-kit swallows the document's clicks for 50 ms after a drop; in vitest that outlives a drag test into the next test's first click, so the drag tests wait it out. In Playwright on a tablet the board sits below the fold, and a touch sent outside the viewport does nothing; the specs centre the column first, which also keeps the drop clear of the auto-scroll edges. A swipe that scrolls the board proved nothing on its own (a no-hold sensor still let it scroll); the spec checks dnd-kit's live region says nothing about the card after the swipe, and names the drop after the real one.

**Tests.** `QueryBoard.test.tsx` drives real dnd-kit pointer drags with the columns laid out by a `getBoundingClientRect` stub: a drop makes the menu's write and toast and joins the undo stack, *No value* deletes the property, own column and *Other values* write nothing, and only a column the card can go to is outlined, with `axe` while a card is lifted. `e2e/advanced-query-board.spec.ts` adds a mouse drag and a touch long-press drag on an iPad landscape viewport (CDP touches) with a swipe that must scroll. Shown red: dropping the own-column guard, dropping the card's listeners (component and both e2e), the droppable's `disabled`, the own-column outline check, the touch sensor without its hold, and the fine-pointer sensor on touch. Ran the board, Advanced Query, bookmark, tab and page-link-drag Playwright specs; `just e2e-related` says the whole lane for `reorder-dnd.ts`, so CI's run is the check there and for WebdriverIO. Touch drag on a real phone is a line on #6513.

**Not done.** The 500-card measurement from the issue body is still not made. A board on an inline `{{query}}` block (slice 5) is a later issue.

## Session 4199 — the mobile search-view spec clicked a stale row on the bridge

The scheduled `full-suite` run 43590125058 (#3394) failed in `full-suite-nextest (2)`, whose real-backend Playwright step ran `e2e/search-view-mobile.spec.ts` "a result row navigates to its owning page on mobile" on the bridge: no `Page title` reading "Getting Started" within 15 s. The run kept no artifacts. Later dispatched runs were green.

Mechanism: a test race, not a product or seed bug. The spec reaches the panel by escalating the palette's "Review" query, so the panel runs a "Review" `search_blocks` and renders its rows. It then types "Welcome", presses Enter and clicks `[role="option"]` `.first()`. `useSearchResults` uses `keepPreviousData`, so the "Review" rows stay on screen until the "Welcome" reply lands. An IPC log over the bridge showed the click starting while that reply was still in flight; on a fast box it lands before Playwright's actionability checks finish, but on a slow runner the click hits a "Review" row and navigation goes to that row's page. Keeping old rows during a fetch is intended, and clicking one opens the page it shows, so the app is right. The mock answers synchronously, so the mock lane never sees the window. The desktop counterpart in `search-results.spec.ts` starts from an empty panel and has no stale rows.

Traps: the panel searches with `search_blocks`; `search_blocks_partitioned` is the palette's. A delay injected on the partitioned command changes nothing in the panel, which first made the race look ruled out. A uniform delay on every search also hides it, because then the "Review" rows never render before the "Welcome" query.

Fix: the spec clicks the option with text "Welcome", so the click waits for the current query's row.

Shown: with `bridge.ts` delaying the panel's "Welcome" `search_blocks` reply by 300 ms (local, restored by trap), the old spec failed 3/3 with CI's exact error and the fixed spec passed 3/3. Without the delay, the old spec passed 30/30 and the whole real-backend project passed 180/180 at three workers. Fixed spec: 10/10 on the bridge, 2/2 on the mock. Falsified by skipping `navigateToPage` on the resolved-page path: red at the title assertion. `npm run typecheck` clean.

## Session 4198 — a property can hold a list: defining and editing (#6741, PR 2 of 4)

The second of the four pull requests in the design the maintainer approved on #6741 ("Design for option 3 (a list value in the one row)"), on top of PR 1 (#6796, session 4189). This one makes a list reachable: a user can declare a key that holds several values, turn a key into a list or back, and edit, type, copy and review its items. No new migration, table, op type, store, queue, sync message or engine format change.

### What shipped

- **Defining.** "Holds several values" in Settings › Properties' create form and the page Properties table's *Create definition*, for every type but boolean; a list definition reads "select · several values". The space file (`export-graph.ts`, `vault-import.ts`) carries `multiple` when it is set.
- **Change type…** to and from a list. `preview_property_type_change`, `list_property_type_change_values` and `change_property_type` take `multiple` and a `ListSeparator` (`comma`, `semicolon` or none). One rule (`ConversionRule::convert`) serves preview, list and write: a text splits into items at the separator, or is one item; a list joins into a text or a URL with the separator; a one-item list becomes its item; a list converts to another item type when every item does. The dialog previews nothing until a separator is chosen, because splitting `Doe, Jane` at commas makes two people.
- **Don't fit.** Under a list key a value fits as a list whose items the write check takes; a list under a key of one value, or one value under a list key, doesn't. Remove, Convert (the replacement is read as a list), Move (a list only to a list key it fits) and Add to options (a multi-select's missing items) take lists. The frontend's `property-fit.ts`, the inline chip's mark and the page table's row read the items.
- **Editing.** `ListEditor` in `PropertyRowEditor`: one chip per item with a remove button, and an add control of the item type (text, number, date, the options not yet held, the page picker). The drawer and the page table send a list key there, not through `EditorSlot`, which the query table cell shares (PR 3). Removing the last item deletes the property; adding a list key from a definition opens a draft that its first item writes.
- **One line of text.** A list is `key:: a, "b, c", [[Page]]`: `splitListItems` / `joinListItems` in TypeScript, `property_list_items` / `write_property_list` in Rust. Typed in a block, Edit as Markdown and Duplicate read and write it; under a key of one value the line is one value as before.
- **Copies.** Duplicate (through its buffer), templates (`create_blocks_batch` carries `value_list`) and a key renamed from its chip carry a list. `set_property` resolves each item of a ref list as it resolves a single typed ref.
- **MCP and History.** The `set_property` and `batch` tools take `value_list`; the summary and the history read show the items. History's view shows a list op's items.

- **The lanes.** Three builders in parallel, each in its own tree: the backend with the mock and fixtures, the definitions and type-change UI, and the editing UI. They built to one written contract. ## Session 4197 — On Android the keyboard shrinks the layout viewport

Finished #6790 with the native fix #6797 named. With `enableEdgeToEdge()` the window no longer resizes for the IME and WebView ignores `interactive-widget`, so the keyboard shrank only the visual viewport: the page was a short window panned over the full-height layout, and the top of a long page needed a second swipe.

**Native.** `MainActivity.kt`'s inset listener pads the content frame's bottom by the larger of the navigation bar and the `ime()` inset, and zeroes `ime()` in the insets it forwards to the webview, so Chromium no longer shrinks the visual viewport by it. The webview, and with it the layout viewport, now ends at the keyboard's top. Compiled with Gradle's bundled Kotlin compiler against `android.jar` 36 and AndroidX core and activity, with a stub `TauriActivity`; no SDK in the container, so no APK, and no phone.

**Deleted, now dead.** `computeKeyboardInset` (`lib/keyboard-inset.ts`) and everything built on it: `useSoftKeyboardInset` and its two readers (the bottom `Sheet`'s lift and height cap, the phone toaster's keyboard offset), the pinned toolbar's `bottom` tracking, and `InPageFind`'s `computeViewportOffset` translate. Each reads `innerHeight - visualViewport.height`, which is 0 once the layout shrinks; desktop never had an on-screen keyboard and the app has no iOS build. Their unit tests went with them.

**Kept, reshaped.**

- `useScrollCaretAboveKeyboard` is now `useScrollIntoViewOnFocus`. Its focus-time `scrollIntoView` predates the keyboard work and still serves arrow-key and Enter navigation on desktop. The brief expected the browser's own focus scroll to keep the caret above the keyboard; the e2e lane showed it does not: after the viewport shrinks, Chromium leaves the focused block where it was (caret at 810 px on a 519 px screen) until the first keystroke. So the hook keeps a `resize` listener, which now asks the editor to scroll its caret into view.
- That exposed a second gap: the caret then sat under the toolbar pinned on the keyboard (toolbar top 462, caret bottom 501). Page mode already handled this with ProseMirror `scrollThreshold` / `scrollMargin` that add the toolbar's cover; the block editor now uses the same margins, through `pinnedToolbarCover`, moved from `PageModeEditor` to `pinned-toolbar.ts`.
- The quick-capture button's keyboard check (#6789) compared the two viewport heights, which are now equal. Deleting it alone would bring #6789 back (the button sitting on a form's Create button above the keyboard), so it now hides while a text field has focus. `e2e/page-mode-touch.spec.ts` asserted the button visible with the page title focused, a browser-only artefact (a phone raised the keyboard and hid it); that assertion now expects it hidden.

**Tests.** `e2e/phone-keyboard-pan.spec.ts` now models the keyboard as the viewport shrinking: the caret clears the toolbar after the keyboard opens and after typing wraps the line, the screen never pans, and swiping reaches the header. The toolbar and bottom-sheet specs shrink the viewport instead of stubbing `visualViewport`. Shown red: no resize listener (caret 777 vs toolbar 462), no toolbar margins (caret 514, both after opening and after typing), the old pan geometry (screen panned at 276 after the first swipe), the toolbar off the screen's foot, the keyboard as popover collision padding (cap 56), a toast below the foot, and the button ignoring focus. Unit tests for the hook, the button and the toolbar were falsified the same way; the first button test let a missing `focusout` listener survive and was changed to blur.

## Session 4195 — the copied agent config names the bridge by its path; minimum macOS and Windows declared (#6736, #6737)

Two packaging issues found while checking the README against the 0.23.0 artifacts, in one PR.

### What shipped

- **#6736.** `McpStatus` carries `bridge_command` and `bridge_args`, and *Copy Claude Desktop config* / *Copy Claude Code command* run them instead of a bare `agaric-mcp`. `mcp::bridge_invocation` resolves the bridge beside `current_exe()`: tauri-bundler installs every cargo `[[bin]]` in one folder (`/usr/bin`, `Agaric.app/Contents/MacOS`, the Windows install folder, `usr/bin` in an AppImage), which is why there is no `externalBin` in `tauri.conf.json`. An AppImage's mount path changes every launch, so there the config runs `$APPIMAGE agaric-mcp …`, and `main` hands an `agaric-mcp` first argument over to the bridge beside it (`exec_bridge_if_asked`, Linux only). The two copy buttons are disabled while the status has not loaded. README § Using Agaric with MCP clients loses its "put its full path in the config's `command`" sentence.
- **#6737.** `bundle.macOS.minimumSystemVersion` is `13.0`. README's Install table names macOS 13 Ventura and Windows 10 or 11; docs/BUILD.md § Minimum OS versions gives the evidence.

### Decisions and traps

- **Tauri already wrote `LSMinimumSystemVersion` 10.13** when nothing was set (its config default, which also sets `MACOSX_DEPLOYMENT_TARGET`), so #6737's "absence" was a floor of 10.13 nobody had checked.
- **The macOS floor is WebKit's.** Read from a production `vite build`: the app's CSS (Tailwind 4) and regex lookbehind need Safari 16.4; pdf.js 6 touches the `Iterator` global at module load and calls `Promise.withResolvers`, which needs Safari 18.4. Safari 18 runs on macOS 13 and later, so 13 is the oldest system where the whole app can work. The Rust targets allow older (10.12 Intel, 11 Apple Silicon).
- **Windows has no install-time gate.** Tauri's NSIS and WiX templates take no OS version; the floor is Rust's tier-1 MSVC target (Windows 10) and WebView2's support list. No build number was pinned, since nothing evidenced one.
- **Quoting stays double quotes** for both paths in the Claude Code command: bash, zsh, PowerShell and Command Prompt read them the same way for a path with spaces. Git Bash would turn the pipe path's leading `\\` into `\`, as it did before this change.
- **On macOS a config copied while the app runs from the disk image, or translocated from Downloads, points at a path that goes away.** The README says to copy it once Agaric runs from Applications.

### Existing assertions edited

- `e2e/mcp-agents.spec.ts` and `AgentList.test.tsx` expected the copied command and config to run a bare `agaric-mcp`; they now expect the bridge path the status reports.
- `agent-config.test.ts` took a socket path; it now takes what `get_mcp_status` reports, one case per desktop package.
- `e2e-tauri/mcp-agent-token.e2e.ts` spawned a hard-coded `target/debug/agaric-mcp`; it now spawns `bridge_command` with `bridge_args`, as a pasted config does.

### What ran

Rust: the new `bridge_*` and `status_*` tests (`cargo nextest run --workspace`), clippy over the workspace. vitest: `agent-config.test.ts`, `AgentList.test.tsx`, `AgentAccessTab.test.tsx`, `tauri-mock.test.ts`, `conformance-coverage.test.ts`. Playwright: `e2e/mcp-agents.spec.ts`. Each new vitest and Rust test shown red against the old behaviour or a mutation of the new code. The real-backend spec was not run here (no `tauri-driver` or `webkit2gtk-driver` in the container, and too little disk to build them); CI's `e2e-tauri-gate` runs it. Nothing ran on macOS, Windows or a built AppImage; those checks are lines on #6514 and #6515.

## Session 4194 — An Obsidian `%%comment%%` block imports as a comment callout

Built #6751 alone, as PR A of a batch whose PR B is #6749 and #6746.

**What shipped.** `comment_as_callout` (`agaric-engine/src/import.rs`) reads a block that is one `%%…%%` comment, on one line or across lines, as a `> [!comment]` callout of its text. It runs in `normalize_foreign_forms`, so import, paste, *Edit as Markdown* and every MCP content write read a comment alike. The callout needs no frontend change: a type outside the five styles already renders as a note, the quietest. Import counts the comments left inside sentences in one warning (`inline_comment_count`).

**Decisions the issue left to the PR.**

- A comment inside a sentence stays text with its markers, counted, as the issue suggested.
- Export writes the callout as `> [!comment]`, not back as `%%…%%` as the issue suggested. Between `%%` markers a comment's lines are read as Markdown again (a blank line ends the block, a `- ` line is a list item, a `key:: value` line a property), so `%%` would not read back as the same block in general; quoted, every line does. A re-import of the export changes nothing; Obsidian shows the comment as a callout.
- A comment pasted into a block's text joins it as the comment (`callout_as_comment` in `PasteSplice::join`): the normalizer runs after `inline_joined_blocks`, so without it a callout landed mid-sentence.
- A comment holding a blank line reads as its paragraphs, none a whole comment, so it stays text; the normalizer works per block, and merging blocks would break *Edit as Markdown*'s line ids.

**Tests.** Engine unit tests (`tests_comment_callout`); command tests for import with the export re-import, paste, paste into text and an *Edit as Markdown* save, each shown red before the wiring; the join write-back and the warning each falsified. `e2e-tauri/import-obsidian-comment.e2e.ts` covers the import in the real-backend lane, since the mock models no comment.

## Session 4193 — The `space` stamp tests own their clock

Two tests failed once each on `main`, on commits that do not touch them.

### `import_markdown_link_target_is_last_edited_at_its_space_stamp` (run 43632206197)

A test race, not a product bug. The three `*_is_last_edited_at_its_space_stamp` tests check that a page created in a space is last edited at its `space` op, not at its create. Both ops take their `created_at` from the wall clock (`agaric_store::db::now_ms`). The test could only tell the two apart when they fell in different milliseconds, so it made ten pages and hoped at least one would straddle a tick. On a fast runner none did, and its own guard failed.

Shown deterministically: with `now_ms` frozen at a constant, the old tests fail 3/3 with CI's message. Unfrozen, 1 run in 5 failed locally.

#### What shipped

- `agaric_store::db::distinct_now_ms()`, a `test-util` seam: once called, `now_ms` never hands out the same millisecond twice and stays at or ahead of the wall clock. It is process-global, which is fine because nextest runs each test in its own process.
- The three tests call it, create one page each, and assert the page's `space` op is newer than its create and that `last_edited_ms` equals it. The ten-page hope is gone.

They pass with `now_ms` frozen. They go red on `last edited at its newest op` when the three commands drop their `enqueue_without_dispatch(space_op…)`, which leaves the page at its create's stamp.

### `advanced-query-saved-views.spec.ts:57` (run 43630056291), not reproduced

The failed run's `error-context.md` shows Advanced Query with the Rename button focused and no dialog. Both toasts ("Loaded view", "Saved view") are still up 15 s after the click. Locally they expire within 4 s, so in CI sonner had paused them: the pointer was over the toast stack or pressing it. Two readings fit:

- The press hit Rename (which is why it holds focus) and the release hit a toast, so no `click` fired. Playwright checks only the first pointer event of a click against its target, so it reported success.
- The dialog opened and something closed it, and Radix gave focus back to Rename.

Not reproduced in:

- 30 plain runs
- 20 runs at 6x CPU throttling
- 8 runs with sonner's transitions stretched to 3 s
- 100 runs on oversubscribed workers while clippy built

Instrumented runs pinned down the geometry at 1280x720:

- Rename's centre sits at (1140, 564), inside the toast column (x 900–1256).
- Collapsed toasts never come above y 600: entering, lifting, and both removals.
- Only an expanded stack reaches the button. The older toast's gap bridge spans y 560–575, and once the stack is expanded the pointer on Rename keeps it expanded.

Nothing found expands the stack while the pointer travels from Load to Rename. No fix is guessed.

### Suites run

- `cargo nextest run --workspace -E 'test(/is_last_edited_at_its_space_stamp/)'`: normal, frozen clock, and the two mutations above.
- `cargo clippy --workspace --all-targets -- -D warnings`.

## Session 4192 — The top of a long page with the keyboard up: a spec, and why no fix beyond #6792

#6790: on Android, with the keyboard up after typing at the end of a long page, the top of the page could not be scrolled back into view. #6792 had removed the visual viewport `scroll` listener of `useScrollCaretAboveKeyboard`, but it had not been run on a phone. This session was to decide whether #6792 fixes the issue, and to remove the condition behind it: the keyboard shrinks only the visual viewport, so the screen is a panned window over a full-height layout.

## Session 4180b — Writers take turns at the write lock

The first of two maintainer decisions left open by #6766 (#6567): a fair queue for the writer, by a gate in `begin_immediate_logged`. The second, SQLite's busy code as `pool_busy`, is session 4179 (#6784).

Session 4179 called this one session 4178. That was the number assigned to it; 4179 merged first and put 4178 below the numbering guard's floor, so this log is 4180.

### What was wrong

The write pool has two connections and SQLite gives its write lock to whichever of them polls first. A writer waiting on the lock sleeps between polls, up to 100 ms at a time, so a writer that begins again the moment it commits, or one that takes the connection a commit just freed, gets there first every time. The waiting writer gave up at the 5 s busy timeout. #6766 saw the background consumer starved this way by back-to-back batch commands.

### What shipped

- **`begin_immediate_logged` queues.** It waits for a turn on a fair async mutex before it takes a connection, and returns a `WriteTx`: the transaction and the turn. The turn ends when the transaction commits, rolls back or is dropped. There is one queue per database file (`write_turns`), found from the pool's connect options, so the function's arguments did not change and a second pool on the same file waits in the same line.
- **`WriteTx` derefs to `sqlx::Transaction`**, as `CommandTx` does. `&mut tx` still passes to every `*_in_tx` helper; an executor use is `&mut **tx` where it was `&mut *tx`. That, and the type's name where a transaction is stored or passed by value (`CommandTx`, `commit_with_deltas`, the sync projection's begin and commit), are the whole caller diff.
- **Five production transactions that opened with `pool.begin_with("BEGIN IMMEDIATE")` now open through the helper:** the three `peer_refs` stamps at the end of a sync session (`session_state_machine.rs`), the catch-up stamp (`snapshot_transfer.rs`) and the boot draft write-back (`draft_recovery.rs`). So does the test-only `append_local_op_at`.

### The trace

**Write transactions not opened through the helper.** Besides the six above, the four boot recoveries in `src/db/recovery.rs` open a deferred `pool.begin()` and write. They run inside `init_pools`, before the pool is handed to anything else, so there is no other writer to queue behind. Left as they are. Every other `pool.begin()` in production only reads.

**Single statements run on the pool outside a transaction are not in the queue.** There are many, across all four crates. The ones on a hot path: `save_draft` (typing autosave), the materializer retry queue's rows, the FTS removals, `derivations::record`, the `SetBlockPageId` space stamp, `record_page_open`, the MCP `stamp_last_used`, and the apply-cursor advance. Each holds the lock for one statement and takes it by polling, as before, so a run of queued writers handing the lock to each other can still starve one of them to the busy timeout. Left, and reported in the PR as a decision.

**Holding one write transaction while starting another.** None found, in production or tests, in any of: the same task nesting a second begin; a transaction held across a materializer flush or settle, a blocking queue send or a joined task; an async lock taken in both orders. Things that depend on how the queue is built, and hold:

- The turn is taken before the connection. The history commands read on the pool's second connection while they hold their transaction; a queued writer holding that connection would have made the read wait out the pool's acquire timeout.
- `CommandTx::begin_immediate` can fail its space guard after the transaction opened. The turn goes with the dropped transaction; `space_guard_refuses_inside_the_write_transaction_5402` opens a second `CommandTx` straight after the refusal and would hang otherwise.
- `save_all_engines` holds its own process-wide mutex across its write transaction; no caller holds a write transaction when it calls in.

### Traps

- The wait for a turn has no timeout. A nesting the trace missed would hang where it used to fail busy after 5 s. A bound on the wait was left out on purpose: `tokio::time::timeout` under a paused test clock fires as soon as the holder is waiting on SQLite's thread.
- A dropped `sqlx::Transaction` rolls back on SQLite's worker thread, after the drop returns. The next writer's `BEGIN IMMEDIATE` can find the lock still held for a moment and polls for it.
- Tests that hold the lock so a contender fails busy take it with `pool.begin_with`, outside the queue. One that held it through the helper would make its contender wait instead.

### Edited test values

`derivations::tests::GOLDEN` hashes the source of each derivation rule. The `&mut **tx` rewrite changed the hashed text of `PageLink` and none of its output, so its golden hash is new and its version is not, as that test's message directs: no vault rebuilds for it.

### Suites run

`cargo nextest run --workspace` in two halves, `cargo test --doc --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, and `scripts/check-raw-tx.mjs` over the tree. Both new tests were shown red by one mutation, the helper taking its turn from a fresh mutex: the order test served `[1, 2, 3, 4, 5, 0]`, and the starved writer was refused with SQLite's busy code at the test's 200 ms busy timeout.

## Session 4179 — SQLite's busy code reaches the frontend as `pool_busy`

The second of two maintainer decisions left open by #6766 (#6567). The first, a fair queue for the writer, is session 4178 and its own PR.

### What was wrong

`docs/architecture/operations.md` said a command that cannot get the write lock within the 5 s `busy_timeout` fails as `pool_busy` and is retried by `retryOnPoolBusy`. That was true of sqlx's pool timeout only. SQLite's own `SQLITE_BUSY` came through `From<sqlx::Error>` as `AppError::Database`, which `sanitize_internal_error` collapses to `internal`, so the frontend showed a failure and retried nothing.

### What shipped

`From<sqlx::Error>` routes a database error whose primary result code is `SQLITE_BUSY` to `AppError::PoolTimedOut`. The primary code is `extended & 0xFF`, so `SQLITE_BUSY_SNAPSHOT` and the other extended busy codes go the same way. `SQLITE_LOCKED` stays a `Database` error. The parse of the primary code, written twice before, is one function, `sqlite_primary_code`.

### What the kind change touches, as checked

- **Rust.** `AppError::is_write_contention` already answered yes for both shapes, so the materializer consumer and `maintenance.rs` behave as before. `sync_protocol/operations.rs` treats `Database` and `PoolTimedOut` alike as transient. `sanitize_internal_error` passes `PoolTimedOut` through, which is the point. No Rust code matches on the busy message text.
- **Frontend.** `retryOnPoolBusy` is the one consumer that changes behaviour: it now re-invokes a command refused at the lock. `categorize-history-error.ts` files `pool_busy` and `internal` in the same bucket, and `useDraftAutosave` reads the kind only to label a log line.
- **Mock and conformance fixtures.** Neither produces `pool_busy`, `database` or `internal`; nothing to change.

### Is the retry safe

A re-invoke is safe when the failed attempt wrote nothing. Every command behind `retryOnPoolBusy` was read from begin to return: each commits as its last fallible step, and `CommandTx::commit_and_dispatch` cannot fail after SQLite committed. One exception, which predates this change: `create_block` for a page (and for a tag that already exists) reads the row back from the write pool after the commit, and a pool timeout there already surfaced as `pool_busy`. The retry finds the page the first attempt created and returns it, so there is no duplicate, but it appends no op and the creation never reaches the undo stack. A plain read in WAL mode does not normally see `SQLITE_BUSY`, so this change does not make that window wider in practice. Left as found.

### Edited assertion

`purge_blocks_by_ids_inner_surfaces_unwrapped_contention_at_the_boundary_4018` (`src/maintenance.rs`) drove a real `SQLITE_BUSY` through a command and asserted `AppError::Database(sqlx::Error::Database(_))`. That was the behaviour this decision changes; it now asserts `AppError::PoolTimedOut`. Its second assertion, that `is_write_contention` accepts the error, is unchanged.

The edited assertion was shown red by mutating the new match arm out: it failed with `Database(Database(SqliteError { code: 5, .. }))` where it expects `PoolTimedOut`.

## Session 4177 — window 5: a delete's, restore's or purge's cascade is written in the op's transaction

`Refs #6521`. Option 1 of the stage B comment: the engine half of a cascade moves into the transaction of the op that caused it. Since #6777 boot builds each engine from its saved rows and replays no op, so a kill between an op's commit and its cascade lost the cascade for good: a restore left SQL live and the engine deleted, and peers never saw it; a purge left the blocks in the engine.

### The paths that had the gap

Every one wrote its cascade through `saving_fan_out`, a transaction of its own after the op's commit.

1. **The materializer's single-op apply** (`apply_op_with_mode`: `ApplyOp` for draft recovery and the retry queue, `ReplayApplyOp`): a delete's cohort, a restore's cohort and ancestor chain, the cohort a `MoveBlock`'s tail un-swept.
2. **The materializer's batch apply** (`apply_batch`: `BatchApplyOps`, `ReplayApplyOps`): the same three, after the whole batch had committed.
3. **The delete commands.** `delete_block_inner` and what shares `delete_block_in_tx` (the page source save, MCP `batch`, merge-with-previous, the name-collision repair), the content repairs and the boot empty-block sweep: the descendants. `delete_blocks_by_ids_inner`: every engine write.
4. **The restore commands** (`restore_block_inner`, `restore_blocks_by_ids_inner`, `restore_all_deleted_inner`): every engine write.
5. **The purge commands** (`purge_block_inner`, `purge_blocks_by_ids_inner`, `purge_all_deleted_inner`): every engine write.

Undo and redo already wrote their cascade in their transaction (`drive_reverse_engine`). A sync import applies no op: it projects engine state, and a peer's cascade arrives as that state.

### What shipped

- **The kernel writes the cascade.** `apply_op_tx_with_mode` calls `dispatch_cohorts` after the op's projection, so paths 1 and 2 and every delete that routes through `apply_op_projected` get it with no caller involved. The fan-out helpers lost their pool and their transaction: `engine_apply` records into the rollback log the caller's transaction armed, so the op's `loro_doc_delta` row holds the cascade and a rollback rewinds it.
- **The commands that do not route through the kernel** (batch delete, the three restores, the three purges) call the same helpers before `commit_and_dispatch`. What stays after the commit is derived SQL: the link and FTS repair of the cohort.
- **Removed:** `saving_fan_out`; `engine_apply`'s log parameter (every caller now passes the transaction's); `repair::fan_out_deletes`; `SweptBlock::effects` and `DeleteInTx::op_record`, which only the post-commit fan-out read. `dispatch_deletes` is `remove_deleted_fts`, which is all it still does.
- **`split_after_cascades` is gone.** Boot replay cut a chunk after each delete and restore because an op behind one in the same transaction saw the cohort's old state. It now sees the new one. `delete_then_purge_meters_no_fallback_5418` and `create_after_restore_matches_per_op_oracle_5418` cover this: with the split removed they go red when a batch mirrors its cohorts after its last op.
- **`registry.rs`** imports `AtomicBool` with the sibling atomics (review note on #6777).

`delta::write_engines` keeps one caller: the tombstones a sync import's projection swept (`fan_out_swept_tombstones`). A kill there leaves blocks deleted in SQL and live in the engine, which `mirror_sql_tombstones_onto_engine` repairs before the next export. Moving it into the projection transaction needs a rewind on every failure path after an import the transaction does not own (item C of stage A's notes), so it stays and is on the issue as a decision.

### Tests

`tests/commands/engine_delta_tests.rs`, twelve new, each red on the unfixed code. The fault is a trigger on `loro_doc_delta` that lets a set number of further rows in.

- One more row allowed, where the op's own transaction already wrote the engine: `delete_block_inner`, and a delete then a restore the materializer applies alone and as a batch. Red was the oracle (`settle`): the cascade's row was refused and the engine held writes no row did.
- No row allowed, where the cascade is the transaction's only engine write: the batch delete, each restore, each purge, and a `MoveBlock` out of a deleted parent applied alone and as a batch. Red was the command returning `Ok` with its op committed. Green asserts the op is not in the log and SQL and the engine are as they were.

### Cost of the largest cohort

The cascade's engine writes were already made under the write lock, in the transaction after the op's. They are now in the op's, so the total is unchanged and the longest single hold grows by them. `durability_cost_tests` has a new case, the cascade of a delete over every block of a space through `dispatch_delete_descendants`, each sample on a newly rehydrated engine. One release run in this session's container (4 cores, load about 1), median and range of 5:

| Cohort | Engine writes | Delta and commit | Row |
|---|---|---|---|
| 10,000 blocks | 91 to 112 ms [83 to 114] | 5.8 to 5.9 ms [4.3 to 6.9] | 100 KB |
| 100,000 blocks | 945 to 1014 ms [881 to 1170] | 39 to 44 ms [39 to 56] | 1.04 MB |

Each cell spans the two seedings the harness runs (no edits, and ten edits a block). That is about 10 µs a block. The write pool's `busy_timeout` is 5 s, and the SQL half of the same cascade was in the op's transaction before; it is not in this harness.

## Session 4175 — Nested tags: a tag filter finds the tags named under it, and the Tags view nests them

Set out to build #6760: someone importing an Obsidian vault with `#projects/web` gets nothing from a filter on `projects`, and a flat Tags view.

### What shipped

- **A `Tag` leaf matches the tag and every live tag of its space named under it.** `FilterPrimitive::Tag` compiles to `tag_id IN (TAG_AND_NESTED_IDS_SQL)` in `PagesProjection` and `SearchProjection` (`filters/primitive.rs`), so search (`tag:#projects`, `SearchFilter.tag_ids`), query blocks and the query builder (`run_advanced_query`), the Pages view's tag filter and the MCP `search` tool all nest. The hierarchy is read from `blocks.content` at query time (`substr(name, 1, length(parent) + 1) = parent || '/'`, `COLLATE NOCASE`); nothing is stored. `under:` (`tags_match_inline_and_inherited`) widens the same id set over attached, inline and inherited rows.
- **A name no tag holds stands for the tags under it.** A vault that only ever wrote `#projects/web` has no `projects` tag. The search box then sends the nested tags' ids as one group of the new `SearchFilter.tag_any_of` (one tag of every group, AND-ed with `tag_ids`), and a query block compiles the name to an `Or` of `Tag` leaves. The builder opens such a text as text only: saving the `Or` would freeze it to today's tags.
- **The Tags view nests.** `TagList` feeds the tags through `buildPageTree`, the Pages view's namespace tree, and renders the rows depth first: a tag shows its last name segment, indented, with `aria-level`; a name no tag holds is a plain row.
- The mock mirrors both (`tagAndNestedIds`, `tagAnyOf`), pinned by `conformance/fixtures/query_nested_tags.json`.

### Decisions

- **A bare `tag:projects` nests** (the orchestrator's provisional call, the maintainer's to overrule on the PR). No spelling for the exact tag fell out of the existing syntax, so there is none. `TagOrRef`, the leaf a tag's own page lists by, still matches the one tag, so a tag's page and its usage count are unchanged. The Tags view's boolean query (`TagExpr`) and backlink filters are unchanged too.
- **Inherited tags are separate from nesting.** `block_tag_inherited` is not written for a parent name: a block under one tagged `projects/web` inherits `projects/web` only, and `under:#projects` finds it because that tag's id is in the nested set.
- **One bind, read from `blocks`.** A first cut bound the id twice (`SELECT ? UNION ALL …`), which renumbered every placeholder in the assembly goldens. The tag row is always in `blocks` (`block_tags.tag_id` is a foreign key), so `n.id = p.id OR (…)` needs one bind; SQLite plans it as a multi-index OR over the primary key and `idx_blocks_space_type`. `tags_cache` was not used: it lags a tag just created.

## Session 4165 — boot builds each engine from its saved rows (#6521, stage B)

`Refs #6521`. Stage B of the plan approved on the issue: boot builds each space's engine from its `loro_doc_state` snapshot and the `loro_doc_delta` rows stage A (session 4132) saves with every engine write, and no longer replays the op log into engines. The design note went on the issue before any code (comment 6872629807); this log records what the build changed in it.

### What shipped

- **`rehydrate_registry`** (`agaric-engine/src/loro/snapshot.rs`) builds an engine from its snapshot and its rows through `LoroEngine::import_saved_rows`: the snapshot, then the rows as one `import_batch`. A space with rows and no snapshot is built from the rows alone. A space built from rows is marked dirty.
- **`recover_at_boot`** (`agaric-sync/src/recovery/boot.rs`) skips the cursor heal and the replay, and dispatches the index fan-out (#3298) for the local ops above the cursor (`replay::fan_out_ops_past_the_cursor`). The inbox replay, the drafts and the backfills are as they were.
- **The marker** `loro.boots_from_saved_rows`, one `app_settings` row, says the saved rows hold every engine write that committed. Without it boot is the older one, unchanged: `delta::start_replay_boot` deletes the marker and every row in one transaction, the engines come from the snapshots, the heal and the replay run. `recover_at_boot` sets it at its end when the replay did not abort, every draft's op reached the engine, and no op is parked in `materializer_retry_queue`.
- **A snapshot pass commits nothing when an engine was rewound since its collect** (`LoroEngineRegistry::no_rewind_since`, checked in `write_pass`). Each rollback checkpoint counts as open until it is dropped; the pass waits, inside its write transaction, for the count to reach zero.
- **Disaster recovery** (`db/recovery.rs::reproject_blocks_from_engine`) clears the marker when it rebuilds SQL from the snapshots.

No schema change. The marker is a row in a table that exists.

### Decisions, and what the build added to the design note

- **Why a marker.** A vault from a build before stage A and one from stage A show the same cursor and stamps; only the first lacks rows for its ops past the stamp. Inferring it from "no rows, and ops past the stamp" reads a replay boot killed part-way as finished.
- **Rows that leave changes pending send boot through the replay**, they do not stop it. The replay loses what the older boot lost and nothing more, because the pass still stamps its rows as before. A row that will not import does stop boot, as an unreadable snapshot does.
- **Found while building: draft recovery writes in two steps.** A draft's op and SQL row commit in one transaction, and its engine apply runs later through the foreground queue. A kill in between left an op in the log that only the replay would apply. So the marker is cleared before a draft is written back and set again once the queue has drained. A draft that fails before its op commits does not hold the marker back: an over-long draft fails that way at every boot for as long as its row stays. Nothing else in production appends an op and applies it later.
- **Found while building: a pass moves the stamp of rows it does not write.** An engine built from a row plus deltas is clean after `install_engine`, so the next pass would have moved its stamp over ops only a delta held, and a later replay boot would skip them. Hence the dirty mark.
- **Found while building: an op parked in the retry queue is in no engine.** The older boot also reached it through the heal's rewind. While one is parked the marker stays absent.
- **The pass's rewind check counts open checkpoints instead of ordering on the lock release**, because the materializer's apply paths drop their transaction before they rewind, and a failed commit releases the lock before anyone knows it failed.

### The independent read

A second model read the diff before the last full run, without building. Acted on:

- **Rows were deleted before the snapshots were known to import.** With rows that leave changes pending in one space and an unreadable snapshot in another, boot discarded every row and then stopped. The snapshots are now imported first.
- **A rollback can rewind an engine past a sync import** (item C of stage A's notes, with a consequence it did not list). The import writes the engine outside the write lock and saves its row later. If the import appended ops of this device's own (the kept-text moves of #6561, the sibling-order migration), those ops sit on top of the rolled-back write; the rewind drops them, their row is saved all the same, and the next commits reuse the op ids they were built on. A boot from those rows would apply them to another history. The rewind now notes when it dropped another peer's ops, and the next commit clears the marker, so that boot replays.
- A misplaced doc comment, a second read of the drafts, and a branch that could not be taken.

Confirmed and not fixed here: the cascade window below. The read's judgement is that it will be met in practice, more often than the design note allowed.

### Traps

- `LoroDoc::import_batch` reports what is pending for the whole doc only when given two or more blobs; with one it returns that blob's own status. Both are right here, since the snapshot leaves nothing pending.
- A row can depend on a later row: a sync import writes the engine before its projection saves its delta, and a local write made on top can commit first. Judging "pending" row by row calls that a gap (`a_row_that_depends_on_a_later_row_builds_the_engine_6521`).
- The two-device harness (`spaces/session_save_tests.rs`) never booted a device before using it, so every `kill_and_boot` was a first boot and went through the replay. It now boots each device as the app does, and each kill-and-boot scenario runs under both boots.
- Comparing the two boots by engine version is wrong: the replay mints op ids of its own. The oracle tests compare what the engines hold (every block's text, place, tombstone, tags, properties) and SQL.
- The replay boot ranks again every sibling group it touched, where a session leaves a gap in SQL `position` after a purge. The oracle's SQL comparison leaves the ranks out; the saved-rows boot's SQL is compared whole.
- Purging a whole space through `purge_block_inner` leaves that space's engine, snapshot and rows in place; only the apply path (`apply_purge_block_via_loro`) evicts them. The replay boot happened to drop the engine when no pass had saved it. Not changed here.

- `a_pass_that_saved_a_write_which_then_rolled_back_is_saved_over_6521`, renamed `a_pass_writes_nothing_when_a_write_it_exported_rolled_back_6521`: it asserted that a pass saved the uncommitted write and the next pass saved over it. A pass now writes nothing in that case.

## Session 4155 — An imported restore un-deleted blocks the restoring device kept in its Trash

Set out to test the three paths session 4150 read as clearing `deleted_at` without a link reindex, and to fix any that was real with the cohort link reindex. One was real, and the missing link rows were a symptom: the block should not have come back at all.

### Sync-imported restore: real, fixed at the cause

Device A trashes block D, then D's parent X, which takes X's other child Y along. A restores D. The local restore brings X back as D's ancestor and leaves the rest of X's cohort, Y, in the Trash. Device B, which imported the two deletes before the restore, imports X's cleared delete mark and clears X's whole cohort in SQL (`reproject_block_deleted_at_from_engine`, the restore arm). Y's own mark did not change, so Y is not in the import's changed set and gets neither the pass's re-stamp nor the per-block link and FTS tasks. On B, Y was live with no `block_links` and no `fts_blocks` row, while A had it in the Trash and B's own doc still marked it deleted. No concurrency is needed, only the two syncs in that order.

The fix is in the import's soft-delete pass (`project_pass_c`): the restore arm now returns the cohort it cleared, and the pass re-reads each member's own mark from the doc and re-projects the ones that carry one. Y stays in B's Trash, as on A. The recovery reprojection visits every block, so by reading it already left Y there. A member with no mark of its own stays restored, as before.

No link reindex was added for the members that do stay restored. They come back with the rows they had: an import drops a block's rows only when that block's own doc state changed while it was trashed, and no route was found that does that and then restores it without its mark changing.

The first scenario tried was the one session 4150 guessed: B moves a block under X while A, unaware, trashes and restores X. It does not fail. In the run, every import from A reported that block as changed while A had not seen B's move, so the pass re-stamped it from its own mark.

### MoveBlock un-sweep: no production route

`unsweep_inherited_cohort_after_move` clears rows only for a move whose subject carries an inherited tombstone. Nothing in production applies such a move:

- a foreign device's ops are audit rows, never applied; sync arrives as a doc import. `Materializer::dispatch_op` and `MaterializeTask::BatchApplyOps` have no caller outside tests;
- every local `MoveBlock` author checks the subject is live: `move_block_inner`, the undo path (`reparent_active_block`), and the orphan and journal-duplicate repairs select live blocks only;
- boot replay re-applies local moves through the engine arm, which un-sweeps nothing. Its SQL-only fallback (a block with no space or absent from its engine) can un-sweep, but only for a block a later op in the same replay trashes again: local moves are written on live blocks, so a tombstone met at replay comes from a delete further down the log.

No code, no test.

### Recovery reprojection: nothing specific to the cleared tombstones

`reproject_blocks_from_engine` runs when the `blocks` table was rebuilt from nothing, or to retry such a boot. It then rebuilds `fts_blocks` in full, from page titles and not through `block_links`. `db/recovery.rs` does not touch `block_links`; the vault-wide derive is `backfill_block_links` at boot, gated by a marker. So after a rebuild every block lacks its link rows until that pass runs, restored or not, and a vault whose marker is already set gets none. That needs the `blocks` table to vanish on a current vault. The cause the code names is a table rebuild cut short in migrations 0073 to 0089, all older than the marker. Left alone; if it is wanted, `rederive_block_links` in `rebuild_caches_after_engine_reproject` is the place.

Three comments said the edit projection filters `deleted_at IS NULL`. `project_edit_block_to_sql` is unguarded on purpose (#2909); they now say so.

## Session 4145 — a math fence holding a quoted `$$` line stays a fence

`agaric-engine import::parse_proptest::normalizing_is_idempotent` drew a real counterexample in another session's pre-push run, on code that session had not touched. ### Cause

`math_fences_as_blocks` writes a closed ```` ```math ```` fence as a `$$` block unless the fence holds a line that is `$$`, because that line would pair with the `$$` it writes. The check now reads the line through `unquoted`, as `literal_block` does. The fence-opener half of the same check was left alone: a quoted fence line inside a `$$` block opens nothing on either pass, so it has no failure to fix.

### What a user would have seen

A Logseq or Obsidian file with a `math` fence holding a quoted `$$` line imported with that fence turned into a broken `$$` block, and text between it and the next `$$` line kept as literal instead of having its `^^highlight^^` and `\[math\]` read. ## Session 4140 — Android's link-preview client trusts bundled roots, so the platform verifier is never asked

#6763 said that on Android an `https` link preview may abort the app: reqwest's certificate verifier there is `rustls-platform-verifier`, which panics unless the app has given it a JVM handle, and release builds abort on a panic. The session set out to check that trail against the resolved dependency graph and the crates' sources, then fix whatever was exposed. Nothing here was run on a device.

### The trail holds

Read from `cargo tree --workspace --target aarch64-linux-android -e features -i rustls-platform-verifier` and the sources in `~/.cargo/registry`:

- `rustls-platform-verifier` has one dependent in the Android graph, `reqwest`. Both of reqwest's public rustls features (`rustls`, `rustls-no-provider`) pull it; reqwest 0.13 has no feature that selects bundled roots instead.
- In `ClientBuilder::build`'s rustls branch reqwest installs `rustls_platform_verifier::Verifier::new` only when verification is on and `tls_certs_only` was not called. `tls_certs_only` builds a plain `RootCertStore` verifier, and a client given a whole `ClientConfig` (`tls_backend_preconfigured`) skips the branch.
- On Android `Verifier::new` succeeds and the first `verify_server_cert` reaches `android::global()`, which `expect`s a handle set only by the crate's five `init_*` functions. Nothing in this repo or in the registry sources of the graph (tauri, wry, tao, reqwest, iroh) calls one, and the Gradle project does not carry the crate's Kotlin component.

### Which clients are exposed

| Client | On Android | Exposed |
| --- | --- | --- |
| `link_metadata::shared_client` (agaric-store) | default verifier, reached by a paste, a hover or the link popover | **yes** |
| OTLP exporter (`agaric-observability`) | same default verifier, but built only when `AGARIC_OTEL` and an `AGARIC_OTEL_ENDPOINT` are in the process environment, and verifies only for an `https://` loopback collector | no: an app started by the launcher has neither variable |
| iroh (`net_report`, pkarr), `n0-dns-resolver` DoH | `tls_backend_preconfigured` with their own `ClientConfig` over `webpki-roots` | no |
| iroh-relay client | `tokio-websockets` over iroh's `CaTlsConfig`, whose default is `webpki-roots`; its `platform-verifier` feature is off | no |
| iroh QUIC (`noq`) | its own verifier for the peer's key | no |
| tauri's `reqwest::ClientBuilder` | compiled only under `cfg(all(dev, mobile))`, the dev-server proxy | no, not in an APK that ships |
| the release check | made in Kotlin (#6726) | no |
| `tauri-plugin-updater`, `tokio-tungstenite`, `rustls-native-certs` | not in the Android graph | no |

### Fix

Option (a) of the issue: on Android `shared_client` calls `with_bundled_roots`, which is `tls_certs_only` over `webpki-root-certs` (the Mozilla set as DER, a target dependency for Android only). No JNI, no Gradle change. The other option, initialising the verifier in `jni_on_load` and adding its Kotlin component, follows the phone's trust store but needs a patched generated Gradle project, an R8 keep rule and handles crossing from `jni 0.22` to the verifier's `jni 0.21`, none of which CI can run.

The trade: a CA the user installed on the phone is not trusted, so such a link stays a plain link. A failed fetch was already an `AppError` the UI handles.

`rustls-platform-verifier` stays in the Android graph, because reqwest cannot be built without it; the after-tree is identical to the before-tree. What changed is that the exposed client no longer installs it. `webpki-root-certs` appears under `agaric-store` for the Android target and under no desktop target's normal edges.

### Guard

`bundled_roots_client_never_consults_the_platform_trust_store` (Linux hosts): `SSL_CERT_FILE` makes the platform store hold one throwaway certificate, served by a local TLS stub. The negative control shows reqwest's default verifier trusts the stub; the guard shows a `with_bundled_roots` client refuses it as an unknown issuer. A reqwest update that routes `tls_certs_only` through the platform verifier reddens it. Falsified by swapping `tls_certs_only` for `tls_certs_merge`: red on the guard's `expect_err`.

Not covered on the host: that `shared_client` applies `with_bundled_roots` under `cfg(target_os = "android")`, and that a real site's chain verifies against the bundle. With the `cfg` forced on, the 90 `link_metadata` lib tests pass on Linux; the phone check is a line on #6513.

- `rcgen` (dev-only, for the throwaway certificate) adds 14 packages to `Cargo.lock`, most through a weak `x509-parser?` feature that is never built, and re-resolves `quinn-udp`'s `windows-sys` edge to a version already in the lock. A committed key would have needed a `detect-private-key` exclusion instead.

## Session 4132 — a `loro_doc_delta` row for every engine write (#6521, stage A)

`Refs #6521`. Stage A of option (2) from the spike (session 4096): every write to a space's Loro engine saves, in a transaction, the update it added, in the one table the maintainer approved. Boot is unchanged apart from one delete, nothing reads the rows in production, and a test oracle rebuilds every engine from its saved rows.

### What shipped

Migration 0132 creates `loro_doc_delta (id AUTOINCREMENT, space_id, bytes) STRICT`, with no index: its readers take every row in `id` order or delete one space's rows during a pass.

Where each engine write saves its row (`agaric-engine/src/loro/delta.rs`):

- **A transaction that arms the rollback log.** `RevertLog` now records the engine's version vector beside the frontier at first touch, and `commit_with_deltas` exports each engine's update since it and inserts it before the commit. `CommandTx` (every local command, undo and redo, batch ops, bootstrap, the boot repairs and hydrations, the empty-block sweep) and the materializer's `apply_op` and batch/replay transactions commit through it. A failed export or insert rolls the transaction back and rewinds the engine. An engine the transaction only read saves nothing, and neither does one the registry no longer holds (a purged space's, evicted in that transaction).
- **The engine writes that follow a commit**: the cohort fan-outs of delete, restore and a move's re-derived tombstones (`materializer/handlers/apply.rs`), the three purge commands' engine purge (`commands/blocks/crud.rs`), and the tombstones a sync projection swept. `write_engines` runs them under the write lock in a transaction of their own. `merge::engine_apply` takes the fan-out's own log.
- **A sync import**, which writes the engine before its projection transaction opens: `LoroEngine::capturing_delta` exports what the import added, under the engine lock, and the projection transaction saves it where it clears the inbox slot. The trusted no-op path saves it before its slot delete; when the projection does not commit it is saved on its own.
- **The export's format stamp, the tombstones `mirror_sql_tombstones_onto_engine` writes, and the sibling-order migration a rehydrate can append**: `capturing_delta`, then an insert (the mirror's in the transaction it already holds).

A snapshot pass reads the newest delta id before it collects any engine and deletes each saved space's rows up to it in the transaction that writes the snapshot row. The purge of a space deletes its rows.

### Departures from the findings, and why

- **A sync import saves what the engine gained, not the inbound blob.** An import can append this device's own ops: the one-time sibling-order migration, and since #6561 the moves that keep local blocks a remote purge would have taken, which landed on `main` while this was in review. It can also leave part of a blob pending. The blob holds none of the first and all of the second.
- **Boot deletes the rows an earlier process left** (`rehydrate_registry`). Boot still builds engines from the snapshots and replays the op log, and a replayed op mints new Loro ops under the ids the dead process's rows hold; kept, those rows would rebuild another state under the same version. What boot writes saves rows of its own.
- **A post-commit write stands when its delta cannot be saved** (the lock times out, the insert fails). The first build rewound it, which the review showed is a regression: before this change the cascade always reached the engine, and a restore or a purge that does not is a divergence peers see. The gap lasts until the next snapshot pass saves the space.
- `CommandTx::commit_and_dispatch` and `commit_without_dispatch` return `AppError`, since a failed export is not an `sqlx::Error`.

### The oracle

`delta::saved_engine_divergences` rebuilds each space from its snapshot, its deltas in `id` order, the blobs `loro_sync_inbox` and `loro_sync_quarantine` still hold, and what fixtures seeded, and compares version and state with the live engine. `Materializer::assert_saved_engines_match_live` panics on a divergence; the shared `settle` helper calls it, and so does each step of the two-device harness in `spaces/session_save_tests.rs`. So the conformance fixtures, the differential fuzz and most command tests run it after every op.

Traps it hit, all test artefacts:

- Loro lists a root container in the state once a reader has looked it up, empty or not. The comparison ignores empty roots.
- A fixture that writes through a materializer of its own (`bootstrap_spaces_for_test`, `ensure_test_space_with_defs`, `create_test_property_def`) saves deltas for engines the test's materializer does not hold, and the test's engine then reuses their op ids. Each drops the rows it saved.
- Fixtures that write an engine directly go through the new test-only `LoroEngineRegistry::seed`, which the oracle counts as saved (`conformance.rs`, `undo_redo_tests.rs`). One that called the apply kernel on a bare connection now uses the transaction shape the materializer uses, with `BEGIN IMMEDIATE`: a deferred transaction that upgrades fails at once with "database is locked" under a background writer, which showed as one test passing only on retry.

After those, the whole suite ran with the oracle and no production path was found writing an engine without a row.

### Left open, for stage B (in the issue comment)

- The fan-outs save their delta after their op's transaction, so window 5 is as it was.
- A write whose delta was not saved leaves later rows depending on ops no row holds until a pass saves the space. Harmless while nothing reads the rows; stage B has to decide what a boot does with it.
- A pass can export an engine while a transaction's write sits in it uncommitted. When that transaction rolls back, the row holds its ops until the next pass saves the space over (#6765). The rewind keeps the peer id (`revert_to_frontier`), so a write committed in between saves a delta under the rolled-back ops' ids, and a boot that read the rows then would rebuild another engine. Read from the code, not run.

## Session 4131 — A commit's background tasks take one queue slot; a busy writer is waited out; a settle runs what the queue shed

Set out to reproduce and fix what the #6724 session found and left: after one `create_blocks_batch` of 1,000 blocks and a `set_property_batch` over them, the settled integrity check reported blocks with no `fts_blocks` row and no `agenda_cache` rows.

### What was wrong

`CommandTx::commit_and_dispatch` enqueued each op's background tasks one at a time with a send that does not block. A content create is four tasks, so a batch at its cap offers the 1024-slot channel several times its capacity before the consumer has run, and the surplus was shed. Three things followed:

- **The shed tasks waited for the sweeper.** A shed task goes to `materializer_retry_queue` with a first backoff of a minute, and the sweeper ticks once a minute. A global rebuild shed once per op escalated its own row: 1,000 `RebuildAgendaCache` sheds are one row at the shed ladder's five-minute cap.
- **`flush_background` returned at its barrier** with those rows still waiting, so the integrity check, the tests' `settle` and the `after_rebuild` event of #6724 all read a vault that had not settled.
- **Each shed spawned its own retry-row write** on the two-connection write pool.

A second cause showed only once the first was fixed: under batch commands sent back to back the background consumer itself waits out the 5 s busy timeout (SQLite's busy handler polls, it is not a queue, and a writer that begins again at once wins every time). After three attempts the task was counted failed and sent to the retry queue on the failure ladder.

### What shipped

- `Materializer::dispatch_commit`: a commit of one op enqueues as before; a commit of several sends one `MaterializeTask::CommitFanOut`, which the consumer unpacks into its drain before the dedup. A shed commit is deduped and persisted by one spawned writer.
- The background consumer runs its retry schedule again while it ends on write contention (`AppError::is_write_contention`, moved from `maintenance.rs`).
- `Materializer::settle_background`: a flush, then every shed-marked retry row again as one `CommitFanOut` on a blocking send, then a flush. The integrity check, the `after_rebuild` event and the tests' `settle` call it. `flush_background` stays a barrier.
- `dedup_tasks`: a `RemoveFtsBlock` lets a later `UpdateFtsBlock` of the same block through. Keep-first dropped the restore's update of a block deleted and restored in one commit (a point-in-time restore), and the removal deletes the row whatever the block's state. A commit landing in one drain used to be likely; it is now certain.

### Traps

- The first version put the shed re-run inside `flush_background`. The reviewer found its other callers: quit and boot flush on the main thread, the snapshot pass flushes under its mutex, and a pull flushes inside its message budget. None of them promises a settled vault, so the re-run moved to its own method.
- With only the first fix reverted the scenario tests still find every row, because the tests' settle now runs the shed tasks; they fail on the shed counter alone. A test of the queue has to read `bg_dropped`, not just the derived rows.
- The test fixture's space block is a raw insert with no index row, so an integrity report in a test is never empty: compare with a baseline report.
- The measurement harness (`measure_dated_batches_back_to_back`, `#[ignore]`) is not a gate: which writer wins the lock is poll timing. Its settle time scales with the work (two batches, five batches), so the five seconds it prints at five batches is not a busy timeout.
- `database is locked` on a command did not reproduce in the Rust lane at ten batches of 200. What the harness shows is direction: a single create issued while the queue drains waited an order of magnitude longer before the fix.
- A whole-workspace test build filled the disk mid-link (`No space left on device` on `libagaric_lib.rlib`); `rm -rf src-tauri/target/debug/incremental` and `CARGO_INCREMENTAL=0` as `docs/BUILD.md` says.

### Not fixed

- Boot replay's `fan_out_replayed_ops` still dispatches per op, so a replay of a few hundred ops after a kill sheds the same way and heals at the sweeper's pace.
- A task with no retry kind (`RemoveFtsBlock`, `ReindexFtsReferences`) that is shed leaves no row, as before, and no settle runs it.
- A command that waits out the busy timeout gets `SQLITE_BUSY` as a `database` error, which the frontend's `retryOnPoolBusy` does not retry; `docs/architecture/operations.md` describes it as `pool_busy`.
- The two write connections still take the lock by polling. A fair queue (a write pool of one, or a gate in `begin_immediate_logged`) is a design call.

### Suites run

`cargo nextest run --workspace` in two halves on the final code (4,051 of 4,052 and 4,044 of 4,044 passed; the one red is a random property test in `agaric-store`, `incremental_fts_writers_leave_what_a_rebuild_produces`, red about one run in twelve on unchanged code and reported in the PR), doc-tests, `SQLX_OFFLINE=true cargo check --workspace --all-targets`, `cargo clippy --workspace --all-targets -- -D warnings`, `just gen-sqlx`, `just gen-bindings`, the manual-stage hooks. Each new test was shown red by one mutation. An independent reviewer read the diff before the gates. Not run: vitest, typecheck, lint, Playwright, WebdriverIO; nothing they read changed.

## Session 4130 — the persist-retry budget test no longer races a second task against the backoff

`materializer::tests::retry_metrics::persist_recovers_within_bounded_budget_851` failed once in CI, on a Markdown-only PR (#6734, `cargo-tests (2)`): `record_failure_with_retry` returned `false`. The session set out to say whether that was a test race or a retry budget too short for a slow device, and to fix whichever it was.

### Cause

A test race. The test dropped `materializer_retry_queue` and spawned a task that polled `retry_queue_persist_errors` and recreated the table once two attempts had failed. A missing table fails at prepare, at once, so the loop's remaining budget was its two last backoffs of wall-clock time. In that window the watcher had to wake from its poll, hand a `CREATE TABLE` to a SQLite worker thread and have it commit. When those hops were scheduled late, attempts three and four found no table.

It is not a product weakness. The failure the budget exists for is write-lock contention, and there each attempt already waits out the pool's `busy_timeout` before it fails, so the backoff between attempts is the smaller part of the budget. Only a failure that returns at once, like the missing table, leaves the backoff as the whole budget, and nothing in production drops that table.

### Reproduction

Each run is its own process, as under nextest, on a 4-core box.

- Ordinary load did not reproduce it: 0 of 2700 runs failed across CPU oversubscription (up to 128 parallel runs beside 128 busy loops) and an fsync-heavy disk load.
- Starvation did: the test pinned to one core at `nice 19`, six at a time, beside three busy loops on that core at `nice 0`, failed 17 of 600 runs, each with the CI panic at the same line.
- The rewritten test under the same starvation: 0 of 400.

### Fix

`record_failure_with_retry`'s loop moved into `persist_with_retry`, which takes the persist attempt as a closure; `record_failure_with_retry` passes `record_failure`. The test passes a closure that recreates the table at the start of its third call and then calls the real `record_failure`, so the recreate happens before the attempt by construction and there is no second task. It asserts exactly three attempts and exactly two persist errors, where it asserted "at least two".

Paused tokio time was not usable: sqlx runs SQLite on its own threads, so the runtime looks idle while a statement runs and the clock auto-advances past the backoff, which is the same race.

Falsified by cutting `PERSIST_RETRY_ATTEMPTS` to 2: the test went red on its `persisted` assertion.

### Siblings

No other test in `retry_metrics.rs` shares the cause. `record_failure_persist_error_is_metered_pend24_m1` never brings the table back, and the poll in `foreground_applyop_exhausted_persists_and_re_enqueues_on_boot` waits for an outcome with a deadline, not against a product budget.

### Scope

Touched `agaric-engine/src/materializer/consumer.rs` (the persist-retry helper only) and `agaric-engine/src/materializer/tests/retry_metrics.rs`. Another session is changing the background queue; nothing there was touched.

### What ran

The `retry_metrics` tests, the loops above (on the test binary directly with `--exact`, one process per run), `cargo clippy --workspace --all-targets -- -D warnings`, and the pre-push verify, whose nextest lane ran 6280 tests green.

## Session 4127 — engine loss windows 4, 6 and 2: a rolled-back write, two passes at once, rows ahead of the cursor

`Refs #6521`. The three windows the maintainer chose to close without a schema change, after the spike (session 4096, PR #6722). One commit per window.

### What shipped

**Window 4.** A snapshot pass can export an engine while a transaction's write sits in it uncommitted. When the transaction rolled back, the engine was rewound and nothing marked the space dirty, so the pass cleared the flag and the saved row kept a write nothing else holds. The rollback now marks each space it rewinds, after the rewind. It runs without the registry (a commit failure, a `Drop`), so the registry's dirty set became a shared `DirtySpaces` and each recorded checkpoint holds it.

**Window 6.** `mirror_sql_tombstones_onto_engine`, the one-time hydration and, since #6731, `save_kept_blocks` call `save_all_engines` themselves, and only `save_engines_and_advance_cursor` took the one-pass lock. The lock moved into `save_all_engines`. The outer function no longer takes it: the drain and the cursor move need no exclusion, and the cursor only moves forward.

**Window 2.** Boot applied every local op past the apply cursor, and the cursor can be behind the saved rows. Two changes:

- A pass writes its rows, and moves the stamp of every row it did not write, in one transaction (`write_pass`). A pass that cannot read the head, export a space or write a row writes nothing. Every row then carries one stamp.
- Boot applies the ops above both the cursor and the lowest row stamp. The ops between the two get their index fan-out and nothing else; the cursor is left for the next pass to move, after its drain.

### Why not the two designs the findings named for window 2

- **Skip per op by its space's stamp.** An op does not record its space. The apply handlers resolve it from SQL as it is at replay, in a score of places, and a `set_property(space)` writes two engines. A block a peer purged resolves to nothing, so its create would still replay and bring it back. Not complete, and not small.
- **Rows and cursor in one transaction after the drain.** The two bare callers have no queue to drain, and a queue that cannot drain would then stop the rows from being saved at all, which widens window 3. Putting only the rows in the transaction and letting boot read their stamp covers the bare callers and a failed drain with no plumbing.

### What this trades, for the maintainer

- **A space that cannot be saved now stops every space from being saved.** Before, the others were written. No such failure has been seen; a write failure on one file hits every row alike.
- **Rows an older build left with a space missing.** An older pass that failed one space's first write, or was killed between two rows, could leave that space with no row while the others moved on. Boot now skips its ops below the others' stamp, and its engine never gets them. It needs that failure or kill on the last run before the update. The old rule replayed them, onto the other engines too.
- **An op that commits between a pass's head read and its export** is in the row above its stamp, and is applied again if a kill comes before the next pass. The gap is the exports of the spaces ahead of it: seconds on a 100K-block space.
- **Window 4's residue.** Between the pass that saved the uncommitted write and the next one, the row on disk still holds it. A kill in that gap boots with it.

All four are in a comment on #6521 with options.

### Found by the independent read, not fixed here

`for_space` marks the space dirty before it takes the engine lock. A pass whose collect falls between the mark and the write exports the engine without the write and clears the flag. The write then sits in a space that reads clean, and the next pass moves the row's stamp over it. Microseconds wide unless the engine lock is contended. Older than this change; reported on #6521.

### Traps

- `main` gained a third direct caller of `save_all_engines` while this was built (`save_kept_blocks`, #6731). The comments that named the two callers were already stale at the merge; they now say "a direct caller".
- A `just gen-sqlx` killed mid-run leaves most of `src-tauri/.sqlx` deleted in the working tree. `git checkout HEAD -- src-tauri/.sqlx`.

- `snapshot_all_engines_during_concurrent_writes_2205` times out when run alone in this container, on unmodified `main` too, and passes inside the full suite. Its writers have no bound, so an idle box grows the documents faster than the exports can follow.
- Removing a runtime query from a file fails the dynamic-SQL hook until the baseline is re-anchored for that file: `node scripts/check-dynamic-sql.mjs --update-baseline <path>`.
- `target/debug/incremental` reached 10 GB; `CARGO_INCREMENTAL=0` kept the disk under its limit for the gates.
- A test that needs "the second row of a pass fails" cannot key its trigger on a space: the pass walks a `HashMap`. Key it on a row already carrying the pass's stamp.

### Tests changed, and why

- `snapshot.rs`: `failed_dirty_space_keeps_watermark_when_several_spaces_attempted_3309` became `a_pass_that_cannot_write_one_space_writes_none_6521`. It expected the pass to save the space that could be written (1 saved, stamps 1 / 500 / 500); it expects nothing saved (0, stamps 1 / 1 / 1), and the next pass to write both.
- `snapshot.rs`: `save_all_engines_does_not_advance_watermark_of_failed_dirty_space_3309` is deleted. It expected the clean row to move to 500 beside a failed one; that is the state the test above now forbids.

## Session 4126 — the sync peer's pull runs past a backoff

The real-backend spec "unpairing refuses the peer's next sync and drops only this device's row" (`e2e-tauri/sync-two-device.e2e.ts`) failed once on a PR that touches no sync code: `waited 60s for the app to refuse this vault's pull; the daemon reported no error`. The task was the root cause, not a retry.

### What happened

It was the test peer (`e2e_sync_peer`), not the app. The app refuses an unpaired device's dial at once; the peer never dialled.

The spec before it, "after a restart the state card shows the last sync before any new one", freezes the peer while the app restarts. When the peer thaws, each device discovers the other and both dial in the same few milliseconds. In the failing run the app's dial took the lock first, so the app refused the peer's dial as busy. A busy refusal is reported nowhere, but it books the dialler's backoff, about two seconds after one failure.

The unpair spec then reached `peer.syncRefused()` about a second and a half after the thaw. `sync_refused` only woke the peer's daemon (`notify_change`); the round it woke ran inside the backoff, `may_retry` skipped the app, and the wake was spent. The peer runs with `NO_PERIODIC_PULL`, so nothing dials again, and the command timed out at 60 s.

The run's own logs show it: the peer books the busy failure at `22:55:19.427`, neither log holds a connection after `22:55:19.44`, and the 60 s wait ends at `22:56:20.9`.

A second failure of the same spec, on #6724 (run `43525977672`), reads the same way: both devices discover each other at `23:29:13.902`, both dials are refused as busy, both book a backoff at `23:29:13.940`, and the peer dials nothing after.

Why now: #6710 added the restart spec, which stages that crossed dial right before the unpair spec. #6676 had made the app's own Sync press clear the backoff before it wakes the daemon (`start_sync_inner`, `user_initiated`), while the peer's `sync` and `sync_refused`, documented as waking the daemon "as `start_sync` does", kept the bare wake.

### What was ruled out

- The dial did not go to a stale address or port (#6703): the app bound once after the restart, and the peer's refused dial two seconds before had reached it.
- No refusal was lost on the way back (#6687): no connection arrived for the app to refuse.
- The app is not at fault. With two peer processes here, an unpaired device's dial is refused in about half a second once the backoff has run out.

The product was left alone. In the app the same skipped wake is picked up by the next resync round, a minute at most; the peer turns that round off on purpose, so its explicit commands are its only dial.

### The fix

`pull_now` in `e2e_sync_peer.rs`: `sync` and `sync_refused` clear the app's backoff and then wake the daemon, as the app's Sync press does. One unit test pins it, shown red by deleting the clear (`the round the pull wakes may dial the app`).

No spec changed, and no wait was lengthened or retried.

### Reproduction

The WebdriverIO lane cannot run in this container (no `WebKitWebDriver`, no `tauri-driver`), so the failure was staged with two `e2e_sync_peer` processes driven by a scratch script, not committed: one hosts the pairing and plays the app, the other joins. The host is frozen, the joiner's `sync_refused` dial times out and books a backoff, the host is thawed and unpaired (its `peer_refs` row deleted, which is all `delete_peer_ref` does), and the joiner is sent `sync_refused` again at once.

- Binary from `origin/main` (`eb66161`): 4 of 4 rounds waited 60 s and failed with the run's exact message.
- The same binary, with 3 s of waiting before the unpair: 2 of 2 refused in about 0.5 s.
- Binary with the fix: 20 of 20 refused in about 0.5 s with `peer not paired with this device`.

### Traps

- This container has no LAN address the bind policy accepts (`eth0` is `192.0.2.2`), so the daemon binds loopback and announces nothing on mDNS. A pairing by QR still works, because the QR carries the address; the crossed dial at a thaw cannot be staged, since it starts from discovery.
- The debug build, the test build, `cargo check --all-targets` and clippy filled the disk during `just gen-bindings`. `rm -rf src-tauri/target/debug/incremental` freed it.

### Ran

On `eb66161` plus this change, and again with `main` at `67d9b68` merged in (it brought Rust changes, one of them a line in `e2e_sync_peer.rs`): `cargo nextest run --workspace` in two halves (4039 and 4033 tests pass, then 4047 and 4040), `SQLX_OFFLINE=true cargo check --workspace --all-targets`, `cargo clippy --workspace --all-targets -- -D warnings`, `just gen-sqlx` and `just gen-bindings` (no diff), `npm run typecheck`, `npm run lint`, `prek run --hook-stage manual --all-files`. Not run: vitest, Playwright (no frontend file changed), and WebdriverIO, which the PR's `e2e-tauri-gate` runs.

`main` moved once more before the push (`ddbbd1b`, #6731, the synced purge). It merged clean and touches neither the peer binary nor the scheduler. On that tree only the peer binary's own tests (22 pass) and the pre-push hooks ran; CI's run on the PR is the check of the whole.

## Session 4117 — a key right after a caret key acts on the moved caret, in blocks and in page mode

The follow-up to #6725 (session 4100). That session's log says the second route to a mid-word split, the one found in Chromium, was "left alone": nobody had reported it and the fix reads a ProseMirror internal. The orchestrating session asked for that claim to be checked and the product fixed if the fix was small and safe. It is, and this is it. #6725 was approved and green when the note arrived, so it merged as it stood and this is its own PR.

### The bug

End, Home and the arrows move the caret in the DOM, and ProseMirror takes that in on `selectionchange`, a task later. A key handled before that task acts on the caret from before the move: the key rules read `editor.state.selection`.

- At a driver's speed, with nothing between End and Enter, Enter split at the old caret 12 of 20 times on the mock in Chromium. Idle, `selectionchange` arrived 10 to 25 ms after End's keydown, and a 50 ms gap passed 10 of 10.
- At a person's speed, with the two keys 60 to 80 ms apart inside a 150 to 300 ms main-thread stall, it split wrong 10 of 10: a busy page handles the queued keys back to back, ahead of the queued event.
- Home then Backspace did not merge, and page mode's Enter split at the old caret, the same way.

### The fix

`readDomSelection` (`src/editor/read-dom-selection.ts`) has ProseMirror read the DOM selection at keydown, before any rule reads the caret. It calls `view.domObserver.flush()`, which is what ProseMirror's own `selectionchange` handler calls, so it is the read that would have happened a task later. Block mode calls it in `useBlockKeyboard`'s capture handler, after the IME guard; page mode in `PageKeys`' `handleDOMEvents.keydown`, which runs before the keymaps, with the same guard: ProseMirror holds its own reads back during a composition.

`domObserver` is a ProseMirror internal with no type. If an upgrade renames it the call does nothing, and `e2e/enter-after-caret-key.spec.ts` goes red.

This does not cover what failed in CI on #6713. There ProseMirror's post-focus timer had already put the DOM caret back, so a read at Enter's keydown reads the click point; #6725's helper change is what fixed that.

### Tests

- `e2e/enter-after-caret-key.spec.ts` holds the main thread while it presses two keys, so the page handles them with no task between: End then Enter and Home then Backspace in block mode, End then Enter in page mode, each read back after leaving the page or from the backend. Before the fix the block-mode pair was red 20 of 20 and page mode 5 of 5.
- `use-block-keyboard.test.ts` and `page-keys.test.ts` move the DOM caret with `selectionchange` held back and press a key. Each was shown red by removing its call, and each IME test by dropping its guard.

### Traps

- **For 200 ms after a focus ProseMirror takes a collapsed caret at the document's start for the browser's focus reset** and puts its own back (`DOMObserver.flush`). Home in a one-paragraph block lands there. The spec's stall is longer than that, and the unit tests put the DOM caret mid-text.
- **jsdom sends `selectionchange` inside `Selection.collapse`**, so ProseMirror has read a moved caret before a test can press a key. The unit tests stop the event at `window` in the capture phase for that one call.
- **A full vitest run that overlaps a falsification reads the mutated file.** One was started before the mutations and thrown away.
- **`diagram-legibility` and `diagram-scrollbar` fail in the cloud container on a clean `origin/main` bundle too**, four tests; `docs/BUILD.md` names the first and not the second.

## Session 4114 — a synced purge keeps the blocks this device added, in the Trash (#6561)

When device A deleted a page and emptied its Trash while device B, out of contact, added blocks under it, B's next pull hard-deleted B's blocks. The maintainer decided on 2026-11-13 that B keeps that text in its Trash and says so. The design note is on the issue; this is what the build found.

### Decisions and traps

- **A block under a purged page is not gone in Loro.** A purge is `tree.delete` of one node; a child keeps its node and its parent pointer, and `tree.mov` accepts it (only a node whose own parent is the deleted root is refused). So the rescue moves the block itself: same id, text, properties and tags. Nothing is copied.
- **"Never seen by the purge" is read from the doc.** A node id is its creation op. `cmp_frontiers(delete op, creation op)` is `None` when the purging device had not received the block and `Greater` when it had; the delete op is `get_last_move_id` of the deleted node at the top of the chain. Only `None` keeps a block: anything else purges, or two devices would trade a block back and forth.
- **Only what the purge never saw, all the way down.** A block the other device had received can sit under a new block here (indented offline). Moved along, it would come back without the properties and tags the purge had deleted, so the rescue deletes it again after the move, and its text does not count when deciding whether a blank block is worth keeping. An independent review found this.
- **The rescue is saved at once.** Its ops are in no op log, so after a crash the engine would mint its next op under ids a peer may already hold. The space is saved right after the import, as `mirror_sql_tombstones_onto_engine` does for the same reason; the inbox row replays the import if the save fails.
- **`blocks.page_id` is derived in the background, and the session-end sweep does not wait for it.** A kept block still named the purged page when the sweep deleted that page, and the sweep failed on the foreign key. The import now restamps the kept page's subtree in its own transaction. The crash-replay path does not (it has no list of kept pages); there the rebuild that boot replay arms does it before the next sweep, or that sweep fails once and the next one passes.
- **A page moved to another space leaves its old doc as a purge does**, so blocks added under it meanwhile land in the old space's Trash, and the toast says "deleted or moved".
- **Not kept:** an offline edit to a block the other device already had. The toast says "the blocks you added" for that reason.
- **A debugging trap:** `PRAGMA foreign_keys = OFF` also turns off `ON DELETE CASCADE`, so a foreign-key check run that way reports rows the real purge would have removed. Check inside a transaction with keys on.

### Shipped

`agaric-engine/src/loro/engine/keep.rs` and its call in the import; `ImportDelta.kept` and `ApplyOutcome::Imported.kept`; `SyncEvent::LocalTextKept` with its event name in the bindings; the emit in the pull session and in the snapshot catch-up; `useSyncLocalTextKept` and its toast; `docs/FEATURE-MAP.md`, `docs/features/sync.md`, `docs/architecture/data-and-events.md`.

### Decisions

- **MediaStore, not the share sheet.** The issue asked for one of the two. Downloads is where "a file the Files app opens" is, and it needs no permission from API 29.

With `panic = "abort"` a panic there is a crash, so the check uses `HttpURLConnection`. If the reading is right, `fetch_link_metadata` has the same hazard on Android; it is untouched here and is a #6513 line.
- **No setting gates the check.** The issue says "the same setting that gates the desktop check"; the desktop check has none, only the debounce and the Flatpak guard. None was added.
- **A stored "update available" from another build is rechecked at once**, or Settings › About would name the release the user just installed for up to a day. Desktop has the same staleness and was left alone.
- **The save toasts where the file went on Android**, which has no download UI of its own. Every caller that toasts success (the two exports, *Save as Markdown file*, the bug-report ZIP) skips its own toast there: it would say the same thing under a name the OS may have changed. The reviewer's note on the exports is in.
