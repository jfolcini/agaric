# Session 1488 — MCP argument validation: malformed ULIDs and the reserved `space` key

Three gaps in the MCP tool handlers, all in the same layer and all about what an agent is allowed to hand us. The maintainer narrowed #3301 to exactly these on 2026-09-02; the two change-notification findings in the issue body were dropped and are not touched here.

`app_error_to_rmcp` had three arms and `AppError::Ulid` was not in any of them, so it fell to the catch-all. An agent that called `search({space_id: "personal"})` — a plausible mistake, since `list_spaces` returns a `name` next to the `id` — got `-32603 an internal error occurred` and an ERROR-level line in the daily log. Under the JSON-RPC convention that `-32603` is a server fault the agent retries the identical call, and an operator triaging internal errors chases a typo. `Ulid` now joins the `invalid_params` arm: its `Display` names the offending string and carries no sqlx or OS detail, so the #698 scrubbing contract is untouched. The stale comments that rationalised the old mapping — in `tools_ro.rs` at the `space_id` gate, in the handler-implementations header, and beside the match in `rmcp_adapter.rs` — say `-32602` now, and so does `src-tauri/src/mcp/AGENTS.md`.

`handle_search` validated `space_id` strictly (#2956) but only `normalize_ulid_arg`-ed `parent_id` and each `tag_ids` entry, and that helper passes anything that is not 26 alphanumerics through unchanged. A tag ULID copied one character short was uppercased, bound, matched nothing, and the tool answered `{items: [], has_more: false}` — the agent concludes no block carries that tag and has no signal to retry. Both now go through `BlockId::from_string`, exactly as `space_id` does. The parse deliberately runs *after* `validate_search_term_budget`, so an oversized `tag_ids` vector still gets the actionable "too many filter terms" message rather than a ULID complaint about its first entry.

`handle_set_property` never looked at `args.key`, so `space` reached `set_property_inner`. That key is column-backed on `blocks.space_id`, exempt from the cross-space ref guard in the engine, and projects as `UPDATE blocks SET space_id = ? WHERE id = ? OR page_id = ?` — the canonical cross-space move of a page and every descendant. `validate_block_in_space` cannot catch it, because the block genuinely is still in the declared space at check time. No privilege is gained (the agent supplies `space_id` itself and `list_spaces` is on the RW surface too), but a hallucinated `key: "space"` silently re-homed a subtree and the activity feed rendered it as a key plus an eight-character prefix. The tool rejects the key up front, against `agaric_store::op::SPACE_PROPERTY_KEY` rather than a fresh literal. The neighbouring predicates do not fit: `is_builtin_property_key` does not cover `space` at all, and `is_column_backed_property_key` also covers `todo_state` / `priority` / `due_date` / `scheduled_date`, which agents legitimately set. The module header's "deliberately NOT exposed" list and the `key` schema description now say so too.

Three tests pin it. The `app_error_to_rmcp` table test gains a `Ulid → -32602` row with its exact wire message. `search_malformed_parent_and_tag_ids_error_not_empty` mirrors the #2956 `space_id` test for both remaining ids, including a 25-character tag ULID, and ends with a control call that returns the seeded hit so the rejections are provably about the ids and not an empty vault. `set_property_reserved_space_key_rejected` asserts the Validation error *and* re-queries `blocks.space_id` to prove the page stayed put. Each was shown red against a copy of its source with the one fix reverted, then restored and `cmp`-checked.

A later round caught `parse_block_id_arg` inserted between `normalize_ulid_arg`'s doc block and its `fn`, so a 25-line doc ending "anything else passes through unchanged" attached to the function that does the opposite, and `normalize_ulid_arg` was left undocumented. Moved below it. A second note asked to fold `search_malformed_parent_and_tag_ids_error_not_empty` into the #2956 `space_id` test. That was first declined on the grounds that the merged test would need a rename and `search_malformed_space_id_errors_not_empty` is cited in the merged, immutable `session-1209-mcp-surface-correctness.md`, so renaming it would red the dead-symbol-citation guard. Both halves of that were wrong. The reviewer pointed out that appending assertions needs no rename at all; and running the guard against the rename — rather than assuming, which is what had happened — exits 0. The merge is done: one test, one seeded fixture, one control call, covering all three ids under a name that says so, 56 lines out for 21 in. The lesson is the one this repo already writes down: a prose claim that something was checked is a hypothesis until it is run, and that applies to a reason for declining as much as to a reason for shipping.
