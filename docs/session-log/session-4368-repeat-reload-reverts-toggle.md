# Session 4368 — a repeating task's reload reverts another task's toggle

#6972: ticking a repeating task to DONE reloads the page for its next occurrence (`reloadIfRepeating`). A checkbox on another task clicked meanwhile snapped back while the backend kept the new state, so the next click wrote the state after one the user never saw.

**Cause, confirmed in code:** `handleToggleTodo` writes the new state into the page store before `set_todo_state` answers, and nothing told `load()` about that write. A reload whose snapshot was read before the write committed replaced `blocks` with the old state, and nothing corrected it after: the load generation (#753) orders loads against each other only. Any reload hits it, not only the repeat one; a sync reload is the other caller.

**Fix:** the store's holds (#6559, #6814) already make a load wait for a create, split or merge in flight and read again when one began while its snapshot was on its way. `holdLoads()` takes the same kind of hold without naming a block, so writes keep their own ordering and a toggle does not replace a create's hold on the same block. The todo toggle holds loads from its optimistic write until its command answers, and releases before its own repeat reload, which would otherwise wait on itself. The priority toggle has the same shape; no failure has been seen there, so it is unchanged.

**Tests:** two in `use-block-properties.test.ts` drive the hook on a real store against a backend model that reads and writes task states when called. One starts the other toggle before the repeat reload, one while the reload's snapshot is on its way. Shown red with the hook's hold removed (both), with the load not waiting on load holds (both), and with `holdLoads` not counting as a hold (the second). `e2e/task-repeat-toggle-race.spec.ts`, on the mock and the bridge, clicks the repeating task and then the other task with no settle between, and checks both states after reopening the page and through `get_block`. On the bridge it passed 30 of 30 with the fix, and failed 3 of 10 with the hook's hold removed, each time on the other task's checkbox. The race needs the click to land inside the reload's read, so the spec catches a regression only some of the time; the vitest is the deterministic check.
