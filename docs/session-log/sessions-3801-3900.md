## Session 3898 — Copying attachments into the Markdown mirror (backend)

#5363 slice 4, setting 3, PR A of two: the backend, with the setting unreachable from the UI until PR B adds the control.

### Decisions (coordinator, recorded on #5363)

- **What is copied:** what pages link, per space, as the export does. An attachment linked from two spaces is copied into both. The file render (`PageRead::File`) loads no attachment rows, so the copy set is exactly the `attachment:<id>` links in the rendered file.
- **Where copies go:** the export's layout, `<space>/assets/<id>/<name>`. The page links a copy by a path relative to its file, one `../` per namespace folder.
- **The scan:** the mirror's new-file scan and `read_back::pending` skip only folders shaped `<space>/assets/<26-char id>/`. A copied `notes.md` is never read as a page, and a page titled `assets/x` is still read back.
- **Names:** the export's TS naming moved into an exported `assetName` (`src/lib/export-graph.ts`) and is ported to Rust as `assets::asset_name`. `conformance/asset-names.vectors.json` (25 rows: `/`, `\`, `:`, reserved names, trailing dots, BOM, NEL, CJK) is asserted by a vitest and a Rust test. Page paths keep `paths::sanitize_segment`, so no page file moves.
- **Turning it off:** a full pass puts `attachment:` links back. Copies still as written are removed; a changed one stays and is listed under `diverged`, with an empty `page_id`.
- **Read-back:** only `(../)*assets/<id>/…` naming a live attachment maps back to `attachment:<id>`, before `apply_page_source_inner`. Anything else stays text, and a file dropped into `assets/` is never read.

### The change

- **`src/mirror/assets.rs`:**
  - the name sanitizer;
  - `Links`, the link rewrite per page;
  - `delocalize`, the read-back mapping;
  - `is_copy_dir`;
  - `Copies`, the record of copies written, `mirror/copies.json` in the app's data. A copy is rewritten when it is missing or its length or modification time changed since. It is removed, while unchanged, once its attachment is gone, once no page of its space links it after a full pass that rendered every page, or once copying is off.
- **`mod.rs`:**
  - a page's render is localized before it is compared or written;
  - each pass ends with a sweep of the copies no longer wanted;
  - turning the setting on or off makes the next tick a full pass.
- **`ingest.rs`:** `ingest` and `create` delocalize before saving and write back localized. Their shared write-back moved into `rendered_back`, which keeps `create` under the 70-line limit.
- **The setting:** `mirror.copy_files` (`"true"` only), the `set_mirror_copy_files` command, and `MirrorStatus.copy_files`. The command has a mock handler and a waiver in both waiver lists, beside `set_mirror_read_back`.

### Tests

- **`src/mirror/assets_tests.rs`:**
  - the vectors;
  - the copy-folder rule;
  - the link rewrite at two depths and with `<…>` destinations;
  - `linked`;
  - tick tests for: off by default; on, copy and link; a missing and a changed copy rewritten; off, removing unchanged copies and listing a changed one; a deleted attachment's copy removed; a renamed attachment linked at its new copy, with the old one gone; an edit beside a link read back as `attachment:`; and the `assets/` scan cases.
- Each falsified by a planted defect, in one script that restored the files on exit; each failed the test it targets:
  - no link rewrite;
  - an existing copy never rewritten;
  - a changed copy removed;
  - dead attachments counted live;
  - no read-back mapping;
  - copy folders not skipped;
  - copying on by default.
- Review of the first push: renaming an attachment left the page linking the old name's copy, which the end-of-pass sweep then removed. A page now links only the copies placed for it in that render, not every recorded copy of its space. Linking from the record again failed the new rename test.
- Copying on by default first survived: the default test stored `false` explicitly. Its fixture now leaves the setting unset.
- **Existing tests edited for the new required `MirrorStatus.copy_files` field:** the `get_mirror_status` stubs in `DataTab.test.tsx` (two) and the `status()` fixture in `MirrorSection.test.tsx`.
- **Results:**
  - `cargo nextest run -p agaric -E 'test(/mirror/)'`: 109 passed;
  - vitest over the settings, the mock and the vectors: 69 files passed;
  - `npm run typecheck` and `cargo clippy -p agaric --all-targets -- -D warnings` are clean.

### Bench

`mirror_bench.rs` gains two cases. The numbers come from `cargo bench` with `CARGO_PROFILE_BENCH_LTO=false CARGO_PROFILE_BENCH_CODEGEN_UNITS=16`, not the shipped profile, on a shared cloud box at load 1.5 to 3.9; each is Criterion's [low, mean, high]:

- `mirror_copy_first/500`: the first full pass, 500 pages each copying a 64 KiB attachment (32 MB), took 2.04, 2.15 and 2.26 s.

The unchanged pass costs about what a plain full pass of 500 pages does (`mirror_startup_pass` measured about 0.7 ms a page), so checking copies in place adds little. Both run on the mirror's background task, a tick after boot, so neither delays first paint.

## Session 3895 — "Sync complete" only after a session finished

Issue #6551, its first item. The second (a local edit triggers a sync, and a served pull makes the responder pull back) is untouched.

- **Premise, confirmed.** `start_sync_inner` only calls `scheduler.notify_change()` and returned `state: "complete"`. `syncAll({ userInitiated: true })` raised "Sync complete" as soon as that resolved, which it does with the peer switched off. The scheduled tick wrote `syncing` then `idle` the same way.
- **Backend.** `start_sync_inner` returns `state: "queued"`. No type changed (the field is a `String`), so bindings and the `start_sync` conformance waiver are unchanged. The mock's `start_sync` said `syncing`; it now says `queued` too.
- **Frontend (`useSyncTrigger`).** A press waits, under the existing `SYNC_TIMEOUT_MS`, for the terminal `kind: 'sync'` update on the channel its `start_sync` opened (`ChannelEventSink` turns `SyncEvent::Complete` / `Error` into `complete` / `error` there). `complete` is the only success. An `error` while the store still says `syncing` is a failure no `sync:error` reported, and gets the per-peer failure toast. An `error` after `sync:error` already set `error` (a reported failure) or `idle` (a cancel) stays quiet, as that event answered it. A timeout gets the per-peer failure toast, and the press's own `syncing` returns to `idle`. Every peer is asked at once and the waits run side by side (one shared 60 s bound): one `start_sync` wakes a daemon round with every paired peer, so asked one by one, a later peer's session from that round could still hold its lock and refuse the press as already in progress.
- **Scheduled tick.** It does not wait for its session and no longer writes `syncing` / `idle`. The session's own channel updates and `sync:complete` / `sync:error` drive the store. It only drops an `offline` the network's return made untrue, which its old `syncing` write used to do.
- **Trap (e2e).** Sonner renders a toast on a `setTimeout(0)`. Under `page.clock.pauseAt`, a toast never appears until the clock runs. A `toHaveCount(0)` on a toast is vacuous unless the clock was run first (`page.clock.runFor`).
- **e2e.** The mock lane can show this: its `start_sync` resolves at once and reports nothing, as the backend does with the peer off. That is why the spec is in `e2e/sync-happy-paths.spec.ts` and not `e2e-tauri/`. `keepSyncChannels` / `streamSyncProgress` moved from `sync-peer-progress.spec.ts` to `e2e/helpers.ts`, and `finishSyncSession` (`e2e/domain.ts`) plays both halves of the backend's session end. The two specs that pressed Sync and emitted only `sync:complete` now also end the session on its channel, because a press now waits for that.
- **Checks that ran.**
  - vitest red first: 4 new `useSyncTrigger` tests failed against the old hook. Six mutations of the new code were each killed.
  - nextest red first: the three `start_sync` state assertions failed on `"complete"`.
  - The Playwright spec reds against the old hook on its `Sync complete` count assertion.

## Session 3893 — One sticky formatting toolbar per view (#6562, first checkbox)

**Goal.** Block mode's formatting toolbar was the first child of the focused block's `.block-editor`, in flow, so focusing a block pushed its text and everything below it down 27 px; a double-click's second press landed on a toolbar button. The maintainer decided on one sticky bar per view, hidden at rest. The second checkbox (click-to-caret) is not built: `StaticBlock.handleOuterClick` and `rovingEditor.mount` are untouched.

**What changed.**
- `src/components/FormattingToolbar/view-toolbar.tsx` (new, TipTap-free): `useViewToolbar(element)` publishes the edited block's bar into a module store from a layout effect, with an owner token so a surface that unmounts late cannot clear its successor's bar; `ViewToolbarSlot` renders it. The slot is mounted once in `App.tsx`, first in the main scroller after the phone header slot, so every view gets exactly one (the journal week and stream views included) and no editing view is outside it. In the journal and the page editor (`room`) it keeps the bar's room at all times: a sticky `h-3 md:h-1` spacer that, with the scroller's top padding, is the bar's `h-7`, the bar absolute at `-top-4 md:-top-6` over both. Showing and hiding the bar moves nothing and it covers no content at scroll-top at either breakpoint. Its strip spans the pane; its buttons sit on the blocks' `max-w-reading` column (the only views with editable blocks). On touch the slot keeps no room: the bar pins above the keyboard.
- `EditorSurface` hands its `FormattingToolbar` element to the slot instead of rendering it. Because the slot renders the same component in the same place, the bar stays one mounted element while the roving editor moves between blocks (spec and unit test check element identity). The bar renders outside the tree, so `EditorSurface` passes `listStyle` from `useListMarker` (Turn into read it from `ListMarkerProvider` context before).
- `focusStaysInEditor` (`src/editor/editor-portal.ts`) skips `[data-view-toolbar]` in its "a visible overlay holds the editor" scan. The bar carries `data-editor-portal` and is now outside the block's wrapper; without the skip it would keep every edit open forever. Focus moving *into* the bar is still caught by the first check.
- Page mode's and *Edit as Markdown*'s sticky bars move from `top-0` to `-top-4 md:-top-6`: sticky offsets count from inside the scroller's padding, which left a 24 px band above them.

At 640 px the full-width bar fits every button, so the overflow spec uses 480 px. The `toolbar-and-blocks` #4320 popover spec's anchor is now the bar under the header, never mid-viewport: its filler blocks and centring went, and its title and comment say what it checks (room below the bar runs out).

## Session 3892 — Ctrl+Z in a block with nothing left to undo runs the page's undo

#6556, its one checkbox. In a focused block of the page editor, Ctrl+Z (Ctrl+Y / Ctrl+Shift+Z) did nothing once the editor's own history was empty: the history resets on every mount, and `useUndoShortcuts` steps aside while any block has focus. Escape then Ctrl+Z worked, which nobody could guess.

### What changed

- `use-block-keyboard.ts`: two rules ahead of the chord rules. `undoLastPageOp` / `redoLastUndoneOp` match only when `editor.can()` says the history cannot take the press (`ctx.canHistory`, a call so only those chords pay for it), and hand it to the new `onPageHistory(direction)` callback, which says whether it took it. When it declines the key goes on to ProseMirror as before.
- `use-block-page-history.ts` (new, wired in `BlockTree`): unmounts the editor and flushes through `runUnmountFlush`, awaiting the save, so the page undo never runs under unsaved text. Clears focus before the undo, since `load()` keeps a focused block's old text, and registers the block in `preserveEmptyBlockIds` so the empty-block cleanup does not delete an Enter stub in that window (without it the cleanup's delete races the undo's). After `performPageUndo` / `performPageRedo` it mounts the editor on the same block with its reloaded text, or on the row above when the undo removed the block. Declines outside the `page-editor` view: the journal is a later stage of the undo sequence.
- `useUndoShortcuts.ts`: `runBlockPageHistory` runs the block's chain and drops a press while one runs; the global listener also stands aside meanwhile, since focus is cleared for the reload and a key repeat landing during the flush would otherwise run a second page undo (found in review, pinned by its own spec test). `performPageRedo` extracted as the twin of `performPageUndo` (the keyboard redo branch now calls it); header and the focused-block comment describe the chain.
- Docs: `docs/features/editor.md` § Pitfalls, `docs/features/keyboard.md`.

### Decisions and traps

- Page mode (`PageModeEditor`) and *Edit as Markdown* are separate editors and untouched; the issue scopes the page editor's block mode.
- Typing the debounce already saved shares the block's `edit:<id>` undo entry with its later saves, including the save of the editor's own undo. So after Ctrl+Z has taken the typing back in the editor, the next press undoes that entry: the text stays as it is and the toast shows. Pinned by the last spec test.
- The hook's ref param is named `preserveEmptyBlockIdsRef`: the React Compiler lint only treats `*Ref` names as refs inside `useCallback`.

### Checks run

- `e2e/block-undo-chains-page-undo.spec.ts` (9 tests): the first four red on main at the first post-Ctrl+Z assertion; the in-flight-press test red with the listener's guard removed, the rest with the `onPageHistory` wiring removed. Flush, `canHistory`, the row-above fallback and the empty-block preservation each falsified.
- vitest: `use-block-keyboard.test.ts` (new #6556 block), `use-block-page-history.test.ts` (new), `useUndoShortcuts.test.ts`, BlockTree reload / a11y / focus-renders / import-graph. `npm run typecheck` clean; oxlint clean on the touched files.
- Playwright: `undo-redo-blocks`, `kind-change-undo`, `editor-keyboard-chords`, `reload-keeps-editor`, `keyboard-customization` and the new spec, 40 passed. `just e2e-related` selects 250 specs; CI runs the rest.

After the PR opened, the reviewer bot pointed out that a failed save before the chained undo was ignored: the page undo still ran and reversed an earlier, unrelated step while the typed text was already out of the editor. The run now stops there, remounts the block with the typed text and resets the baseline to the loaded text, so the typing is still unsaved in the editor and the press undoes nothing. A hook test covers it, red with the check disabled.

## Session 3891 — a Logseq or Org file merges into the page of its title (#6277 G5)

G5 item 3, the last of #6277: re-importing a Logseq page or an Org file now
updates the page of its title in place, as a Markdown file already did, where
it used to import as `Title (2)`. The maintainer chose merge by re-rendering
(2026-11-11): no second save path, and the readers unchanged.

Premise check first, agreed with the coordinator:

- A Logseq `id::` uuid is not stored: the import uses it only to resolve the
  file's `((uuid))` refs. So a re-rendered block pairs by its text, and its
  uuid's refs become refs to the block its line pairs with.
- Collapse is not stored either: the import returns the folded blocks to the
  frontend. A merge now returns them too.

What shipped (`markdown_import_merge_outline.rs`):

- `render_outline` puts the outline reader's blocks into a `PageExportData` as
  an import would store them (task state, priority as the import maps it,
  planning dates, list styles, the rest as rows; aliases, tags and page
  properties as front matter), each block under a minted placeholder id, and
  renders it with `render_page_document`. A `((uuid))` to a block of the file
  becomes a ref to that block's placeholder.
- `link_outline_ids`, after the lines pair, writes the id of the block each
  placeholder's line paired with over the placeholder, and the lines pair
  again; a placeholder on a new block is resolved after the save, by content,
  as #6580's `^name` is. The folded blocks come back the same way (`fold_ids`).
- `MergeRule` merges every dialect; its Logseq-or-Org warning is gone.
- The import dialog asks about a Logseq page or an Org file too: its title is
  read from its text (`title::`, `#+TITLE`), so `ImportUnit.merges` may be a
  function, resolved one file at a time.

Traps:

- A Rust `\` line continuation eats the next line's indent: the first
  fixtures lost their nesting and planning lines and passed without covering
  them. The fixtures are `concat!` now, and the Logseq test asserts each shape
  was stored before it re-imports.
- The backend never sees Org text: the frontend's `orgToMarkdown` sends
  Logseq-style Markdown (`ID::`, `((uuid))`), so the Org twin's fixture is that
  output.

Existing tests changed, each pinning the rule this replaces (a Logseq or Org
file never merges):

- `a_logseq_file_is_title_2_and_a_folder_note_or_a_note_with_files_merges`
  becomes `a_logseq_file_a_folder_note_and_a_note_with_files_merge`; its
  Logseq case asserts a merge.
- The vitest pins of `merges` being undefined for an Org file and a Logseq
  page, in `vault-import.test.ts` and `vault-import-merges.test.ts`.

Shown red:

  `an_org_file_imported_twice_leaves_its_page_as_it_was` and

## Session 3890 — A clean focused block takes the peer's text on a reload (#6533, second item)

#6533's second checkbox. Since #6578 a reload keeps the focused editor mounted, but `load()` still kept the focused block's pre-reload text in the store (`staleFocusedBlock`) and never re-fed the editor, so with nothing typed the first keystroke committed the old text plus that key over a peer's edit.

**Change.** `takeReloadedText(blockId, markdown)` in `src/editor/active-editor.ts`: when the published roving editor is mounted on the block and clean (`getMarkdown() === storedMarkdown`, the same test `commitNow` uses to skip), it replaces the document out of undo history and with `preventUpdate` (no commit or draft debounce armed), puts the selection back clamped by `setTextSelection`, and rebases the commit baseline with `markCommitted`. `load()` calls it for the focused block whose fresh text differs; only when it returns false does the store keep the old text and record `staleFocusedBlock`. `BlockTree` publishes its roving handle with the editor (`setActiveEditor(editor, rovingEditorRef.current)`); page mode publishes none.

**Review fix.** A reload snapshot read before the user's own commit landed is older than the editor, and a clean editor would have taken it, undoing the commit on screen so the next key committed the older text. `load()` now reads `reloadBaseline(blockId)` when it starts (null when the editor is dirty, composing, or not on the block), and `takeReloadedText` takes only while the editor's baseline is still that text. The selection is restored after the dispatch in its own guard, so a selection failure cannot leave the document replaced yet reported as not taken.

**Decisions.** No editor on the focused block, or a parse failure, counts as "not taken" and keeps today's behaviour: a lazy editor's buffered mount still holds the old text, so taking the fresh text into the store there would leave editor and store apart. The re-feed lives in the registry, not on `RovingEditorHandle`, because a new handle member would ripple into every hand-built handle in the tests, and the registry already holds the editor; `parse` is already on `BlockTree`'s eager graph, and the lazy-import-graph test stays green. The issue's prescription said "keep the old text only when dirty"; the no-editor case is the one deliberate departure.

**Siblings.** The journal's day and week trees are `BlockTree`s with their own store and roving editor: the global focus names the block, the registry holds the editor the caret was last in, and `takeReloadedText` checks that editor is on that block, so they take the same path. Page mode clears the global focus, so `load()` takes every block's fresh text, and `remote-patch.ts` already patches the caret's block in place unless it holds unsaved text. *Edit as Markdown* (`PageSourceEditor`) reads the page once and never watches reloads; unchanged and untraced beyond that.

**Tests.** `e2e/reload-keeps-editor.spec.ts`, new describe: a clean focused block shows the peer's text after `sync:complete`, stays focused, and one key commits text holding the peer's edit (re-queried); red on `main` at `toHaveText`, red again with the handle dropped from `BlockTree`'s publish. A dirty editor (key typed inside the commit debounce) keeps its text through the reload: red at `toHaveText` when the dirty check is removed. `active-editor.test.ts` drives a real TipTap editor: clean take (text, caret, baseline, no update signal, no undo entry), dirty keep, editor on another block or no handle; each assertion shown red by removing the line it covers. `page-blocks.crud.test.ts`: dirty keeps text and records the stale copy, a taken text is stored with none.

**Ran.** `npx vitest run` over the BlockTree, EditableBlock, page-store, active-editor, content-commit, page-mode and journal test files (50 files, 1250 tests, green); `npm run typecheck`; oxlint and oxfmt on the changed files. Playwright: the new tests, then `reload-keeps-editor`, `sync-refresh` and `editor-lifecycle`.

## Session 3848 — Deleting lines from a mirrored file duplicated blocks

The convergence proptest (#6507) failed in a full run on `main`: blocks `["w0", "s2", "s0", "s1", "s2"]`, "no block is duplicated". It reproduced from its shrunk case in a clean checkout.

### The cause

An ingest saves a file against one of the texts the mirror last wrote, the one `closest` picks in `src/mirror/ingest.rs`. It picked the text differing from the file in the fewest lines, counting lines on both sides.

The shrunk case: Agaric edited `w1` to `s0` and added `s1` and `s2`, then wrote `w0 s0 w2 s1 s2`. An editor then cut the file to `w0 s2`. That is closer, in that count, to the older text `w0 w1 w2` than to the newest one. Against the older base, the three-way merge kept Agaric's edit and its two added blocks, which the deletes never touched, and created the file's `s2` as a new block. So the user's deletes were undone and a twin appeared on the page: a data-integrity bug, not a test-model mistake.

### The fix

`closest` ranks each text by the file's lines it does not hold, the lines the user must have typed, then by the old two-sided difference, with ties going to the newest. Deleting lines from the newest text can no longer make an older, shorter text the base.

The tie-break came from review. With the first key alone, a stale save that only deletes lines ties the older and the newest texts, and the newest won. A block Agaric added after the editor opened then read as deleted and was lost unseen. Ranked this way, an ambiguous file can at worst bring back a block the user deleted, never silently delete one.

The stale-editor case still picks the older text, because a stale save holds edited lines only the older text explains (`a_save_from_a_stale_editor_does_not_undo_what_agaric_wrote_since`).

### Tests

- `deleting_paragraphs_after_two_added_blocks_duplicates_none` (`tests/command_integration/mirror_convergence.rs`) is the shrunk case as a named test. It was red on `main` with the same duplicate.
- `deletes_and_adds_on_both_sides_duplicate_none` is a second shape the proptest found in #6570's run: blocks deleted in Agaric, and lines added and deleted in the file, across two ticks. Under the old metric it fails with `s0` duplicated; it passes with the fix.
- `tests/proptest-regressions/mirror_convergence.txt` holds both seeds, so the proptest replays them first. With the old metric planted, the proptest fails on them.
- `a_stale_save_that_only_deletes_lines_keeps_a_block_agaric_added_since` (`src/mirror/ingest_tests.rs`) is the review's case: the editor opens `a b c`, Agaric adds `d`, the editor saves `a c`, and the page keeps `d`. It was red under the first key alone, which lost `d`.
- Falsifications, each in one command that restored on exit:
  - without the first key, the duplicate regression fails;
  - without the tie-break, the delete-only stale save fails;
  - always taking the newest text fails the stale-editor test.
- 256 random cases of the proptest with the old metric planted did not find the bug, so the named test is what pins it.
- All 96 mirror tests of the `agaric` package pass. `cargo clippy -p agaric --all-targets -- -D warnings` is clean.

## Session 3826 — Benches for the Markdown mirror

#5363's Performance boxes: the Criterion group, the `apply_page_source_inner` merge cost on a large page, the polling scan's idle cost, the re-scan after a snapshot catch-up, and the boot check.

### Premise check

- `mirror_startup_pass/10000`: the first tick of a freshly opened mirror over a folder it already wrote. It is a full pass that writes nothing.
- `mirror_idle_tick/10000`: a tick with nothing to write. It is the polling scan, one stat per file and per folder, paid every `TICK`.
- `mirror_catchup_pass/100000`: the full pass a sync naming no page asks for, at 2K pages × 50 blocks.

The shape probes:

- The setup checks one file per page and nothing diverged or failed.
- After timing, the dirty, large-page and merge cases check their writes landed, and the idle case checks it wrote nothing.

### Numbers

All numbers come from `cargo bench` with `CARGO_PROFILE_BENCH_LTO=false CARGO_PROFILE_BENCH_CODEGEN_UNITS=16` (not the shipped thin-LTO profile), on a shared cloud box at load 1.4 to 3.3. | Case | Time |
|---|---|
| dirty tick, 10 pages | 41.7, 43.8, 44.9 ms |
| dirty tick, 100 pages | 277, 292, 309 ms |
| dirty tick, 1000 pages | 0.83, 0.97, 1.23 s |
| large page tick, 2K blocks | 57.4, 58.4, 59.7 ms |
| startup pass, 10K pages | 6.98, 7.11, 7.24 s |

## Session 3803 — Trash rows say when they were deleted, in the browser mock

On the mock backend (`npm run dev`, the e2e lane), every trashed row read "Deleted: NaNd ago".

- Cause: `nextCohortMarker()` stamped `deleted_at` as an ISO string with a `#000001` sequence suffix, which no date parser reads. The backend stamps the delete op's `created_at`, an epoch-ms integer (`blocks.deleted_at` is INTEGER since migration 0080).
- Fix: the marker is an epoch-ms number, at least one past the last so two deletes in one millisecond still get distinct cohorts. `list_trash` keys its order and cursor on the number, as the backend's `Cursor.deleted_at: Option<i64>` does.
- Why conformance missed it: the snapshot normalizer turned any non-null `deleted_at` into `'DELETED'`, so the type never reached the comparison. It now maps only a number to the sentinel and passes anything else through raw. With the old marker, the conformance test fails on every fixture that deletes.
- Test: `e2e/trash-deleted-time.spec.ts` deletes a block and requires its Trash row to read "Deleted: just now". It went red on the old marker with "Deleted: NaNd ago".
- Test edit: `revert.test.ts` pinned the marker as a string. It now pins a positive number, the backend's type.
