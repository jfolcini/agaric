# Session 1486 — Mutants shard matrix (#3393, steps 2 and 3)

The weekly Rust mutants lane ran `cargo mutants --in-place --workspace` inside a 90-minute wall budget and tested 11 of the 691 mutants it generated. Mutant order is deterministic and ordered by package, so the same 11 were tested every week, all of them in `src/reverse/`, and `agaric-store`'s `op.rs` and `op_log/` — the hash-chain core the lane was created for — were never mutated at all. #3393's narrowed scope of 2026-09-02 asked for three things in order: measure the per-mutant cost on the runner, derive the shard count from that number, then shard the lane. Session 1483 shipped the measurement as a dispatch-only probe workflow (PR #4614). This session spends those numbers and deletes the probe; what follows is the whole derivation, because the probe workflow that produced half of it no longer exists.

## The numbers

From the weekly lane's own uploaded outcomes (run 33384085834, 2026-08-31, cargo-mutants 27.1.0, 4-vCPU `ubuntu-24.04`): the workspace baseline cost 1088 s (370 s build, 718 s test); of the 11 mutants tested, the 6 viable ones cost a mean 600 s each (128 s incremental build plus a 473 s run of the whole `agaric` nextest suite) and the 5 unviable ones 67 s, since an unviable mutant stops at the build. Generated mutants split 183 `agaric` / 383 `agaric-engine` / 125 `agaric-store`.

From the probe (run 33681606316, 2026-09-02, `-p agaric-store --shard 0/25 --sharding round-robin`): a package-scoped baseline cost 164 s (76 s build, 87 s test) against the workspace's 1088 s, and a viable store mutant cost 117 s (29 s build, 88 s test) against `agaric`'s 600 s.

A shard's capacity is `floor((wall budget − baseline) / cost of one viable mutant)`, with every mutant assumed viable — the conservative side, since an unviable one is about six times cheaper. A package's shard count is then the smallest `n` whose LARGEST slice fits that capacity: round-robin gives shard `i` the mutants `i, i+n, i+2n, …`, so what has to fit is `ceil(generated/n)`, not the average. The budget stays 5400 s, now per shard.

A baseline and a mutant do not cost the same thing: a baseline pays a full build plus the suite, a mutant an incremental build plus the same suite. So `agaric`'s baseline is its 370 s build plus its 473 s suite — ~843 s, not the ~600 s a mutant costs (128 s incremental build + the same 473 s).

| package | generated | baseline | per viable mutant | per shard | shards |
|---|--:|--:|--:|--:|--:|
| `agaric` | 183 | ~843 s | 600 s | 7 | 27 |
| `agaric-store` | 125 | 164 s | 117 s | 44 | 3 |
| `agaric-engine` | 383 | not measured | not measured | 44 | 9 |

`agaric` : `floor((5400 − 843) / 600)` = 7 per shard, and `ceil(183/27)` = 7 fits where `ceil(183/26)` = 8 does not → 27. `agaric-store` : `floor((5400 − 164) / 117)` = 44, and `ceil(125/3)` = 42 → 3. `agaric-engine` : capacity 44 as well (below), and `ceil(383/9)` = 43 fits where `ceil(383/8)` = 48 does not → 9. **39 shard jobs**, which on a public repo cost nothing but wall-clock.

`agaric-engine` is the one row not measured, and it is sized on `agaric-store`'s measured cost — the nearest comparable case, a package-scoped crate with its own in-crate suite — rather than on a number invented for it. It has one: 458 `#[test]` / `#[tokio::test]` functions across 23 files under `agaric-engine/src` (`loro/engine/mod.rs` 84, `import.rs` 78, `loro/projection.rs` 65, `draft/tests.rs` 36, `loro/engine/snapshot.rs` 32, plus `loro/engine_proptest.rs`), so `-p agaric-engine` pays a build AND a real suite per mutant, and its survivors are exactly as trustworthy as any other package's. The estimate is the part to distrust: if those shards report PARTIAL coverage every week, it was optimistic and the package needs more shards. That is what the per-package split in the merged summary is for.

The wall budget is the free variable in all of that, and it stays 5400 s. Raising it buys fewer, longer shards — at 20400 s the same arithmetic gives 32/173/173 per shard and 6/1/3 = 10 jobs, so 10 redundant baselines instead of 39 (27 × 843 s of `agaric` baseline alone) — but it costs wall-clock: GitHub allows 20 concurrent jobs on a Free account and caps a job at 6 h ([Actions limits](https://docs.github.com/en/actions/reference/limits)), so 39 short shards finish in ~2 waves of ~90 min ≈ 3 h, while 10 long ones are one wave of ~5.5 h (`843 + 31 × 600` s for an `agaric` shard) with barely 30 min under the hard cap for a suite that grows weekly. On a public repo the runner minutes those extra baselines burn are free and the latency is not, so: keep 5400.

`--sharding round-robin` rather than the default `slice`: a shard that runs out of budget then leaves a gap spread across the package's files instead of a tail of one file, so the partial coverage a shard reports is a sample rather than a prefix. Each shard still runs its own baseline — `--baseline=skip` would buy back one baseline per shard, but the zero-coverage guard from #3057 is built on a `Success` baseline in that shard's own `outcomes.json`, and this lane's whole history is false greens that nothing could see. The capacities above already pay for it.

## What shipped

`mutants` is a `fail-fast: false` matrix of `{package, shard, shards}`, one flow-style line per entry. The comment over them carries the shard counts and a pointer here; the derivation is stated once, above, rather than a third time in the workflow. Each shard uploads `mutants-out-<package>-<shard>` (upload-artifact v7 rejects duplicate names) and runs the zero-coverage guard unchanged in substance, per shard, so one dead shard reds itself rather than hiding inside a merged total. cargo-mutants is pinned to `27.1.0` — the version every number above was measured under, and the version whose mutant ordering the shard denominators divide.

`mutants-merge` downloads `mutants-out-*` into one directory per shard and concatenates them back into the single `mutants.out` layout the summary step and `file-mutation-survivors` have always read: the four `.txt` lists are one finding per line and the shards partition the mutant set, so concatenation is the union; `outcomes.json` sums `total_mutants` and concatenates `outcomes[]`; `mutants.json` is the concatenation of the per-shard slices, which the shards partitioning the mutant set makes the union — no `unique`, which could not fix a double count, only hide one, and would shrink the `generated` denominator the summary reports against. Nothing downstream learns about shards. The summary step moved into that job. The merge also counts the shards that uploaded an `outcomes.json` against what the matrix declares, because a short merge is indistinguishable from real data downstream: the missing shards' survivors are simply absent from `missed.txt`, which `file-mutation-survivors` diffs against the tracking issue's marker block, its only cross-run memory, so the absent lines report as "Resolved since last run", leave the tracked set, and come back as new the following week (#3364). With `fail-fast: false` across 39 jobs the realistic failure is a handful of dead shards, so the fix is NOT to throw the week away: the partial merge is published — its artifact and summary are the shards that did run, which is real signal — and the counts ride out as job outputs so `file-mutation-survivors` runs `--dry-run` when they disagree. Dry-run performs every read and skips only the `gh issue edit`/`comment` writes, so the body it would have written still lands in the log; the marker block is what is protected. A `::warning::` in the merge and another in the filer name both counts and say why. Only a merge with nothing in it fails, as before — there is no artifact to publish, and the filer's `--require-rust` reds on the absent `missed.txt`. Fail-closed detail: `mutants-merge` dying outright leaves both outputs empty, which the filer's expression counts as short. The expected count comes from `check-mutants-scope.mjs --shard-count`, which reads the matrix — the guard already parses it, and a second hand-written copy of the shard total is the drift that guard exists to catch. Shards are counted by `outcomes.json` files rather than by directory, which keeps the count independent of how `actions/download-artifact` lays the extraction out. Whether one dead shard in 39 turns out to be the rare case this assumes or the usual one is the first thing to read off the early crons: while it holds, no survivor is filed or cleared that week, which is the safe side of #3364 but not a state to leave standing. If it proves weekly, the fallback is to scope the short-merge check per package, so a dead `agaric-engine` shard stops suppressing `agaric-store`'s survivors. The second thing those crons settle is whether `mutants.json` under `--shard` is that shard's slice rather than the full package list, which the summary's "of N generated" denominator and the per-shard PARTIAL notice both rest on; if it is the full list, every shard reports PARTIAL from the first run and `agaric`'s denominator inflates ~27x. Cosmetic either way — the zero-coverage guard gates on `total_mutants` and the baseline, never the ratio. `file-mutation-survivors` now needs `mutants-merge`, and `report-scheduled-failures` needs both.

`scripts/check-mutants-scope.mjs` had to learn the matrix, because the matrix is now the lane's statement of scope: the invocation says `-p "$PACKAGE"`, and what keeps all four `examine_globs` entries reachable is the union of the matrix's `package` column, not any one job. It resolves that token only when the job also maps `PACKAGE: ${{ matrix.package }}`, and reports `package-selection-unknown` otherwise rather than guessing. It also fails when a package's shard indices are not exactly `0..n-1` for the `shards` denominator its entries declare: a missing index is a slice nobody tests, and it drops its mutants out of the summary's tested count *and* its generated count, so no downstream reader can tell it from a smaller package. `--shard-count` prints how many jobs that matrix declares, for `mutants-merge` above; it exits 2 with empty stdout when it cannot read a matrix, because a count of 0 is a comparison every merge trivially clears.

The probe workflow is deleted. It measured what it existed to measure and its numbers are in the table above.

## Verified

`node scripts/check-mutants-scope.mjs` and its `--self-test`, plus `src/__tests__/check-mutants-scope.test.ts` (4 tests). The guard's three new failure paths were falsified against a copy of the workflow, each restored afterwards: dropping one `agaric` shard entry reports `shard-matrix-incomplete` with the gap listed; dropping the `PACKAGE: ${{ matrix.package }}` mapping reports `package-selection-unknown`; renaming one package's entries to a package the globs do not reach reports the incompleteness on both sides of the rename. `--shard-count` was run against fixture roots declaring 2 and 3 shards, and its fail-closed path was falsified against a copy of the guard: made to print `0` instead of exiting, the vitest case reddens (`expected +0 to be 2`), and the copy was restored. The merge shell was extracted and run against a two-shard fixture: against a 2-shard matrix it merges silently (`total_mutants` summed, both `missed.txt` lines, both `mutants.json` entries) and reports `merged=2 expected=2`; against a 3-shard one it publishes the same merged output, emits the `SHORT MERGE: only 2 of 3` warning and reports `merged=2 expected=3`, which is what puts the filer in `--dry-run`. `actionlint` type-checks the `needs.mutants-merge.outputs.*` the filer reads — renaming one to a non-existent output reds it, which is how that wiring was falsified. `prek run --files` over the changed files: actionlint, zizmor, oxlint, oxfmt, typos and the rest pass.

Not verified here: an actual sharded run. The first weekly cron is the first real measurement of the derivation, and the per-package split in the merged summary is what says whether it holds — a package testing well under its generated count every week needs more shards. cargo-mutants' flag semantics were read from its book rather than assumed: `--shard k/n` with `k` in `0..n-1`, `--sharding round-robin` assigning mutant `i` to shard `i % n` (the default is `slice`), and package selection where `-p` scopes generation while the test scope follows it — the baseline "runs the tests from all and only the packages for which mutants will be generated" and "each mutant runs only the tests from the package that's being mutated", which is what makes a package-scoped shard affordable at all.

A review round found the short-merge gate counting the wrong thing, and it is worth stating why the wrong version looked right. `merged` was `find shards -name outcomes.json | wc -l`, and uploading is not the same as having results: the per-shard upload is `if: always()`, and a shard whose baseline fails or times out still writes an `outcomes.json` carrying that verdict and an empty `missed.txt`. The week that breaks it is the one this job's own comment predicts — the `agaric` suite outgrowing `--timeout` — where all 27 of its shards abort on a Timeout baseline, every one uploads, `merged` reads 39 of 39, and the filer runs live against a `missed.txt` missing every `agaric` survivor. `--require-rust` passes on empty-but-present (its own case asserts that), so all of them report as "Resolved since last run" and come back as new next week: #3364 at package scale, in the week the mechanism was added to prevent it. The gate now counts only shards whose `Baseline` summary is `Success`, which is what the per-shard zero-coverage guard already means by a usable shard, and names each excluded shard in a warning. "Nothing to merge" became "nothing usable to merge".

The same round found the guard blind on the half of the plumbing sharding moved. `checkOutputPlumbing` is scoped to the `mutants` job, and that job still uploads `mutants-out-<package>-<shard>` correctly — but the single `mutants-out` artifact the filer downloads is now produced by `mutants-merge`, which nothing checked. Renaming or re-pathing it would leave the guard green and red `file-mutation-survivors` on the next cron a week later, with a message about the filer: the #3386/#3387 shape the guard exists for, reintroduced by the change that created the second job. `checkMergeProducer` closes it, as the producer-side twin of `checkFilerPlumbing`. All three of its paths were falsified against a copy of the workflow and restored: renaming the merged artifact reports `merge-upload-missing`, uploading it from `.` reports `merge-upload-path-mismatch`, renaming the job reports `merge-job-missing`. The first version of that last path crashed instead of reporting, because `jobLines` returns `undefined` rather than `[]` for an absent job — fixed to match `checkFilerPlumbing`, which had it right. The self-test was itself falsified: forcing the path comparison true reds it (`1 assertion(s) failed`), and the copy was restored.

One number in the `--timeout` comment was misattributed, and the review round that caught it read the consequence correctly from what the comment claimed. Run 30981051402's baseline TEST phase of 604 s is a WORKSPACE figure — all three packages' suites, which run 33384085834 measured at 718 s four weeks later — and the comment asserted it was still `agaric`'s number "because `-p agaric` runs that same suite". It does not: `agaric`'s own suite is the 473 s the derivation spends, and 718 − 473 is the other two packages. Read the comment's way, `agaric`'s baseline would be 974 s and capacity 6, so `ceil(183/27)` = 7 would not fit and all 27 shards would report PARTIAL from the first cron. Read correctly, sharding WIDENED this headroom rather than spending it — the phase `--timeout` applies to is now one package's suite, 473 s against 900 s (1.90x, where the workspace figure gave 1.49x). The derivation was right and the comment about it was wrong, which is the more dangerous of the two, because the comment is what the next person sizing this lane reads.

Also from that round: `checkOutputPlumbing` and `checkMergeProducer` had grown separate upload-step scanners with subtly different regexes, so the artifact `name:` was parsed two ways. `uploadsIn(lines)` is now the single reader returning `{step, name, path}`, with `normalizeUploadPath` beside it; the one subtlety — `name:` being both the step name and the artifact name, told apart by the list dash and not by value — is stated once instead of twice. All five plumbing paths were re-falsified against a copy of the workflow after the refactor and restored: `merge-upload-missing`, `merge-upload-path-mismatch`, `merge-job-missing`, `artifact-path-mismatch`, `artifact-upload-missing`. The `artifact-upload-missing` message also still told the reader that `file-mutation-survivors` downloads the `mutants` job's artifact; since this PR it downloads `mutants-merge`'s, so the message now names the shard-then-merge path it actually breaks.

A later round found the one pair sharding created that nothing related: `mutants` names its per-shard upload `mutants-out-<package>-<shard>` and `mutants-merge` downloads it by `pattern: mutants-out-*`, in two jobs 40 lines apart. Rename either alone and the merge downloads zero artifacts while the guard, its self-test and the vitest suite all stay green; it reds a week later as `merged=0`, one cron after the survivors went unfiled. `checkShardPattern` compares the glob against the names the shard job actually uploads. Closing it needed `uploadsIn`'s artifact-name regex widened from `(\S+)` to `(.+?)`: the per-shard name interpolates `${{ matrix.package }}`, whose braces contain spaces, so the name the pattern has to agree with was the one name the reader could not see. Falsified against a copy of the real workflow and restored: renaming the shard artifact to `shard-${{ matrix.package }}-${{ matrix.shard }}` reports `shard-artifact-pattern-mismatch` and exits 1.

The short-merge warning was also saying the wrong thing about right code. It claimed the merged artifact covered "only the $merged shards that ran", but the concatenation loops over every shard that uploaded, unusable ones included — which is precisely what makes a dead package render as `0 of N  <-- NOT COVERED` rather than vanishing from the summary. The sentence was corrected to describe that, not the code.

A third thing the first cron settles, and the one with teeth. `agaric`'s shards are sized at exactly capacity — 7 mutants of a 7-mutant slice, ~5043 s of the 5400 s budget, 6.6% headroom — against a suite the step's own comment says grows every week. A shard that gets through 6 of its 7 before the wall budget stops it still has a **Success** baseline, so it counts toward `merged`, the merge is not short, and the filer runs live. The untested mutant's survivor is simply absent from `missed.txt`, so it reports as "Resolved since last run", leaves the tracking issue, and returns as new the following week: #3364 again, at a granularity below the one the merge gate watches.

The gate deliberately does not close this yet. The signal that would close it is the per-shard PARTIAL notice, whose denominator is `mutants.json` — and whether that file under `--shard` is the shard's slice or the full package list is itself unsettled (above). Wire PARTIAL into the gate under the wrong reading and every `agaric` shard reports partial from the first cron, putting every week into `--dry-run` permanently: nothing filed, nothing cleared, lane green. That is strictly worse than the gap it would close. PARTIAL is not the only candidate, though, and saying it was overstated the case: `timeout`'s own exit status is independent of the `mutants.json` question entirely, and line 1081's `|| true` currently throws it away. Whether it reliably surfaces truncation is its own question — the wrapper uses `--signal=INT`, and if cargo-mutants catches SIGINT and exits on its own terms, `timeout` may report that status rather than 124 — so it is a second thing to read off the first cron rather than a fix to reach for now.

So the order is fixed — read `mutants.json`'s semantics and `timeout`'s exit behaviour off the first cron, then decide whether a truncated shard should count as unusable. Until then the PARTIAL notice is a log line a human reads, not a gate.

Declined from the same round: pinning `--shard-count` to 39 in the vitest case, which asserts only `/^[1-9]\d*$/` today. The number is derived from the matrix precisely so that no second copy of it exists to drift, and a test asserting the literal would be that second copy. What carries the load is the matrix-completeness check, which reds when a package's shard indices are not exactly `0..n-1`.

Out of scope, and stated here so it is not mistaken for an oversight: the `examine_globs` widening and the filer's third "untested" state were both dropped from #3393 by the maintainer on 2026-09-02. The widening is worth revisiting only after a full pass over the current surface has actually run.
