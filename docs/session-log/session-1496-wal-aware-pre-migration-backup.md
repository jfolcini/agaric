# Session 1496 — the pre-migration backup did not include the WAL tail

#3267 was narrowed on 2026-09-02 to one of its three findings: replace the raw `std::fs::copy` in `backup_db_before_migration` with a WAL-aware snapshot, drop the `PRAGMA wal_checkpoint(TRUNCATE)` from the `make_migration_pending` fixture, and add a test that leaks a hot `-wal`. Widening the trigger to damaged at-head vaults and the partial-copy cleanup were dropped.

The vault runs WAL with a 5000-page autocheckpoint, and nothing checkpoints at shutdown: `RunEvent::Exit` persists Loro snapshots only, and the maintenance checkpoint job is gated on `!is_foreground` with a 3600 s interval, so it never fires during an active session. A `-wal` therefore survives every exit, and the backup — a copy of the main `.db` alone — held the vault as of the last autocheckpoint, not as of the last commit. Restoring it was worse than lossy: the post-migration `-wal` sits beside the restored file, so SQLite replays stale frames onto it on the next open. `snapshot_vault` runs `VACUUM INTO` over a short-lived read-only connection instead. That reads through the WAL and writes one self-contained file, so the snapshot holds every committed transaction and restoring it needs no `-wal`.

The fixture's `PRAGMA wal_checkpoint(TRUNCATE)` is gone, so the tests no longer pre-satisfy the guarantee they are meant to check, and `backup_created_and_byte_identical_when_migration_pending` became `backup_created_with_vault_content_when_migration_pending`: `VACUUM INTO` rebuilds pages, so the backup is a logical snapshot and a byte comparison would assert the wrong thing. It opens the backup as a SQLite file and compares `_sqlx_migrations` counts. `backup_includes_rows_still_in_hot_wal` is the new one: it commits three rows, then `std::mem::forget`s the pool rather than dropping it, because a clean close checkpoints and deletes the WAL, which is exactly what a killed process never does.

**A raw-copy fallback had to be added, and the falsification is what found it.** `VACUUM INTO` cannot open a file SQLite will not read — and that is precisely the fail-safe branch above it, where an unreadable `_sqlx_migrations` is treated as PENDING so that a vault in unknown condition is backed up before a migration touches it. The first draft failed `backup_created_when_pending_state_undeterminable`, an existing #3062 test, on its own baseline: the snapshot errored, nothing was written, and the vault a migration is most likely to damage was the one vault with no copy. The `Err` arm now removes any partial target (`VACUUM INTO` refuses a target that exists) and falls back to `std::fs::copy`. That copy cannot carry a `-wal` tail, but nothing can read one beside a main file SQLite rejects, so a byte copy is all such a file admits.

Falsified against a copy, restored and `cmp`-verified. Reverting `snapshot_vault` to `std::fs::copy` reddens `backup_includes_rows_still_in_hot_wal` and nothing else; dropping the fallback reddens `backup_created_when_pending_state_undeterminable` and nothing else. The pair is what the two arms need: either mutation alone leaves the other half unpinned.
