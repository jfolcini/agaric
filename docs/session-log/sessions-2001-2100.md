## Session 2099 — Graph: keep each page link's shared space on `page_link_cache`

#5426 item 4 follow-up, a migration the maintainer approved on the issue. The
space-scoped graph read (`list_page_links`) checked both ends of every cached
edge against the space's live pages. The problem-tier probe measured it at
424–478 ms against a 200 ms budget at 100K.

Migration 0122 adds `page_link_cache.space_id`: the space both pages share, or
NULL for an edge between spaces, an edge with a space-less end, or an edge whose
target is not a page. It depends only on the two pages' `blocks.space_id`. Every
path that changes a page's space queues `RebuildPageLinkCache`: the `space` op's
dispatch arm is new, and sync, restore and space purge already rebuilt. Every
writer computes the same expression: the incremental reindex, both rebuilds
(now in 7-column chunks) and the reconciliation oracle, which folds it
independently. A covering partial index on `(space_id, edge_count DESC, …)`
makes fetch and count a range read. `idx_page_link_cache_live`, whose only
reader went with #5415, is dropped. Between a space change committing and its
background rebuild, a moved page's edges show in its old space, the same
bounded staleness the 0096 flags already have.

The old read and the #5547 read stay as `#[cfg(test)]` oracles. Tests:
- the 0122 backfill, including the dropped index;
- a parity test of fetch and count against both oracles;
- an EXPLAIN test pinning `USING COVERING INDEX idx_page_link_cache_space`;
- writer agreement across the reindex and both rebuilds;
- the oracle catching a stale `space_id` in both directions;
- an end-to-end `move_blocks_to_space` test.

Test fixtures that cached links before stamping spaces now stamp first, as a
real vault would. The 3894 dangling-key test seeded a vault at 0110 and then ran
today's reindex, so it now migrates to head first.

Falsified on copies in the lane:
- dropping the dispatch arm's rebuild turned the move, 5275 and placement tests
  red;
- unscoping the fetch turned the parity and EXPLAIN tests red, and five
  existing `list_page_links` space tests.

The review also caught a plan comment that overclaimed (with planner statistics the count can scan a one-space cache, still
far under the old read), and a stale "never holds cross-space rows" comment in
`block_links.rs`.

Suites run:
- `just gen-sqlx` against a migrated scratch database, after each merge of
  `main`;
- nextest on the graph, page-link, migration, `db::tests`, cache, materializer,
  reconciliation and conformance subsets: 942 passed;
- clippy and `cargo doc` with the CI lint flags.

## Session 2098 — Page aliases are ops, undoable and synced like tags

Aliases used to live only in `page_aliases`, written in place with no op, so
they could not be undone and never reached another device. Two op types,
`AddPageAlias` and `RemovePageAlias`, now carry every alias change (approved on
#5387). They go through the op log and one new Loro root, `page_aliases`, per
page; SQL is a projection of it. `ENGINE_FORMAT_VERSION` is 3, so a peer still
on 2 is refused at the handshake instead of receiving ops it cannot apply.
Page-level undo inverts them, history lists them, and a one-time backfill at
boot (`repair_page_aliases`, idempotent, as housekeeping) turns each device's
legacy rows into engine state.

Review found three defects, each fixed with a test shown red first:

- A contested alias (two devices claim one alias for different pages offline,
  most likely through each device's legacy backfill) converged in the engine
  but projected to different pages on each device. Reprojection now gives it to
  the lowest page id, an `EXISTS`-guarded eviction; forward projection keeps
  first-claim so a replayed old op never takes a row from a newer one. The
  issue said "first page by op order"; the engine has no cross-page order. A
  two-device real-socket test pins it.
- A peer's alias ops were indexed with `op_log.block_id = NULL` because the
  payload carries `page_id`, so page history never listed them on the
  receiving device. `extract_indexed_ids_from_payload` falls back to `page_id`.
- A cross-space page move dropped the page's aliases from the new space's doc;
  hydration now seeds them.

`src-tauri/migrations/AGENTS.md` said aliases have no op-log entries; it now
says `page_aliases` is a projection of the engine root that only disaster
recovery reprojects, not boot (maintainer approval in this session). The same
claim was aligned in `prek.toml` and `db/tests.rs`.

Gates: whole-workspace nextest (6868 run, 0 failed, 8 partitions), clippy,
`SQLX_OFFLINE=true cargo check --workspace --all-targets`, `just gen-sqlx`
(one new entry for the eviction in the root, engine and sync caches),
bindings unchanged, conformance fixtures reproduced, vitest on the touched
frontend and the mock, `npm run typecheck`. Not run here: the e2e-tauri
alias-undo spec, which needs the real backend lane.

## Session 2093 — Agenda filters: push `filtered_blocks_query` down to id sets

#5426 item 3. `filtered_blocks_query_inner` walked `blocks` in id order and
tested every row with correlated `EXISTS` subqueries, one per property or tag
filter. A rare filter therefore scanned the whole space. The new
`interactive_slo` probe (a key on 20 of 100K blocks) measured 22.69 ms against a
10 ms budget before the change.

The base SQL is now static per call shape:
- `+b.space_id = ?` always, with the `+` keeping the planner off
  `idx_blocks_space_type` and its sort;
- `b.block_type = ?` only when set;
- `b.id > ?` only with a cursor.

A non-reserved property filter becomes `b.id IN (SELECT bp.block_id FROM
block_properties bp WHERE bp.key = ? …)` with the unchanged value predicate.
Tag filters become id-set subqueries over direct, ref, inherited and prefix
tags: one `IN` per clause in AND mode, one `IN` over a `UNION ALL` in OR mode.
Reserved columns and the soft-delete filter are untouched. The old composition
is a `#[cfg(test)]` oracle.

The trade, accepted on #5426: a filter matching a dense id set builds that set
in full before the `LIMIT`. Presence of a key nearly every block carries, an
`eq` on a value almost every block shares, and a tag on every block each go
from about 0.1 ms to about 30 ms at 100K. A report-only problem-tier probe
measures the broad-key case.

Tests:
- A parity test pages the production function against the EXISTS oracle with a
  small limit, over every operator, the four reserved columns, direct/ref/
  inherited/prefix tags (including an escaped `%`), and/AND/xor modes,
  `block_type` and the cursor.
- An EXPLAIN test pins the id lookup on `sqlite_autoindex_blocks_1` and
  `idx_block_props_key*`, with no correlated step and no temp sort.

Falsified on copies in the lane:
- dropping the `+` turned the EXPLAIN test red;
- dropping the inherited-tag arm turned the parity test red.

The review also ran a differential fuzz of both SQL shapes in SQLite over about
16,100 random pages and found no difference. It found three stale "composed
`EXISTS`" comments, now corrected.

Suites run:
- nextest on the filtered-blocks, query, agenda and conformance subsets, plus
  the bindings test;
- clippy and `cargo doc` with the CI lint flags, after merging `main`;
- the `bench-slo` lane before the change.

## Session 2092 — Pages: seek a path glob's literal head on the title index

#5426 item 2. `PagesTreeSection` lists a page's children with the path glob
`<title>/*`. `PagesProjection::compile_path_glob` compiled every glob to
`LOWER(title) GLOB ?` over `pages_cache`, a full scan, run twice on a first page
(fetch and COUNT). The new `interactive_slo` probe (`Notes/*` among 100K pages)
measured 13.45 ms against a 10 ms budget before the change and 0.73 ms after.

A pattern with a literal head before its first `*`, `?` or `[` now also bounds
`title COLLATE NOCASE` to `[head, head with its last char bumped)`, a range seek
on `idx_pages_cache_title_nocase`. `prepare_globs`, `LOWER()` and NOCASE all
fold ASCII only, so every title the GLOB matches lies inside the range: the
range is a necessary condition and the result set is unchanged. A pattern with
no literal head, or whose last head char cannot be bumped, keeps the GLOB alone.
The old body stays as a `#[cfg(test)]` scan oracle.

Tests:
- A parity test runs the range and the scan oracle over a mixed corpus,
  include and exclude, across brace, class, `?`, accented, uppercase and
  DEL-ending patterns.
- A unit test pins the exact bounds.
- An EXPLAIN test pins the index on the real composed IPC SQL.
- Two conformance vectors (`PROJ*`, `Café*`) run on both the backend and the
  TypeScript side.

Falsified on copies in the lane:
- dropping `COLLATE NOCASE` from the range turned four tests red: the EXPLAIN,
  parity, exclude and conformance tests;
- dropping the bump turned five red, the bounds and parity tests among them.

The review found the claim "only the alias differs" in
`docs/architecture/filters.md` and two test comments, now corrected.

Not changed: a one-letter head that matches most pages walks the index plus a
row lookup per hit and can be slower than the scan. `PagesTreeSection` always
sends a full title as the head.

Suites run:
- nextest on the glob, `list_pages_with_metadata`, pages-metadata, filters,
  query and conformance subsets;

## Session 2091 — Week view: copy, cut and paste a selection across days

The journal week view mounts one `BlockTree` per day, and every tree runs the
copy/cut/paste listener over the one global selection. Each tree filtered the
selection to the ids its own store held, so a selection spanning two days was
copied twice (each day's share, in whichever order the listeners ran), cut
removed both shares but left a clipboard holding only one, and paste landed once
per day that held a selected block.

Only the tree whose store owns the anchor (the last selected id) now acts.
`selectionByPage` collects the selection roots of every mounted page store
(`forEachPageStore`) and orders the pages by the document position of their
first root. Copy renders each page with its own `get_blocks_source` call,
because the backend renders one page per call, and joins the text in that
order. Cut removes blocks only after the clipboard write resolves, and nothing
at all when any page fails to render. Paste lands once, after the anchor.
Single-day behaviour is unchanged.

Tests:

  writes and removes nothing when one day fails to render. They went red with
  the per-tree gate restored, with the document-order sort disabled, and with

  and check copy, cut and paste end to end.

## Session 2082 — Review notes from #5550

Three non-blocking notes from the #5550 review, which made a focus move
re-render only the trees that own the old or new block.

1. **The reveal effect's ownership guard was dead.** `BlockTree` reads
   `focusedBlockId` through a selector that returns the id only when this

## Session 2080 — The e2e-tauri lane reaps an app that outlives its session

The real-backend WDIO lane sometimes wedged partway through: every spec after
one point timed out in `POST /session`. The cause is an orphaned app, not a spec.
`afterSession` SIGTERMs `tauri-driver`, which SIGKILLs `WebKitWebDriver` and
exits; if that driver had not yet closed the app, the app survives. It still
holds the `tauri-plugin-single-instance` name on the run's one shared D-Bus
session bus, so every later launch hands off to it and exits during plugin
setup, and `WebKitWebDriver` waits forever. Two wedged runs show it: after
spec 32 (run 38665925103) the passed spec's app keeps logging under its old
worker prefix 52 s after its worker exited, and each later app prints only the
AT-SPI warning, never the boot log that runs after plugin setup; run 38658790656
wedges the same way after spec 1. The two runs share no spec, so it is a race
between `deleteSession` and killing the driver.

`reapSessionApp` in `wdio.conf.ts` runs from `afterSession` before the sandbox
is removed: it finds this session's app in `/proc` by executable and its
`AGARIC_DATA_DIR`, gives it 2 s to exit, SIGKILLs any survivor with a warning
(`outlived the session`), and throws if it still has not gone. The connection
retry budget drops from 3 × 120 s to 1 × 30 s, so a wedged session fails in
about a minute instead of eight; every real request in the logs answers in
about a second.

Not run locally: the lane itself (no tauri-driver or WebKit driver here). The
`/proc` matcher was exercised in a scratch script against an orphaned
grandchild (found, prefix- and suffix-differing vaults not matched, gone after
the kill). Ran `tsc -p tsconfig.wdio.json`, oxlint, oxfmt, the vault-isolation
and driver-gate checks, and `npx vitest run e2e-tauri`. The PR's lane run is
the evidence; a wedge caught by the fix shows the `outlived the session` line
followed by the next spec booting normally.

## Session 2079 — Backlink panels: count the collapsed unlinked panel in SQL

#5422 asked whether the two backlink panels do more work than they show.
Stage 0 added two report-only problem-tier probes to `interactive_slo`.
The first is the collapsed unlinked panel (`list_unlinked_references` with a
limit of 1) on a title mentioned past the 10,000-row FTS cap. The second is
the linked panel (`list_backlinks_grouped`, limit 50) on a target with 5,000
backlinks spread over 100 pages. Their seeders give every block a `page_id`
and an `fts_blocks` row. `seed_blocks_bulk` sets neither, and the older
`backlink_query_bench` seeder makes orphans, so it only times the FTS scan.

The collapsed panel shows only a count. To get it, the list path pulled up to
10,001 FTS hits into Rust, resolved their root pages and grouped them. The new
read command `count_unlinked_references` runs the same capped FTS window,
taken from the SQL shared with the list path (`unlinked_fts_hits_sql`), and
counts it in one statement. `ROW_NUMBER() <= FTS_ROW_CAP` keeps the rows the
list path keeps. The root-page join drops orphans and self-references, the
same rows `unlinked_total_count` drops.

`useUnlinkedReferences` calls the count while the panel is collapsed and
unfiltered. With filters on, it keeps the limit-1 list call. The list path
stays live as the oracle: store tests assert that the count equals the list
path's `total_count` and `truncated` on these fixtures:
- plain matches;
- linked sources;
- matches on the target's own page;
- orphans;
- aliases;
- the space filter;
- exactly and past the cap;
- zero matches.

The mock handler derives its count from the list handler, and a conformance
query step pins both. The linked panel now moves its fetched rows into their
groups instead of cloning them, since a block has one root page.

Left out on purpose:

- **Deriving `total_count` from the group query:** it counts only the first

- **A per-group member cap in SQL:** it is exact only for the creation sort,

## Session 2077 — MCP batch and edit_page_markdown (#5399 slice 2)

Two read-write MCP tools. `batch { ops, space_id }` applies `append_block`,
`update_block_content`, `set_property`, `add_tag`, `remove_tag`, `move_blocks` and
`delete_block` ops in one transaction: each op is parsed as its tool's own arguments
and validated through that tool's checks (split out as `prepare_*`) before the
transaction opens, because the space check takes the writer on its own connection;
each op's new `_in_tx` half then runs inside one `BEGIN IMMEDIATE` with the engine
rollback armed. A call is one activity entry and one undo, and a batch that would
write more ops than one undo reverts is refused. `edit_page_markdown` saves an agent's
edit of a page's source through `apply_page_source_inner` with `merge: false`; `base`
is required and a stale one is refused with `RequiresRefresh`, because a merge keeps
blocks changed twice and an agent cannot review that. `get_page_markdown` gains
`editable: true`, which returns that source.

The old single-tool entry points now wrap the new `_in_tx` functions; the review
compared each old body with its wrapper pair line by line. `delete_block_inner` calls
`dispatch_deletes` instead of inlining the same post-commit calls. The rebase onto
main took `space_id` on `get_page_markdown` (session 2063) alongside `editable`.

Review fixes: the bulk-equivalence baseline recorded the ten new bulk-named
functions; `at_op` names `ops[i]` on a malformed ULID; tests for the engine rollback,
the post-commit emits and the delete fan-out, each shown red with its code removed.
Gates: clippy on the workspace, the whole workspace under nextest in four partitions
(one conformance test timed out at 60 s under load and passes alone),
`ts_bindings_up_to_date`, the bulk-equivalence guard.

## Session 2075 — Escape right after Enter no longer leaves a blank block

On the real backend, Escape can land while Enter's `create_block` is in flight. It
acts on the source block (its editor already flushed and emptied) and clears focus;
the create then answered and `handleEnterSave` focused the new blank block anyway,
so the editor came back after Escape and no later focus change ever left that block
for the empty-block cleanup. `dropBlankIfFocusLeft` in
`use-block-action-orchestration.ts` reads the live focus once the create answers:
when it has left the source and is not in the new block, the new block is removed
the way the cleanup removes one (`undoable: false`) instead of being focused.

The e2e-tauri controls waited on the wrong block for the same reason: while the
create is in flight, the source block's emptied editor already reads as blank.
`focusedBlankBlockId` became `enterBlankSibling`, which presses End and Enter and
waits for a blank editor in a block other than the one it left.

Specs: `e2e/escape-right-after-enter-cleans-blank.spec.ts` holds the create until
Escape has landed (10/10 red with the fix disabled on a copy, at the no-editor
assertion; 10/10 green with it); three orchestration unit tests (drop, keep when
focus is in the new block, log a failed remove), each shown red.
`e2e/journal-add-block-while-editing.spec.ts` relied on this bug to reach its
state; it now gets there with a plain Enter and still fails with its own guard
removed. Suites run: the orchestration, cleanup and BlockTree vitest files,
