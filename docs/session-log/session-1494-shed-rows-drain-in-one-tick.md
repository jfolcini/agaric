# Session 1494 — shed retry rows: their own backoff ladder, and a tick that drains

#3301-style narrowing applies here too: the maintainer's 2026-09-02 comment scoped #4208 to making `SHED_LAST_ERROR` rows eligible for a fast re-attempt "(or drain them in a loop until empty)" and re-measuring, and dropped import back-pressure and sweep-time coalescing. Both halves of the first clause turned out to be needed, for different reasons.

The ladder half is what the issue names. `materializer_retry_queue` escalates 1 min → 5 min → 30 min → 1 h, which is right for a task that keeps erroring and wrong for a task that never ran: a row persisted by a SHED lost a race for a queue slot, and the next sweep can win it. `BackoffClass::of` reads the `SHED_LAST_ERROR` marker #2541 already writes and puts those rows on 1 min → 2 min → 3 min → 5 min. Both ladders start at a minute — the sweeper's tick, the floor `lease_entry` depends on, and the point below which a shorter delay buys nothing because no sweep runs to consume it — and both reach their cap tier at `attempts >= 4`, so `metrics::note_persistent_enqueue`'s measure-item-2 counter keeps meaning the same thing. The shed ladder still escalates, so a permanently saturated queue re-offers a row every 5 minutes instead of spinning. `record_failure` picks the ladder from the `last_error` it is about to write and binds the four delays into the same SQL `CASE`, so the schedule stays defined in one place; `lease_entry` takes the class from the row it read.

The ladder alone does not close the issue, and it is worth saying why rather than shipping it as if it did. `sweep_once` fetches `SWEEP_BATCH_LIMIT = 64` due rows and `spawn_sweeper` calls it once per 60 s tick, so the queue retires at most 64 rows a minute whatever the backoff says. The issue's own N=5000 run left 17,932 shed rows: 17,932 / 64 = 281 sweeps, or about 4.7 hours to drain — which is the "minutes-to-hours" the issue measured, and it is a property of the batch and the tick, not of the ladder. Lowering the first rung from an hour to a minute moves nothing. So the tick now calls `sweep_until_no_progress`, which repeats `sweep_once` while a pass enqueues a FULL batch. The first version stopped on `re_enqueued == 0` and justified it with an invariant that is false, which review caught: `sweep_once` deliberately does not `lease_entry` a shed row (#2541) because the shed path's `record_failure` is spawned fire-and-forget, and the two `Err` arms push nothing either — so those rows keep their original `next_attempt_at`, and `fetch_due` orders by it ascending, so they return at the head of the next batch. A batch mixing `ApplyOp` rows (which go to the foreground queue and enqueue fine) with background rows that shed is positive and still re-grinds the shed ones. The condition is that a pass ADVANCED a full batch, counting the rows it leased and the rows it retired: both are gone from the next `fetch_due`, and the second round of review pointed out that counting only leases re-imposes the same 64-per-tick ceiling on the retirement arms (give-up, unknown `task_kind`, the five superseded-`ApplyOp` gates), which dispatch nothing — exactly the backlog a compaction or a burst of superseding edits produces. `sweep_once` keeps returning the enqueue count its log line and its tests are about; `sweep_once_counted` carries both, and the count that would be easy to get wrong is the one with three enumerable sites (shed and the two `Err` arms leave a row where it was), so `advanced` is `due.len()` minus those. The drain changes who waits, and the doc comment says so: persisted `ApplyOp` rows dispatch through `enqueue_foreground`, whose `send` blocks on a full 256-slot channel, so one tick offering 512 batches where it offered one keeps that channel busy for the whole drain and a user command queues behind it. Accepted rather than mitigated — the wait is FIFO over sub-millisecond handlers, bounded by the same 512, and those ops are unmaterialized primary state that has to be applied either way (#621). `MAX_SWEEPS_PER_TICK` stays, but it is no longer a spin guard — that is the condition's job now; it bounds one tick's wall clock so `spawn_sweeper` keeps reaching its `shutdown_flag` check, which the loop itself does not have. The boot pass uses it too, for the same reason: a previous session's leftovers are the same backlog.

Five new tests; the existing `backoff_schedule_escalates_then_caps` gained the explicit `Failure` class. `shed_backoff_schedule_is_short_and_capped_4208` pins the four rungs and asserts, for every `attempts` in 2..=50, that the shed delay stays strictly under the failure delay — the escalation is bounded, not absent. `backoff_class_reads_only_the_shed_marker_4208` pins that the marker alone selects the ladder, including that the other seed marker and a `None` stay on the failure ladder. `record_failure_shed_row_uses_the_shed_ladder_4208` and `sweep_once_leases_shed_rows_on_the_shed_ladder_4208` cover the two writers. `sweep_until_no_progress_retires_more_than_one_batch_4208` seeds 200 due rows and asserts both arms: one `sweep_once` moves exactly 64, and the loop retires the remaining 136 in the same tick — the pair, so a bigger batch would not pass for the fix. `sweep_until_no_progress_stops_on_a_shedding_pass_4208` covers the stop condition, using a `#[cfg(test)]` shed-allowance counter on the coordinator (the same shape as the existing `shed_persist_test_hooks`): the established way to saturate the channel takes the writer hostage, which would also block the `lease_entry` the enqueueing half of a mixed batch needs, so the two cannot hold at once. Its assertion is deliberately about row 65 — a row the FIRST batch never reaches. Asserting on a row inside that batch does not discriminate, because whether it is shed twice depends on whether its spawned `record_failure` committed before the next `fetch_due`, which on an idle test writer it usually has; written that way first, the mutation came back FLAKY rather than red. Row 65 has no such race: pass 1 fetches rows 0..=63, and a second pass fetches it either way (window 64..=127 with the sheds committed, 4..=67 without).

`sweep_until_no_progress_drains_a_retire_only_backlog_4208` covers the retirement half: 128 rows with a `task_kind` from a future version, all of which hit the unknown-kind retirement arm, so the tick re-enqueues nothing and the assertion is on the table being empty. Under a lease-only stop it retires 64 and leaves 64.

Falsified against copies, then restored and `cmp`-checked. The three ladder mutations were run by the builder agent, not re-checked here, against `cargo nextest run --workspace -E 'package(agaric) and test(retry_queue)'` before the drain test existed, so their population is 65 tests: collapsing `BackoffClass::of` to always return `Failure` left 62 passed, 3 failed — the classification test and both writer tests, and nothing else; collapsing the shed ladder onto the failure ladder's rungs left 63 passed, 2 failed — the schedule test and the lease test; post-restore 65 passed. The drain change was falsified separately over the same filter, now 67 tests and with `--retries 0` so a flaky pass cannot hide behind a retry: baseline 67 passed; reverting the stop condition to `re_enqueued == 0` left 66 passed and 1 failed — `sweep_until_no_progress_stops_on_a_shedding_pass_4208` alone, since `moved == 4` holds under both and the row-65 assertion is the only one that can go red — and the restore compared identical, POST 67 passed.

**Not re-measured here, deliberately.** The issue asks for a re-run of its N=1000 / N=5000 table, which was taken on 16 cores and 28 GB with a release build. This session's container has 4 cores and 15 GB, so a re-run would produce numbers that cannot be compared with the ones in the issue — a table that looks like evidence and is not. The arithmetic above (64 rows per 60 s against 17,932 shed rows) is what justifies the drain change and is reproducible from the constants; the 200-row test pins the behaviour. The comparable-hardware re-run stays open on #4208.
