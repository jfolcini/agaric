# Session 1560 — Group by a property or a date bucket from the picker

#4553 Phase 2, in the narrowed form the 2026-09-02 comment fixed: `GroupKey::Property` and `GroupKey::DateBucket` join the group-by picker on the advanced-query surface, and the buckets render through the grouped view that already exists. The summary table, expandable buckets, and the text query language stay dropped.

Nothing moved on the wire. Both variants have been in `GroupKey` and in `bindings.ts` since #1413, the engine folds every declared value type since #4604 and #4610, and `GroupedResults` already renders a `Property` or `DateBucket` key verbatim. The only code that did not know about them was `QueryControlsBar`, whose `groupValue` explicitly folded both back to `None` so the native select stayed in vocabulary — which is also why a saved view grouped that way loaded as ungrouped. The picker now carries two more options: `Property` reveals a key input, `Date` seeds `due` × `week` and reveals a source select (due, scheduled, created, last edited) and a unit select (day, week, month). The sentinel-plus-secondary-control shape is the one the aggregate target picker already uses for `AggregateTarget::Property`, so the `PROPERTY` sentinel is now shared between the two selects rather than duplicated.

No command, mock, or fixture changed. The mock's grouped path is synthetic and already waived in `conformance-coverage.test.ts` (one bucket keyed by the `GroupKey` type), which is what the Playwright spec asserts against; real bucket labels are pinned by the engine tests. `Priority { is_null }` was offered as a rider "if trivial" and is not: it needs a popover button, a change to `summaryPriority` (which would otherwise render an empty list), i18n and tests on both the Pages and advanced surfaces, so it stays in Phase 4. The three stale docblocks the comment mentions were already corrected by #4569.
