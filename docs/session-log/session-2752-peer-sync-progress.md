# Session 2752 — Per-peer sync progress in the device row

Issue #5842: show a peer's running session in its device row in Settings › Sync & devices, ops first, then the attachment exchange with bytes.

**Premise check.** The store held one global copy of the file progress (`filePhase`, `filesDone`, `bytesDone`, …) that nothing read, and `DeviceManagement`'s *Sync now* and *Sync all* passed no progress callback. That missing callback did more than leave the row blank. `start_sync` only wakes the daemon and returns. The progress reaches the frontend over the channel `SyncScheduler::register_channel` keeps for that peer, and a later registration replaces an earlier one. So a press with no callback also silenced the channel `useSyncTrigger` had registered. The channel stays registered after the command resolves, so the row clears on the stream's terminal updates (op `complete` / `error`, files `complete`), not when `startSync` resolves.

**What shipped.** `useSyncStore.peerProgress` is keyed by peer id, written by `recordPeerProgress(peerId, update)`. It replaces the global file fields, which had no reader. `useSyncTrigger` and both `DeviceManagement` sync paths feed it. `PeerSyncProgress` renders in `PeerListItem`: the visible text, a native `<progress>` labelled per device when bytes are known (the `ImportSection` precedent, since there is no Progress primitive), and an always-mounted `<output>` live region that changes at most every 3 s.

**Background-sync decision.** No `sync:progress` listener. `TauriEventSink` drops `FileProgress`, so a listener would show a daemon session's op counts and never its attachment bytes, which is the part the issue is about. Showing them needs Rust changes. The progress shows for sessions this device starts (*Sync now*, *Sync all*, the periodic `useSyncTrigger` run), not for a session the other device dialled in. `docs/features/sync.md` and `docs/architecture/data-and-events.md` now say so. The latter's claim that per-invoke channels live only as long as one `invoke()` was wrong for `start_sync` and is corrected.

**Tests.** Vitest covers the store keying and terminal clearing, the row (op phase, file phase with progressbar values, clearing, the throttled live region, axe), and *Sync now* routing channel updates into the store. Each was shown red by a mutation. The mock-lane spec `e2e/sync-peer-progress.spec.ts` keeps the channel the app hands `start_sync` and plays the backend's stream. It went red with the *Sync now* callback removed. No `e2e-tauri` spec: a two-device sync finishes in a few ticks, and asserting on its transient progress would only test timing.
