# Session 3881 — boot stops on a snapshot this build cannot read (#6525, first checkbox)

A space whose `loro_doc_state` blob failed to import at boot was logged and skipped. The first access then made an empty engine for it, marked dirty, and the next snapshot pass replaced the blob under the same PeerID. Opening a vault once with a build one engine format behind (0.21.0 against 0.22.0) did this to every space.

- **What changed.** `rehydrate_registry` returns `Result<usize, AppError>`: a table read error, a peer-id mint error and any import failure are errors, and nothing is installed when one occurs. `recover_and_bootstrap` propagates it with `?`, the same path as the peer-epoch load, so `boot` returns before `spawn_background_tasks` starts the periodic save, and `setup_app` shows the existing dialog and calls `process::exit(1)`. That means `RunEvent::Exit` never runs its save, and nothing is in managed state for it to find anyway. On mobile, `setup_app`'s `tracing::error!` and `show_fatal_error_dialog`'s mobile arm log it. No mobile UI was built (out of scope).
- **Messages.** These are hard-coded English like every other boot-failure text, carried in `AppError::Snapshot`. A blob whose stamp is newer than `ENGINE_FORMAT_VERSION` says the vault was last opened by a newer version and to install it. Every other failure names the space and says it cannot be read. The newer case is found by reading the stamp after the failed import (`LoroEngine::format_version_stamp`). A newer build whose bytes Loro itself cannot decode gets the "cannot be read" text. Both are fatal either way.
- **Dialog body.** It is extracted from `setup_app` into `boot_failure_dialog_body`, so the test asserts what the user sees.
- **Format bumps.** The doc on `ENGINE_FORMAT_VERSION` now says a bump ships with a migration in the same commit, so a build from before this fix stops at the migration check instead of opening the vault and overwriting.
- **Tests.** Two tests in `lib.rs` `boot_path_tests` drive the real boot phases 4 and 5 (`build_materializer`, `recover_and_bootstrap`) over a vault with one seeded row. In one the row is stamped `ENGINE_FORMAT_VERSION + 1` (built with the new test-util `LoroEngine::export_snapshot_as_format`); in the other it is garbage bytes. Each asserts that boot fails, that the dialog text is right, and that the whole row (blob, `updated_at`, `op_count`, `applied_through_seq`) is identical afterwards. They were red on the unchanged code: boot returned Ok. Each half was then reddened by its own mutation: the boot caller swallowing the error, the newer arm made unreachable, and a row write before returning.
- **Left alone, for the orchestrator.** `save_all_engines_does_not_advance_watermark_of_unrehydrated_space_3309` still passes and was not edited. Its doc comment said `rehydrate_registry` skips a space whose blob fails to import; the reviewer corrected the comment, nothing else. As far as I can see, no production path now leaves a `loro_doc_state` row with no engine behind it: `write_snapshot_row` is the only writer, and a purge deletes the row in the same transaction as the eviction. So the `installed` exclusion in `advance_clean_space_watermarks`, which that test pins, may now guard nothing. Deleting both is a separate decision. The production comments on the exclusion no longer claim a live case.
- **Not done.** The other three checkboxes of #6525.
- **Checks run.** `cargo nextest run --workspace -E 'test(6525) | test(rehydrate) | test(snapshot)'` passed 190 of 190. Every test that reaches a changed `rehydrate_registry` call passed (17 of 17). `SQLX_OFFLINE=true cargo check --workspace --all-targets` and `cargo clippy --workspace --all-targets -- -D warnings` were clean, and `cargo fmt --all --check` passed.
