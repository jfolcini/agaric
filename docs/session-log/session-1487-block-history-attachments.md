# Session 1487 — Attachment ops in the per-block History sheet

#4336, found in the review of #4335: `delete_attachment` and `rename_attachment` carry no `block_id` in their payload, so `op_log.block_id` is NULL on those rows and `list_block_history`'s bare `WHERE block_id = ?1` could never match them. Opening History on the very block whose attachment you just deleted showed no record of it, and picking either op type in the sheet's filter dropdown always returned an empty list. #4277 closed the same hole in `list_page_history`; this was the last query in the family still deciding "does this op-log row belong here" without accounting for a NULL `block_id`.

The fix is the disjunct `list_page_history` and `undo_page_op_inner` already share, scoped from `id IN (SELECT id FROM page_blocks)` down to a bare `block_id = ?1`: the live-`attachments` probe that resolves a rename's owning block from the row it renamed, and the paired-`add_attachment` probe over the indexed `op_log.attachment_id` column that resolves a delete's owner without the row, since the delete hard-DELETEs it in the same transaction. It departs from the page version twice, deliberately. The inner `op_type = 'delete_attachment'` gate is gone: the row loss it guards against also strands a *rename* of an attachment that was later deleted, which the gate left unlisted. That makes the two sheets disagree about one row — an `add → rename → delete` rename is listed here and omitted from `list_page_history`, which `test_list_page_history_omits_orphaned_attachment_ops_4277` pins — and the asymmetry is the point: this query knows which block it is asking about, so the paired-add probe answers "is this MY attachment" with certainty, where a page subtree cannot. That is what #4278 narrowed the page probe for. Recorded in both doc blocks, since `list_page_history`'s asks for exactly that. And the page version correlates each candidate against `json_extract(ol.payload, '$.attachment_id')`, which no index can serve, and affords it because a page's op count short-circuits `LIMIT 51` early; one block rarely has 51 ops, so the same shape here would walk all of `op_log` on every sheet open. For one block the candidate set is two indexed seeks, so this asks `ol.attachment_id IN (…)` instead — `OpPayload::attachment_id` populates that column for all three attachment op types (`op.rs`) and `idx_op_log_attachment_id` (migration 0064) covers it. EXPLAIN QUERY PLAN on `dev.db`: the old shape is `SCAN ol USING INDEX idx_op_log_created` with a correlated scalar subquery per row (`attachments` by its `id` autoindex, `op_log` by `idx_op_log_block_created`) and a TEMP B-TREE for the right part of the ORDER BY; the new one is a MULTI-INDEX OR, `idx_op_log_block_created` for the `block_id` arm and `idx_op_log_attachment_id` for the other, with the candidate set built once as a list subquery. It is not free: the temp b-tree covers the whole ORDER BY now, not just its right part. Two indexed seeks and one sort beat a full scan with a subquery on every row. The bind list is unchanged: `?1` is simply reused three times, the way `?7` already is in the space-scoped branch.

The test is the block-scoped sibling of `test_list_page_history_includes_attachment_ops_4277`, on a block owning one attachment that is renamed and one that is renamed and then deleted, among five ops that carry their own `block_id`, with a sibling block on the same page carrying an op of its own. It pins all eight ops newest-first with the delete and both renames in their real positions, pins that the op-type filter reaches the delete and returns *both* renames — one per probe, the live-row one and the deleted one, so neither arm of the disjunct can rot unnoticed — and pins that the sibling sees only its own op, since the disjunct resolves one owning block, not the page. Premise guards assert all three attachment ops really do carry a NULL `op_log.block_id` and that the deleted attachment has no live row, so the test cannot pass for the wrong reason.

No frontend change: `HistoryPanel` keys expansion and restore by `entry.seq`, `BlockHistoryItem`'s `index` prop only builds DOM ids and drives arrow-key movement within the fetched list, and nothing maps a position in this list onto a position in an undo query — the per-block sheet has no equivalent of the `undoDeleteOfImpl` index consumer #4328 removed. The four `.sqlx/` caches moved with the SQL text in the same commit.

Verified: the nine existing `list_block_history` tests plus the new one green under `SQLX_OFFLINE`, as CI compiles it, then the whole `agaric-store` package green. Falsified against a copy each round — first reverting the WHERE clause to `block_id = ?1`, which red the then-seven-op list at 5; then, after the gate came out, re-adding `op_type = 'delete_attachment'` to the add-op probe, which drops seq 6 alone, the rename of the since-deleted attachment. Restored and `cmp`-checked identical after each.
