# Session 1487 — Attachment ops in the per-block History sheet

#4336, found in the review of #4335: `delete_attachment` and `rename_attachment` carry no `block_id` in their payload, so `op_log.block_id` is NULL on those rows and `list_block_history`'s bare `WHERE block_id = ?1` could never match them. Opening History on the very block whose attachment you just deleted showed no record of it, and picking either op type in the sheet's filter dropdown always returned an empty list. #4277 closed the same hole in `list_page_history`; this was the last query in the family still deciding "does this op-log row belong here" without accounting for a NULL `block_id`.

The fix is the disjunct `list_page_history` and `undo_page_op_inner` already share, scoped from `id IN (SELECT id FROM page_blocks)` down to a bare `block_id = ?1`: the live-`attachments` probe that resolves a rename's owning block from the row it renamed, and the paired-`add_attachment` probe over the indexed `op_log.attachment_id` column that resolves a delete's owner without the row, since the delete hard-DELETEs it in the same transaction. Kept byte-identical to the other two, including the inner `op_type = 'delete_attachment'` gate and the `src_add.is_replicated = 0` filter, so the five predicates in this family stay readable as one thing. The outer table needed the `ol` alias the others already carry — without it the correlated `json_extract(payload, …)` inside the `src_add` EXISTS would bind to the subquery's own `payload` column. The bind list is unchanged: `?1` is simply reused three times, the way `?7` already is in the space-scoped branch.

The test is the block-scoped sibling of `test_list_page_history_includes_attachment_ops_4277`, on a block owning one deleted and one renamed attachment among five ordinary ops, with a sibling block on the same page carrying an op of its own. It pins all seven ops newest-first with the delete and the rename in their real positions, pins that the op-type filter now reaches the delete, and pins that the sibling sees only its own op — the disjunct resolves one owning block, not the page. Premise guards assert the two attachment rows really do have a NULL `op_log.block_id` and that the deleted attachment has no live row, so the test cannot pass for the wrong reason.

No frontend change: `HistoryPanel` keys expansion and restore by `entry.seq`, `BlockHistoryItem`'s `index` prop only builds DOM ids and drives arrow-key movement within the fetched list, and nothing maps a position in this list onto a position in an undo query — the per-block sheet has no equivalent of the `undoDeleteOfImpl` index consumer #4328 removed. The four `.sqlx/` caches moved with the SQL text in the same commit.

Verified: the nine existing `list_block_history` tests plus the new one green, then the whole `agaric-store` package green. Falsification against a copy — reverting the WHERE clause to `block_id = ?1` reds the new test at 5 of 7 ops, restored and `cmp`-checked.
