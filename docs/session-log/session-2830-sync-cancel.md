# Session 2830 — Cancel stops a running sync, during the dial and while the peer is silent (#5739)

The maintainer chose to build #5739's Cancel fully. Before this, `cancel_sync` was dropped during the dial ("cancel_sync ignored"), and mid-session it was checked only before each receive, so a silent peer kept the session waiting; the device row also showed nothing during the dial, so there was no Cancel to press.

- **Backend (`agaric-sync`).** A session takes cancel ownership and registers as live before it dials, and takes its progress channel before "connecting", so the dial shows in the row with its Cancel. The dial and each receive of the message loop race the cancel through one helper, `unless_cancelled`, which polls the flag every `CANCEL_POLL_INTERVAL` (moved to `sync_constants`, shared with file transfer). Local apply work is never raced, and snapshot catch-up, sends and the closing wait finish before a cancel is seen. A cancel reports a new `SyncErrorCode::Cancelled` and books nothing against the peer. `CancelGuard` clears the shared flag only when no other session is still live: once dialling peers also own the cancel, the first to notice would otherwise clear it and leave the others syncing. `abort_all` in `run_change_round` is gone: it existed for that race, and aborting a task mid-await left its row never hearing the session ended. A repeated failure whose toast is suppressed (#4120) still sends the row its "error" update, so an offline peer's row does not show "connecting" and a dead Cancel forever.
- **Frontend.** `PeerListItem` shows *Cancel sync* while that peer's progress is set, calls `cancelSync`, and moves focus to *Sync now*; a rejection toasts. `useSyncEvents` treats an error coded `cancelled` as idle with no toast, and maps `connecting` to syncing. No pending-cancel store field: the backend code identifies a cancel exactly, and a flag could hide the peer's next real failure.
- **Spec.** `sync-two-device.e2e.ts` pauses the peer (`SIGSTOP` through new `pause`/`resume` in `sync-peer.ts`), presses *Sync now* then Cancel, checks the state card reads Idle with no failure toast, then resumes the peer and syncs a new block across. It failed with the session registered only after the dial.

- **Reconciled with #6006**, which had merged a `failed` progress update for a session that fails. Under this change the session's sink is the row's channel from before the dial, so every failure and cancel already ends the channel with its `error` update, and #6006's emit made two terminal updates in a row. It is gone, with the `failed` case it added to `toPeerProgress`'s sync branch; `a_failed_session_ends_its_progress_channel_5842` now asserts exactly `connecting`, `exchanging_heads`, `error`. #6006's `failed` file tick stays: a failed attachment transfer does not fail the session, so that tick is what clears the row.

- **Review.** With #6006's `failed` update gone, `useSyncTrigger`'s channel callback mapped the terminal `error` to idle and overwrote the red state the `sync:error` event had just set, so a failed sync left the sidebar dot idle. A terminal `error` now only ends a `syncing` no event ended (the suppressed repeat failure of #4120). Stale comments and docs that said the cancel stops a sync "at once" or per device now say it is device-wide and ends the sync while dialling or waiting for the next message.

`cancel_sync` stays global, so one row's Cancel stops every live session, responders included. The maintainer chose to say so: the button's accessible name is now "Cancel sync: stops every sync running on this device", with the visible text unchanged.

Suites run: `cargo nextest run -p agaric-sync`, a workspace nextest filter over cancel, sync commands, the scheduler and the driver, clippy with `-D warnings`, `SQLX_OFFLINE=true cargo check --workspace --all-targets`, fmt, the changed and related vitest suites, typecheck, lint, the e2e-tauri vitest and typecheck, and `just e2e-real e2e-tauri/sync-two-device.e2e.ts`. Every new test was shown red by putting back the old behaviour.
