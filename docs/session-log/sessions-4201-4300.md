## Session 4296 — the mirror keeps a file's lines while their render is unchanged (#6540 slice A)

Slice A of #6540, approved with the maintainer's answers relayed on the issue: the three-way splice, for every mirror.

The mirror's splice kept a file's own lines for a block only when they read as the block's render does. A block that reads as other text, as one another editor wrote, was rewritten into Agaric's form on the next write of its page, even when the write was for an unrelated change: another block edited, a linked page renamed. Adopting a folder in place (#6540) would rewrite such blocks of the user's files on the first unrelated write.

Now each text the mirror writes keeps the render it was written from (`Shadow::render`, stored with the page's state), and the next write splices against it as a base: a block's file lines, and the front matter, are kept while their render is what the base held, whatever they read as; only a block changed in Agaric since takes the render's lines. A state written before keeps no render and splices as before.

### What ran

- `cargo nextest run --workspace -E 'test(/mirror/)'`.
- The base check for blocks, for front matter, the relaxed read-back check (both halves), and the base passed by `try_write_page`, each falsified once: each reddened its own test.
- `cargo clippy --workspace --all-targets -- -D warnings`.

## Session 4295 — an inline query's Load more and a query table's list editor survive the real backend

Two frontend bugs that kept `query-blocks.spec.ts` and `query-table-list-filter.spec.ts` off `REAL_BACKEND_SPECS` (#6529). Both files now join it.

- **#6911, Load more dropped.** The backend's late events for the query block's own save move a refresh counter while `fetchNextPage` is in flight. `useInvalidateOnCounter` invalidated at once, and `invalidateQueries` cancels a running fetch and refetches only the pages the cache holds, so the second page vanished. The fix waits for any Load more in flight under the prefix (`fetchMeta.fetchMore`, its `query.promise`) and invalidates once it lands, so the refetch covers every page. `cancelRefetch: false` was rejected: it joins the running fetch, and the success clears the invalidation, so a refresh would be lost. The fix sits in the shared hook, so every infinite list it refreshes (references, unlinked references) gets it.
- **#6912, list editor closing.** The cause is not the refetch. `ListEditor` disabled its add field while the write ran. Chromium moves focus off a field that becomes disabled at its next rendering update, and the query table's cell closes when its field loses focus to nothing. The mock answers before that update, so the field was enabled again in time. The bridge is slower, so focus moved and the cell closed. The add field is now `readOnly` while busy. The `writing` ref already refuses a second write. The Properties table's list editor shares the component and kept the same lost focus.

Each fix was shown red with the fix reverted: a vitest test (the hook test, with a held next page; the ListEditor test, with a held `set_property`), and on the bridge (Load more 3 of 6 failed at the post-click row assertion; the list cell failed 2 of 2 at `Remove Dee`).

Ran: typecheck, oxlint, vitest over `src/hooks`, `src/components/properties` and `src/components/query`; both files on the bridge (`--repeat-each=5`, 90 passed) and on the mock with the neighbouring query, references and property specs. `just e2e-related` names the whole lane for the hook, so CI's run is that check.

## Session 4282 — the mirror no longer rolls its folder back after a restore, and asks before reading a returning folder in

First of three PRs for #6887, the data-loss paths two reviews found in the Markdown mirror. This one is items A and B.

**A. A restored or new vault rolled the folder back.** The mirror's per-page states live in the app data dir, outside `notes.db`, so after a backup restore (or a new vault given the old folder) its first full pass removed every file of a page the vault lacked and wrote older text over files edited since. After each completed pass the mirror now saves a `head` file in the folder's state dir: this device's durable op head (`next_seq_for_device - 1`, which survives compaction, unlike `MAX(seq)`) and the hash of the op there. A vault behind that head, or holding another op at it, pauses the mirror before anything is read or written. The hash check matters: without it a restored vault that minted a few ops past the gap lifted the pause. The pause is sticky (`older` in the head file) so compaction pruning that op cannot lift it either. The way out is choosing the folder again, which starts fresh: states and head forgotten, and attachment copies whose attachment the vault lacks unrecorded so the sweep never removes them (dropping the whole record would overwrite a copy the user changed). A fresh start that fails part way keeps its flag and runs again; clearing it first left no head and the old states, the rollback again.

**B. Choosing a folder again read in changes made meanwhile unasked.** The settings switch showed a local `true` while the mirror was off, and `set_mirror_folder` never ran the pending gate. ## Session 4276 — Android Gradle builds ride out a registry 429

Run 43889772262's `android-build` failed attempt 1 when Maven Central answered `:buildSrc`'s Kotlin plugin POMs with 429; attempt 2 passed unchanged. The cause is Gradle's own retry, read from the v9.6.1 source the wrapper pins: `ErrorHandlingModuleComponentRepository` retries a transient failure (`NetworkingIssueVerifier` counts 5xx, 408 and 429) `org.gradle.internal.repository.max.tentatives` times, 3 by default, waiting `org.gradle.internal.repository.initial.backoff` ms, 1000 by default, doubled each try, then disables the repository for the rest of the build. The failed Gradle run lasted 20 s and its log shows "Repository Gradle Central Plugin Repository is disabled".

Shipped: `GRADLE_OPTS` with 8 tries from 2000 ms on the three Android jobs (`ci.yml` `android-build`, `android-launch-smoke.yml`, `release.yml` `android-build-and-release`), about 4 min of backoff before Gradle gives up.

Proof, local, Gradle 9.6.1 against a Python server that answers 429 to the first N requests, with `org.gradle.jvmargs` set so the build runs in a separate daemon as Tauri's generated project does: defaults with N=4 fail after 3 requests 1 s and 2 s apart; the committed values with N=7 succeed on the 8th request, the requests 2, 4, 8, 16, 32, 64 and 128 s apart. So `GRADLE_OPTS` system properties reach the daemon.

Not done, and why:
- A Gradle dependency cache. `setup-java`'s `cache: gradle` saves in an always-run post step from any ref, so a run that fails mid-resolution freezes a partial cache under the exact key (it never restores with a prefix and never re-saves a hit), PR runs save too, and its default key globs Gradle files that `tauri android init` only creates later in the job. A hand-rolled `actions/cache` restore/save pair saved only on `main` avoids that but adds a Gradle home to the shared cache quota the Rust `target/` trees already crowd, for a path-gated job that `main` runs only when an Android path changes, so the nightly would often find it evicted. The retry fixes the observed transient failure on its own.
- `release.yml` gets the retry only: its own jobs restore no cache (`.github/AGENTS.md` § Caches, #3542), and this one signs and publishes.

Sweep of the 7 days to 2026-11-18 over `ci.yml`, `scheduled-deep-checks.yml`, `release.yml` and `android-launch-smoke.yml` runs (failed runs and every re-run attempt): job 133387826139 is the only Gradle or registry download failure. ## Session 4269 — mirror-inbound reads the mirror status after the ingesting pass

Part of a flake sweep over two days of CI and e2e-tauri runs. One real-backend failure was not its PR's fault: `e2e-tauri/mirror-inbound.e2e.ts:91` in run 44231948303 (shard 4). There, `get_mirror_status().diverged` listed the test's own page right after the block had taken the outside edit, and the next two runs of the same branch passed.

**Cause.** A race in the spec, not the mirror. In `Mirror::read_edit` (`src-tauri/src/mirror/mod.rs`) the settling tick lists the page as diverged. The spec polled the block, saw the edit, and read the status inside that window.

It reads the status of a pass that ended after the ingest committed. The ingest's own ops, past the mirror's watermark, guarantee the next tick runs a pass. No timeout was raised and no retry or sleep was added.

**Verified.** The fixed spec passes alone on the real backend locally (`WDIO_SKIP_TAURI_BUILD=1` after CI's own `tauri build`; WDIO's in-process build fails here because its loader leaks into the child `vite build`). Falsified by widening the window: with a 3s sleep after the ingest's notify in `read_edit`, main's spec fails at `:91` with the page's file in `diverged`, the CI symptom, and the fixed spec passes. The sleep was reverted by the same command.

## Session 4265 — apt installs from a content-keyed .deb cache

Set out to stop the Ubuntu mirror from redding CI. Main run 44240707721 lost `validate / cargo-tests (2)` to "apt-get install exceeded 300s twice" (exit 75), and `cargo-coverage` went red behind it for want of shard 2's lcov. PR #6880's `mcp-tests` failed the same way.

**Root cause.** The skipped "Restore apt archives" step on main was by design: main ran the combined `actions/cache` step, and in job 134587774849 that step logged `Cache hit for: apt-tauri-Linux-v1` (61 MB). The install still pulled from the mirror, because the key was fixed. `actions/cache` never re-saves on an exact hit, so the key's .debs were frozen at the versions of its first save. Every `-updates`/`-security` bump since then, plus the fresh index from `apt-get update`, made apt want files the cache did not have. Shard 1 of the same run hit the cache too and still spent 3.5 minutes installing.

**What shipped.** `actions/apt-install` owns the cache behind `cache: 'true'` (off by default, so a job that signs or publishes restores nothing, #3542; `release.yml` stays off):
- The key is a hash of `apt-get install --print-uris` against the runner image's own lists (name, size and checksum; the URI is dropped because the mirror host differs per region). It names the image and the package set, so a list change or an image update moves the key, with no `-vN` to bump.
- The entry holds the .debs and the `/var/lib/apt/lists` they were resolved from. On a hit the first attempt installs against those lists with no `apt-get update`, and apt opens no connection. On a miss the old path runs: a bounded, advisory update, then the install. Any successful install on main or a branch dispatch saves.
- An install attempt that runs out its bound moves the host it was last fetching from (its final `Get:`/`Ign:` line) to the end of `/etc/apt/apt-mirrors.txt` at `priority:99` before the retry. apt's mirrorlist fails over on errors, never on slowness, and #6889's own runs trickled from us-east-2.ec2 at about 100 KB/s for two full bounds. Main's first run after merge takes the miss path to seed the keys, so a trickle there would keep the cache from ever seeding. Checked with real apt: a silent host at `priority:1` hangs `apt-get update` until its bound; demoted, the update finishes at once with no connection to it.
- `warm-only` replaces `ci.yml`'s hand-written `lookup-only` probe of the `apt-e2e-tauri-runtime` key.

Every per-workflow cache step and its fixed key is gone (`_validate.yml` cargo-tests, `actions/toolchain`, `actions/e2e-tauri-runtime`, `e2e-tauri-weekly.yml`, six lanes of `scheduled-deep-checks.yml`). `cargo-coverage`'s `lcov` is now cached too. The install runs `-q` rather than `-qq`, so the log printed on a failure shows the `Get:` lines naming the mirror (with `-qq` the log was empty).

**Traps.** The first version skipped the update on a miss too and saved only after a first attempt that installed without one, on the theory that the image's lists name what a cache keyed on them should hold. #6889's first CI run disproved it: the archive had already dropped the image's gstreamer `1.24.2-1ubuntu0.6` (it keeps one superseded version), so that attempt could never succeed, its key would never be saved, and it burned its whole 300s bound before the refresh. Caching the refreshed lists alongside the .debs keeps the pair consistent whatever the image ships. Separately, `apt_update`'s retry loop reused the outer `attempt` variable. After an update the retry believed it was attempt 1, marked itself cacheable and slept again. The new unit test caught it; the fix is `local attempt`.

**Verified.** `scripts/apt-install-action.test.mjs` passes, and each new assertion went red under its mutation: the refresh gating, the demotion call removed, the demotion run on a non-timeout failure. The real-apt proof (scratch harness: a local mirror that accepts connections and never answers, with `archive`/`security.ubuntu.com` pointed at it, timeouts 15s): the old action with a frozen-key hit missing 5 of 54 .debs exits 75 after 80s; the new action on a genuine miss also exits 75 with `AGARIC_APT_INFRA`; the new action on a hit (the .debs and lists restored) installs lcov and xdotool in 2s, with zero connections to the mirror. prek over the changed files is green, zizmor included, and so are the lint job's node:test files.

## Session 4262 — slow writes on a pulled vault were planner statistics taken while it was empty (#6811)

#6811: on a vault pulled from a peer, or with a peer paired before the writes, a split took about 2 s and a 300-line paste 91 s in the real-backend lane, against 0.3 s and 2 s on a vault the app wrote. The weekly `pulled_vault_bench` had found no gap in the commands or the engine.

Premise check: the same bench run in a dev-profile build gave the same parity (split ratio 0.98 over n=337, paste 0.99 over n=11), so the debug build alone was not the cause.

A new `#[ignore]`d measurement, `pulled_vault_writes` in `src-tauri/tests/command_integration/`, added the rest one ingredient at a time: devices running the sync daemon, a real pairing and pull over loopback, the running materializer, the app's commit hook, the `e2e_sync_peer` binary frozen mid-session or after the pull, and the app's boot with commands sent through the invoke handler. None of these opened a gap. Running `maintenance::pragma_optimize` before the data arrived did, which is what the maintenance daemon's first tick does a minute after a new device boots (5 s under the e2e sandbox).

The cause: `PRAGMA optimize` writes `sqlite_stat1` for `blocks` at the bootstrap's few rows. With those statistics SQLite drives `write_dense_ranks`, the `UPDATE … FROM json_each` that every create and move runs, from a scan of `blocks` instead of a primary-key search. `EXPLAIN QUERY PLAN` after `ANALYZE` scans with 50 or fewer rows and searches from 100 on. Edits and deletes rank nothing, so merges stayed fast. The statistics stay until the job runs again, up to 4 hours later.

Fix: `pragma_optimize` deletes the `sqlite_stat1` rows of any table or index under `MIN_ANALYZED_ROWS` (1,000) and reloads the statistics on the connection that ran it. With no statistics the planner assumes a large table, which is what the queries are written for. A vault that already holds such statistics loses them at its next optimize.

Numbers (debug, one run each, same harness): split on the optimized-while-empty arm 1,362 ms [1,286–1,507] before and 29 ms [20–32] after, against 21–25 ms app-written; the paste and a new vault's first 1,000-block batch went from unfinished after 60 s to 4.2 s and 5.4 s. Full table in `docs/architecture/operations.md` § Loro engine cost.

Not checked: the real-backend lane itself (the WebKit driver is not installed in this container). Connections opened before the dropping optimize keep the old statistics until the app restarts.

### What ran

- `cargo nextest run --workspace -E 'test(pragma_optimize)'`: 3 passed. Three falsifications, each in one command that restored the file on exit. Without the delete, the new-vault test failed on its statistics count (11 against 0). Without the reload, it failed on its plan assertion with the scan plan. With the threshold multiplied by 10, the grown-vault arm failed.
- `cargo test -p agaric --test command_integration pulled_vault_writes -- --ignored --nocapture`, run before the fix (the old `pragma_optimize` swapped in) and after it.

## Session 4254 — links open from the AppImage on a newer host

#6871: links did not open from the 0.24.0 AppImage on Fedora 44 (Bluefin), and the maintainer could not reproduce it on Ubuntu 24.04.

**Cause.** The AppImage's inner launcher (`AppRun.wrapped`, AppImageKit's) sets `LD_LIBRARY_PATH` to the bundle's `usr/lib`. The linuxdeploy hooks set `GIO_MODULE_DIR`, `GSETTINGS_SCHEMA_DIR` and more. The opener plugin's `xdg-open` inherits all of it.

- The bundle carries the build host's GLib 2.80 and OpenSSL 3.0, which are Ubuntu 24.04's own, so nothing breaks there.
- On Fedora 44, the host `gio` needs `g_unix_mount_entry_*` (GLib 2.84) and is linked `BIND_NOW`, so it dies at load.
- `xdg-open`'s fallback runs the browser's `.desktop` line, `flatpak run …`, whose `libostree` needs `OPENSSL_3.4.0`.
- The plugin's detached spawn never reads the launcher's exit status, and `openUrl` dropped the plugin's error on desktop, so nothing reached the log.

**Fix.** The maintainer wants the opener plugin to stay the way links and folders open.

- **Wrapper:** the plugin cannot be handed an environment, so the AppImage now ships `src-tauri/scripts/appimage-xdg-open.sh` as `usr/bin/xdg-open` (`bundle.linux.appimage.files`). `AppRun` already puts `usr/bin` first on `PATH`, so the plugin's `open::that_detached` starts the wrapper.
- **What the wrapper does:** it drops every entry under `$APPDIR` from every variable, removes a variable left empty, and runs the host's launcher in the `open` crate's order (xdg-open, gio, gnome-open, kde-open).
- **Logging:** `openUrl` logs the plugin's refusal before its `window.open` fallback.
- **Cache refresh:** the AppImage cache refresh (`update-desktop-database`, `gtk-update-icon-cache`) runs with the same environment (`appimage_integration::host_env`) and logs a failed or missing tool. Before, it threw both away.

**Traps:**

- A first build replaced the plugin on Linux with an app-side launcher, a new `open_external_url` command and the `open` crate. The maintainer asked for the plugin instead.
  - Adding `open` to `Cargo.lock` also tripped the pre-commit `cargo deny` hook on RUSTSEC-2026-0543 (chrono unmaintained), a new advisory that fails any commit touching the lockfile. #6877 waives it.
- The launcher's exit status is still not logged: the plugin spawns it detached.
- The app cannot drop the variables for itself: WebKit's helper processes load the bundle's libraries through them.
- A wrapper that leaves its own dir on `PATH` finds itself as `xdg-open` and re-execs forever, so the unit test spawns it with a timeout.
- `bundle.linux.appimage.files` goes through `fs_utils::copy_file` / `copy_dir` (`fs::copy`), which keeps the exec bit. A wrapper without it would be passed over on `PATH`.
- `open` 5.4.5 states it will not rewrite an AppImage environment; `tauri-plugin-opener` 2.7.3 does nothing about it either.

## Session 4248 — a key typed right after Enter while a pull reloads the page

#6814: while a peer's edits were pulled in, the key after an Enter could reach `<body>`. The open question was whether the reload after the pull or a refused Sync press's toast took the focus. It was the reload.

`createPageBlockStore().load()` waited for in-flight creates, splits and merges (`heldBlocks`, #6559) only before it asked for its snapshot. When a sync's `reloadChangedPageStores` asked first and Enter's command started while the snapshot was on its way, the snapshot landed without the block Enter had made (and, for a split, with the source text whole). Applying it dropped the provisional row, so the roving editor unmounted and the next key went nowhere: every symptom in the issue, down to "block 250 whole again, no editor open".

Fix: `hold` moved from the reducers to `page-blocks.ts`, which owns the load generation, and counts the holds it takes. A load that sees the count move while its snapshot was in flight reads again (after waiting for the holds). Every tree on the page store gets it: journal day, week and the page editor. Page mode's single editor already reads again when a reload overlaps one of its saves (`save.writes` in `PageModeEditor.tsx`), and an Enter there unmounts nothing.

Not built here: #6811's maintainer comment asks for a deterministic Rust sync simulation with this bug as one seeded case. This race is in the frontend store, which no Rust simulation can reach, so the simulation stays with #6811.

### Tests

- `src/stores/__tests__/page-blocks.split-merge.test.ts`: a reload asked before `splitOff` and answered after it keeps both halves shown throughout. Red without the fix (the new block went missing).
- `e2e-tauri/enter-during-pull.e2e.ts`: pairs `e2e_sync_peer`, opens a page the peer wrote, has the peer edit it and the app pull. Every read of the page asked before Enter is answered 3 s late, with the snapshot taken when it was asked, and Enter is pressed while one is on its way. The wrapper sits on `window.fetch`: Tauri's `__TAURI_INTERNALS__.invoke` is read-only, so a wrapper assigned there silently does nothing. It has to delay every read, not only the first: the pull reloads the page on `sync:complete` and again on `blocks:changed`, and the newer load's generation discards the older one, so with only the first read late the spec passed on `main`. The focus must still be in the editor once the read lands, and the key typed then must be in the new block after a nav round-trip. The Sync press is a script click, which leaves the focus in the editor.

## Session 4239 — background sync stops raising toasts (#6870)

## Session 4223 — The differential-fuzz lane reports a divergence instead of timing out

## Session 4205 — Engine state: compact on size, no save at a session's end (#6521, stage C)

Stage C of #6521, the last. Stage A (#6767) saves a `loro_doc_delta` row with every engine write in its own transaction; stage B (#6777) builds each engine at boot from its snapshot and those rows and replays no op; #6785 moved the delete, restore, purge and move cascades into the op's transaction; #6793 drops a purged space's engine and rows. What was left: stop the session-end save, compact on size, decide the inbox replay.

### The save paths, each decided

| Path | Before | Now |
|---|---|---|
| A sync session's end (`SpacePlacementSink`, #6525) | a snapshot pass after every session that changed something, and after an `Error` or a converged session while an engine was dirty | deleted: an import's delta commits with its projection |
| The backgrounded maintenance job `loro_snapshot_if_dirty` | a pass every 60 s while backgrounded and dirty | deleted: a second copy of the periodic tick |
| The periodic task (`spawn_periodic_compaction`, five minutes) | a pass | `compact_when_due` |
| OS suspend (mobile) | a pass | `compact_when_due`: Android freezes the process, often before the tick |
| App exit | a pass | `compact_when_due`: a session shorter than the tick still compacts |
| `Headless::shutdown` | the suspend pass | `compact_when_due`, as suspend |
| Op-log compaction (`save_engines_then_compact`, #6518) | a pass first | kept: the purge deletes ops the replay fallback restores engines from |
| The one-time hydration repair, mirrored tombstones, blocks kept from a purge | `save_all_engines` | kept: none of these writes is in the op log, so only a snapshot keeps it across the replay fallback, which deletes the rows |

`compact_when_due` runs a snapshot pass once one space's delta rows reach `DELTA_COMPACTION_BYTES`. The pass writes every dirty space, not only that one: `write_pass` moves the stamp of every row it does not write, which holds only for a clean engine, and the replay fallback reads those stamps. Below the threshold it reads the op-log head, drains the background queue and moves the apply cursor, so the next boot does not fan the index work out again (#3298). That is safe for the fallback: a replay boot rewinds a cursor above the lowest row stamp before it applies anything (`heal_orphaned_apply_cursor`).

### The threshold

`durability_cost_tests::boot_by_tail_size` (new case in the committed harness; command in its module doc) boots a space from its snapshot plus a delta tail of 0, 1000, 4000 and 16000 typed words, one row each, and times the export a compaction then runs. Release build without LTO, a 4-core cloud container, one run; each cell is the median of five, then the range.

| Tail | 10K blocks, no history | 10K, ten edits a block | 100K, no history | 100K, ten edits a block |
|---|---|---|---|---|
| none | 69 ms [65–97] | 71 ms [67–72] | 889 ms [857–1089] | 890 ms [851–1284] |
| 1000 deltas (90 KB) | 102 ms [97–124] | 117 ms [104–161] | 936 ms [899–1088] | 1074 ms [987–1298] |
| 4000 deltas (360 KB) | 186 ms [178–215] | 210 ms [206–212] | 1077 ms [1014–1273] | 1187 ms [1155–1310] |
| 16000 deltas (1.4 MB) | 465 ms [453–519] | 554 ms [527–729] | 1704 ms [1466–2547] | 1682 ms [1634–1804] |
| Compaction export after the longest tail | 54 ms [46–141] | 68 ms [63–255] | 370 ms [359–1272] | 470 ms [450–1099] |

Direction: the cost grows with the tail at both sizes. On a 100K-block space a tail of 4000 deltas is still inside the range of the boot with none, and one of 16000 is outside it in both cases. On a 10K-block space every tail is outside the no-tail range, but the absolute cost stays below a snapshot export of the large space. `DELTA_COMPACTION_BYTES` is 256 KiB, below the 4000-delta tail: about 2800 typed words between two exports of a space, where the old schedule exported every dirty space every five minutes and at every session's end.

A cascade over every block of a 100K-block space writes one row of about 1 MB (the existing `cascade_in_its_transaction` case), so one such delete is followed by a compaction at the next check.

### The inbox replay stays

A sync import reaches the engine after its write-ahead `loro_sync_inbox` slot and before its projection commits. A compaction in that gap saves the import in the snapshot; a kill before the projection then boots with the import in the engine and not in SQL, and the peer does not send it again, because this device's version vector holds it. Only the slot's replay at boot projects it: `a_compaction_between_an_import_and_its_projection_is_healed_by_the_inbox_6521`. The replay is also how a projection that failed is retried at the next start, and how a slot that keeps failing reaches the quarantine and its *Retry* (#6057, #3226). With the boot replay removed, 262 inbox, quarantine, recovery and session tests ran and exactly two went red: that test and `status_reports_quarantine_only_on_the_boot_that_moved_it_6057`. The other inbox tests call `replay_sync_inbox` directly and do not see the boot call go.

### Interactions checked

- **Sync export (`prepare_outgoing`)** saves its stamp and mirrored tombstones as delta rows after the engine write. A pass reads `delta_head` before it collects any engine and deletes only the rows at or below it, so a row saved during a pass outlives it: `a_delta_written_during_a_compaction_outlives_it_6521`.
- **The dirty mark** is unchanged: a compaction clears only what it exported, under the stamp it collected.
- **`space_move`** commits through `CommandTx`, so its two spaces' deltas commit with it, and a pass during it either holds the move or, if the move rolls back, writes nothing (the rewind check).
- The lock order is unchanged: `write_engines` takes the write lock before it opens a checkpoint, and a pass's write transaction is the last thing it takes.

### What the fallback loses now

Decision 2 stands: saved rows that leave changes pending send boot through the replay, with an error in the log. That boot deletes the rows and builds from the snapshots, so it loses from the engines what a peer sent since the last pass, until the next sync delivers it again. Before this change the last pass was at most one session's end away; now it is the last compaction. The `replaying_the_op_log` twins of the session-end tests asserted the old window and now run under the saved-rows boot only (listed in the PR).

What would let the replay code go: no vault from before stage B left to open (its first boot needs the replay), and no remaining source of unusable rows. The sources left are a failed save of the tombstones a sync projection swept, an import whose own save failed, and a kill during an import's projection after a local write on the same space; the third could be closed by importing a space's inbox blobs with its rows at boot.

## Session 4203 — OR between filters, in the search box and query-block text; a failed e2e test keeps its trace

Built the second item of #6742 after posting its design on the issue, plus a CI change from a maintainer brief: a failed Playwright test in CI keeps its trace.

**Grammar.** `OR` and parentheses are grammar only in a query that holds the word `OR`, so `parse` hands such a query to the new `src/lib/search-query/or-query.ts`; every other query takes the old `classify` path and reads as before, parentheses included. The implicit AND binds tighter than OR, as FTS5 does. Words stay one full-text expression AND-ed with the filters, so an `OR` joins two words or two filters, never one of each. A word inside an OR of filters is an invalid token. Words in parentheses are the full-text expression only when the parentheses hold every word of the query. That keeps `cats OR dogs tag:#work`, which ran as `(cats OR dogs) AND work`, sayable as `(cats OR dogs) tag:#work`. `NOT` before a filter or group is invalid. Negated groups, date ranges and comparisons are left for later.

**Trap: context-dependent errors.** The round-trip property test found that a group holding a word or a one-sided `OR`, once flattened into its parent, serialised to a text that read differently. Such a group is now one invalid token spanning the whole group. A second trap: `tokenize` closes a quote only before whitespace, so `(tag:#x OR tag:#"my tag")` lost its last value. With `parenClose`, used only for OR queries, a quote also closes before a run of `)`. Values ending in `)` are quoted on the way out.

**Shape.** `SearchQueryAST` keeps `filters` flat (chips, spans, autocomplete) and gains `expr`, a tree over their indices, only when an OR between filters remains. `compileFilterTree` (`search-query/compile-filter.ts`) compiles each AND run as a flat query's filters are, and both the query block and the search box use it. ## Session 4202 — the agenda projection spec re-enters Agenda mode when it retries

`e2e-tauri/agenda-projected-repeat.e2e.ts` "lists the coming week of projected occurrences in Agenda mode, up to each bound" failed on #6805's real-backend lane (run 43691475299): `[data-testid="agenda-view"]` never existed within 60 s. #6805 touches no agenda code.

Mechanism: a test bug in the spec's retry branch. The test enters Agenda mode with the Journal's "Agenda view" tab, then polls the projected rows. When the first read is stale (the agenda cache rebuild has not landed), it remounts the view with `navigateTo('Pages')` and `navigateTo('Journal')` and waits for the agenda view. The sidebar's Journal item switches an Agenda-mode journal back to Daily (`AppSidebar.tsx`, `if (journalMode === 'agenda') setJournalMode('daily')`), so the remount shows the daily view and the wait can only time out. The branch runs only when the first read loses the race, hence intermittent. The ENOTEMPTY vault cleanup and `Not found: block` lines elsewhere in that shard came from other workers.

Fix: after `navigateTo('Journal')` the retry branch clicks the "Agenda view" tab again, as the test does on the way in.

Shown in CI on #6807, since this box has no tauri-driver: a temporary commit forced one pass through the retry branch. On the old code the spec failed with the original error (`agenda-view` still not existing after 60000ms); with the fix and the forcing it passed. The forcing was then removed.

## Session 4201 — Short terms in replace across pages, the backlinks Contains filter and query text

#6781 made a search term under three characters work in the search box. The maintainer chose to lift the same floor in the three places that still dropped it: replace across pages (`MIN_FIND_LENGTH`), the References panel's `Contains` filter and a query block's (and the Advanced Query box's) full-text term.

### What shipped

- **One predicate, three callers.** `add_shown_text_contains`'s SQL moved into a free function, `shown_text_contains` (`fts/filter_builder.rs`), which returns the `EXISTS` over `fts_blocks_content` with its placeholders numbered from a given slot and the `LIKE` patterns to bind. The search builder, `resolve_contains` (`backlink/filters.rs`) and `compile_query_ctx` (`query/engine.rs`) all call it, after `parse_query`, now `pub(crate)`.
- **Backlinks.** Beside a MATCH the predicate narrows it; alone, `resolve_contains` walks `blocks` by id through the primary key and stops at `FTS_ROW_CAP`, as the MATCH query did. `compile_contains` had its own `sanitize_fts_query` early return, which would have kept the panel's compiled path empty; it is deleted and `Contains` joins the other pre-resolved leaves, since `resolve_contains` and `membership_fragment` already return the empty set for an empty query.
- **Query engine.** `sanitize_fulltext` became `parse_fulltext`. The short-term predicate is AND-ed after the filter, its binds appended to `filter_binds`, so every statement (count, rows, aggregates, grouped) binds it in the same order. A text of only short terms has no MATCH and keeps the structural FROM; a `Relevance` sort key would make `resolve_sort` refuse it, and every row ties on it anyway, so the flat path drops it. A text left with nothing to search for is still refused, with the "at least 3 characters" clause gone from the message.
- **Replace across pages.** `candidateQuery` keeps every non-blank stretch between quotes; search answers a quoted phrase under three characters as a short term. `tooShort` became `noText` (empty box) with a new i18n string. The count, the `MAX_BATCH_BLOCK_IDS` refusal and the undo are the existing code, which already loads every candidate page before it counts.
- **Mock.** `matchesSearchText` applies `splitShortTerms` per row; `run_advanced_query` and the backlinks `Contains` arm use it, and a short-only advanced query ranks nothing and drops `Relevance`, as the engine does.
