# Session 3466 — A Busy refusal caches the address that answered

Issue #6353: `e2e-tauri/sync-two-device.e2e.ts` intermittently timed out waiting for the vault's pull. Right after pairing both devices dial each other, and one is answered with the responder's `Rejection::Busy`. `peer_refs.last_address` was written only by `record_session_success`, so the address that had just reached the right device was never cached, and with no mDNS (CI runners, a LAN that filters multicast, since QR pairing needs none) `resolve_peer_address` had no dialable path for any later attempt.

**Fix.** The address write moved out of `record_session_success` into `cache_peer_address`, and `record_session_failure` calls it too when `session_rejection` reads `Busy` (it takes the `DiscoveredPeer` now; putting the check in `try_sync_with_peer` pushed that past the 70-line clippy cap). A refusal arrives only over a connection iroh authenticated against the bound `endpoint_id` (`dial_addr` builds the `EndpointAddr` from it), so the cached address keeps its "only with the bound key" property. The check runs ahead of every branch of `record_session_failure`, so it covers the pairing-window branch too (the case the spec hits) without touching that branch: backoff, UI events and the #3505/#6051 classification are unchanged.

**Test.** `a_busy_refusal_caches_the_address_that_answered_6353` in `sync_daemon/tests.rs`: a responder holds the per-peer lock, a bound initiator dials it. Red before the fix (`left: None`), green after.
