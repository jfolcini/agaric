# Session 4203 — OR between filters, in the search box and query-block text; a failed e2e test keeps its trace

Built the second item of #6742 after posting its design on the issue, plus a CI change from a maintainer brief: a failed Playwright test in CI keeps its trace.

**Grammar.** `OR` and parentheses are grammar only in a query that holds the word `OR`, so `parse` hands such a query to the new `src/lib/search-query/or-query.ts`; every other query takes the old `classify` path and reads as before, parentheses included. The implicit AND binds tighter than OR, as FTS5 does. Words stay one full-text expression AND-ed with the filters, so an `OR` joins two words or two filters, never one of each. A word inside an OR of filters is an invalid token. Words in parentheses are the full-text expression only when the parentheses hold every word of the query. That keeps `cats OR dogs tag:#work`, which ran as `(cats OR dogs) AND work`, sayable as `(cats OR dogs) tag:#work`. `NOT` before a filter or group is invalid. Negated groups, date ranges and comparisons are left for later.

**Trap: context-dependent errors.** The round-trip property test found that a group holding a word or a one-sided `OR`, once flattened into its parent, serialised to a text that read differently. Such a group is now one invalid token spanning the whole group. A second trap: `tokenize` closes a quote only before whitespace, so `(tag:#x OR tag:#"my tag")` lost its last value. With `parenClose`, used only for OR queries, a quote also closes before a run of `)`. Values ending in `)` are quoted on the way out.

**Shape.** `SearchQueryAST` keeps `filters` flat (chips, spans, autocomplete) and gains `expr`, a tree over their indices, only when an OR between filters remains. `compileFilterTree` (`query-text.ts`) compiles each AND run as a flat query's filters are, and both the query block and the search box use it. The search box sends the tree as the new `SearchFilter.filter_expr` (`#[serde(default)]`), which `prepare_metadata` checks for depth and for leaves the syntax writes, and which `add_metadata` splices as one parenthesised `SearchProjection::compile_expr` clause. The #6795 short-term rule lifts on its own for an OR between filters, since the FTS query is the free text alone. The builder writes text for `And`/`Or` trees (`filterToQueryText`, still checked by reading the text back, now as a normalised tree), and the query block's header pills show `OR` between branches.

**Part B.** `_validate.yml` already uploaded `test-results/` on failure. The config's `trace: 'on-first-retry'` never recorded, because there are no retries. In CI it is now `retain-on-failure` without screencast frames, plus `screenshot: 'only-on-failure'`. Checked with `CI=1` and a forced failure: the failed test left `trace.zip` (DOM snapshots, no frames) and a PNG, the passing one nothing.

**Tests.** Parser tests and an OR-grammar generator for the round-trip property, compile and builder tests (the tree property included), `useTagResolution.byName`, `QueryResult` pills, autocomplete after `(`, Rust tests for the splice and the refusal, three backend-authored OR pairs in `query_text_tokens_match_search.json` (search box against query block, same rows), and e2e in `query-block-text.spec.ts` and `search-filters.spec.ts`. Each was shown red by one mutation, restored on exit. Edited assertions: three `filterToQueryText` cases and one `QueryBuilderModal` case that pinned "an `Or` stays `v2:`", the two field lists of the mock's `search_blocks` dispatch guard, and the `useTagResolution` exact-shape checks, which gain `byName`.
