# Session 3882 — Escape selects a block without a bar or a shift; the batch bar's Delete offers Undo

Finishes issue #6547: its Escape item, and the batch bar half of its Delete item (#6575 landed Enter after a heading and the block menu's Delete).

**Escape.** `BlockBatchActionMenu` renders only when the whole selection holds two blocks or more. It reads the global selection size from `useBlockStore` itself, not the tree's share: one block selected in each of two journal days is a selection of two, and each day keeps its own bar, so `week-cross-day-clipboard` (both lanes) still sees one bar per day. The size is read inside the menu so `BlockTree` keeps subscribing only to its own slice (#5447). `BlockInlineControls` no longer hides the task checkbox while a selection is active. Hiding it was half of the reported shift. The other half was the selection checkbox: in the desktop lane beside the grip and a parent's chevron it outgrew `--block-lane` by about 12 px, so every parent row moved right once any block was selected. On a fine pointer it now sits out of flow, left of the lane (`absolute right-full`), inside the page's padding at 900 px and wider (checked from screenshots). On touch it is unchanged: a touch device has no way to select a block without a hardware keyboard (long-press opens the block menu), so the in-flow checkbox on the selected row can still move that row there.

**One selected block, no bar.** Delete, task state and priority are in the block menu: right-click, or long-press on touch, where the bar never mattered. Its Delete shows the Undo toast. Ctrl+C / X / V, Shift+Arrow, Ctrl+Space, Ctrl+Arrow and Escape are document-level listeners that ignore the bar, and drag works from the grip. From the keyboard alone, the bar was reachable with Shift+Tab. Now Ctrl+X removes a selected block, and task state (Ctrl+Enter) and priority (Ctrl+Shift+1–3) are keys in the editor before the Escape. In block mode the menu key does not open the block menu on the focused row: the row `li` takes focus, and the menu handler sits on the `sortable-block` div inside it. That gap predates this change.

**Batch delete Undo.** `handleBatchDelete` takes the selection roots (`computeSelectionRoots`) before the delete, and its success toast carries an Undo that calls `undoDeleteOf(pageId, roots, reload)`. `undoDeleteOf` now accepts a block id or an array of them. It scans page history for each id's newest local `delete_block` row (a batch scans `PAGINATION_MAX` rows: the backend appends a row per selected block, so after Ctrl+A on a nested page a root's row can sit below fifty of its children's, which the first cut's window of fifty plus one per root missed; caught in review) and undoes them in one `undoOps` (still one `undoOp` for a single ref, as `undoByRefs` does). If any root's row is missing, nothing is undone. The single-block path behaves as before, and its existing tests did not change. Only the roots go in because undoing a root restores its whole `deleted_at` cohort, selected children included. The earlier claim that undoing every id fails when a parent and its child are both selected could not be confirmed: the mock accepts it, and from reading the Rust, `restore_block` on a live row errors nowhere. The toast text dropped "— Ctrl+Z to undo", which was false in the journal.
