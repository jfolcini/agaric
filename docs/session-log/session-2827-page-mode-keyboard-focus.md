# Session 2827 — page mode keeps the keyboard where an Obsidian user expects it

Four keyboard-focus findings from the #5691 review of 2026-10-21, all real.

- **Tab on a focused chip restructured the page.** A keydown on a chip inside the contenteditable still reached ProseMirror's keymaps, so Tab indented the caret's block. The `PageKeys` plugin now returns `handleDOMEvents.keydown: (view) => !view.hasFocus()`: ProseMirror skips its key handling while a chip has focus and the browser's default moves the focus on. That also keeps Backspace, `Ctrl+Enter` and the rebindable indent chords from acting at the caret then. Escape is the exception: on a chip it still leaves the text for the frame, as it does from the text (the review found the first version swallowed it).
- **Escape dropped the focus to `<body>`.** Escape now focuses the box around the editor (`tabIndex={-1}`, `focus-ring-visible`), and Tab from it goes back into the text at the caret, close to Obsidian's normal mode. The blur still saves through the existing flush. The grip was tried first and dropped: the app's `Ctrl+K` routing treats any focus inside `.ProseMirror` as the editor's, so a focused grip swallowed the palette.
- **A mode switch kept the block but not the caret offset.** The cursor handed between modes is now `{ blockId, pos }`, a position in the block's own document, which counts the same in block mode's editor and inside a `pageBlock` (`page-mode-switch.ts`). Page mode hands block mode a caret only while its document has focus. The switch button no longer takes focus on a click, so the editor keeps the caret through it.
- **The scroll position was lost on a switch,** both ways: page mode's skeleton collapsed the page while it loaded, and block mode reloads its store on mount. The switch now records the block at the top of the view and its offset and puts it back once the new mode shows its blocks. It anchors to a block, not a scroll offset, because the two modes draw blocks at different heights.

The review added a test that `Ctrl+E` (#6022), pressed while typing, keeps the caret's offset and the top block both ways. Page→Blocks lands within a row: block mode's rows take their measured heights a moment after the restore, and the browser's scroll anchoring holds the focused block still. The Escape frame has no accessible name, because a role on it fails the project's a11y lint; a screen reader may announce little when Escape lands there.

Not done: a numeric placement in the roving editor's `mount` would replace the one-shot focus listener that places block mode's caret; `isFocusInsideEditor` could test `isContentEditable` so `Ctrl+K` opens the palette from a focused grip or chip, which was already so before this change.

Suites run: vitest over page mode and `src/components/pages`, typecheck, lint, oxfmt, and Playwright `page-mode`, `page-mode-setting`, `page-mode-block-menu`, `page-mode-gutter`, `page-mode-reveal` and `page-mode-input`. Each new test was shown red by putting back the old behaviour. WebKitGTK and the e2e-tauri lane were not run.
