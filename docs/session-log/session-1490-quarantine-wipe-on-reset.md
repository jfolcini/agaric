# Session 1490 — Quarantine dies with the lineage it belongs to (#3243)

Snapshot catch-up (#1054) is a RESET: `apply_snapshot` swaps the core tables and, in the same transaction, wipes the Loro sidecar so that nothing from the old lineage can reach the new engines. `loro_doc_state` goes because it would rehydrate the pre-reset vault at next boot; `loro_sync_inbox` goes because boot recovery would replay its write-ahead slots into the post-reset engines; `log_snapshots` goes because this device would otherwise keep offering the old vault to a third device; and the #792 peer epoch is bumped so post-reset op counters cannot fork against the ops peers still hold.

#3226 added `loro_sync_quarantine`, which is where an inbox slot goes after it fails to clear across `QUARANTINE_AFTER_BOOTS` boots. The bytes it parks are byte-identical to the inbox bytes it was moved from — the same peer blobs, in the same lineage — and it was not in the wipe. On a device that had just caught up by snapshot, a surviving quarantine row was dead weight with no recovery path: it kept the boot report's standing backlog warning lit forever, and `readmit_quarantined_slot` would push pre-reset bytes back into the inbox for the boot walk to replay under a retired peer epoch, with nothing on the row to tell a caller the lineage had moved on. Nothing automatic re-reads the table, so this was latent rather than live, but it went live the moment anyone used the manual route the feature exists to support.

The fix is the one the inbox already gets: `DELETE FROM loro_sync_quarantine` next to `DELETE FROM loro_sync_inbox` in the RESET transaction, so quarantine dies atomically with the lineage it describes. The alternative the issue floated — stamping the peer epoch on each row and refusing a stale one at re-admission — buys a column and a check to preserve blobs that are unreplayable anyway; the protocol's own repair for a blob whose content reached neither the op-log nor SQL is another snapshot catch-up, which is exactly what just happened.

The `# HAZARD` block on `readmit_quarantined_slot`, which said in so many words that this table is not wiped by the RESET, is now false and is replaced by three lines saying the opposite. `readmit_quarantined_slot` has no production caller and the two remaining readers are diagnostics (`count_quarantined_slots` for the boot census, `list_quarantined_slots` for a human), so nothing depended on those rows outliving a RESET.

The assertion lives in the existing #607 restore test, which already seeds a `loro_doc_state` row, an inbox slot and a non-zero apply cursor and asserts all three are gone: it now seeds a quarantine row too and pins it at zero. The test name enumerated what it covered, so it gained `quarantine`. Falsified by removing the new `DELETE` against a copy — the assertion goes red on `quarantine_rows` and nothing else does.
