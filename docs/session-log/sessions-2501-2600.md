## Session 2594 — The broken-chip spec clicks Undo on the newest toast

`link-chip-lifecycle.spec.ts › from a static block…` (from #5863) failed on #5870's
Playwright shard: the click on the toast's Undo timed out, with the front toast
reported as intercepting pointer events.

**Cause:** the test removes the broken link twice, so two "Broken link removed" toasts
can be on screen at once. `removedToast` took `.last()`, documented as the newest,
but sonner prepends each new toast to its list, so the DOM's last toast is the oldest,
stacked behind the front one. Whether the test passed depended on the first toast
having expired before the second click. It now takes `.first()`.

**Shown red:** with the toast given `duration: Infinity` so the first one stays on
screen, `.last()` failed exactly as CI did (front toast intercepts pointer events, at
the Undo click) and `.first()` passed.

**Ran:** the whole spec file, 8 passed; oxlint and oxfmt on it.

## Session 2591 — link-chip spec: Undo on the toast the step raised

**Flake:** `e2e/link-chip-lifecycle.spec.ts`, "a broken chip removes itself
when clicked (#5736) › from a static block", red on #5866, #5867, #5869
and #5871 and once on main: the toast's Undo was "not stable", then the
front toast intercepted the click, then the button detached.

**Cause:** sonner 2.0.8 prepends each toast (`[toast, ...toasts]`, the
newest is `data-index="0"`, `data-front="true"`), and `notify.success`
keeps sonner's default 4 s. The test removes the chip twice, so the first
removal's toast is still alive at the second; `removedToast` took
`.last()`, the oldest, stacked behind the front one. A probe before the
Undo click on the old code: two matching toasts live in 5 of 6 runs,
`.last()` on `data-index="2"`, and those 5 failed with CI's call log. On a
pass it could press Undo on the wrong removal.

**Fix:** `removedToast` matches `[data-sonner-toast][data-front="true"]`
with the text, so it addresses the toast the step just raised. No wait,
retry or timeout. 160/160 with `--repeat-each=20 --workers=4`; 80/80 under
4× CPU throttling, with two matching toasts live in every run and the
locator on `data-index="0"`.

**The same file's other flake** (CI run 39057639127, "a ((block)) chip
shows the target block's edited text (#5245)"): the chip kept the original
text, so the `End` then `Shift+Home` selection never took; e2e/AGENTS.md
§ Flakes names that race (ProseMirror reads a native caret move only on a
late `selectionchange`). It now uses `replaceEditorText`, which selects
through ProseMirror. Not reproduced locally in 100 throttled runs.

**Checked, no change:** every other `[data-sonner-toast]` lookup in `e2e/`
and `e2e-tauri/` raises a given text at most once per test.

## Session 2584 — a failing CI job stops the PR's other jobs

**Ask:** the maintainer: a failing job, the PR collision job for one, let the
rest of the PR's jobs run to the end, wasting CI slots and time.

**Design.** GitHub has no workflow-wide fail-fast. A step `if: failure()` that
cancels its own run would turn the failing job's red into `cancelled` (the
runner merges Failed with Canceled into Canceled), and the checks list would
no longer say which job failed. So each gating job gets a tiny
`stop-after-<job>` job that starts only once it has failed, and calls
`_stop-pr-ci.yml`: it cancels every unfinished run of the PR's head commit,
its own run last, and leaves the Claude workflows running (the review judges
the code, and a new push re-runs it). Every API failure there is a warning:
a fork or Dependabot token is read-only, and a run may finish between the
listing and the cancel.

**Where:**
- `_validate.yml`: one per job `validate-all` reads. The vitest, Playwright
  and cargo-tests matrices fail fast on a PR, because `needs:` on a matrix
  waits for every shard; pushes to main keep every shard's result.
- `dco.yml`: after `dco`.
- `pr-overlap.yml`: after `merge-result` and `session-log-pr-collision`.
  The latter fails closed on "could not verify", so an API blip there now
  stops the PR's CI too.
- `ci.yml` and `release.yml` grant `actions: write` to their `validate`
  caller; a nested job can't ask for more than its caller grants.
- `scripts/check-pr-overlap-trust-boundary.mjs` lists `_stop-pr-ci.yml` as a
  trusted write-scoped target (#4183): it runs no PR code and holds only
  `actions: write`. Pointing the job at another local workflow is still
  flagged.

**Not triggers:** CodeQL, the e2e-tauri smoke and mutation-pr are not
required, and an infrastructure failure there must not cancel the gate. They
are cancelled when a gating job fails. `ci.yml`'s `build` and
`android-build` need `validate`, so nothing of CI runs beside them.

**`validate-all`** stays out of the stop jobs and they stay out of its
`needs`. It runs `if: always()` after the cancel and fails closed on a
cancelled job.

**Shown:** the stop script, pulled out of the YAML and run against a stub
`gh`, cancels the unfinished non-Claude runs with its own last, and a failing
listing or cancel only warns. Each case went red under its mutation: the
Claude exclusion removed, the own run cancelled first, the own-run warning
dropped. The nested permission grant can only be shown by a real run, which
is this PR's own.

**Costs:** fourteen more skipped rows in a PR's checks list. A flaky or
infrastructure failure in a gating job now cancels the rest, so a re-run
re-runs them all. A run shows only the first red shard's failures.

## Session 2564 — a WebM voice note shows its length before it is played

**Gap:** a voice note recorded on Android or Windows showed `0:00` and no
total length in its inline player until it had been played to the end.
Chromium's `MediaRecorder` records `audio/webm;codecs=opus` and writes no
Duration element in the WebM Segment Info, so `<audio>.duration` is
`Infinity` until playback reaches the last frame. Seen on the Android
emulator (API 36, WebView 133) with 9.96 s and 3.30 s notes, and reproduced
in Playwright's headless Chromium: a recorded note's player reported
`duration` `Infinity` before any play.

**Fix, in the player:** `AttachmentAudio` gives its `<audio>` a ref
callback, `resolveUnknownDuration`. On `loadedmetadata` with a non-finite
duration it seeks to `Number.MAX_SAFE_INTEGER`; the element scans for the
last frame and fires `durationchange` with the real length, and the first
finite one seeks back to 0 and unsubscribes, so a later length update during
playback leaves the playhead alone. A seek plays nothing. The rewind
supersedes the far seek before it completes, so the controls' only
`timeupdate` is at 0 and the scrubber never shows the end. The callback is
module-level, so React attaches it once per element; React 19 runs its
returned cleanup on unmount, which aborts every listener, so an element
that unmounts mid-scan is never touched again. Ogg Opus (WebKitGTK, our own
writer) and MP4 (WKWebView) report a finite duration at `loadedmetadata`,
so the callback does nothing for them; the Ogg spec still passes.

**Why not the recorder:** writing the Duration into the WebM header at save
time needs an EBML patch (no dependency for it is installed) and would leave
every note already recorded broken. The player fix covers old and new notes.
An exported WebM still lacks the header field; other players handle that
themselves.

**Tests:**
- `e2e/voice-note-record.spec.ts`: a new WebM test records through
  Chromium's `MediaRecorder`; both tests now check, right after saving and
  again after leaving the page and coming back, that the player's duration
  is between 2.5 and 4.5 s, `currentTime` is 0, it is paused with nothing
  played, and no `timeupdate` reported a non-zero time. Shown red three
  ways: the fix disabled ("Received: Infinity"), the rewind removed
  (`currentTime` "Received: 3.24"), and the rewind moved to `seeked`, which
  lets the far seek finish (a `timeupdate` at 3.24).
- `AttachmentRenderer.test.tsx`: the non-finite path seeks far and rewinds
  only once the length is finite, and not again on a later length update; a
  known length seeks nothing; after unmount the element is never seeked.
  Each shown red by removing, in turn, the abort on cleanup, the
  unsubscribe, the finite check on `durationchange`, and the finite check
  on `loadedmetadata`.

## Session 2562 — block mode commits every typed kind on one leave

**Asked:** make leaving a block in block mode commit its task marker,
`key:: value` lines and `#tags` together, as page mode does, instead of one
kind per leave. Also stop `stripPropertyLines` leaving a blank line where a
property paragraph was.

**Premise, confirmed:**
- `runUnmountFlush` took exactly one branch of split → checkbox → property →
  tag → edit. A new vitest leaving `- [ ] call mom #work` + Shift+Enter +
  `status:: done` saw only `set_todo_state`; the property line and the tag
  stayed text.
- A task paragraph's Shift+Enter break serializes as `\` and a newline; a
  bare newline after a task line parses as a second paragraph and splits.
- Page mode (`commitTyped` in `PageModeEditor.tsx`) runs `commitPageTask`,
  then `commitPageProperties`, then `commitPageTags`, each on the text the
  one before it wrote, each writing its own edit.
- `stripPropertyLines("status:: done\n\nmore text", {0})` gave
  `"\nmore text"`. Its only caller is `commitInlineProperties`, which page
  mode shares.

**Design:**
- `classifyUnmountFlush` still names the first kind the edit introduced;
  its callers only compare against `split` and `edit`. The property and tag
  payloads it no longer needs are gone.
- Past a split, `runUnmountFlush` runs `commitTyped`: the checkbox commit,
  then the property commit on the text it wrote, then the tags on the text
  after that. One `bumpFlushSeq` token covers the chain, and it stops once a
  newer save of the block has started.
- Each step writes through one `write` wrapper. It records the text the
  step meant to write, so a failed write is carried by the next step's
  write. It skips a write of the same text, as page mode's wrapper does.
- A refused task state keeps the marker as text, and the property and tag
  steps still run. The tags still wait for a saved text, as before. The
  outcome is `false` only when the last text write failed.
- The chain is tracked for the empty-block cleanup when it starts with a
  marker or a property. The tag-first case keeps its synchronous text write,
  `invokeSync` and the #1062 dedupe.
- Undo is unchanged: each helper notifies the undo store as its
  single-kind path did, and the writes of one leave fall in one group
  window.
- `stripPropertyLines`: a run of stripped lines that was a paragraph of its
  own takes one blank separator line with it. That is the blank after it, or
  the blank before it when the run ends the block.

**Tests and reds:**
- `unmount-flush.test.ts`, "one leave commits every kind":
  - all three kinds commit. Stopping after the checkbox gave

  - a newer save stops the chain. Without the check, `set_property` ran.

## Session 2560 — Page mode shows queries and embeds

and `embeds` blockers and their `pageMode.blocked.*` strings are gone. The cap

**What block mode does** (traced first):
- Both are block text. `StaticBlock` sniffs it: `{{query ` … `}}` draws
  `StaticQueryBlock`, which draws `QueryResult`; `parseEmbedToken` draws

## Session 2547 — maintenance jobs run on every tick (#5741)

**Found:** while the due-reminder spec ran on the real backend
(`e2e-tauri/reminder-due-task.e2e.ts`, #5835), a 60 s maintenance job ran
only every 120 s. Reminders dispatched at 06:53:55 and 06:55:55, with
nothing at 06:54:55, so a due reminder could come up to two minutes late.

**Cause:**
- `run_tick` decided whether a job was due from `Instant::now()` at the
  tick's start, but on success stamped `last_run` with `Instant::now()`
  after the job finished.
- The next tick fires one `TICK_INTERVAL` after the previous tick's
  scheduled time, so a 60 s job saw less than 60 s elapsed and skipped.
- Longer jobs (1 h, 4 h, 24 h) slipped one extra tick per period.

**Fix:**
- `spawn_daemon` passes the instant `Interval::tick()` returns, which is the
  tick's scheduled deadline, to `run_tick_at`. That function decides due-ness
  from it and stamps it.
- Stamping `Instant::now()` at the tick's start would not do: wake latency
  varies, so the gap falls under 60 s whenever a tick wakes earlier than the
  one before.
- The #3311 rule is unchanged: no stamp on failure.

**After a stall,** missed ticks burst with their own past instants. A 60 s
job then runs once per missed tick. All three such jobs are idempotent:
- the reminders have an at-most-once ledger;
- the projected-agenda refresh does nothing within the same day;
- the Loro snapshot is skipped once clean.

**Test:** `run_tick_runs_a_tick_interval_job_on_every_tick`, on paused
tokio time.
- A 60 s job that takes 1 s, on a tick that wakes 5 ms late, is stamped with
  the scheduled instant.
- It runs again exactly one `TICK_INTERVAL` later.

**Shown red:**
- stamping `Instant::now()` after the job fails the stamp assertion by
  1.005 s;
- stamping `Instant::now()` at the tick's start fails it by 5 ms.

## Session 2546 — Loro bytes travel raw after a header frame (#5761)

**Set out to:** let a space past about 64 MB of Loro state sync (#5761).

**Premise held.** The issue's claims checked out against the code. One
correction: `transport/bulk.rs` carries only attachments, and the snapshot
catch-up sent its snapshots as ordinary `LoroSync` frames. The "snapshot blobs
ride bulk" lines were wrong in `sync-protocol-spec.md`, `sync-and-network.md`
and `operations.md`.

**Design:** `transport::session` owns the split, so no caller changes.
- `send_sync_message` writes a `LoroSync` as the existing
  `SyncMessage::LoroSyncChunked` frame (the header that
  `LoroSyncChunkedHeader::split` builds), then the bytes raw on the same stream.
- `send_sync_message` refuses bytes over `MAX_LORO_SYNC_PAYLOAD_SIZE` as
  `AppError::Validation` before writing anything (added in review).
- `recv_sync_message` reads the frame. It refuses a `size_bytes` over
  `MAX_LORO_SYNC_PAYLOAD_SIZE` as `AppError::Validation` before it reads or
  reserves anything. Then it reads exactly that many bytes with `read_body`,
  straight into the buffer the engine imports from, and returns the `LoroSync`.
- No new message type.
- `send_bulk` is not used. The payload is already one `Vec` in memory, and
  `read_body` already reserves exactly, in two steps, with no claim-bought
  allocation.
- `LoroSyncChunked` lost its dead `compressed` field. `set_size_bytes` and the
  JSON round-trips of `LoroSyncMessage` (tests that pinned a shape no longer on
  the wire) are deleted.

**Decision, peer compatibility:** `ENGINE_FORMAT_VERSION` 4 → 5, not a new
ALPN. The wire changed, so the version moves. The bump reuses #5728's coded
`EngineFormatMismatch` refusal at `HeadExchange` ("update both devices") with
no new machinery. An ALPN mismatch fails the QUIC handshake before any
application byte moves, so it shows as an unreachable device with no coded
message. Neither format 4 nor #5728 is in a release: 0.18.0 is format 3, and
it refuses a mismatched peer with the older uncoded text, as it did before. So
the bump protects only devices running builds from `main`, and only those pay
its cost: export stamps `5` into each doc, which a format-4 build refuses, so
their vaults cannot go back to a format-4 build.

**The page-mode property flake.** Both recorded counterexamples type a
`key:: value` line into a block that a peer then deletes before the save.
Page mode keeps the text under a new id, and the leave-time commit, keyed by
the old id, finds nothing to commit, so the line stays text. Then either Enter

line becomes a property once the caret leaves that block, and the model did

`commitPageProperties`' one rule: a line counts unless the block held its key

becomes the property of the block that holds it. Block mode commits a pasted

mounted with). Block mode cannot set the property on a peer-deleted block
either: `set_property` takes an `ActiveBlockId`. The model already took this
rule for task markers ("or by an earlier step that could not leave the
block"). Its property check now derives the expected properties from the
block's lines in the same way, for the keys the backend check reads.

while page mode treats a block made by Enter as all typed.

## Session 2537 — a block Enter splits off commits its typed lines on leave

**Asked:** the maintainer wanted block mode's Enter split to match page mode. Page mode reads a block made by Enter as typed. When the caret leaves it, a `key:: value` line becomes a property, a task marker a task and a `#name` a tag. Block mode left all three as text in the half Enter split off.

**Cause:** `handleEnterSave` creates the new block holding the after-text, and EditableBlock's auto-mount mounts the editor on it with that text. So the leave-time flush's baseline (`originalMarkdown`) is the after-text itself. An unchanged block then unmounts as "no change" and nothing is classified. No commit or comment gave a reason. #5160 D2 (#5172) set the baseline to "the text the editor loaded" for blocks loaded from Source, import or paste, and the split-off half inherited it.

**Fix:** after the split, `handleEnterSave` flushes `setFocused` (`flushSync`), so the auto-mount has run. `readSplitOffAsTyped` then rebases the baseline to `''` (`markCommitted('')`), but only when that baseline makes the after-text a `checkbox`, `property` or `tag` classification. Plain text keeps the loaded baseline, so leaving it writes nothing. Several paragraphs keep it too, so they stay one block, as page mode keeps them. Enter at the start of a block also keeps it: block mode moves the whole text to the new block, while page mode keeps that text in its loaded block. The leave-time rules themselves are unchanged.

**Traps:**
- Mounting the new block directly from `handleEnterSave` loses the caret: React moves the editor's DOM after the mount. Playwright showed the editor not focused.
- Without the `flushSync`, the auto-mount runs after `markCommitted`, which is then a no-op on an unmounted editor.

**Knock-on, as traced:**
- Paste and Enter at the end of a block take other paths and are untouched.
- In-editor undo right after the split has no history either way, since mount clears it.
- A source block's stored properties never reach the new block (`createBelow` copies none), so a line split off becomes its property.
- On a blur leave, `useEditorBlur` Step 3 first re-saves the unchanged text once (its baseline is now `''`), then the property commit runs.

## Session 2523 — a page a link creates passes the integrity check (#5741)

App health reported "1 row diverged in `pages_cache.last_edited_ms`". This

- Each create-page path stamps the new page's `space` with

  but never dispatches.
- The `space` stamps use it in four places: `create_page_in_space_inner`

## Session 2514 — a tag chip names a tag the preload missed (#5740)

**Found:** on the real backend, `e2e-tauri/import-obsidian-vault.e2e.ts`
sometimes saw an imported page's tag chip render `#01ABCDE...` instead of the
tag's name.

**Cause:**
- A `#[ULID]` chip reads its name only from the resolve store.
- The store's tag half is preloaded from `tags_cache`. The materializer fills
  that cache in the background, so a tag that an import just created can be
  missing when the import runner's post-import preload reads it.
- `useBlockLinkResolve` fetched missing `[[ULID]]` and `((ULID))` targets
  through `batch_resolve`, but never `#[ULID]`.

**Fix:**
- `ULID_LINK_RE` in `use-block-link-resolve.ts` gains a `#[ULID]` arm, so an
  uncached tag id goes to `batch_resolve` with the page and block ids.
- `batch_resolve` reads `blocks` directly, so it never waits on the cache.
- Page mode shares the scan and gets the fix too.
- A tag in another space, or a trashed tag, now renders the way page-link
  chips already do.

**Kept:** the import runner's preload. Search rows, the agenda, History and
the other plain store readers still depend on it.

**Specs:**

## Session 2512 — Page mode mounts a block's controls as it nears the view

A performance slice of #5743, after slice 3's priorities and dates (#5814).
Page mode's `pageBlock` node view mounted block mode's checkbox and metadata
row for every decorated block as the page opened. It now mounts them as each
block nears the viewport.

**Design** (`src/editor/page-mode/page-tasks.ts`):
- `ControlsGate`, one per editor, holds one `IntersectionObserver` for all its
  blocks. The root is the scroller the page is in (`scrollParentY`, as block
  mode's `useViewportObserver` finds it), with a `rootMargin` of a screen
  (`100% 0px`). With the implicit viewport root, the `ScrollArea` clips each
  block before the margin applies, so a block mounted only once it was on
  screen. The observer is built at the first node view drawn once the editor
  is in the page: `EditorContent` draws the node views again when it attaches
  the editor (`createNodeViews`).
- A block's controls mount on its first intersection and then stay. Its id is
  remembered, so a node view drawn anew for a new depth (a Tab, a peer's move)
  mounts at once instead of blinking for a frame until the next report.
- The caret's block mounts at once, through a plugin view's `update` on the
  same plugin as the task keys. Ctrl+Enter, the priority keys and Ctrl+Shift+D
  never needed the controls: they act on the caret's block through the page's
  task actions. They now show what they changed where they were pressed. A
  block that becomes a task while its controls are mounted mounts its new
  checkbox at once.
- Nothing mounts for print: the app has no print path, and the page sits in a
  clipped scroller that would print one screen. Export reads the backend, not
  the DOM. Find in page walks the DOM: the blocks' text is all there, as it was.
  A chip's text ("P1", "Oct 20") is found only once its row has mounted. Block
  mode's off-screen rows are empty placeholders, so its find already misses
  more than that.
- A runtime with no `IntersectionObserver` mounts everything at once. jsdom has
  the test setup's polyfill, which never reports, so the editor's tests stub
  `EnteringIntersectionObserver` (every block in view), as
  `AttachmentRenderer`'s tests do.

  checkbox's box is absolutely positioned in the slot page mode keeps left of
  the text, so it takes no room. The row's empty box keeps the row's height in
  CSS (`.page-block-metadata:empty`): its top margin, then a date chip's height

  the legacy `list_blocks(parent_id=…)` path.
