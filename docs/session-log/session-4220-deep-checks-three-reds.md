# Session 4220 — Four tests that failed by chance in CI

`Refs #3394`: dispatch run 43718156458 of `scheduled-deep-checks.yml` failed three lanes, and #6834's first head failed a fourth test. Each one is fixed at its cause.

- **`mutants-frontend-merge`**: the liveness guard reported no report for `history-utils`. Stryker's dry run failed because the `OP_TYPE_LABEL_KEYS` test (#6802) reads `src-tauri/agaric-store/src/op.rs`, and `ignorePatterns` kept all of `src-tauri` out of the sandbox. No other module's tests read a Rust source, so there was no precedent to copy. Stryker walks the tree with ignore-walk semantics, so `src-tauri/**` plus `!src-tauri/agaric-store/src/op.rs` copies that one file: the sandbox went from 3142 to 3143 files. A bare `src-tauri` cannot be negated this way: once the directory is re-included, its children no longer match it.
- **`bench-perf-gates`**: `durability_cost` (#6808) was terminated at nextest's 2x30s window on both tries. It is a measurement harness that prints timings and bounds none, and its module doc names this sweep as the place it runs at 1K blocks. A kill there only loses the numbers, so it stays in the lane with a `profile.default` override of 6x30s, like `reconcile_all_scale_sweep_4901`.
- **`full-suite-frontend`**: `AgendaView` "load more routes through loadMoreUnfilteredAgenda" fired load-more after the filter change committed but before that change's page-1 re-run had started. A trace showed the order: commit, then `waitFor` passes, then the re-run's passive effect. The effect runs in a later Scheduler `setImmediate` task, and the test only continues after RTL's `setTimeout(0)` drain, so a 1 ms stall lets the test win. In that order the re-run lands after the append and replaces the list, which matches the DOM the failure printed (one block, `hasMore` true). The re-run for `[]` now returns a page the DOM can tell apart, and the test waits for it before loading more. That also pins that load-more resumes from the re-run's cursor.

- **`query-text` property (#6809)**: "never writes a text that reads back as another filter" is unseeded and asserted `writtenWithOr > 20`, but its OR-texts came only from random trees, most of which the syntax cannot say. The trees alone wrote 23 to 40 a run here, and CI drew 19. A third input arm now builds an AND around an OR group of two or three distinct leaves the syntax can say, so a third of the 2000 runs write an OR: about 660 a run. The bound is now `> 300`, above anything the trees alone reach and about 17 standard deviations below the arm's mean. Falsified twice: dropping the parentheses and the writer's read-back check fails the round trip on an OR-arm counterexample; dropping only the parentheses makes the writer refuse those texts, and the bound catches it (251).
