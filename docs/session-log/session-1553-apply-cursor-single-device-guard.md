# Session 1553 — A release-build guard on the single global apply cursor

Closes #4661, found while auditing #4638. `apply_op_projected(.., advance_cursor = true)` moves one global scalar cursor to `record.seq`, which is only sound while every applied op comes from one device: `op_log.seq` is a per-device counter, so a foreign device's op drags the cursor past the local device's unmaterialised ops and boot replay's `WHERE seq > cursor` walk then never replays them. Blocks that exist in the op log and in Loro would simply never appear in the SQLite views, silently. The batch arm rejects a mixed-device batch in every build; this path had only a `#[cfg(debug_assertions)]` block, so release did no checking at all.

The trace says the exposure is not reachable today — every enqueue path filters `is_replicated = 0`, and `dag::insert_remote_op`, the one ingest that would produce a foreign locally-authored row, has no production caller — but "cannot happen yet" is what the debug-only assert was already betting on, and AGENTS.md item 5 puts invariants on a write path in every build.

The reason the check stayed debug-only is real, and it is a property of the query rather than of the predicate. Deciding "is the whole op_log one device" is `MIN`/`MAX` over `op_log`, which SQLite plans as a SCAN: measured on a synthetic 100K-row log, about 10 ms per applied op, and about 20 ms once a peer's audit rows are in the table. So that query stays where it is. What the release build now runs instead is a PK point lookup on the record's own row — about 20 µs, index-backed regardless of log size — refusing a replicated op. That is the shape a foreign device's op actually takes at this site: migration 0099 stamps every replicated record `is_replicated = 1` exactly so the apply pipeline can never treat it as local, and this is that isolation boundary failing loudly, with the batch arm's `AppError::InvalidOperation`, rather than silently. The debug assert stays for the predicate the cheap lookup cannot express, with a comment saying which case each one owns.

The first version of the guard also refused a record with no `op_log` row, on the reasoning that such a record cannot index a cursor over `op_log.seq`. That reddened two pre-existing harnesses — the apply/reproject proptest and the FIFO status test — which build synthetic records to exercise the projection and never write them to the log. It was over-reach rather than a defect they had: only op-log rows carry provenance at all, no foreign op can arrive without one, and refusing absence bought nothing while forcing two unrelated tests to fabricate log rows. The guard now refuses only what it can prove.

Verified: with the guard forced off the refusal test goes red on the apply that should have failed; with the guard forced on for everything the two cursor-advance assertions go red instead, so neither arm of the pair is open. Both mutations were made against a copy and the file restored `cmp`-identical. A third test pins that `advance_cursor = false` — the local command sites, #1257 — never reaches the check.

Shipped: fix for #4661.
