## Session 2300 — Middle-click opens a page in a background tab; right-click offers it

#5684: the maintainer asked for middle click on desktop to open a page in a
background tab, and for right-click to offer the same.

**Tab model.** `src/stores/tabs.ts` had `openInNewTab`, which switches to the
new tab, and no background variant. `openInBackgroundTab` adds the tab and
leaves the active tab and the view alone. The tab bar shows on desktop only,
once two tabs exist.

**Shared pieces, not per-call-site handlers:**
- `useOpenInBackgroundTab`, with `middleClickProps` and
  `delegatedMiddleClickProps`, which cancel Linux autoscroll on mousedown and
  the primary-selection paste on mouseup;
- `NewTabTarget`, which wraps an element with the middle click and a Radix
  context menu;
- a new `ui/context-menu.tsx` primitive. Pages rows and search results had no
  context menu before; only the block menu did.

**Covered:**
- `[[links]]` and `((refs))` in static blocks, through one delegated handler
  on the block tree. Right-click on a link puts "Open in new tab" first in the
  block menu.
- Everything that uses `PageLink`: reference and search group headers, the
  tag view, agenda page names.
- Pages rows and tree entries, bookmarks, the recents strip, search results
  and recent searches, reference rows, agenda and task rows, and graph nodes.

**Skipped:**
- breadcrumbs, which open the Pages view or stay on the page;
- a context menu on graph nodes, which d3 draws;
- middle click inside the block being edited, which was not tested.

**Ctrl/Cmd+click.** The graph and the recents strip already used it for "new
tab" and switched to it. It now opens a background tab, like middle click and
like a browser.

**Mobile.** There are no tabs, so the menu item is hidden and middle click
does nothing.

**Tests.** 23 vitest mutations and two Playwright mutations (each rebuilt)
were all killed at the predicted assertion. A `stopPropagation` that no
mutation could make matter was deleted.

**Flake noticed.** graph-view's "label same height at three zoom levels"
failed 4 of 12 runs on main's own code. It goes on the flake list, to be
checked against tonight's reduced-motion change (#5666).

Gates: full vitest (21,384), `npm run typecheck`, oxlint, oxfmt, the new spec
with the tabs, menus, navigation and links specs (171/171 at `--repeat-each=3
--retries=0`), and one pass of the pages, search, agenda, references,
bookmarks and graph specs.

## Session 2298 — References sort: no internal keys, a direction toggle, sortable types only

#5683: the References sort offered keys like `is_space` and
`personal_to_work_migration_v1`, had no direction control, and the maintainer
asked that their own properties be offered only when their type has a
meaningful order.

**The keys.**
- `is_space` marks a space's page; the space setup and migrations 0035 and
  0039 write it.
- `personal_to_work_migration_v1` was written once by a migration removed in
  #4132 and survives on old installs' Personal space page, with no
  definition. It is reported, not migrated.

The same leak covered `accent_color`, `template`, `journal-template`,
`listStyle` and three image keys. None were in `INTERNAL_PROPERTY_KEYS`, which
has no Rust mirror.

**Where they leaked:**
- the References sort and add-filter lists (linked and unlinked);
- the property value and `::` key pickers;
- search `prop:` autocomplete;
- the add-property lists in the block drawer and the page property table;
- the query builder and query-table columns.

**One rule.** `INTERNAL_PROPERTY_KEYS` now lists them and is applied at the key
cache and at the three definition-based lists. Beside it,
`isSortablePropertyType` admits:
- number, by value;
- date;
- select, A–Z by option text, because the backend cannot sort by option
  order.

It leaves out:
- text, which the backend sorts by bytes, so "Zed" precedes "apple";
- url, ref and boolean, which have no useful order;
- properties without a definition, which count as text.

**Design.** A field picker joined to an arrow button that shows and flips the
direction. Built-in fields (Created, Due date, Scheduled, Priority,
Completed) come first, then "Your properties". The default is Created,
oldest first, which the backend already used, and the arrow works from the
start. Both controls are 44 px on touch. Sorting orders blocks within each
source page; the pages stay alphabetical.

**Bugs fixed on the way:**
- Sorting by due date, scheduled date or priority did nothing. A reserved key
  never has a `block_properties` row (migration 0088), so the backend now
  orders by its own `blocks` column; the spliced name is one of the fixed
  `RESERVED_PROPERTY_KEYS` literals.
- Number and date properties sorted as text.
- Each sort change dropped keyboard focus.
- The mock ignored sort; `query_backlinks_grouped_sort` pins it to the
  backend.

**Not done:**
- select by option order, which needs a backend change;
- a direction toggle for the Agenda and the Pages browser, whose paging
  assumes a fixed direction;
- a space's own page property table still shows `is_space`.

Gates: vitest (96 files, 2,559), `npm run typecheck`, oxlint, oxfmt,
Playwright (174/174 at `--repeat-each=3`, plus related specs), the Rust sort
tests (12/12) with a backend-authored fixture, clippy and rustfmt. Eleven

## Session 2296 — Toolbar icons render at 16 px instead of a blurry 12

#5682: the maintainer asked whether the toolbar icons were small and blurry.
They were, and smaller than the code said.

**Measured** (Playwright against the mock, at pixel ratios 1, 2, 0.9, 1.1
and 1.25):
- **Size.** Every icon in the formatting toolbar, the selection bubble and the
  Format popover rendered at 12×12 in a 24 px button. The `icon-xs` Button
  variant forces 12 px on any icon without a `size-*` class, which overrode
  the `h-3.5 w-3.5` the call sites asked for.
- **Stroke.** lucide's two-unit stroke becomes a 1 px line at 12 px that
  mostly lands between pixels. At 1x, 84% of the bubble's inked pixels were
  only partly covered.
- **Position.** The icons do sit on half pixels, because the page title's
  37.5 px line box shifts everything below it. Rendering them on whole
  pixels changed nothing, so position is not the blur.
- **Thinner strokes.** 1.5 and 1.75 looked fainter, not sharper, so the
  default stays.

**Fix.** One shared `toolbarIconClass` (`size-4`) for every icon in the
formatting toolbar, the Edit as Markdown toolbar, the overflow button, the
bubble menu and the Format popover. The buttons keep their 24 px (44 px on
touch), so the toolbar layout and its overflow do not move. Partly covered
pixels in the bubble at 1x fell from 84% to 68%.

`e2e/toolbar-icons.spec.ts` requires 16×16 for the 17 toolbar and 7 bubble
icons. It failed with all 24 at 12×12 with the old class restored, and
passed ten repeated runs with the fix.

**Not done here.** `icon-xs` forces 12 px on about 49 other call sites that
ask for 14 or 16 px, and `h-*`/`w-*` on an icon inside any Button has no
effect; only `size-*` does. Fixing that is the follow-up on #5682.

Gates: vitest (564), `npm run typecheck`, oxlint, oxfmt, and the toolbar,
bubble, mobile, Edit as Markdown and overflow Playwright specs (150 passed,
2 skips that already existed).

## Session 2290 — No scrollbar on diagrams that fit; Mermaid styled to best practice

The maintainer: hovering over a Mermaid diagram (maybe images and math too)
showed scrollbars, and some Mermaid elements lacked borders or had opaque
fills. They asked for best practice, then for it to be implemented. Tracked
as #5677 and #5678.

**#5677, scrollbars.** Radix's ScrollArea always sets `overflow-x: scroll` on
its viewport, overflowing or not, expecting its own CSS to hide the native
bar. Our `index.css` turns native bars back on, so every diagram and display
equation reserved a 10 px scrollbar, even when nothing overflowed. A comment
there claimed Radix scrolls only on overflow; it is corrected. Images are not
in a scroll container and never had this. `SCROLL_ONLY_WHEN_WIDER`
(`overflow-x: auto` on the viewport) is used by the Mermaid and display-math
ScrollAreas. Wide content still scrolls. `e2e/diagram-scrollbar.spec.ts`
enables real scrollbars. Without the fix the bar is 10 px instead of 0, and
`hidden` instead of `auto` fails the "wide content still scrolls" check. The
hover-only flash itself could not be watched in WebKitGTK here; it follows
from the cause.

**#5678, Mermaid styling.** Rendered in light and dark for flowchart,
sequence, class, state, gantt and ER diagrams.
- **Already fine:** flowchart, state and ER node borders, flowchart edge
  labels, and clusters (canvas fill with a border).
- **Wrong before:**
  - class-diagram edge labels sat on opaque node-fill boxes, which Mermaid
    hard-codes;
  - notes were barely distinct from nodes;
  - in dark gantt, a heavy grey band, a done-task label at 1.32:1 and crit
    text at 3.52:1; in light gantt, the active task's border at 1.07:1;
  - ER zero-markers filled solid white in dark mode.
- **Now:**
  - notes take the pending-status tint;
  - gantt states take the done, active and error tints, each with its own
    border;
  - ER rows and section bands use the page and fill tokens, and gridlines the
    border token;
  - a small `themeCSS` puts edge labels on the canvas and makes ER markers
    hollow.

Across all six themes, text on fills measures 4.7–16.4:1 and borders
5.3–12.5:1. Gridlines are 1.2–1.4:1 on purpose; the axis labels carry the
information. `mermaid-theme.test.ts` pins each property, and six one-line
mutations each reddened their own test. `diagram-legibility.spec.ts` fails
with `themeCSS` emptied or node strokes removed.

**Found, filed, not fixed here:**
- under reduced motion, a Mermaid flowchart renders several times too large,
  because the global reset keeps `transition-property: all` at 0.01 ms and
  Mermaid measures mid-transition;
- wide display math is clipped when edited at phone width.

## Session 2284 — The boot harness times what the user waits for, in isolation

#5419 is gated on re-measuring boot after #5418 step 2. Its decision turns on
the part of boot before the window is usable, and the harness could not see
that part: `main` logged no frontend milestone.

**Milestone.** Each call to `useBootStore.boot`, retries included, sends one
`boot resolved` line with its outcome (`ready` or `error`). Production drops
`logger.info`, so the line goes to the backend sink, which `main.tsx` sets to
`logFrontend`. Calling `logFrontend` directly broke twenty tests in suites
that never stub `log_frontend`; the sink is the existing seam. In the JSON
log it lands as `target: "frontend"`. That is #5419's third acceptance item.
Dropping the error-path line, logging the ready line twice, and dropping the
warn on a rejected write each reddened the new tests.

**Harness.** `scripts/measure-boot.mjs` now reports:
- process start to the first log line;
- log start to engines rehydrated, replay done, sync started and `boot
  resolved`;
- the frontend part on its own;
- the time between consecutive backend milestones, so a dominant step stands
  out.

A rewind of 0 leaves the apply cursor alone, for a quiet boot.

**Isolation the old harness lacked:**
- The app inherited `WAYLAND_DISPLAY`, so its window could open on the
  desktop.
- The webview wrote its storage into the real
  `~/.local/share/com.agaric.app`, because WebKit follows the OS app
  directory and not `AGARIC_DATA_DIR`. Each run now gets its own `XDG_*`
  directories. On the maintainer's machine that store was last written at
  their own app's exit, so tonight's runs left nothing there.
- GTK asked the private bus for the desktop portal, which never answered, so
  every boot stalled 25 s before its first log line. Timing from the log
  start had hidden it. The bus now starts no services.

The run sits under `unshare -rn xvfb-run -a dbus-run-session`, with openbox
waited for and Wayland checked inside the wrapper. strace showed X traffic
only to Xvfb and the one network connect blocked.

Phase 2, the release build and the measurement on a vault copy and a very
large synthetic vault, follows in its own change.

Gates: the boot store vitest files (60), `npm run typecheck`, oxlint, oxfmt,
`node --check`, and `check-vault-isolation`.

## Session 2280 — The pairing scanner fills its viewfinder and starts on one press

On Android 0.18.0 the camera started (#5386's fixes), but its image did not
fit the preview box. Choosing "Scan QR code" in the pairing dialog then
needed a second "Scan QR code" press inside the scanner. The maintainer
asked for one press.

**Cause.** html5-qrcode 2.3.8 makes its video as wide as the container and
lets the camera's shape set the height. A 4:3 camera left a 256×192 strip in
the 256 px square, and a tall phone stream spilled past it. The scan box was
a fixed 250×250, taller than a 192 px image, so no frame was drawn at all.

**Fix.**
- **Square stream:** the scanner asks the camera for a square image
  (`aspectRatio: 1`). There is no `object-fit` crop, because the library
  derives the decode region from the video's on-screen size.
- **Scan box:** 70% of the video's shorter side.
- **Clipping:** the viewfinder clips. A camera that ignores the request still
  shows its frame inside the picture: a wide image is letterboxed, a tall one
  is trimmed.
- **One press:** the camera starts when the scanner opens. The start waits one
  microtask, so React StrictMode's double mount starts one camera. A failure
  from a cancelled session (closed, or replaced by Retry) is ignored.
- **Errors:** a camera error stays on the scanner, as the maintainer decided:
  the message in a live region that is mounted before it fills, and "Retry
  camera" with focus on it. The drawer's existing passphrase button is the
  way out, so no second one was added.

**Review found two bugs.**
- html5-qrcode passes a `getUserMedia` failure on as a string, while the
  message mapping only read `.name`. So a denied camera never said "Camera
  permission denied". The unit mock rejected with an `Error`, which hid it;
  it now rejects with the library's string.
- A camera error also raised a dialog banner whose Retry restarted pairing,
  not the camera, and that outlived a successful retry. The path and its
  keys are gone.

The orchestrator restored the cancelled-session guard, which review had
dropped together with the parent callbacks.

**Tests.**
- vitest pins the auto-start, StrictMode starting one camera, a quick close
  stopping the camera, Retry, the error staying on the scanner with focus,
  the live region, and the string mapping. Each was shown red.
- `e2e/qr-scanner-camera.spec.ts` runs a fake camera, square and tall, at
  phone and desktop sizes. It checks that the video fills the viewfinder,
  that the scan frame lies inside it, and that on a touch phone both error
  buttons are 44 px and the passphrase button shows the word inputs.

Gates: the peers and pairing vitest files (307), `npm run typecheck`, lint,
and the scanner and pairing Playwright specs.

## Session 2276 — A manual Sync starts its session at once

**Problem.** Pressing Sync waited about 3 s before any session started.
`start_sync` answered "complete" at once, but the real session began 3 s later.
In real-backend run 38925731657, every click took about 3.07 s to reach
`try_sync_with_peer` for a session of about 0.25 s. The real-lane sync specs
waited on it too.

**Cause.** The path is sidebar Sync → `syncAll` → `start_sync` per peer →
`start_sync_inner` → `notify_change()` → the daemon's
`wait_for_debounced_change`, which waits out `DEFAULT_DEBOUNCE`. The debounce
only coalesces bursts. Its only production callers are `start_sync_inner` and
the two pairing commands; no local edit or materializer path calls
`notify_change`. Bursts are the per-peer calls a few milliseconds apart, and
a round already dials every peer at once (`run_change_round`).

**Fix.** `DEFAULT_DEBOUNCE` is 250 ms, and so is the copy in `e2e_sync_peer`.
Every stale claim of a 3 s window or of "a sync after each local edit burst"
is corrected: the protocol comments, the daemon docs,
`sync-and-network.md` (which now names the constant instead of a figure)
and three frontend comments. `sync-refresh.e2e.ts` polls every second instead
of every 3 and 5 s, with its timeouts unchanged.

**Test.** `sync_now_opens_one_prompt_round_per_burst`, on a paused clock,
checks that one `notify_change` opens a round within 500 ms and that five
calls 5 ms apart make exactly one round. It was red on 3 s ("opened its round
after 3s"). With a 1 ms window, the burst half went red at 6 rounds against 2.

Gates: targeted nextest (scheduler, supervisor, daemon, pairing, sync
commands) 380 passed; full workspace suite 3494 + 3486; clippy;
`SQLX_OFFLINE=true cargo check`; fmt; `npm run typecheck`.

## Session 2274 — The integrity check audits tag inheritance and the Loro engine

#5628 had three gaps in the Settings integrity check (`reconcile_all`):
`block_tag_inherited` was never audited, the Loro engine was never compared
with SQL, and the check's report-only stance was never decided. Since #5418's
snapshot pass advances the apply cursor, boot replay no longer heals a write
that took the SQL-only fallback or a skipped engine fan-out. That makes this
check the place such drift shows.

**Gap 1.** `block_tag_inherited` is rebuilt by the oracle with the production
walk, depth bound and nearest-ancestor rule, then diffed. A stale row and a
missing row are both named.

**Gap 2.** Each space's doc is exported under the engine lock, only long
enough to clone the handle, and read in a throwaway engine. Block rows,
sibling order and the engine-held properties and aliases are compared with
SQL. Sibling order is compared by each block's place among the siblings both
sides hold, not by raw rank. The first vault run showed why: every one of 234
position reports was a gap a purge leaves in SQL ranks, with order unchanged.
Readers sort by `(position, id)`, so a gap harms nobody. Soft-deleted rows,
space-less blocks, detached nested pages and tombstones the engine keeps all
read as agreement.

**Gap 3.** The check stays report-only, as the issue leaned. Drift remains
visible as a defect instead of being repaired away.

**What it found.** On a copy of the maintainer's vault, the check found one
real divergence: a live block missing from Work's engine. The block was
pinned by #5670, whose diagnosis traced it to the pre-#5418 boot replay that
#5630 also fixed. #5670 adds a targeted one-shot repair for vaults already in
that state.

**Stale claims.** Every comment and doc that said boot replay reconciles
these writes is corrected. That covers the apply kernel, the SQL-only
fallback, the materializer handlers, `loro_sync.rs`'s tombstone fan-out,

## Session 2270 — The reduced-motion graph settles instead of freezing

The maintainer left it to this session whether the reduced-motion layout
should keep `alphaDecay(1)`. It should not.

**Cause.** Every reduced-motion path set `alphaDecay(1)` before ticking
`REDUCED_MOTION_TICK_LIMIT` times synchronously: mount, update and resize on
the main thread, and the worker's `start`. d3-force decays alpha before it
applies the forces, so alpha was already 0 on the first tick. Link, charge
and gravity never acted. Collide and center do not scale by alpha, so nodes
did not overlap, but links stayed at 32–40 px against a rest length of 60,
and a page added by an update stayed where d3 seeded it, 519 px from its hub.
Each tick still computed every force, so the setting saved nothing.

**Fix.** The paths tick with d3's default decay, which brings alpha from 1 to
`alphaMin` in exactly `REDUCED_MOTION_TICK_LIMIT` ticks; from 0.3 (update,
resize) it needs fewer. Dropping it broke drag release, which had relied on
the leftover decay, so drag now follows the reduced-motion rule as well:
- while a node is held, only that node follows the pointer, drawn once per
  move;
- release settles once from where it was let go;
- a click with no movement changes nothing.

The builder's first version coasted for about four seconds after a release.
The second re-settled on every click. Review then found that the main thread
did not draw the held node during a drag, and that the worker animated the
neighbours. All four were fixed before merge.

**Tests.** `src/lib/__tests__/graph-reduced-motion.test.ts` drives real
d3-force on both paths. It checks that links end within 5 px of the link
distance (charge and collision stretch a settled link slightly) at mount,
after an update and after a resize. It checks that a drag moves only the held
node and settles once on release, and that a click applies and posts nothing.
Putting `alphaDecay(1)` back reds each path. So does a click that settles, and
so does the earlier restart-on-move.

Not changed: a drag release on the main-thread fallback (no Worker) does not
call `onSettled`, so labels are not re-placed there. Update and resize had
the same gap before.

Gates: graph vitest, `npm run typecheck`, `npm run lint`, and the graph-view
and graph-restore Playwright specs at `--retries=0`.

## Session 2264 — A vitest run failed on an announcement after teardown

#5661, a docs-only PR, failed a vitest shard with every test passing and one
unhandled error: `document is not defined` in `announcer.ts`'s `getOrCreate`,
reached from `flushQueue`.

**Cause.** Announcing two distinct messages shows the first and arms a real

leftover timer finds nothing to flush. No production code changed.
`src/__tests__/announcer-teardown.test.ts` announces twice and ends. Its
`afterAll` stands in for teardown: it removes `document` and waits out the
timer. Without the reset line, that run reports the unhandled
`ReferenceError`. With it, the run is clean.

## Session 2232 — Search queries survive a chip edit

The search-query property `parse(serialize(parse(s))) === parse(s)` failed on
a main push (run 36985456234, seed 2008733170) and passed on the next one
with the code unchanged. The counterexample `" A:"#` reproduces every time,
so this was a real bug that the random input reaches only sometimes.

**Causes:**
- **A chip with an unclosed quote.** A filter word whose mid-word `"` never
  closed still became a chip, and its extent depended on the text after it.
  `serialize` puts free text after the chips, so a `"` in that free text
  could close the chip's quote and swallow everything between.
- **Values holding quotes.** `quoteValueIfNeeded` checked only for
  whitespace and surrounding quotes. A value like `a" "` breaks when quoted,
  and `"` or `a"b` break when bare. The bare `#x` alias also kept quotes that
  `tag:#` strips.
- **Non-ASCII spaces.** The tokenizer split on ASCII whitespace while the
  free-text cleanup collapses all of `\s`, so `a<no-break space>#a` came back
  as a `#a` tag chip. macOS types a no-break space on Option+Space.

**What a user saw.** Typing `rock" prop:title="Hello` and then adding a tag
chip rewrote the query to `prop:title="Hello tag:#x rock"`: the tag vanished
into the property value and the free text was lost.

**What changed** (`src/lib/search-query/`):
- `tokenize` flags a word whose quote never closes, and splits on `\s`.
- `classify` keeps a flagged word as free text, and the bare `#x` alias goes
  through the `tag:` recogniser.
- `quoteValueIfNeeded(v, prefix)` emits a value bare only when the tokenizer
  reads `prefix + v` back as one closed word; `prop:` passes its key as the
  prefix.

Behaviour change: `prop:status="in progress` is free text until its quote
closes, and `#"my tag"` matches the tag `my tag`.

**Tests.** Ten counterexamples are fixed round-trip cases, among them
`" A:"#`, `"a" X:" q"z`, `rock" prop:title="Hello` and `a #a`, plus
tokenizer, classifier and autocomplete cases. Reverting the source turns
them red. The property passed 20,000 seeds of 200 runs, and two hunts of
2,000,000 samples over quotes, every prefix and non-ASCII whitespace found
nothing. `numRuns` stays at 200.

## Session 2230 — The real-backend typing helper stops losing keys

The real-backend WebdriverIO lane's slowest typing specs spent most of their
time waiting out read-back budgets. A CI survey timed `pages-most-linked` at
about 24 s and `search-bm25-order` at about 21 s.

doc blamed a janky first render; the log shows the driver.

- `distinctKeyChunks` splits the text into runs in which no character
  repeats, and the first attempt sends each run as its own call.
- An attempt ends once the read-back has stopped changing for 400 ms, with
  3 s still the bound. The retry still types one key at a time.
- The `readBackTimeout` parameter went with the 10 s budget it carried.

**Tests.** `e2e-tauri/helpers.test.ts` pins the chunks for `[[wdio-rival` and
`zap of ink`, and a fast-check property checks that the chunks join back to
the text with no character twice in a chunk. Splitting only at adjacent
repeats turns three red, the space case among them.

**Not run locally:** the WebdriverIO lane needs a native build. The PR's
e2e-tauri run is the check: the typing-heavy specs should drop, and

## Session 2226 — An open tag search misses a peer's new tag (#5255)

The real-backend `sync-refresh.e2e.ts` failed once on PR #5645, which touches
no search or sync code: an open `tag:#marigold` search never listed the
block a paired peer had tagged, through twelve more Syncs. The previous run
of the same code passed.

**Cause.** An app race in `useTagResolution`. A pull publishes two name
changes about 5 ms apart: `sync:complete`, before the `tags_cache` rebuild

the one pull carrying all the peer's writes and the `tags_cache` rebuild

started before the bump discards its own answer. `reloadKey` stays, since it
is what re-runs the effect.

**Checked, not changed:**

## Session 2222 — Crash replay carries a later-deleted block's ops to the engine (#5630)

Boot replay resolved each op's space with `resolve_block_space`, which skips
tombstones. SQL already holds the replayed tail, so in it a delete, and any
edit, property, tag, alias, move or create on a block that a later op
deletes, found no space and took the SQL-only path. The engine never got
those ops, and a page deleted in the tail stayed live there.

**What changed:**

- **The resolver.** On replay only, `resolve_op_space` falls back to the
  soft-deleted resolver, so those ops reach the engine. The edit, property,
  tag and alias helpers and `resolve_doc_space` take a `replay` flag; move
  and create read `replay_dirty`.
- **The delete.** `apply_delete_block_op` normally captures its cascade
  before its `UPDATE`. On replay over SQL that already holds the delete, it
  rebuilds the cascade from the rows stamped with the delete's timestamp
  (`collect_cohort_deleted_at`, split out of `collect_restore_cohort`), so
  the post-commit fan-out writes the engine.
- **No sweep on replay.** Review found a tail that came out wrong. W moved
  into P, then out to Q, then P was deleted. The replayed move into P saw
  P's later tombstone and swept W into it. The move out ran the engine arm,
  which never un-sweeps, so W ended trashed in SQL and the engine. On replay
  the engine arm no longer sweeps; the later delete's own replay stamps W if
  W is still under it.

  Every local move producer checks that the target parent is live, so a
  local move lands under a tombstoned ancestor only in a damaged vault. A
  probe of that case gave the same result with and without the skip.

**Tests** (`agaric-sync/src/recovery/tests.rs`):

- `crash_after_a_snapshot_pass_replays_only_the_tail_5418`;
- `crash_tail_ops_on_blocks_deleted_later_reach_the_engine_5630`;
- `crash_tail_move_in_move_out_then_delete_the_old_parent_5630`, review's
  case. It was red on the first commit ("W is live in SQL, as in the
  session") and red again with the skip reverted.

**Comments corrected:** the move-routing claims in `loro_apply.rs`,
`projection.rs` and `sql_only.rs`; the delete cohort's "unrecoverable
afterwards" and "captured before the UPDATE" in `kernel.rs`;
`op_log_head`'s list of boot-only engine writers; and the `SpaceUnresolved`
text in `sql_only_fallback.rs` and `sql-only-convergence.md`.

**Not done** (#5647):

- A restore, a purge, a page's space move or a retried op in the tail still

- In a damaged vault, replay does not put a live sweep's tombstone back

## Session 2216 — The AppImage's title bar shows the host's window buttons

The maintainer asked why Agaric has no minimize button. Agaric draws no title
bar of its own, so GTK draws one, and on Ubuntu GNOME the AppImage showed only
a close button.

Tauri's AppImage runs linuxdeploy-plugin-gtk's startup hook, which points
GSettings at the schemas bundled inside the AppImage. Those carry upstream
GNOME's `button-layout` default, `appmenu:close`. Ubuntu ships
`:minimize,maximize,close` as a vendor schema override rather than a dconf
value, so the bundled schema hid it. A PyGObject probe under the hook's
environment reproduced it: GTK read `menu:close`. The same key read through
the host's schema dirs gave `:minimize,maximize,close`. A layout the user set
explicitly was always honoured, because the dconf backend is bundled too.

`apply_host_decoration_layout_if_running` runs at boot, inside an AppImage
only, on the same `$APPIMAGE` guard as the desktop self-integration. It chains
a `SettingsSchemaSource` from the `XDG_DATA_DIRS` entries outside `$APPDIR`,
reads `button-layout` through it, and sets `gtk-decoration-layout`. It is
set once, so a layout changed while the app runs applies at the next launch.
A host with no GNOME schemas, such as KDE, logs at info and keeps GTK's
layout. `gtk` becomes a direct dependency at the version Tauri already
resolves, so nothing new is built.

Only the dir selection is unit-tested. Excluding by string prefix and keeping
empty entries each turned a test red. The debug binary ran under Xvfb with the
hook's environment, a private D-Bus session, a sandboxed data dir and moved
XDG dirs. It logged `layout=:minimize,maximize,close`, and a control run
without `$APPIMAGE` logged nothing. The user's running instance and desktop
launcher were left untouched. That run used the host's GTK and GLib, so a
rebuilt AppImage on GNOME Wayland is the final check.

## Session 2214 — Pages the backfill places in Personal reach its engine

A review of #5631 (#5418 step 2) after it merged found a regression. The
review used a scratch repro and compared the cursor-advancing pass against
the old one.

**The bug.** The space-less page backfill (`backfill_space_less_in_tx`, on
every boot and after every inbound sync) appended a `SetProperty(space)` op
per page. It wrote `blocks.space_id` with a chunked UPDATE and never touched
the Loro engine. Before #5631 the next boot's replay was what hydrated those
pages into Personal's doc. Once any snapshot pass may advance the cursor,
even a quiescent one, those ops are skipped, and the pages stay out of the
engine. From then on they don't sync through the CRDT, a reprojection from
the engine loses them, and every edit takes the SQL-only fallback. #4743 had
fixed the same shape for tags; the page migrator was left behind.

**The fix.** `migrate_pages_to_personal_space` (no longer batched) applies
each record through `apply_op_projected` in the same transaction, as the tag
migrator does. Both callers arm the engine rollback, so a failed commit
leaves no half-hydrated engine. The chunked UPDATE is gone.

One cost: hydration is quadratic in page count, because each page's hydrate
reprojects Personal's top-level page list. The review measured a legacy first
boot with three children per page, release-test profile:

| Pages | Bootstrap now | Bootstrap before | Next-boot replay before |
|---|---|---|---|
| 1,000 | 3.3 s | 0.07 s | 2.0 s |
| 2,000 | 7.4 s | 0.11 s | 9.4 s |
| 4,000 | 38.7 s | 0.21 s | 34.2 s |

The work moved from the second boot to the first rather than grew. Three
things did change with it:

- **One transaction.** Replay committed in chunks and resumed after a
  force-quit; the bootstrap is one `BEGIN IMMEDIATE`, so a user who kills
  the frozen first boot starts over.
- **Boot-fatal errors.** A hydrate error now fails boot instead of landing
  in the retry queue. No real vault was shown to hold a row that triggers
  one.
- **The writer is held longer.** Mid-session, the sync placement pass holds
  the writer past `busy_timeout` once it places about 1,500 pages. Such
  pages normally arrive inside a space's doc and are stamped from it, so a
  pass that size needs a legacy peer.

All of this falls only on pre-spaces vaults, and was accepted rather than
optimised. Dense reprojection of the root group also renumbers the
`position` of other top-level pages, which nothing orders by.

**The premise, corrected.** #5631 claimed every op below the head is in the
engine. The `op_log_head` doc now lists the engine writes that land after
commit:

- the single-delete cohort;
- batch delete, seed included;
- the three restores;
- the three purges.

Draft recovery, the empty-block sweep and repair also write the engine after
commit, but only at boot, before the periodic pass is spawned. A crash
before the next pass loses the mid-session ones, which is #5630's territory. Every
comment that still said "the cursor stays put so boot replay re-applies"
now says the snapshot pass moves it, in code comments, tests and the
architecture docs. Review found copies the first sweep missed: in `tags.rs`,
the materializer, batch delete and restore, the bulk-equivalence twin,
conformance tests, the crash-injection tests and `rollback-safe-engine-apply.md`.
Those are fixed too.

About 15 "boot replay reconciles" comments on the SQL-only fallback paths
were left alone. They make a separate claim, many were never true even
before #5418, and each needs its own check. #5628's engine-vs-SQL gap is
where that population becomes visible.

**Sweep.** Every production op-log append site was classified. The page
backfill was the only deterministic miss. Attachment ops and the seeded
space blocks never reach an engine by design, before and after #5631.

**Tests:**

## Session 2212 — Diagrams and display math you can read (#5638)

Mermaid diagrams and display math were hard to read in several ways:

- Display math was clipped at phone width, and nothing could scroll it.
- Mermaid's stock themes ignored the app's tokens, so diagrams did not match
  the theme, and edge labels sat on grey boxes.
- Mermaid's `useMaxWidth` shrank a wide diagram to fit, without limit. On a
  phone its labels came out a few pixels tall.

**What changed:**

- **Display math** sits in a horizontal `ScrollArea`. KaTeX's error colour
  is now a token. Inline math is unchanged.
- **Mermaid** renders with `theme: 'base'` and `themeVariables` built from
  the design tokens, and re-renders when the theme changes. WebKitGTK
  returns `oklch()` unchanged from both `getComputedStyle` and a canvas
  `fillStyle`, so `readDiagramColors` paints each token onto a pixel and
  reads sRGB back. `securityLevel: 'strict'` stays.
- **Wide diagrams** stop shrinking where the smallest label would drop
  below a legible size, and scroll from there. Tall ones are capped, with a
  fade.
- **The viewer.** `ImageLightbox`'s zoom and pan became `useZoomPan` plus
  `ZoomControls`, which a new `DiagramViewer` shares. Its controls:
  - Expand, which is always visible on touch;
  - Fit, 100%, zoom and pan, including pinch;
  - Copy source and Download SVG.

  Display math gets the same viewer with Copy LaTeX. The lightbox's tests
  pass unchanged, and it gained pinch.
- **Edit mode.** The Expand button and the viewer stop clicks so a static
  block does not enter edit mode. Opened from the editor, the viewer
  carries `data-editor-portal`.

**One premise was partly false.** The issue expected the dark theme to fail
contrast. The stock dark theme already passed, so contrast alone could not
show the fix red. The e2e checks instead that text, edges and edge-label
backgrounds take the theme's tokens. With the stock theme forced back, all
six resolved themes fail that check.

**Not done:** the viewer's fit and the inline fade are not recomputed on
resize. Download SVG reuses `downloadBlob`, as export and bug reports do.

Review found that pinch, wheel and drag worked only on the diagram's own box.
On a phone the fitted diagram can be a thin strip, so a pinch across it did
nothing. The gesture handlers now sit on the whole viewer and the transform
stays on the diagram; a pinch that starts outside the strip was shown red
first. Review also cut twenty theme variables that Mermaid's `updateColors`
derives from the ones still set, and an unused `maxZoom` option.

## Session 2210 — Closing the palette returns focus to its opener (#5639)

Review of #5636's header search button found that closing the Ctrl+K palette
left keyboard focus on `<body>`, from every trigger. A keyboard user who
pressed Escape lost their place and had to Tab from the top of the page.

The cause is Radix's modal dialog content. On close it prevents FocusScope's
own return step and focuses `Dialog.Trigger` instead; the palette is opened
from a store and has no trigger, so nothing took focus. FocusScope's step
would not have helped either: it records the element focused when its effect
runs, and by then the palette input already had focus.

`CommandPalette` now handles `onCloseAutoFocus` and focuses the element the
store already captured on open, `previousFocusedElement`, the one `[[page]]`
insertion reads. It does so only while focus is on `<body>`, so a close that
navigates (a page, the search view) keeps the focus that navigation placed.

Two Playwright specs in `palette-desktop.spec.ts` pin both halves. Removing
the handler turned the Escape test red at `toBeFocused()` on the opener;
dropping the `<body>` check turned the escalation test red at the search
view's input. jsdom cannot reproduce Radix's close-time focus timing, so
there is no vitest test.

## Session 2204 — A visible search control in the desktop header (#5636)

Desktop had three search surfaces: the Ctrl+K palette, in-page find
(Ctrl+F), and the full search view (Ctrl+Shift+F). Only the last had a
visible entry point, the sidebar's "Search", and it is the slowest way to
open a page. Phones already had a magnifier at the right end of the header.

`HeaderSearchButton` puts a magnifier and "Search" in that same spot on
desktop. It opens the palette through `useCommandPaletteStore.open$`, the
call the Ctrl+K handler makes, so there is no second path. As the maintainer
asked, the shortcut lives in the tooltip ("Search Ctrl K", "Find in page
Ctrl F"), built the way `JournalControls` builds its own: `getShortcutKeys`
plus `KbdChord`. Both lines follow a rebinding. The accessible name is the
action alone and `aria-keyshortcuts` carries the chord, as in
`JournalControls`, so macOS users are not read "Ctrl".

The same `useShouldShowMobileChrome()` gate picks between this button and
the mobile `SearchSheetTrigger`, so exactly one renders. Desktop chrome
starts at 1024 px. Below `lg` the word hides and the icon keeps its name.
The header stays one 48 px row at 1024 and 1440 on Journal, the busiest
header, and on Pages.

Each new test was shown red against a one-line break: the click handler,
the palette call, each tooltip binding, and both triggers rendering. A
Playwright spec opens the control, types a page title, and lands on that
page.

Review also found that closing the palette leaves focus on `<body>`, from
every trigger, including Ctrl+K. That predates this control and lives in the
palette, so it is #5639 rather than part of this change.
